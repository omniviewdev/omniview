# `ui-next/plugins/`: the host's side of the plugin seam

How the new shell shows the pages the installed plugins contribute. It is **host code and plugin-agnostic**: no plugin word appears in this directory (the vocabulary guard scans it, tests and comments included; the fixture plugin is the one exemption, because a plugin is not the host), and no plugin's code is in this repository: a real plugin reaches the host as an installed bundle, and CI runs one through this seam from outside this tree. The design, the evidence and the sequence of steps are in `docs/ui-next/slices/n19-plugin-seam.md`; this page is the map.

**The default screen.** The native window loads `/` and cannot take a parameter, so nothing in the URL decides what it shows: it shows the window the user left (S3a: the tabs, the one on screen, the rail's choice and the bottom panel come back from the session the host's window service holds, `shell/session`), and opens **no page by itself** (decision A17): with nothing saved it is the empty window (`host/NoTabs.tsx`: the plugins that can be opened, in the order the plugins declare for the window's rail, `contribution.rail.order`, not the order of their ids), and it shows the kit's empty state under the name "Plugins" when no plugin contributes. A tab of a plugin that has not loaded is drawn from the face it was saved with, its page the kit's loading state, until the plugin registers; one whose plugin is not in the list of installed plugins says so and stays. The window's rail (`host/rail.ts`) has one entry for each plugin that contributes, chosen once every plugin has settled (until then its track and the sidebar are reserved empty, so a plugin that registers late moves no entry), and choosing one shows that plugin's sidebar without closing a tab. Closing the last tab leaves the empty window and opens no page by itself; Command or Control W there closes the window (decision A17). While a plugin loads the shell draws its frame with the regions reserved, so nothing moves when it arrives. A browser can say more in the hash, `#/<plugin>/<page>?connection=<id>`: a deep link at load, and a hash typed later; each opens a tab through the tab model. The window never writes the hash.

## Rules

1. A bundle exports `contributionV1` and nothing else is the host's business. The version is the export name.
2. A plugin imports its own files, the shared list and nothing else. Sharing the runtime's whole barrel would put the old UI library into the new build (1.88 MB, measured); the runtime joins as a curated entry.
   ReactDOM is internal to the host and its kit. Only the duplicate-kit negative control bundles that dependency itself.
3. The plugin's words never reach the page: a failure is a kind and a sentence the host wrote; the detail goes to the log.
4. A contribution's hook runs in the host's React, inside the contribution's own boundary.
5. A page is a `list`, a `detail`, an `overview` or a `custom` page (rule 11). A detail page is the page of one object: a route names it by a page id and the object's identity as string parameters (`RouteV1.params`), the tab is called `{name} · {Kind}` from the route and the definition alone, and it has no sidebar entry (it needs an object; `home` is never one). An overview page (HM3) is the page of a scope, a connection: the detail page's anatomy (the page header, the in-page tabs, the Overview's summary and sections) drawn for the connection the route names, with the connection's NAME as the heading (the page's title while the route names none) and `[plugin, connection]` as its path. It needs no object and takes no parameters, so it may be `home` and a sidebar entry, and it is the page a freshly opened connection lands on; a connection chosen while on it keeps it (`host/connections/actions.ts`). Both kinds were added to version 1 as minor additions: the rule that decides minor or a new `contributionV2` is written at the head of `contract/v1.ts`, and `admit.test.ts` keeps a bundle written before each. A host that predates the overview refuses a bundle that has one by naming the kind at admission (`pages.<id>.kind is "overview", and this version draws "list" and "detail" pages`, the `contract` failure), and never draws it wrong.
6. A link inside a plugin's page is the kit's `Link` in the host's `LinkProvider` (`host/links.ts`): it names a page of its own plugin and that page's parameters, carries the address as its `href` (`#/<plugin>/<page>?connection=<id>&<name>=<value>`, the grammar the hash is read in), and a plain click or Enter is smart open, Command or Control or a middle click opens a background tab.
7. An overview follows the detail view (HM3). An overview page's hook answers the detail page's view (`DetailPageViewV1`), and its tile, its tabs, its sections and its states are the detail page's, so a change to the detail view's types reaches overviews, and is judged for both kinds. Three things are called `overview` and they are three: the page kind (`kind: 'overview'`), an in-page tab whose id a plugin chose to call so (a tab's id is the plugin's own word), and `DetailTabContent.kind: 'overview'` (the typed summary and sections a tab may hold, as against `custom`).
8. No fake zeros (HM3). A section of the detail page and of the overview states loading, partial, failed or not available, in the plugin's own words in the section; a plugin never draws a zero, a dash or `None` for a read that has not answered or has failed. The page has ONE state for the whole page (`DetailState`) and says nothing of any one section, and the host cannot know what a read is, so it contains instead of enforcing: a section that throws while it draws, or whose rows or items are not a list, says `<title> failed to display.` with a Retry in its own card, and the header, the summary and the other sections stay (`ui-next/page/SectionBoundary.tsx`; the error goes to the log, rule 3). The rule is written at the head of `contract/v1.ts`.
9. A place is one tab, whichever way the person gets there (HM3). A connection chosen on a tab keeps the page and replaces the tab's history entry (`host/connections/actions.ts`, `switchTab`), unless another tab already shows that connection's page: that tab is shown and the tab on screen keeps its own connection, as opening it from Home does (`reuse` of the tab model's `navigate`, `shell/core/tabs/README.md`), so no two tabs are named alike for one place.
10. A connection's name is clipped once, where it comes in (HM3). It comes from a page's lane, from what a window has learned and from the host's own list of connections, and `nameText` (`host/connectionName.ts`) holds it to `NAME_MAX` (200 characters, an ellipsis for the cut) in each, so the heading, the path, the tab, Home's rows and the picker's options cannot draw a longer one; a name a person could have given a connection is never cut. The tab's own limit for a scope label (`LIMITS.scopeLabel`, 24) is a label's and is not the name's.
11. A custom page is a page the plugin draws itself, and a landing is the one a plugin opens at (KL2). `{ kind: 'custom', scope, title, icon, layout?, Body }`: the `Body` is a component, given `{ context }` (`CustomPageContextV1`: the context every hook gets, `connections` and `setParams`), and draws the whole page from the kit; the host draws the tab, the page's error boundary (`This page failed to display.` with a Retry; the plugin's words go to the log, rule 3) and, for `scope: 'connection'`, the scope lane (the connection's NAME, from the window's own list, with the picker). `scope: 'plugin'` is a page read in NO connection: `complete` drops a connection that a link or a sidebar entry carries to it, it has no lane, its panel handle has no `ports`, its plugin's entry in the rail is current while it is on screen, and the window draws the plugin's sidebar only as the sidebar's hook answers it for the page (rule 13: the skeleton's entries are pages of a connection, and a tree whose every entry opened the landing again would be a trap). `layout` is `document` (default: the island scrolls the page) or `pane` (the page owns its scrolling and its root fills the island, as a kit `DataView` does). A custom page reads its route's parameters, `context.route.params` (rule 13), and changes them itself with `context.setParams` (rule 15). `ContributionV1.landing` names a custom page of scope `plugin` and admission refuses anything else with one sentence (`landing "x" is a list page: a landing is a custom page of scope "plugin"`). With a landing, every open of the plugin that names no connection is the landing's, instead of Home, the connection last used or the plugin's first: Home's row (with no "Choose one of the connections" detour), the rail, `+`, the palette's row for the plugin, a link with no page and no connection, and a route to a page of a connection that names none. None of them waits for the list of connections (the landing says it is reading them). A tab that is open keeps the route it has, `home` keeps its meaning (the page a connection chosen opens), and a plugin with no landing is completed as it always was (`contributions.test.ts`). Both were added to version 1 as minor additions on the terms at the head of `contract/v1.ts`: a host that predates them refuses a bundle that has one by naming the kind (`pages.<id>.kind is "custom", and this version draws "list", "detail" and "overview" pages`) and never draws it wrong.
12. A landing reads the plugin's connections from the window and holds no store of its own (KL2). `context.connections` (`host/connectionsHost.ts`, `ConnectionsHostV1`) is the window's list cut to the plugin: `useSyncExternalStore(connections.subscribe, connections.getSnapshot)` gives `{ loaded, failed, connections }`, each connection with its `key` (never drawn), `name`, `description`, `labels`, `state`, the host's `word` and the kit `Status` `role` for it, `reason` when a start failed and `busy` while the host is doing something to it (rule 14); `open(key, { newTab })` starts the connection first, as a press on one of Home's rows does, and opens the plugin's `home` in it (smart open: a tab that shows it is shown, else a new tab; the landing keeps its tab); `refresh()` asks the plugin's backend to load its connections again and reads the list (call it from a person's action). A link to another page of the plugin is the kit's `Link` (rule 6), a menu is the kit's `useMenu` and `menuTrigger` (as Home's rows have one), and the page header, a data view and cards are the kit's: the fixture's landing variant uses all of them (`fixture/src/landing-pages.tsx`).
13. A plugin's sidebar is the plugin's on a landing too, and the host adds the tree's features and nothing of what is in it (KL5). The sidebar's hook is called for a page read in no connection as for any page (a route that names no connection and carries the page's own parameters as text, KL7: it was told none, so a navigator could not tell which place of a page was on screen, nor carry what the page keeps in its route to the entries it opens; `SidebarContextV1.connections` as a custom page is given them), and what it answers is the sidebar: its skeleton is never drawn there, and none is drawn while it answers `undefined` or nothing that opens something (a plugin with no hook has none on its landing, as before). The host knows no organisation of connections: the plugin's nodes say what the tree draws, with six optional members of a node, all minor additions (`contract/v1.ts`, the rule at its head): `page` and `params` (a leaf that opens a page with the route parameters it is opened with; the leaf's `id` is its own name, since two leaves of one page cannot both be called by it), `connection` (a leaf that opens one of the plugin's connections as `connections.open` does: the host starts it first, and a start that fails or an open the window refuses is told in an error notice, `Couldn't open <name>`, as a row of Problems is), `status` (`{ role, label }`: the kit's glyph for the role at the end of the row, the label as the row's accessible text and the glyph's tip), `tone` (one of the kit's data colours, for the row's glyph) and, on a group, `expanded` (KL7: it starts open). A group says `expanded: true` and the tree opens it once, the first time it has the group on screen (when it mounts, when a later answer of the hook brings the group, as the connections of a landing arrive after the first answer, or when it comes into view inside a group that was closed); from then on what the person did with it is theirs, so a group they closed is not opened again by a later answer or by the tree coming back from the window's memory. Initial state only; without it groups start closed, and the person's open groups are the window's for its life. A leaf opens one thing, and `sidebarTargets.ts` reads it for everyone who asks (the gate for what a hook answers, admission, the palette, a press): what is not valid is a sentence at admission and an entry left out of what a hook answers, never a control that does something else. The leaf that is selected is the one whose page and parameters are those on screen (else the page's leaf that names none: the plain leaf of a page opened with a parameter nobody listed, or of the list under an object's page), and the same place is one tab whoever opens it (the tab's key holds the parameters), so a leaf with parameters is smart open's: it moves the tab on screen to that place, and a tab that already shows it is shown. The palette lists a leaf with parameters as that place and no leaf that opens a connection (it lists the connections itself). A custom page reads the route's parameters as `context.route.params`; they are saved with the tab, so a window comes back at the same place, and a change of them alone is another place of the tab but not another page: the page host keys a custom page by its page and its connection (rule 15), so the Body, and what it keeps in state, stays and is given the new parameters. What the sidebar is called on a page read in no connection can be said by the plugin (`SidebarV1.pluginScope`, KL7: `{ title?, label? }`, each member that is left out falling back to the sidebar's own; admission refuses a member that is not a non-empty string): the navigator there is another list than the tree of a connection's pages, and its heading says which. A label of its own makes it another tree for the window's memory of what the person opened. The tree's one tab stop, its arrow keys and its one tooltip are as they were: a badge is an attribute for the window's one tooltip, and a tone a data attribute the stylesheet reads, so a row costs nothing more than the nodes it has.
14. A landing may act on its connections, and the host asks the person about what is destructive (KL4). A connection carries `labels` (the labels the plugin's backend put on it, the ones whose value is text, `{}` when there are none, the same object while they do not change) and `busy` (`connecting`, `checking`, `disconnecting` or `removing` while the host is doing it). `connect(key)` starts a connection and opens no page; `check(key)` asks the plugin whether it is healthy and reads the list again (ok when it is, else a sentence); `disconnect(key)` stops it; `remove(key)` removes it from the plugin's list. Each answers `{ ok: true }` or `{ ok: false, reason }`, never rejects, and is the plugin's own (a key of another plugin is not found). `disconnect` and `remove` ask first, in the HOST's dialog (the kit's `ConfirmDialog`: the connection's name and state, and for a disconnect how many open tabs and sessions of it will lose the connection), and do nothing until the person says yes, so a plugin cannot run either without the question: a no answers `{ ok: false, cancelled: true }` (nothing to tell the person), and a stop that fails keeps the dialog open with the host's line, for another try. One verb at a time on a connection: while one runs, `busy` says which and a second verb on it (`open` and `connect` too) is answered with a sentence (`north is being checked. Try again when it has finished.`); a connection that is `connecting` is not checked, disconnected or removed either, because the host's own stop waits behind a start that does not end (backend catalog B-56). A page draws `busy` over the state's word, may disable what would be refused, shows the `reason` it is given, and never asks the person itself. The sidebar's hook is given the same handle (rule 13), so a navigator may read `labels` and `busy` too; the verbs are for a person's action, not for a hook. The state `certificate` (the word `Certificate problem`) is the host's reading of the code CERTIFICATE_ERROR, which was drawn as `unreachable`; a plugin that does not know a state treats it as `failed`. The fixture's landing variant has all four in the menu of a card and says each answer in a notice (`fixture/src/landing-pages.tsx`).
15. A custom page changes its own parameters in place, and the host keys a page by its page and not by its parameters (KL7). `context.setParams(next, { history? })` (`CustomPageContextV1`) changes the parameters of the route of the tab the page is in: `next` is the whole set (a parameter it does not name is gone, an empty value names nothing, a call that names what the page has changes nothing), text only, and never `connection` (the connection a page is read in is the host's: a call that holds anything else is ignored with one line in the console, `[plugins] <plugin> page <page>: setParams was ignored: <why>`, and the connection stays). `history` is `replace` (the default: the page's entry in the tab's history takes the new parameters, nothing is pushed, and the tab's page memory stays: `replace` of the tab model) or `push` (a new entry, which Back leaves, as it does for a link: `navigate`, which also asks the unsaved-changes question and applies the singleton rule). The call never throws and does nothing once the tab has left the page. The tab's route is what changes, so the sidebar's current entry, the saved session and Back and Forward follow it by the tab model's own rules, and what changes the parameters of a page already on screen in its tab by any other means (a link, an entry of the sidebar with `params`, Back, Forward) updates it the same way. **What is drawn from scratch is decided by `pageKeyOf` (`PluginHost.tsx`, handed to the page host as `pageKey`):** a custom page is another page when its plugin, its page or its connection changes, or its tab is reloaded, and is the same page, given the new `context.route.params`, when its parameters alone change, so its Body keeps what it keeps in state (a search, an open picker, the focus, the scroll of its region) and re-renders once; a list, a detail and an overview page are keyed by their place as they were (a detail page's parameters are its object). Keep-alive is by tab (`state.mounted`: the model keeps or evicts a tab's page whole, whatever its parameters, and a page it let go is drawn from scratch with the tab's current route) and a tab's page memory (`pageState`, which a custom page does not read) by tab and history entry, so two tabs of one page with different parameters are two pages with a Body each, and a change in one leaves the other as it was. `open` still deduplicates by place: a leaf or a link whose place another tab shows shows that tab; `setParams` does not (as `navigate` does not): two tabs may come to show one place. The fixture's landing is the working example (`fixture/src/landing-pages.tsx`: a filter strip that pushes, an order that replaces, a search that keeps its text).
16. A call of `setParams` is held to the page instance that made it (KL7). The host answers for a callback a page left behind: it changes nothing once that instance is gone, which is when the tab is at another plugin, page or connection (a `setParams` of the page of connection A cannot change the parameters of the page of connection B that the tab went to, though the tab's route names the same plugin and page), when the page is drawn again (a reload of the tab, a return to the page by Back or by a link, a plugin that came back, a page the keep-alive cap let go and the tab showed again), and while the page is not on screen, because a hidden page's effects are released (HSH-21) and a call that comes from one is a late one. A call dropped for this is silent, as a call that came after the tab left the page was; only a call that is not valid (not text, or naming `connection`) says so in the console. `PluginHost.landing.test.tsx` keeps one callback across a change of connection and a return to the page.

## A navigator on the landing

```ts
// the sidebar's hook: for a page read in no connection, answer the entries the landing wants; for any other, answer what it did (or nothing: the skeleton stands)
function useNodes({ route, connections }: SidebarContextV1): readonly SidebarNodeV1[] | undefined {
  const view = useSyncExternalStore(connections.subscribe, connections.getSnapshot);
  const { sort } = route.params;                                                                                         // the route's own parameters (KL7): what the landing keeps in its route besides the filter
  return useMemo(() => (route.page !== 'landing' ? undefined : [
    { id: 'all', label: 'All', icon: 'layers', page: 'landing', params: sort === undefined ? {} : { sort }, count: view.connections.length }, // the landing with no filter, the order carried (a leaf that carries `params` has an id that is no page's key): selected on the bare landing
    { id: 'attention', label: 'Needs attention', icon: 'bell', page: 'landing', params: { filter: 'attention', ...(sort === undefined ? {} : { sort }) }, count: 1 }, // the same page with its parameters, the order carried: the entry whose parameters are the page's is the one selected
    { id: 'connections', label: 'Connections', icon: 'server', expanded: true, children: view.connections.map((c) => ({  // a group that starts open (KL7), when the tree first has it
      id: `connection-${c.key}`, label: c.name, icon: 'server', tone: 'green', connection: c.key,                         // opens the connection, the host starts it first
      ...(c.role === 'healthy' ? {} : { status: { role: c.role, label: c.word } }),                                       // a badge: the kit's glyph, the words as text and tip
    })) },
  ]), [route.page, sort, view]);
}
```

Answer on the first render (the sidebar then draws with the page; an answer that comes later moves the page once), keep the same array while nothing changed, give a leaf that carries `params` an `id` that is no page's key (a host without the members would otherwise open that page without them), and read the parameters in the landing's `Body` from `context.route.params`; the hook is told the same ones (KL7), so an entry can carry what the page keeps in its route and the entry of the place on screen is the one selected. A group says `expanded: true` to start open (initial state only: the user's open groups are the window's for its life, and a group they closed is not opened again); without it groups start closed. The page changes its own parameters with `context.setParams(next, { history? })` and keeps what it keeps in state (rule 15). The sidebar may be called something else on these pages (`sidebar.pluginScope`: `{ title: 'Connections', label: 'Acme connections' }`; a member left out is the sidebar's own). The fixture is the working example: `fixture/src/landing-navigator.ts` (and the filter strip, the order and the search in `fixture/src/landing-pages.tsx`), written with the landing variant. A plugin adopts it by vendoring the host's contract and kit at a host commit that has it, as for the landing, and answering the navigator in the hook it has.
