# `ui-next/page/`: the list page

The first page of the new shell (slice 1a plan, PR 1a.6): a collection of rows with its page header, quick filters, search, table and count, in one pane. It is **host code and plugin-agnostic**: it knows a screen only by the data the screen states it with, and no plugin word appears in this directory (the vocabulary guard scans it, tests and comments included).

## What a screen gives it

`ListPage` takes two plain values and draws them (`definition.ts` has the types):

| Prop | What | Held by |
|---|---|---|
| `definition` | `title` (the plural name: the heading, the table's name, the word of the states and of Refresh), `nouns` (the count's words), `tile?`, `commands?` (the page's own; Refresh is the page's), `quickFilters?` (a named strip of `{ id, label, tone, test }`), `columns` (the kit's `DataTableColumn`s: a column that declares a `sortKey`, and a `sortKind` where its keys are numbers, sorts), `defaultSort?` (the column and direction the page opens in), `lines` (1 or 2), `getRowKey`, `searchText` (lower case) | type |
| `source` | `state` (`loading`, `ready`, or `failed` with its words and, only when asking again can help, a `retry`), `rows` (in the source's own order, which a tie keeps; a changed row is a new object), `complete` (the whole set is here), `refreshing`, `refresh()` (resolves when the read is over, never rejects) | type |

The page is a **pure function of `(definition, source)` and what the person chose**: the source is a prop, never a hook the definition calls, so the page reads no data layer. What the person typed (the search, the chosen filter) and the sort they chose are the page's own state; what is listed, and whether it is all of it, is the source's. The page does not sort: the kit's table does, by the keys the columns declare, in the order the page holds (below).

## Where a plugin meets it

A plugin's bundle states its page as plain data: a `definition` and one data hook that returns the page's `source` and its frame (`ListPageV1`, `ui-next/plugins/contract/v1.ts`). The host runs the hook and hands both values to `ListPage` and `Shell` in `ui-next/plugins/host/PluginHost.tsx`: **the type checker holds the two shapes together there**, where a drift is a compile error. The page knows no plugin and imports none; its own probe (`probes/`, run by hand) draws it on a neutral fixture.

## What it decides (`view.ts`, pure, tested without a browser)

- The rows: the source's, narrowed by the search (a substring of `searchText`, 500 ms after the last key, at once on Enter or when cleared) and then by the chosen quick filter. A filter chosen twice is cleared; All clears it.
- The counts of the strip are taken **after the search and before the chosen filter**, so choosing one leaves the others' counts as they were. Nothing is counted while nothing is known (a load in progress): a chip with no number, and a zero is a count.
- The body: loading until the first rows or the whole (empty) set arrive; an error, with the one Retry, when a failure left no rows (no footer: the mock draws none); empty when the whole set holds nothing; no-match when rows exist and the query hides them all; ready otherwise. A failure that came after rows does not replace them.
- The footer's count: exact once the set is complete, `N loaded` while it is arriving (decision A10), `K of N` when a search or a filter narrows it.
- Clear filters: one command, in the toolbar, while a search or a filter is applied; it drops both and hands the focus to the search it cleared.
- The sort (`sort.ts`, K3a): the sort in force is what the person chose, else the definition's `defaultSort`, and only ever a column that declares a sort key (one that names a column with none is skipped and not an error: the list is then the source's order, as it was drawn before there was a sort). The page hands it to the table as `sort` and `onSortChange`, so the headers of the columns that sort are buttons that say their state in `aria-sort`; a press sorts a column ascending and a press on the column in force turns it round and back, **with no third state** (the mock's sort action and the kit's rule: the lines of the mock are quoted in `docs/ui-next/status/K3a.md`). The sort is **stable**: a tie keeps the order the source gave its rows in, in either direction, and a row whose key is `undefined` is last in either (the mock breaks a tie by the host key; here the source's order is the tie-breaker). The table sorts on every change of the rows, as the mock does on every render: a row whose key changed moves to its place and no other row moves relative to another. A press is one commit and no more work on the rows than the sort itself (`ListPage.sort.test.tsx`, `probes/sort-probe.mjs`). Clear filters does not drop the sort.
- What the page keeps (`memory.ts`, `kept.ts`, H7): what the person chose is written to the page's **memory**, which the host backs with the tab's `pageState` (`ui-next/plugins/host/pageMemory.ts`), and read once when the page opens: the sort (`sort.ts`), the search once it is applied (500 ms after the last key, at once on Enter or when cleared), the quick filter, and where the table is scrolled (`useScrollMemory.ts`: written once the scrolling stops or at once on a press or key in the page, put back as soon as the table can reach it; the kit's table takes no offset, so the page reads its named scroll region). Nothing is written when the page opens or while it is left alone. It survives a switch of tabs, a reload of the tab, closing and reopening the tab and a page the keep-alive cap let go, and the tab's history keeps it with the entry the page is left at, so **Back and Forward give the list back as it was left** and a navigation to a place the tab has been at opens as it was left, at its top (`ui-next/shell/core/tabs/README.md`, "Page state and history"). A value it reads that is not what it wrote (another version of the plugin, a hand-edited snapshot) is no search, no filter and no position, and is not an error. It is not saved to disk, so not across a restart (the mock does not either: the only path of its list module that it registers for saving is the Columns chooser's).

## The user's own Refresh is felt

The Refresh command of the page header (`Refresh <title>`) is unavailable, with its reason as its description, while a refresh runs. The acknowledgement is the header's **operation slot**, not the footer: `Refreshing…` from the click until the read is over and at least 700 ms have passed, then `Updated`, a calm outcome the presenter clears by itself. A refresh nobody asked for is silent, and a failed one is not called an update. Both moments are announced politely through a live region that is in the page from the start.

**A refresh that does not finish is said (S3).** A source's `refresh` resolves when the read is over and never rejects, and a plugin's may reject, throw, or never answer. The one hook that draws the user's Refresh (`useRefreshFeedback.ts`, used by the list page and the detail page, so by an overview) catches the failure and waits a bounded time for the answer, `REFRESH_LIMIT_MS` (30 s: as long as the host waits for a plugin's bundle to load, longer than a healthy read takes, and short enough that a person who cannot cancel it is not left at an unavailable button for a minute). Then the slot says `Refresh did not finish`, in the page's own words, as a failure the presenter keeps until it is dismissed, with a Retry that asks again, Refresh is available again, and the error, if there is one, goes to the log. The politeness is the same: `Items did not refresh` is announced. A read that was given up on and answers later changes nothing: what was said stays said, and the late answer of an earlier read never ends a later one.

## The detail page (D1a)

`DetailPage` is the page of ONE object: the page header (kind tile, the one h1, the state chip, at most four facts, the commands in the one order the design allows, the operation slot), the kit's in-page tabs and the tab's panel. The breadcrumb lives only in the shell footer. A parent with a declared route opens that route through the tab model; label-only ancestors and the current page are plain text.

Like the list, the page is a pure function of its inputs: `definition` (`detailDefinition.ts`: the kind, the tile, which route parameter names the object and which qualify it, the list it belongs to, the tabs), the route's `params` and a `source` (`state`: loading, ready, not found, denied, failed with an optional Retry; `view`: the object as plain data; `refresh`). Its words and decisions are in `detailView.ts` (pure, tested without a browser): the name and heading come from the route, the strip is drawn from the definition before any data is read, and the identity line is always there (a progress word while the object is on its way, the kind as the one fact when the plugin gives none), so nothing of the header or the strip moves when the object arrives; a state other than ready replaces the body only, with the kit's state bodies; a failure that follows a view does not take it away.

The Overview (`DetailTabContent` of kind `overview`) is a one-line summary and typed sections, each in a kit `SectionCard`: `kv` (a key-value list), `table` (a small table: the kit's `DataTable`, main column only), `tags` (key and value chips, a bounded first set and Show all N) and `list` (rows of a title, a muted detail and a trailing value). A section has a `placement` (`main`, or `aside`, which stacks under the main column below 992 px of page width) and a `priority` (lowest first, 50 by default) and is not drawn when it has nothing to say. Any other tab is the plugin's own content (`custom`). Commands report to the plugin's callbacks (`onSelect`); the page wires nothing else.

A section is contained (S2): each one is drawn in a boundary of its own (`SectionBoundary.tsx`), so a row, a cell or a section that throws while it draws, or whose rows or items are not a list (`hasContent` draws such a section, so that its own card can say so), is THAT section's failure. Its card keeps its heading and says `<title> failed to display.` in the kit's failure notice, with a Retry that draws it again, and the header, the summary and every other section stay. The plugin's own words (the error) go to the log and never to the page. A section the plugin gives anew is tried again by itself, so a read that works after one that did not needs no press, and the sections of another connection do not inherit the failure of the one before. The page's own boundary, the host's, is for what the page cannot draw at all.

**No fake zeros.** A section states loading, partial, failed or not available; a plugin never draws a zero, a dash or `None` for a read that has not answered or has failed. The page has ONE state for the whole page (`DetailState`: loading, ready, not found, denied, failed) and says nothing of any one section: a section's own state is the plugin's own words in the section (its rows and cells, its `count`, its `action`: a Retry on the section). The page cannot know what a read is, so it cannot enforce the rule; the contract's text (`ui-next/plugins/contract/v1.ts`) states it, and the boundary above is what the page does about a section that cannot be drawn.

What the tab is called is not the page's: `detailIdentity.ts` gives `{name} · {Kind}` and the qualifiers from the route and the definition alone, and the host's `describeDetail` (`ui-next/plugins/host/contributions.ts`) turns them into the tab's face and the status path, so a restored or background tab is named before the page has run. The page is a document (the page scrolls), not a pane. The probe (`probes/detail-probe.mjs`, run by CI) draws it on a neutral fixture against the mock's page-kit detail reference (`packages/kit/probes/mock-detail.json`), loading to ready, and through the keyboard.

## The overview page (HM3)

An overview page is the detail page drawn for a SCOPE, a connection, and not for an object: it is what a plugin lands a freshly opened connection on. The contract (`OverviewPageV1`, `ui-next/plugins/contract/v1.ts`) gives it a `title`, a tile and tabs, with no identity, no list and no route parameters, and its data hook answers what a detail page's hook answers, so it needs no section of its own and none was added. **`DetailPage` is unchanged and has no overview mode**: the host (`OverviewContribution` in `ui-next/plugins/host/PluginHost.tsx`) draws it from a definition made from the overview's (`overviewAsDetail` in `host/contributions.ts`: the page's title is its kind, and the one parameter that names its subject holds the connection's NAME). So the heading is the connection's name (the one the page's lane says, else the one the window has learned; the key is never drawn) and the page's title while the route names none, and the summary, the sections, the states, the Refresh and the keyboard are the detail page's own. The tab's title, glyph and path come from `describeOverview`, not from the page, so a tab that was never shown is named as the one on screen is; the page is a document, as a detail page is.

Three things are called `overview` and they are three: the page KIND (`kind: 'overview'`, the page of a scope), an in-page TAB whose id a plugin chose to call "overview" (a tab's id is the plugin's own word, and the page reads no meaning from it), and `DetailTabContent.kind: 'overview'` (the typed summary and sections a tab may hold, as against `custom`: any tab of a detail page or of an overview page may hold it). **An overview follows the detail view**: its hook answers `DetailPageViewV1`, and its tile, its tabs, its sections and its states are the detail page's, so a change to the detail view's types reaches overviews and is judged for both kinds. What a section says of its own loading, partial or failed reads, and how a section that cannot be drawn is contained, is above, under "The detail page": it is the same for both.

A link in a row of a section is the kit's `Link` (a page of the plugin and its parameters). A list's quick filter is the page's own state, kept in the tab's page memory, and neither a route nor a link can name one, so an overview links to the list unfiltered (recorded as a gap in `docs/ui-next/status/HM3.md`).
