# Decisions

Binding for all UI-next work. R1–R20 are the strategy rulings of 2026-11-16; batch A and the channel answers are the owner's. Change one only through the lead.

## The two rules that prevent getting stuck

`main` always ships exactly one complete product. The new UI is built on `main` but reaches users only through a separate feature channel with its own state directory, until one flip. At every moment there are three legal moves: continue, flip, abandon. Abandon is rehearsed once, early (row N13).

The binding constraint is review and decision throughput of two people, not agent output. Conversion is cheap; integration, visual conformance and human review are the cost.

## Rulings

| # | Topic | Ruling |
|---|---|---|
| R1 | Vehicle | The new UI is a `ui-next` feature channel built from `main`: isolated state root, own plugin streams, npm dist-tag. Not a new window kind, not a two-bundle plugin archive. Fallback if the channel system proves unsuitable: a build-flagged second entry. |
| R2 | Freeze | The old shell takes fixes only once the calibration gate (R12) passes. Before it, the old shell develops normally. No feature is built twice. |
| R3 | Library | New package `@omniviewdev/kit` inside this monorepo from day one. The old `ui` repository is frozen, not imported, archived at the flip. The theme engine, CSS Modules approach and reusable sources are carried over file by file with provenance noted. |
| R4 | Names | Never reuse `@omniviewdev/ui`, `base-ui`, `ai-ui`, `editors`: an old plugin bundle must fail loudly. Deprecate `@omniviewdev/ui@0.3.0` and `providers` on npm now. |
| R5 | Primitive base | Base UI for overlays and interactive composites; native elements for per-row atoms, with shared popups through a handle (the host table already does this). No up-front spike: measure at most 3 days on the real table inside the first slice, write the decision rule first, accessibility is a veto, owned code wins ties. |
| R6 | Styling and tokens | CSS Modules, a fixed cascade-layer order, one token re-valuation: no second scale, no alias window. A key is renamed when its meaning changes. No custom-property writes at the root. Text size and density stay (the mock keeps them). |
| R7 | Component API | Closed props (no `className`, no `style`), typed layout props, and one escape hatch: plugin CSS Modules in a dedicated plugin layer. |
| R8 | Build order | Through real screens, consumer first. No component before the screen that needs it. |
| R9 | Table | The mock's "fit every column to content" cannot be computed at scale (291 ms for 60k strings in WebKit against 8 ms). Columns fit from declared widths plus a sampled measurement. This amends the spec. |
| R10 | Trust | Plugins remain trusted code in the host realm. Do now (about 6 days): remove the two consent calls from the bound surface, stop returning the MCP token to JavaScript, make the two fatal state loads recoverable. Build the plugin-free consent window once, on the new library, with the approvals slice. The written claim is limited to: plugin JavaScript cannot forge an approval through the API. A hostile plugin with a terminal and file write is NOT contained; that needs isolation and is a later decision. |
| R11 | Plugin contract | A curated surface with public and unstable tiers and an API report; icon barrels leave it. A build-time manifest describes the skeleton only (pages and slots, enough for lazy loading); per-connection and per-resource contributions stay code. The compatibility gate reads facts from the artifact and refuses on proof of mismatch, never on an unknown version. |
| R12 | Sizing | No total estimate. Build a thin first slice, then a calibration gate sizes the rest from measured throughput. Central guess for the full first slice: 12 weeks (range 10–20); to the flip at minimum scope about 30–35 weeks. Bounds, not forecasts. |
| R13 | Errors | Keep the existing error type; carry per-occurrence facts in standard status details (no wire bump: strictness applies to message bodies); one TypeScript parser and one describer. The Phase-0 fixes ride with slices and do not gate the first screen. Startup retries that exist because the backend may not be ready stay. |
| R14 | Preparation | Runs beside the first slice: delete the 168 files verified dead with no edit to live code; turn minify on; take an honest baseline with the existing `bench/app --minify on`; add lint ratchets. The old shell gets no other investment. |
| R15 | Spec | The mock becomes a checkable specification: one errata pass with one owner, then per-component cards (anatomy, states, keyboard, tokens) plus rendered goldens, vendored into the host and cited by content hash. The tag alone is a snapshot, not a freeze. |
| R16 | Review | Required checks and a merge queue for everything; a human approval only on hand-written contract paths; independent agent pre-review; agents commit under their own identity. This replaces a rule bypassed on 88% of merges today (owner amendment: batch A4). |
| R17 | Architecture pass | Not a separate phase. The layering is better than first reported (14 of 661 files in cycles). The controller/view split and the host-event gateway are done per slice, in the new tree. Lint guardrails (no cycles, layer rules, dead-code ratchet) apply from day one to the new tree. |
| R18 | Latest versions | The new tree starts on the latest of everything (Vite 8, plugin-react 6 with the compiler rewired, React Compiler pinned). The old shell is not upgraded. |
| R19 | Plugins | Kubernetes moves in slices on the channel. Proxmox and Flux are ported by their owner, who should release what is already on their `main` now (the marketplace serves builds the current host rejects). AWS and Containers are rebuilt after the flip. Flux, Proxmox and Containers are designed in the mock before their slices. |
| R20 | After the flip | What stops the next rewrite: the curated plugin API with an API report, tokens as a contract, the spec cards and goldens as regression gates, performance budgets in CI, and the compatibility gate. No second stack is ever admitted to `main`. |

| A19 | Data follows the cluster, presentation follows the mock (2026-11-20, lead; the owner may overrule): where the mock's sample data handling and what `kubectl`/the API report disagree, the plugin shows what the API reports, in the mock's presentation. | A20 | Log sessions start from the resource (2026-11-19, owner): sessions are started from the resource for now; a panel-side target picker is deferred until its large-cluster UX is designed. | A21 | A host tool's sessions survive their plugin's unload (2026-11-19, owner through the lead; widened 2026-11-20 by the lead's ruling; built in P1b-3c, `status/P1b-3c.md`): **Sessions of host-owned panel tools stay listed across their plugin's unload, whatever their state, and their lines stay readable until the tab is closed; a session that was running ends with the cause. Sessions restored from a saved window stay hidden until their plugin loads. Everything else follows the mock.** The one deviation from the mock's rule PO1 (a plugin that is off contributes nothing: its sessions are hidden, its running ones end, and they come back ended). Today the host-owned tool is Logs; the sessions of a tool a plugin brought still leave with it. A running or starting session ends with the cause `The plugin was unloaded.`; one that had already ended or failed is kept AS IT WAS, its own state, cause and time untouched (a failed log is the one being read). The stream is still closed at the unload, so no backend session is leaked. A kept session never changes again: the plugin's return clears nothing and a new press of the command opens a new session beside it; the way back to its resource (the card's link and Open button) is disabled with the reason while the plugin is off and works again when it returns. A kept session is saved as ended without lines (the panel saves identity, never what a session held). Not in A21: a history that outlives the tab, a buffer cap (P1c), lines across a restart of the app. |
| A22 | A Logs session is its plugin and its target (2026-11-20, the lead's ruling in P1b-3d, built in `status/P1b-3d.md`): **A session of a host-owned panel tool is identified by (plugin, target id). Opening a target whose session is starting or running shows that session and starts no second stream. Opening a target whose session has ended, failed, is kept after a plugin unload (A21) or was restored opens a NEW session beside it; the old one stays readable until closed. Scope shows on a session tab only to tell same-titled open sessions apart.** Deviates from the mock, which re-activates only its own runner targets. |
| A23 | A reload restores the panel as it was left (2026-11-24, the owner's order through the lead; built in T2d, `status/T2d.md`): **The saved panel comes back as the person left it: open when it was open and closed when it was closed, with its height, its tool and the session each tool was on, whatever sessions it holds.** A clarification of S116 more than a reversal. The written rule is "Sessions restored at startup, adopted from another window, or re-created by Retry do not open it (today's quiet-tab rule)", for the reason "a restored terminal must not cover the page": it is about a session opening the panel, and the person's own saved panel (S103) is not a session. S3a read it as "a panel that holds sessions stays closed", which was harmless while every restored session was dead and left a terminal that is alive again after a reload (T2b) waiting unseen behind a closed panel; VS Code and JetBrains both keep the panel's visibility and the active terminal across a reload. What stays: a restored session opens no panel that is closed and is never revealed, focused or moved (the registry's `reveal: false`), every restored session is `ended` with the panel model's cause until the Terminal tool attaches it, and a session the person starts opens the panel. |
| A24 | The Terminal's find, context menu and links (2026-11-24, the lead's order for T3a, built in `status/T3a.md`): **Find opens on Cmd+F on a Mac and on Ctrl+F and Ctrl+Shift+F elsewhere; Enter steps to the next match and Shift+Enter to the previous one (F3 and Shift+F3, Cmd+G and Cmd+Shift+G step too); Escape closes the bar from the field and from the terminal; a right click goes to a program that asked for mouse reports unless Shift is held; a link opens on Cmd+click (Ctrl+click elsewhere) through the host's open-external call.** VS Code and JetBrains agree on Cmd+F and Ctrl+F (AGENTS.md: where they agree, follow them), so Ctrl+F is taken from the shell on Linux and Windows, as VS Code does with `commandsToSkipShell`; the written spec S52 says Ctrl chords without Shift stay the shell's and names Ctrl+Shift+F, which is kept as a second chord. On a Mac Ctrl+F stays the shell's. Enter is Next as in the mock and in the Logs find bar; VS Code's terminal maps Enter to Previous (the lead's order and the mock win). The match limit is VS Code's 20,000; the search addon counts from the oldest row, so beyond the limit the newest matches are the ones left out (newest-first needs a fork). Links are http and https only, need the platform's modifier (the web-links addon checks none: the handler does), and open through the Wails runtime's `Browser.OpenURL` (ui-next had no open-external helper and uses no `window.open`); the Go side refuses addresses with shell metacharacters. The context menu is the kit's unified host with the trigger on the emulator's helper textarea (the host skips events from any other text field). |
| A25 | A connection lands on an overview page (2026-11-25, the lead's decision in HM3, built in `status/HM3b.md`): **A plugin lands a freshly opened connection on an overview page: `overview` is a third page kind, optional and additive in contract version 1 (the rule at the head of `ui-next/plugins/contract/v1.ts`). It is the detail page's anatomy (the page header, the in-page tabs, the Overview's summary and sections) drawn for a SCOPE, a connection, and not for an object: `{ title, tile, tabs }`, no identity, no list, no route parameters, and its hook answers what a detail page's hook answers (no section kind and no view type is added). It may be `home` and an entry of the sidebar; a detail page still needs an object and stays refused for both.** The heading is the connection's NAME (the page's title while the route names none), the tab is called by the page's title with the connection as its qualifier, the status path is the plugin and the connection, and a connection chosen while on it stays on it. A host that predates the kind refuses a bundle that has one by naming the kind at admission (`pages.<id>.kind is "overview", and this version draws "list" and "detail" pages`, the `contract` failure): a typed refusal, never a crash, never drawn wrong; the cost is the whole contribution of a plugin that makes the overview its `home`, as it was for the detail page. A list's quick filter is addressable by no route or link, so an overview links to the list unfiltered (a gap, `status/HM3b.md`). |
| A26 | A forward is started by a person, is bounded, and says no more than the producer states (2026-11-25, the lead's order for PF2, built in `status/PF2.md`): **`ctx.panel.ports.forward` is accepted only while the window's user activation is active (a click or a key press in the last five seconds), checked by the host and not by the plugin, and refused `FORBIDDEN` otherwise (also in an engine that cannot tell); a plugin holds at most 64 forwards per connection and a window 128 (refused `RESOURCE_LIMIT`, with the number); every string of the request is bounded (`resourceId` 1,024 characters, a body 64 KiB, the whole request 128 KiB; refused `INVALID_REQUEST` before the plugin's backend is asked); and the tool shows what the producer states: with no host stated a forward reads `port N`, Open in browser is disabled with its reason and Copy copies the port.** Reasons: tightening any of these after plugins ship breaks plugins, loosening never does (the review of PR #710, S4 and S5). The host-side verification of where a forward listens, and the SDK's `local_host`, are catalogued (W-PF9, W-PF7), not built. |

## Owner answers on the channel (2026-11-16)

1. Channels are for long efforts tracking `main` with real release linking.
2. The owner registers `feature-ui-next` himself.
3. A mirror branch `feature/ui-next` and the channel tooling as designed (`mirror-ui-next.yaml`, `channels.md`).
4. Version: take the derived one as is (`X.Y.(Z+1)-feature-ui-next.<run>.<attempt>`).
5. Plugin channel sync: investigate its reliability and document it for agents (`channels.md` §4).
6. The state root lives as long as needed.
7. WebKit storage isolation is not a concern now.
8. The channel-to-frontend mapping stays hard-coded in `feature-channel.yaml`.
9. Keep the single optional `ui` input on the shared build workflow `desktop-build.yml`.

Also: no release channel is needed to build the new UI on `main` (`OMNIVIEW_UI=next`); the channel is needed only when a packaged build must be installed beside stable. N5: Reveal removed, clipboard only.
