# Performance baseline of the current app, 2026-11-16 (row N8)

Purpose: a recorded "before" for the UI rewrite, taken with the harness that already exists on `main` (`bench/app`, `bench/render`). It changes no harness code. Read "How far to trust it" before quoting a number.

Summary:

- **Bytes** (deterministic, trustworthy): the entry chunk is 23,045,947 B as shipped and 14,554,523 B minified (-36.8%); brotli 4,496,438 B to 3,860,845 B (-14.1%). The `OMNIVIEW_UI=next` entry is 657,429 B raw / 93,600 B brotli unminified and 229,936 B / 62,067 B minified.
- **Minify on** shortens startup in the whole-app benchmark: cold-start "interactive" median fell 29% (pass 1) and 16% (pass 2) at React `normal`, the ranges never overlapped. Steady-state work (Pod scroll, log stream, drawer) showed no difference outside the noise.
- **Every timing here was taken under load.** The protocol asks for a load average below 2; this machine sat at 7 to 14 throughout (18 cores), from other agent sessions (a `tern` process near 280% CPU and a virtual machine). A second full pass is recorded to show the drift. Frame timings come from software rendering (see below). Treat timings as indicative; treat bytes as exact.
- **`build.minify` is turned on** in this PR (`vite.config.ts`). Gates in "Turning minify on".
- Not measured: native cold start (`scripts/perf/coldstart.sh`), real WKWebView, memory outside the JS heap, idle CPU, the scroll scenarios, anything with a real backend. See "What these benchmarks do not measure".

## How far to trust it

- **Bytes**: exact and reproducible (`bytes.sh` run twice gave byte-identical JSON; the entry sizes also agree to 0.004% with an independent earlier measurement of the same chunk, 23,046,817 B and 14,555,103 B).
- **Within one pass**, the spread of a 5-run cell is under 5% for startup and heap at startup, and visibly wider for total blocking time, long-task counts, Pod scroll busy time (671 to 1,002 ms in one cell), and the log stream and scroll busy times (a trailing `~` in the tables marks a range wider than 25% of the median).
- **Between passes**, the same variant moved by up to 16% at startup (`cold-start` normal, minify off: 997 ms, then 875 ms) and by more than that for the log scroll busy time (143 ms to 209 ms). The unminified build is the noisier one: it parses and compiles 23 MB, which is sensitive to CPU contention. The minified startup medians agree within 5% between passes (705, 739; 704, 728 ms for the k8s variant).
- **Order of `normal` against `profiling` flips between passes** (pass 1: 997 vs 853 ms, pass 2: 875 vs 899 ms for minify off). Do not read a React-build effect out of this data.
- Any difference below about 15% in a timing, or any difference whose sign changes between passes, is noise here. By that rule the minify effect on startup is real (same sign, non-overlapping ranges, both passes, both React builds) and the effect on steady-state interactions is not detected.

## What these benchmarks do not measure

- **Native performance.** Chromium is not WKWebView (the shipped macOS engine), and headless Chromium here used software rendering: compositing and rasterization are disabled, so every frame timing is a CPU diagnostic, not smoothness. The harness says so in its own report.
- **A real backend.** The Wails calls are answered in the page: no IPC, no gRPC, no Go host, no plugin process, no cluster. The plugin is loaded over HTTP from `vite preview`, not from `~/.omniview/plugins`.
- **Native cold start.** "interactive" is the app's `ReportStartupReady` marker counted from Chromium navigation start. It excludes launching the process, the Go host, window creation and the WebView start. `scripts/perf/coldstart.sh` measures that and was **not run**: it needs a full packaged build and launches the app window on this desktop several times, and it is outside the `bench/` harness this row was limited to. It still has no recorded number anywhere. Run `task perf:coldstart -- -n 10 --json <file>` once at each commit (before and after the minify change) on a quiet machine.
- **Parse and compile cost of the entry chunk in WKWebView** (BL-2). The fall in "interactive" above is Chromium's; it is evidence that the minified chunk starts faster, not a WKWebView figure.
- **The scroll scenarios** (`pods-paced`, `pods-reversal`, `pods-jump`) and the reference protocol (30 s warmup, three 20 s trials, 1x and 4x CPU throttle, headed, hardware compositing). Not run; the only recorded runs of them used the unminified build. Pod scroll here is 30 viewport steps once.
- **Anything beyond 30 steps, sort, filter, live updates, the generic table, memory outside the JS heap, idle CPU, accessibility, theme switch, resize.**
- **Real data shape.** Pods and log lines are seeded fixtures. One Kubernetes plugin version was loaded.
- **The two passes are one session**: no day-to-day, thermal or cold-machine variation is captured, and V8 code caching across browser contexts is not controlled for.
- **The `bench/app` build is not the product build**: it adds the fake backend and the profiler wrapper, so its `dist` is 59.6 MB (41.7 MB minified) against 59.5 MB (41.7 MB) for the product build; the byte tables above come from the product build.

## Turning minify on

`vite.config.ts` now has `build.minify: 'esbuild'` instead of `false` (the same minifier `--minify on` measured; it is also what Vite's default would pick). `minify: false` came in with commit `38f1a79f` (2024-04-25, "massive structuring refactor to support monorepo"); no reason was recorded. Gates, run on this change:

- `pnpm test`: 1,746 passed, 3 skipped. (Unit tests do not run through the minifier; they are listed because the task named them.)
- `node --test scripts/react-compiler.test.mjs scripts/ui-flavour.test.mjs` after a minified stable `pnpm build`: 16/16, including "the stable build output holds nothing from ui-next".
- `node bench/app/archive-smoke.mjs --directory <plugin.yaml + assets of Kubernetes v0.21.2>`: PASS, a minified production host loads the real plugin, 118 module registrations, every named shared import resolves against the host namespaces, no console error. The benchmark also ran the plugin screens minified (`cold-start-k8s`, `pods`, `logs`): none of the 160 scenario runs in the two passes, 80 of them minified, recorded a page error.
- The e2e job runs the real application with this frontend: see the pull request for its result.
- A grep of `ui/` and the runtime for `constructor.name`, `fn.name` and `displayName` comparisons found no code that reads a name minification could change; the one `error.name` check is on `DOMException`, whose name is not minified.

Consequences to know about: host stack traces now carry minified names, and `build.sourcemap` stays `false`; whether to ship source maps is a separate decision this PR does not make. `bytes.sh` gives its source-map builds a 16 GB Node heap and did not test a smaller one. If minify must be backed out, set `minify: false`; the change is that one line.
