# The table: row layout, budgets and exact counts on real rows, 2026-11-16 (rows 1a.3 and 1a.3b)

Purpose: the measurement `status/1a.3.md` committed a rule for and did not make. The kit's `DataTable` shipped the plan's spacer layout provisionally (T-03, MNR-T3); this file records the interleaved, paired measurement of that layout against the layout the previous sprint kept, against the table the product ships today and against a plain-DOM control, in WebKit and Chromium on real Pod rows, the rule applied as written, and the budgets and counts of plan 3.3 read in a real engine. Read "What was not measured" before quoting a number.

## Summary

- **The row layout is S, the spacer layout the plan chose.** The rule of `status/1a.3.md` was applied exactly as committed, with the lead's approved reading of B2. Both candidates pass the accessibility veto in both engines. The primary measure (W1 at 1x, 5,025 rows, rAF interval p95, 15 paired trials) **ties in both engines**: every config sits on the engine's own frame cadence (Chromium 16.7 ms; WebKit 18.2 ms, which is also what the idle page and the control give). The tie-break (median frame work on W1) ties too (Chromium 0.13 ms and 0.13 ms, WebKit 0.42 ms and 0.42 ms), and a tie goes to S.
- **The previous sprint's finding does not reproduce as a frame-time effect** ("fixed rows in normal flow: live-update p95 +22.5%, layout +20.9%"): p95 differs by 0% in both engines. Its direction does reproduce in one engine-reported duration: Chromium's layout time over the 5 s window is 27.0 ms for S against 16.6 ms for A (+62.7%), and A's mean frame work is 11.8% lower (0.40 against 0.46 ms); total task time differs by 3.0%. All of it is under 2.1 ms of work in a 16.7 ms frame. WebKit: mean frame work -0.3% and p95 -3.6% for A. On this machine the layout is not what decides a frame.
- **R, the table the product ships, is not faster than S** on any signal: equal p95, frame work median 0.41 ms against 0.13 ms (Chromium) and 3.5 ms against 2.2 ms at p95 (WebKit), 48 mounted rows against 40, a re-mount of its window twice as slow (B1).
- **B1 passes** (re-mount of a 60-row window: p50 4.4 ms and p95 6.6 ms in Chromium, p50 11.4 ms and p95 13.4 ms in WebKit, against 16.7 and 33.4). **B5 is half met**: plan time is within 8 ms and no column width changes while a scripted scroll sweeps all of 5,025 rows, but the sample under-measures the widest strings of a long-tailed set by 27 to 37 px in three of seven text columns (the canvas is within 1 px of the engine's layout: the error is the sample's). **B3, B4, B6 and B7 hold** in both engines (19 elements a row, 573 elements in the document at 5,025 rows, hover 0 commits, one commit a live update, no root write).
- **A defect of the table as built in 1a.3 was found by the counts and fixed**: two commits for every window change in both engines (a same-value `setScrolled` in the scroll handler left a no-op render behind each commit; 26 commits for a 1,200 px scroll in Chromium). Test first (red), then the fix: one commit per window change (13 for the same scroll in WebKit after it).
- Not done in this file: the overscan and step sweep (needs the measurement commit), the mount and sort timings of W3, the 4x CPU cell and the WebKit W0 cell if they are not below, real-cell timing runs, memory, native WKWebView, Windows and Linux. See the end.

## Method (as written in `status/1a.3.md`)

Every trial is a fresh page. One round runs every config once, the order rotating (`s a r c`, `a r c s`, ...); 15 rounds, so 15 pairs. A trial: 1 s idle cadence, a calibration burst (scale 1 in both engines), a 3 s warm-up of the same scroll, back to the top with the rows as they were, 1 s quiet, then 5 s of wheel input at 1,200 px/s at 60 events a second sent from Node, the live-update workload (W1) running through the warm-up and the window: 5 events a second, 2 rows each, every tenth touch a delete and a recreate under a new key (seeded, `bench/table/corpus/updates.mjs`). A frame is a requestAnimationFrame callback; intervals are the deltas of its timestamps (nearest-rank percentiles); **frame work** is from the start of the callback to the next message-channel macrotask (callbacks, style, layout and the main-thread part of paint); the scroll window is the frames from the first to the last whose scroll position moved. Chromium adds CDP `Performance.getMetrics` deltas (layout, style, script and task time over the capture window); WebKit has none. Coverage is read per frame from the first and last mounted row's index and the scroll offset: **0 holes in every one of about 4,600 sampled frames per cell and config**.

Variants: S the kit's `DataTable` (native table, `table-layout: fixed`, spacer rows); A the technique the old table ships, rebuilt on the same components (absolute rows moved by `translateY` of one custom property per row, flex rows, explicit `role`s on every part); R the library table of `@omniviewdev/base-ui` 0.17.3 mounted as the host mounts it (`DataTable.VirtualBody`, fixed 30 px rows, `dataTableImmutableRows`, data-only cells, no row click handler: a small advantage to R); C a scroller of plain divs windowed with the same engine. S, A and C show 40 px rows with a two-line identity; R shows 30 px one-line rows, as it ships. Cells are plain text (the layout is measured, not the cells).

## The decision rule, as it was applied

<!-- RULE -->

Step 1 (veto, `a11y.mjs`): both S and A pass in both engines. The aria snapshot and the Chromium tree show the same 1 table, 2 rowgroups, rows, 6 column headers and cells for S and for A (A's explicit roles restore what `display: flex` takes away); `aria-rowcount` 5026, `aria-rowindex` on the header row and the rows, `aria-sort="ascending"` on the Name header (neither engine's tree API lists the sort property, so the sort state is read from the markup both candidates give the engine: a limit of this veto); no `tabindex` on a row or a cell; Tab (Alt+Tab in WebKit) reaches the region, the five sort buttons and the row checkboxes, never a row; axe-core 4.14.1 finds 0 serious or critical issues (one minor, `empty-table-header`, on the selection column's header, which has `aria-label="Selection"` and no text). R fails the veto's row count (no `aria-rowcount`).

Step 4's text does not say what to do when one engine differs by 10% and the other does not; the reading taken is in `analyze.mjs` (a candidate is preferred only when lower by 10% or more in an engine and not higher by 10% or more in the other). It did not matter: the medians are identical.

**If I think the rule is wrong, I applied it anyway:** its primary measure cannot see a difference here because a table that works 2 ms of a 16.7 ms frame always meets the frame, so the choice is made by the tie-break's median, which is the cheapest frame (a scroll that moves no row boundary: 0.13 ms), not the frames that change the window. By the mean (A 11.8% lower in Chromium) or the p95 of frame work (A 8.4% lower) the answer would be nearer a tie in the other direction, and the 4x cell is the place to look for a real difference.

## B1, B5 (`w3.mjs`, `fit.mjs`)

The sample (first 100, last 100 and the rows in view) misses rare long strings, and the plan did not change because at these widths the planner holds the readable floors. It was not made in this step.

## What was not measured

- **Native WKWebView** (step 1a.11), Windows (WebView2) and Linux (WebKitGTK): headless Playwright WebKit and Chromium only, software rendering, device pixel ratio 1, the system font (no fonts step yet), no hardware compositing. Compositor cadence (the second number of B2) is not page-visible: not measured.
- **Memory** (G-T5): not measured. **4x CPU in WebKit**: the engine has no throttle.
- **The overscan and step sweep ({6/3, 8/4, 10/4})**: not run; the constants stay 8 and 4. It needs `f4b92809`'s knobs: `git checkout 1570a872`, then `node bench/table/run.mjs --engine <e> --workload w1 --configs s@6/3,s@8/4,s@10/4 --tag m2-<e>-sweep` (and `--cpu 4` in Chromium as `-sweep-4x`), then `node bench/table/sweep.mjs m2 s`. Given that p95 ties everywhere, expect the tie rule (the incumbent 8/4 stays) unless the frame-work columns separate.
- **W3 mount and sort timings** (mount to the first row at 25, 1,025 and 5,025 rows; the sort from a click): `w3.mjs --only mount,sort` was written and not run.
- **Timing runs on the real cells**, and R with a row click handler and Base UI cells: not run. The matrix used plain cells by the rule.
- A VoiceOver pass and the Chromium tree's sort property (not exposed by the API).
