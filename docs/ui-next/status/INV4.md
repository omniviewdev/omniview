## What the plugin now promises (INTERIM)

**Complete for every API group that answered discovery; groups that did not are listed in the connection fact `kubernetes.unavailable_api_groups`.** The fact is an object, `count` (how many group versions do not answer) and `groups` (the first 32 of them in order, each `{groupVersion, reason}`; reasons `stale`, `unavailable`, `timeout`, `too_large`, `invalid`, `absent`, `failed`), and is absent while every group answers. It is set at start and follows the installed catalog whichever path installs it (the heal, an explicit refresh). The sentence is in the code comment of `discoverNativeSupport` and in the README. `Coverage` has no place for a note once it is `complete` (`validation.go:829-838`) and an additive field is a wire change, so the note travels in the connection metadata, an existing generic channel.

**Why 32.** The SDK refuses a metadata value over 16 KiB (`MaxConnectionMetadataEntryBytes`) and then fails the observation of every fact of the connection, the server address and the version among them. It counts the JSON of each string (`quotedJSONSize`: a quote, a backslash and the short control escapes take 2 bytes, any other control character, `<`, `>`, `&`, U+2028 and U+2029 take 6), so a name is bounded by its JSON, not by its length. 32 names whose JSON is as long as the longest legal name (a group of 253 characters, a version of 63, with the reason and the JSON around them) are about 12 KiB. `clipGroupVersion` cuts a name a server makes up at the last character whose JSON still fits 317 bytes; a legal name is returned as it is, and a name that is not valid UTF-8 (the SDK refuses one; JSON decoding never gives one) is cut before its first invalid byte. Tests: 200 groups, 40 groups of the longest legal names, one name of 20,000 characters, and 40 names of 249 control characters (what the first version let through: 48 KiB, the whole observation lost), through the real start and the SDK's validation; a table of the characters the encoder escapes.

## The line: "a group is unavailable" or "the cluster cannot be read"

The start fails, nothing is published, the connection is never CONNECTED when: the discovery index (`/api`, `/apis`) cannot be read; **discovery lists no API resource at all** (decided in this round: a cluster with no kinds is not a usable connection, and a refresh that took the answer for one would drop every kind; the base accepted it); **a group version answers 401 or 403** (credentials or permissions are refused, never "unavailable"); a group version answers as another group version; **a built-in group version does not answer, or serves a document that parses and is wrong** (`nativeBuiltinGroups`: core `v1`, `apps`, `batch`, `rbac.authorization.k8s.io` and the other groups kube-apiserver serves in process); or the index or a built-in group version has not answered when the acquisition deadline ends (they have no bound of their own, exactly as before). A group version of an extension group whose document fails after the index was read for any other reason (an error answer, a body that is not a discovery document, a version the aggregator marks stale) is unavailable; **so is one whose document parses and is wrong** (a resource without a name or a kind, the same resource twice, versions of a group that disagree on whether a resource is namespaced: reason `invalid`; the catalog builder refused all three, which failed the whole start for one bad extension), **and so is one whose document has not answered within a bound** (reason `timeout`, next section). The kinds of an unavailable group version are left out of the catalog only when the group version was never read; one the catalog knew keeps what it knew (the table of what a refresh keeps). A group a newer server adds and the list lacks is read as an extension.

The text said "whatever the reason" and "when nothing was read" before; both were wrong for the code (a mismatched answer and the deadline failed the start; an empty answer was accepted). The empty answer is now refused; the sentence is now the list above, in the code comment, the README and here. The first round of this file said that "no read has a bound of its own" and left a hung extension read failing the start (the reviewer's F7, CodeRabbit's third comment); the lead decided on 2026-11-22 that a hung extension group must be unavailable, and the next section is that decision.

## A hung extension group is unavailable (the bound)

The requirement (the lead, 2026-11-22): one broken API group never keeps a user out of a working cluster, and a hang (an aggregated API whose backend a NetworkPolicy black-holes, or that sits on a dead node) is a way one breaks. It matters on the legacy path only: with aggregated discovery (a current server) there is no per-version read, the server answers for a backend that hangs and marks it stale (the reviewer's and my kind runs); on an older server, or behind a gateway that strips the aggregated `Accept`, each group version is a request and a hung one held the start until the acquisition deadline (10.003 s measured by the reviewer) and then failed it.

| Question | Answer, and the evidence |
|---|---|
| The rule | An extension group version's own document that has not answered within the bound is unavailable (reason `timeout`) and the start goes on; the index and the built-in group versions fail closed at the acquisition deadline exactly as before. |
| The value | **Half of what is left of the acquisition deadline when the reads begin, at most 5 s** (`nativeGroupReadBound`): 5 s at the default 10 s when the index is fast, 2 s at 4 s, 0.5 s at the 1 s an operator can set (the range is 1 to 300 s); the bound is computed after the index is read, so a slow index shrinks it (an index of 8.8 s of 10 s leaves 0.6 s and names slow but healthy extension groups `timeout` until a later attempt finds the index fast: the second review's R2). Half, so that the rest of the start has the other half; the cap, because waiting longer than the API server itself does buys nothing. |
| What client-go does | It reads every group version at once (`fetchGroupVersionResources`, one goroutine each) and gives each request 32 s (`defaultTimeout`; client-go v0.37.2 `discovery/discovery_client.go:54-56,1062-1072,1249`), longer than the default deadline, so there the bound never fires before the deadline. |

## What a refresh keeps (the merge)

A refresh replaces the catalog from a new discovery. When the catalog lacked a group, or this discovery finds a group version that does not answer, the discovery is merged into what the catalog was built from (`native_catalog_merge.go`, `mergeNativeDiscovery`) instead of replacing it:

| What the server says now | What the catalog does |
|---|---|
| a group version answers | its kinds are added or updated; a kind its document no longer lists is gone |
| a **built-in** group version answers without a kind it had | the kind stays (a degraded answer is not a deletion) |
| a group version is **listed and does not answer** | every kind the catalog knew of it stays; it is named in the fact |
| the index no longer lists a group (a CRD deleted, an APIService removed) | its kinds are gone; a built-in group is never gone |
| discovery lists nothing | refused: the attempt fails and the catalog stays |

A refresh of a connection that never lacked a group, and whose discovery answers every group, replaces the catalog as it always did. `unavailable`, and so the fact and the loop, always follow the latest discovery.

What this replaces: the first version refused a whole attempt when the new discovery lacked any known kind (`nativeSupportCovers`). That froze the catalog and the fact while one group was dead (a new CRD was not added; the fact named a deleted group and missed a newly failed one), and when the attempt had no failed group at all it did the opposite and trusted a shortened answer (S1: Pods dropped, the loop ended).

**What it cannot tell.** A successful but degraded answer for one extension group's document (a replica that is still syncing CRDs during a control-plane roll, an intercepting gateway) is believed, and the kinds it lacks are removed; when that attempt also finds every group answering, the loop ends, so those kinds are missing until the next reconnect. A degraded INDEX is not believed (below): an index that lists none of the extension groups the catalog knew removes nothing. Built-in kinds never go. The merge works on what discovery read, the resource list of each group version, and builds the kinds from the merged lists as discovery always did: a kind served by a version that answers and a version that does not is served by both, with the preferred version chosen from the new index.

## Dev tools

`docs/ui-next/status/INV4/` (drop the `.txt`; no path is an author's any more, each is a variable): `host.sh` (a host on a throwaway HOME) and `hostkeep.sh` (the HOME kept across a restart, a port it bound itself) take a name of one path component (`^[A-Za-z0-9][A-Za-z0-9._-]*$`), refuse a name whose host still runs and a port that is in use, record the host's pid, start time and command, signal a process only while all three still match, and stop a host that does not answer in 60 s; `lib.mjs` (bound calls by name, 30 s each, a timeout is a result, and the connection fact read as the host's envelope has it: `snapshot.entries`), `ui-lib.mjs` (`INV4_HOST_CHECKOUT`: the host checkout that holds Playwright in its `node_modules` and the generated bindings, default the directory it is run from; a refused session reset stops the probe), `ui-probe.mjs` (first load, Retry only if it is offered, the RPC trace), `ui-heal.mjs` (both engines, heal, sidebar, palette; `KUBECONFIG_PATH`, `BASE_WK`, `BASE_CR`), `ui-422.mjs` (which request answers 4xx in a first load and with what body; `ENGINE=webkit` or the default `chromium`), `authority-probe.mjs` and `wait-catalog.mjs` (the authority table; `wait-catalog.mjs` exits 0 only when the catalog and the fact calls both answered, the metrics types are in the catalog and the fact is gone), `broken-apiservices.yaml`, `host-admit-partial.patch.txt`, `mutate.py.txt` (the fault-injection runner; see the next paragraph).

`mutate.py.txt` works on a scratch copy of the package (`INV4_MUT_BASE`: a copy of `go.mod`, `go.sum`, `pkg/` and `ui/src/kinds/` of the plugin under test, never a worktree; `INV4_WORK` for the scratch copies; `INV4_MUT_OUT` for a JSON of the results). It first runs the unmutated copy: the selected tests must pass, twice, or nothing is counted. A fault is **caught** only by tests that pass at that baseline, fail with the fault, fail again when only they are run again with it and pass on a pristine copy; a failure that does not meet this is dropped as noise and named; a fault that passes everything, does not apply, breaks the build or is seen only by tests the table does not name for it is **not caught**, and the run exits 1. `--converse M1 M2 ...` first requires the fault to trip an assertion of a test named for it (a fault that passes everything has no assertion to remove and fails the converse), then removes, round by round, exactly the one-line testify assertions that tripped until the run passes, and exits non-zero when it does not.

Read before running: they are inert as `.txt`. `INV4_WORK` (default `${TMPDIR:-/tmp}/inv4-work`) holds the hosts (`$INV4_WORK/hosts/<name>`), the saved authority state and the mutation scratch copies; the scripts remove only below it, only a directory whose name passed the rule, and signal only a process whose recorded pid, start time and command still match what they started (a process they did not start is never signalled, and none by a pattern). `hostkeep.sh` finds its port by binding and closing it, which can race with another process; a host that then fails to bind exits and the start fails. `ui-lib.mjs` writes the window session of whatever host it is pointed at (`BASE`). `ui-heal.mjs` expects the stale state to exist already and then scales `kube-system/deploy/metrics-server` up and deletes the cluster-scoped APIService `v1beta1.demo.example.com` in the cluster of its kubeconfig; the authority run scales metrics-server by hand. `broken-apiservices.yaml` makes the stale state: part (1) replaces the `metrics-server` Service and APIService by ones that no Pod backs, which is for a cluster **without** a real metrics-server (it re-points the Service of a real one); part (2), an APIService whose Service does not exist, is safe beside a real metrics-server that is scaled to 0 (the re-runs of 2026-11-22 used that). `mutate.py.txt` writes and deletes scratch directories it creates itself under `INV4_WORK/mut`. Run them against your own kind cluster only.
