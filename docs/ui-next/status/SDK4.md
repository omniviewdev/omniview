### 2.2 The output a session leaves for its first attach (SDK #89, "Host follow-up brief")

**The problem.** A session of a plugin that ends by itself while no window is attached (`echo hi`, a failed `kubectl exec`) keeps its output in the plugin's exec manager for the first `AttachSession` to it (at most 32 sessions, a minute, lazy expiry; nothing for a session the host closed or one that was attached when it ended). A window attaches after it created the session, so for a short command the attach comes after the session has ended and sent its CLOSE. The host deleted `sessionIndex[id]` at CLOSE (`dispatchOutput`), so its own `AttachSession` answered "not found" before it asked the plugin. Red evidence (the controller of `origin/main` on the pin, `SDK4/red-unfixed-host-on-v0.22.1.log.txt`): the late attach returns the host's `{"type":"omniview:session/not-found","title":"Session not found","status":404,...}`.

**The change** (`ended_session.go`, and the call sites in `controller.go`), as the brief says it and with the decisions it left open:

- The record of a plugin's session (`sessionIndex`) now says whether a window is **attached** (a successful `AttachSession` sets it; `DetachSession` clears it, *before* the plugin is asked, so a CLOSE that comes while the call is on its way finds a session whose window has gone: the plugin keeps its output then), whether the host asked to **close** it (`CloseSession` sets it before it asks the plugin: the plugin keeps nothing of a session the host closed) and whether it has **ended** (with its time and its place in the order of ending). The host has to track this itself: at CLOSE the plugin has already taken the session out of its manager, so there is nothing to ask.
- **At CLOSE** (`recordCloseLocked`): a session that was attached, or that the host closed, is over for everyone: its record goes at once, as it always did. One that ended with nobody attached stays, marked ended and dated.
- **An ended record goes at the first of:** a successful attach (the output is for one attach: the record is deleted after the call, whatever the plugin answers), a close or a detach of it, the unload of its plugin (`cleanupPluginLocked` deletes every record of the plugin, which is test (d)), or **90 seconds** after the CLOSE (longer than the SDK's 60 s). The expiry is checked when a record is looked up (`lookupSessionOrEnded`) and when another record is made (`makeRoomForEndedLocked`): **no timer**. At most **32** ended records are kept: the 33rd evicts the oldest. A live session never counts against the limit and is never evicted.
- **An ended session is not a session a window can use.** `GetSession`, `ResizeSession` and `WriteSession` (tested), `IsBusy` and `GetCwd` (through the same lookup) and the multiplexer's input path find it as they found a session after its CLOSE before: not found. Only attach, detach and close find the record. A detach finds nothing (the host's own `SessionNotFound`, as before) and forgets the record. A close of an ended record is a close that has nothing to do: success, the record goes, the plugin is not asked (the output it kept is for an attach nobody will make now).
- **An attach to an ended record** asks the plugin like an attach to a live session. If the plugin answers not-found (a plugin built on an SDK that predates the keeping, which is every plugin until it is rebuilt on v0.22.1, the Kubernetes plugin included; or the output expired there first), the window gets **the host's own `SessionNotFound`**, the words it got when the host forgot the session at CLOSE (the new terminal feed's `isGone` reads that type, `localShell.ts`); so for an older plugin nothing changes for the user, and the record goes at once.
- **Calls about a live record whose session the plugin no longer has** (it ended while a window was attached, and its CLOSE has not reached the host yet): the plugin's answer is returned as it is, and the record is forgotten (an attach or a detach that is answered not-found has nothing left to attach to).

### 2.3 `CloseSession` of a session that has just ended is not an error

SDK v0.22.1: a `CloseSession` that finds the session already gone, because it ended by itself in the instant before the call (it has left the plugin's manager; its CLOSE is still on its way to the host), answers **not-found** (gRPC `NotFound`; it used to answer success when the end came between the lookup and the stop). The host passed that status to the window, which logs it (`provider.tsx:330,350`, `tabs.tsx:170`: `.catch` into `log.error` or `console.error`) and, in the new feed, would not know it for "gone" (`isGone` reads the host's own `omniview:session/not-found`, not a raw gRPC text). Now `CloseSession` treats the plugin's not-found as what the caller asked for: the session is closed. The answer is read three ways, so no provider's form is missed: the gRPC status `NotFound`, the SDK's own `ErrSessionNotFound` (a provider in the host's process), and a classified `NOT_FOUND`. Any other error is the plugin's and is returned, and the session is not forgotten (`TestAFailedCloseIsStillAnError`).

- Held in Go, twice: `TestClosingASessionThatJustEndedIsNotAnError` (both error forms, then the late CLOSE makes no record) and, with the real SDK, `TestClosingASessionThatJustEndedInAPluginIsNotAnError`: the host's multiplexer is not read, so the plugin's frames, the CLOSE among them, wait where the host has not taken them; the test waits until the plugin's manager has no session, and the host, which still holds its live record, closes it: no error, no record. Red on `origin/main` (the raw gRPC status).
- "No error toast": the host returns nothing, so there is nothing for a window to show or to log. For the windows as they are: the legacy ones only log, as above; the new terminal feed throws any close error that is not `isGone` (`execFeed.ts:343-347`), so for a plugin transport (not built yet) this is what keeps a close of a just-ended session from becoming a failure.
