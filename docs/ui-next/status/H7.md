## The rule (decided by the lead, built here)

1. A history entry carries the page state of the page it LEFT; Back and Forward give it back (all of it, scroll included).
2. A NEW navigation opens clean, except: when an earlier entry of the SAME tab holds the exact same route (plugin, page, parameters: another connection is another route) the page starts with what the NEWEST such entry kept, **without `scroll`** (top). A route opened in a new tab, a duplicate and a change of scope (`history: 'replace'`) start clean. An entry the 50-entry cap drops (also with this very navigation) gives nothing.
3. Close drops the history's states and keeps the entry on screen's; reopen brings that back (Back then opens the page before it clean). Duplicate: no page state (ch16 S37).
4. **Not saved across a restart** (the decision, per the mock): `serialise` writes what it wrote (routes only), an older snapshot loads as it did, a snapshot that carries page-state members is read without them (tests: old format, hostile members, `__proto__`). Reasons: ch16 S32 "Page-local state is not persisted unless the plugin opts in"; the mock "Page state is not saved (S32)" (`shell-core.js:2652`) and its list registers only the Columns choices for saving (`k8s-resources.js:98`); the session's own README already says why (a saved offset is wrong after the data changed and races the first load); and a saved state would make the saver write on every scroll.
5. **Bounds.** History 50 entries per tab. A page state is at most `LIMITS.pageStateBytes` = 16 KiB of JSON in UTF-8 (counted in bytes, not characters). **There was no byte limit on `pageState` before this step** (only a depth of 24 in `lenientJson`), so the limit is new and applies to the live state and to each entry alike: a write over it is refused (`setPageState` answers `false`, the page keeps what it had). Totals: a tab holds at most 51 states = 816 KiB; a closed tab one, the 25 closed tabs 400 KiB; a list page writes about a hundred bytes (sort, search, filter, offset).
6. **Keep-alive.** A page that stays mounted keeps its own live state. A page the cap let go, and a page a step or navigation draws, read the tab's `pageState` as they open; the page writes only when the person chooses (never on mount, so a step is ONE commit and idle is none; scrolling writes once the scrolling stops, 150 ms, or at once on a press or key in the page, never when the page goes: the tab has moved on by then and the write would be the next page's).

## What the mock does (measured: WebKit and Chromium agree; scripts and JSON in `~/Notes/omniview/ui-migration/status/H7-assets/mock-measure/`)

The mock's Pods list (89 pods) sorted Memory descending, quick filter Running, search "a", one row selected, scrolled 500; then:

| Action | sort | quick | search | selected | scroll |
|---|---|---|---|---|---|
| open a pod, Back (and Forward, Back) | kept | kept | kept | kept | **top (500 -> 0)** |
| sidebar "Pods" from the detail page (a NEW navigation, same tab; history 4/4) | kept | kept | kept | kept | top |
| Pods -> Deployments -> Back | kept | lost | lost | lost | top |
| Duplicate | kept | lost | lost | lost | top |
| close, reopen | kept | lost | lost | lost | restored (500) |
| switch to another tab and back | kept | kept | kept | kept | restored (500) |

Why (quoted): the shell's own step drops the page state, `shell-core.js:2035` (`history: {...}, pageState: {}`), and the shell's S60 says "a change of page-local state (filter, sort, selection) pushes nothing". The list keeps its state in its OWN per-tab store, `k8s-resources.js:58` (`const ui = id => Shell.get([ROOT, 'tabs', id], {})`), and re-seeds it only when its fingerprint changes, `:57` (`signature = JSON.stringify([route.page, route.item, connection.generation])`) and `:667-669` (`if (ui(ctx.tab).fingerprint !== fingerprint) { ... put(ctx.tab, { ..., quick: '', selected: [], sort: saved.sort || '' ...`); `remember` (`:127-130`) keeps `filters`, `sort`, `labelSelector` per connection and kind for the session (that is what a Duplicate and a reopen are seeded from); `tab:closed` removes the tab's store (`:807`); the only path registered for saving is the Columns choices (`:98`). The detail page's section is in the ROUTE (`route.tab`), so Back/Forward restore it (Back showed Overview, Forward Metrics). Chapter 16: S30 (a closed tab keeps its `pageState` while the window lives), S32 (page-local state is not persisted unless the plugin opts in), S37 (Duplicate: not the page state), S50 and S60 (history), S141 (the scroll offsets are part of the shell's page state).

**Divergences, listed (the lead decided the first two):**
1. Back/Forward restore the scroll offset; the mock goes to the top. A deliberate improvement (browsers, VS Code, JetBrains).
2. A navigation to a route the tab has been at takes the state, scroll aside: the mock does it for the same list (`:57-58`); here it holds for any page of the tab's history (a detail page too), not only a list.
3. Back after another list restores everything here; the mock keeps the sort only. Reopen restores search and quick filter here (they are in `pageState`, which S30 says reopen carries); the mock's list loses them because its own store is removed on close.
4. NOT done, later candidates: the mock's per-connection-and-kind memory of the sort (`:127-130`), which makes a Duplicate and a new tab open sorted as the list was; the **detail page's section** (the mock keeps it in the route; here `DetailPage` holds it in `useState`, so Back/Forward lose it: it needs `memory` on `DetailPage` and the host's `DetailContribution` to pass it, `PluginHost.tsx`, not this step's file); the selected row (the list draws no selection column yet; whatever a page writes is carried).
5. **Found, not mine:** `PageHost`'s scroll memory (`ui-next/shell/tabs/PageHost.tsx`) is keyed by scroller, not by history entry, and is put back when a tab is SHOWN again: after list@800 -> detail -> new navigation to the list (top) -> switch tab away and back, it puts the old 800 back. The kit's table takes no initial offset and has no `onScroll`; this step reads its named scroll region (`role="region"`, the list's title), as the page host does. **Need for the kit:** `DataTable` props `scrollOffset` (initial, applied when it can reach it) and `onScrollOffsetChange`, so the page needs no DOM lookup.
