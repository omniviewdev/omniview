# T3a: Find in the scrollback, a context menu, URL links

**Status: for review (see the PR).** Branch `ui-next/t3a-terminal-find-menu` on `origin/main` b015ceb5 (T2d, #689, is merged). Worktree `~/Repos/omniviewdev/worktrees/ui-next-t3a-terminal-find-menu`. Owner agent `TerminalTool`. The first slice of T3 (`T-terminal-bar.md`): items 1 to 3 of the lead's order, and the unit seconds.

## 1. What this slice is, and is not

In: (1) FIND in the scrollback (a bar over the screen, case, whole word, regex, a count, next and previous, Escape; `@xterm/addon-search` is a lazy chunk); (2) a CONTEXT MENU on the kit's unified menu host (Copy, Paste, Select all, Clear, Find; right click, Shift+F10, the Menu key); (3) URL LINKS (`@xterm/addon-web-links`; Cmd+click opens through the host's open-external call); (5) the unit seconds.

Not built (the slices that follow): file and folder links (they need a host route that opens a file at a position), Split and Rename, the copy-on-select and paste-safety rows of `T-terminal-bar.md`, shortcut hints in the menu (a kit defect, section 5), and the icons of section 6.

## 3. Decisions

1. **The chord (decision A24).** VS Code and JetBrains agree on Cmd+F and Ctrl+F, and AGENTS.md says to follow them where they agree; the written spec S52 says Ctrl chords without Shift stay the shell's and names Ctrl+Shift+F. Both are bound on Linux and Windows, as the lead ordered (quote, VS Code's Terminal Basics: "The integrated terminal has find functionality that can be triggered with Cmd+F (Windows, Linux Ctrl+F). Ctrl+F can be sent to the shell by removing the `workbench.action.terminal.focusFind` command from commands to skip shell"; JetBrains: "To search for a certain string in a terminal session, press Ctrl+F (Windows), Cmd+F (macOS)"). The cost: Ctrl+F no longer reaches the shell on Linux and Windows (readline's forward-char); on a Mac Ctrl+F stays the shell's.
2. **Enter is Next and Shift+Enter is Previous** (the mock and the Logs find bar; VS Code's terminal find maps Enter to Previous, `terminal.find.contribution.ts`: the lead's order and the mock win). F3 and Shift+F3 step the same way in every engine.
3. **The highlight limit is 20,000** (VS Code's value; the addon's default is 1,000). The lead asked for newest-first: the addon counts and highlights top-down from the OLDEST row and stops at the limit, so past 20,000 matches the newest are the ones left out, and `index` can be -1 for a match beyond the count. Newest-first needs a fork. The emulator keeps 5,000 lines of scrollback, so more than four matches a line are needed to reach the limit.
4. **The menu's items are the ones the order names** (VS Code's own menu has no Find entry; JetBrains' has). No shortcut hints are drawn yet: the kit's `MenuPanel` sets `aria-label` to the item's label and leaves out the drawn shortcut, which fails axe 4.14 `label-content-name-mismatch` (WCAG 2.5.3) on every kit menu item that draws one (K1, section 5). The terminal's items pass no `shortcut`; the chords still work.
5. **The right click and Shift.** xterm reports the mousedown (button 2) to a program that asked for mouse reports; our menu must not open then, and `contextmenu` is prevented in the capture phase (the kit host ignores a prevented event and the browser's own menu goes too). With Shift held the kit host opens ours. (xterm's own forced selection is Shift off macOS only; Option with `macOptionClickForcesSelection` on a Mac, which this app does not set.)
6. **Links open through `Browser.OpenURL`** (the Wails runtime, re-exported by the runtime package): ui-next had no open-external helper and uses no `window.open`. The Go side refuses addresses with shell metacharacters (`;`, `|`, `$`); the audit gateway denies the call for remote view-only browsers; in server mode [INFERENCE] the system browser opens on the machine that runs the server, not in the tab (a native window opens it on the person's machine).
7. **Whole word and a selection inside a word.** The addon slices the line at the search start, so a boundary written in the regex reads the cut as a line edge. Before stepping with whole word on, the engine clears a selection that starts or ends inside a word (a match from the same query before the toggle, or a mouse selection), so the search starts from the buffer's end and the active match is always a whole word (A1 names what stays).
8. **The link tooltip is dismissible (WCAG 1.4.13).** Escape hides it while it is shown (a capture-phase `keydown` listener that exists only then; the key still reaches the shell); the same link does not bring it back until the pointer has left it.
9. **A hyperlink a program prints (OSC 8) follows the same policy as a printed address** (CodeRabbit Major on the first push). xterm registers its own provider for them and its default handler asks `confirm()` and calls `window.open`, which would open a WebView window past the host's call. The engine installs its own `linkHandler` from the start: a click opens only with the platform's modifier, through the same open-external call, for `http` and `https` addresses with a host (anything else is refused and draws no tooltip); with no open-external call a click does nothing (no dialog, no window).
10. **The highlight colours follow the mock as far as the addon allows.** The other matches are a dim amber with no border; the current match is the terminal's selection colour. Open decision for the lead: while the Find bar has the focus xterm draws the selection in its INACTIVE colour (a grey), so the current match is that grey and not the mock's accent blue; setting `selectionInactiveBackground` to `selectionBackground` while a find is up would fix it (about 6 lines) and would also recolour the person's own unfocused selections.
