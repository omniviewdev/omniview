## What it does

A pull request now starts with a job `Changed paths` in each of the two workflows (`PR Validation`, `PR Checks`). It runs `node scripts/ci/changes.mjs --base HEAD^1`: the paths the merge commit adds to its first parent (`git diff --name-only -z --no-renames`: a rename lists both paths), each put in an area, and one class for the change. The class becomes three flags, `skip_host`, `skip_ui` and `skip_windows`; a job that needs `changes` and carries `if: needs.changes.outputs.skip_<flag> != 'true'` is skipped when its flag says so. The test is `!= 'true'`, never `== 'false'`: a classifier that wrote nothing skips nothing, and one that fails (exit 1, no output) fails the gates. On a runner the script also writes one annotation, `::notice title=Changed paths::class=<class> skip_host=<bool> skip_ui=<bool> skip_windows=<bool>`, which the check run keeps (see "For the lead").

## The Windows build (ruling 1)

`build-artifacts` was one matrix job, and a job-level `if:` cannot see the matrix, so Windows is now a job of its own, `build-artifacts-windows`, named `build-artifacts (windows/amd64)` (the check name it always had). It carries the matrix job's steps for Windows plus the native React-compiler admission step, `if: skip_windows != 'true'`. The matrix job keeps macOS arm64 and Linux. `changes-workflows.test.mjs` holds the two together step by step (same actions, versions, commands and flags; the macOS-only block and the `-H windowsgui` substitution are the only differences it allows), so a step changed in one and not the other fails. **What a macOS-only kit build break now relies on for a new-UI pull request:** nothing before the merge; after it, the `Main macOS universal` run of the merge commit (`main-macos-universal.yml:76`: `task packages` on `macos-15-intel`, about 17 minutes after the push), then the feature channel's native builds when it is active. A Linux-only break is caught by the UI jobs, which build the kit on Linux.

## Choice: skip at job level, gates stay green (ruling 3, accepted)

The lead's merge gate (`gate.sh`) refuses any `SKIPPED` check that is not by design, and the plan wants stable gate names. Two shapes were possible: (a) skip the parts with `if:` (no runner is allocated) and keep two aggregating gates that always run and report success when a part was skipped by path, or (b) keep every job and guard each of its steps, so that every check is a real success. **I chose (a).** (b) starts about fourteen runners on a documentation-only pull request (a Windows one, and a container image pull for each Go job unless `runs-on` and `container` are also switched by expression), puts a guard on about a hundred steps (a step added later without one runs on the skipped class), and in a busy queue its wall time is the wall time of the last of fourteen job starts: it cannot meet "nothing heavy, under a minute". (a) costs five jobs of 2 to 16 seconds (measured).

- **`UI checks`** (`ui-checks`, same name): needs `changes` and the five UI jobs, runs unless the run was cancelled. A part is green when it succeeded, or when it was skipped and `changes` succeeded and said `skip_ui` is `true`; the summary table says `skipped by path: <class>` for it. A part that failed, was cancelled or timed out, a part skipped for any other reason (the corpus job failed, the flag was missing), a classifier that did not succeed, and an empty list of parts are red, each named in an `::error::` line.
- **`e2e-tests`** (same name, `if: always()`): green when `e2e-application` succeeded, or was skipped while `changes` succeeded and said `skip_host` is `true`; the step after it writes `e2e skipped by path: <class>` to the log and the summary. Red when it was skipped without the flag (a code path never reaches the skip), when it ran and failed or was cancelled, and when `changes` did not succeed.

## Residual risk

- **A macOS-only kit build break on a new-UI pull request** is seen only after the merge, in `Main macOS universal` (about 17 minutes after the push; see "The Windows build"). Windows and Linux are covered before it.
- **A second queue wait.** Every gated job now waits for `Changed paths`, so in a saturated pool it queues twice: on the proof pull requests `PR Checks / Changed paths` waited 3 s in an idle pool and 79 to 185 s in a busy one (the free plan's 20 concurrent jobs; other agents' runs shared it), and the jobs behind it then queued again. In an idle pool the cost is 12 to 16 seconds. The documentation-only and new-UI classes use fewer runner slots than before (5 and about 20 jobs against 17 and 26), which is the relief; the `all` class gains three small jobs.
- The classes are lists of paths: a new reader of a new-UI or status path in a host job is not seen until a search like the one above is repeated. The tripwires cover the readers found; `changes.mjs` says in its header that a path joins a class only with the search that shows nothing reads it.
