## What it does

A pull request now starts with a job `Changed paths` in each of the two workflows (`PR Validation`, `PR Checks`). It runs `node scripts/ci/changes.mjs --base HEAD^1`: the paths the merge commit adds to its first parent (`git diff --name-only -z --no-renames`: a rename lists both paths), each put in an area, and one class for the change. The class becomes two flags, `skip_host` and `skip_ui`; a job that needs `changes` and carries `if: needs.changes.outputs.skip_<flag> != 'true'` is skipped when its flag says so. The test is `!= 'true'`, never `== 'false'`: a classifier that wrote nothing skips nothing, and one that fails (exit 1, no output) fails the gates.

| Class | A change is in it when every path is | `skip_host` | `skip_ui` | What still runs |
|---|---|---|---|---|
| `docs` | `README.md`, Markdown under `docs/`, a `.txt` under `docs/ui-next/status/` (exactly the e2e selector's prose, E1; a test holds this class to never be wider) | true | true | `Changed paths` (two), `Repo guard`, the gates `UI checks` and `e2e-tests` |
| `new-ui` | the new UI (`ui-next/`, `packages/kit/`), its documentation (`docs/ui-next/`) or its own tooling (the probe table and its test, `scripts/ui-next-pods/`, `scripts/ui-next-bundle.mjs`, `bench/table/`, `bench/log/`) | true | false | the above and the five UI jobs; Kit probes and Pods by their own filters |
| `all` | anything else, no path at all, a Go input under the new trees (`.go`, `go.mod`, `go.sum`, `go.work`, cgo files), `ui-next/test-setup.ts` | false | false | everything, as before |

**Host jobs** (`skip_host`): Release packaging contracts, Windows connection profiles, Go checks, Go lint, Bindings freshness, `e2e-application`, the three `build-artifacts`. **UI jobs** (`skip_ui`): C02 error transport corpus, UI build, UI lint and kit contracts, UI component tests, UI runtime contract. The plan's negatives all end in `all`: `go.mod`, `vite.config.ts`, `package.json`, `pnpm-lock.yaml`, any `.github/**`, `Taskfile.yml`, a path never seen, documentation plus one code file.

`Repo guard` (`PR Checks`) is new and runs on every pull request: `scripts/check-tracked-outputs.test.mjs` and `check-tracked-outputs.mjs --base HEAD^1`, moved out of Go checks (whose checkout is back to one commit), then `changes.test.mjs`. It needs Node and Git only: no install.

## Found on the way

1. **The e2e suite loads one file of the new UI** (above). `changes.test.mjs` has two tripwires so that the carve-out stays enough: `ui-next/test-setup.ts` must import nothing, and `vite.config.ts` must name no other file of the new trees than the setup file, the flavour root and the test glob. A pull request that changes `vite.config.ts` is `all`, so the repository guard runs them.
2. **Every probe pull request edits `scripts/ci/probe-shards.mjs`** (K1: a new probe or control is a unit of that table). Left to the default it would make every probe pull request `all`; in the last 150 commits of main 21 of 39 commits that touch `ui-next/` or `packages/kit/` were `all` because of a path outside them (16 `.github/workflows/`, mostly the probe workflow before K1, 5 `scripts/`, 4 `bench/table`, 4 `pnpm-lock.yaml`, 3 `vite.config.ts`). The new UI's own tooling is therefore in `new-ui`, each with its only reader named in `changes.mjs`: the probe table and its test (the kit probes workflow), `scripts/ui-next-pods/` (the Pods workflow), `scripts/ui-next-bundle.mjs` (`scripts/ui-flavour.test.mjs`, in UI build), `bench/table/` and `bench/log/` (no workflow runs them; UI lint lints them). `.github/**` stays `all`, as the plan says.
3. **`git diff --name-only` hides the old path of a rename.** With rename detection on (a user's `diff.renames`, the default of `git diff`) it prints only the new name, so `go.mod` moved to `docs/old.md` would read as documentation. The script passes `--no-renames` and `-z`; a negative test sets the hostile configuration and checks both paths.
4. **A skipped matrix job is reported once, under the raw template**: `build-artifacts (${{ matrix.platform }})`, not three checks. Nothing here depends on it; a gate for the matrix is needed before checks are made required (see "For the lead").
5. A file name is attacker-controlled text: the script prints no path before replacing control characters, so a name with a newline and `::error::` cannot write a workflow command into the log, and writes no path to `$GITHUB_OUTPUT` at all (a negative test).

## Choice: skip at job level, gates stay green

The lead's merge gate (`gate.sh`) refuses any `SKIPPED` check that is not by design, and the plan wants stable gate names. Two shapes were possible: (a) skip the parts with `if:` (no runner is allocated) and keep two aggregating gates that always run and report success when a part was skipped by path, or (b) keep every job and guard each of its steps, so that every check is a real success. **I chose (a).** (b) starts about fourteen runners on a documentation-only pull request (a Windows one, and a container image pull for each Go job unless `runs-on` and `container` are also switched by expression), puts a guard on about a hundred steps (a step added later without one runs on the skipped class), and its wall time in a queue like today's is the wall time of the last of fourteen job starts: it cannot meet "nothing heavy, under a minute". (a) costs five jobs of 2 to 16 seconds. The price is that the skipped parts are `SKIPPED` checks: the lead's `gate.sh` needs the list below (it already has the mechanism for the CI image jobs).

- **`UI checks`** (`ui-checks`, same name): needs `changes` and the five UI jobs, runs unless the run was cancelled. A part is green when it succeeded, or when it was skipped and `changes` succeeded and said `skip_ui` is `true`; the summary table says `skipped by path: <class>` for it. A part that failed, was cancelled or timed out, a part skipped for any other reason (the corpus job failed, the flag was missing), a classifier that did not succeed, and an empty list of parts are red, each named in an `::error::` line.
- **`e2e-tests`** (same name, `if: always()`): green when `e2e-application` succeeded, or was skipped while `changes` succeeded and said `skip_host` is `true` (`e2e skipped by path: <class>` in the log and the summary). Red when it was skipped without the flag (a code path never reaches the skip), when it ran and failed or was cancelled, and when `changes` did not succeed.
- The plan's note on `e2e-tests` read `needs.e2e-application.result` as `success` only; that is now the first of the three cases above, and the skipped case needs the flag.

## Residual risk

- **A kit build that fails on macOS or Windows only is no longer seen on a new-UI pull request.** `build-artifacts` runs `task packages` (`pr.yml:123-125`), which builds the kit (`Taskfile.yml:454-460`); the stable product does not embed it, but the job's result depends on that step. The same command runs on Linux in UI build, UI lint and UI component tests and in every Kit probes shard, the kit's build scripts hold no operating-system branch (`process.platform`, `path.sep`, `win32`: none in `packages/kit/scripts`, `vite.config.ts`, `tokens/`), and the plan's table shows no build-artifacts failure that was not shared with another job or infrastructure (section 5). After the merge: every push to main builds `task packages` on macOS Intel (`main-macos-universal.yml:76`), and the `feature-ui-next` channel builds the kit on the three systems when it is active (`build/Taskfile.yml:32`, `desktop-build.yml:40`). Windows has no other native kit build. If the lead wants one, move the `windows/amd64` entry out of `skip_host` (a one-line change in the table and the workflow, with its test).
- The classes are lists of paths: a new reader of a new-UI path in a host job is not seen until a search like the one above is repeated. The two tripwires cover the one reader found; `changes.mjs` says in its header that a path joins a class only with the search that shows nothing reads it.
- Docs evidence that is not Markdown (`docs/ui-next/status/**/*.yaml|json|png`, 22 files today) is `new-ui`, not `docs`: the UI jobs run for it. E1 left that widening to the owner; the e2e selector keeps it `full`. It would be one more line in `changes.mjs` and in the selector.
