## What it does

A pull request now starts with a job `Changed paths` in each of the two workflows (`PR Validation`, `PR Checks`). It runs `node scripts/ci/changes.mjs --base HEAD^1`: the paths the merge commit adds to its first parent (`git diff --name-only -z --no-renames`: a rename lists both paths), each put in an area, and one class for the change. The class becomes two flags, `skip_host` and `skip_ui`; a job that needs `changes` and carries `if: needs.changes.outputs.skip_<flag> != 'true'` is skipped when its flag says so. The test is `!= 'true'`, never `== 'false'`: a classifier that wrote nothing skips nothing, and one that fails (exit 1, no output) fails the gates.

| Class | A change is in it when every path is | `skip_host` | `skip_ui` | What still runs |
|---|---|---|---|---|
| `docs` | `README.md`, Markdown under `docs/`, a `.txt` under `docs/ui-next/status/` (exactly the e2e selector's prose, E1; a test holds this class to never be wider) | true | true | `Changed paths` (two), `Repo guard`, the gates `UI checks` and `e2e-tests` |

## Choice: skip at job level, gates stay green

The lead's merge gate (`gate.sh`) refuses any `SKIPPED` check that is not by design, and the plan wants stable gate names. Two shapes were possible: (a) skip the parts with `if:` (no runner is allocated) and keep two aggregating gates that always run and report success when a part was skipped by path, or (b) keep every job and guard each of its steps, so that every check is a real success. **I chose (a).** (b) starts about fourteen runners on a documentation-only pull request (a Windows one, and a container image pull for each Go job unless `runs-on` and `container` are also switched by expression), puts a guard on about a hundred steps (a step added later without one runs on the skipped class), and in a queue like the one on 2026-11-20 its wall time is the wall time of the last of fourteen job starts: it cannot meet "nothing heavy, under a minute". (a) costs five jobs of 2 to 16 seconds (measured). The price is that the skipped parts are `SKIPPED` checks: `gate.sh` needs the list in "For the lead" (it already has the mechanism, `ALLOW_SKIPPED`, for the CI image jobs).

- **`UI checks`** (`ui-checks`, same name): needs `changes` and the five UI jobs, runs unless the run was cancelled. A part is green when it succeeded, or when it was skipped and `changes` succeeded and said `skip_ui` is `true`; the summary table says `skipped by path: <class>` for it. A part that failed, was cancelled or timed out, a part skipped for any other reason (the corpus job failed, the flag was missing), a classifier that did not succeed, and an empty list of parts are red, each named in an `::error::` line.
- **`e2e-tests`** (same name, `if: always()`): green when `e2e-application` succeeded, or was skipped while `changes` succeeded and said `skip_host` is `true`; the step after it writes `e2e skipped by path: <class>` to the log and the summary. Red when it was skipped without the flag (a code path never reaches the skip), when it ran and failed or was cancelled, and when `changes` did not succeed.

## Residual risk

- **A kit build that fails on macOS or Windows only is no longer seen on a new-UI pull request.** `build-artifacts` runs `task packages` (`pr.yml:123-125` at main), which builds the kit (`Taskfile.yml:454-460`); the stable product does not embed it, but the job's result depends on that step. The same command runs on Linux in UI build, UI lint and UI component tests and in every Kit probes shard, the kit's build scripts hold no operating-system branch (`process.platform`, `path.sep`, `win32`: none in `packages/kit/scripts`, `vite.config.ts`, `tokens/`), and the plan's table shows no build-artifacts failure that was not shared with another job or infrastructure (section 5). After the merge: every push to main builds `task packages` on macOS Intel (`main-macos-universal.yml:76`), and the `feature-ui-next` channel builds the kit on the three systems when it is active (`build/Taskfile.yml:32`, `desktop-build.yml:40`). Windows has no other native kit build. If the lead wants one, move the `windows/amd64` entry out of `skip_host` (a one-line change in the table and the workflow, with its test).
- **A second queue wait.** Every gated job now waits for `Changed paths`, so in a saturated pool it queues twice: on the proof pull requests `PR Checks / Changed paths` waited 3 s in an idle pool and 79 to 185 s in a busy one (the free plan's 20 concurrent jobs; other agents' runs shared it), and the jobs behind it then queued again. In an idle pool the cost is 12 to 16 seconds. The documentation-only and new-UI classes use fewer runner slots than before (5 and about 20 jobs against 17 and 26), which is the relief; the `all` class gains three small jobs.
- The classes are lists of paths: a new reader of a new-UI path in a host job is not seen until a search like the one above is repeated. The two tripwires cover the one reader found; `changes.mjs` says in its header that a path joins a class only with the search that shows nothing reads it.
- Docs evidence that is not Markdown (`docs/ui-next/status/**/*.yaml|json|png`, 22 files today) is `new-ui`, not `docs`: the UI jobs run for it. E1 left that widening to the owner; the e2e selector keeps it `full`. It would be one more line in `changes.mjs` and in the selector.

## For the lead

- **`gate.sh`**: with this change a documentation-only or new-UI pull request has `SKIPPED` checks, so the gate stops on them unless `ALLOW_SKIPPED` names them. The names are exactly (checked against the 12 skipped checks of the documentation proof, #601): `^(Release packaging contracts|Windows connection profiles|Go checks|Go lint|Bindings freshness|e2e-application|build-artifacts \(.*\)|C02 error transport corpus|UI build|UI lint and kit contracts|UI component tests|UI runtime contract)$`. For a new-UI change only the first seven alternatives (the host jobs) are skipped, and the UI jobs must be SUCCESS. By the model of the CI image jobs, honour the list only when `Changed paths` (two checks, one per workflow), `Repo guard`, `UI checks` and `e2e-tests` are all present and SUCCESS (they are on every pull request, never skipped); a skipped `UI checks` or `e2e-tests` is never by design.
- **Making checks required later**: a skipped matrix job reports one check under the raw name `build-artifacts (${{ matrix.platform }})`, so the three expanded names would never report on a skipped pull request. A gate job over the matrix (as `UI checks` is over the UI jobs) is needed first; I did not add one (not asked).
- **Decisions**: (1) keep the Windows `build-artifacts` for kit changes (see Residual risk); (2) widen `docs` to the non-Markdown evidence under `docs/ui-next/status/`; (3) whether a changed `.github/workflows/ui-next-*.yml` should be `new-ui` (the plan says any `.github/**` is `all`; I kept that).
