# T2d: the panel comes back as it was, a taken terminal can be taken back, and a dropped connection is rejoined

**Status: for review (see the PR).** Branch `ui-next/t2d-terminal-followups` on `origin/main` 994d557c (T2b, #688, is merged). Worktree `~/Repos/omniviewdev/worktrees/ui-next-t2d-terminal-followups`. Owner agent `TerminalTool`. Follow-ups 1 to 3 of `T2b.md`, and the unit seconds.

## 1. What this slice is, and is not

In: (1) after a reload the panel restores its saved open state, active tool and active session (and height); (2) a terminal another tab took, whose taker has since gone, offers "Take it back"; (3) when the page's events connection drops and opens again, each running terminal re-joins by offset (a gap in the host's ring heals by a replay); (5) the unit seconds of the terminal units from the runner's samples.

Not built, the next slice: (4) Find in the scrollback (Cmd+F, case and regex, next and previous; xterm's search addon loaded lazily) and the terminal's context menu on the kit's unified menu host (#678: Copy, Paste, Select all, Clear, Find). It was left out on purpose: (1) to (3) each needed the real host, a probe section with controls and a seam scenario with perturbations, and the order says that when the budget is short they go as one pull request and (4) after.

## 3. Decisions

1. **S116, read as written, is a clarification and not a reversal.** The written rule (ch. 16, S116): "The panel opens when the user starts a session, runs *Open logs*, or picks a tool. Sessions restored at startup, adopted from another window, or re-created by Retry do not open it (today's quiet-tab rule). ... *Why:* a restored terminal must not cover the page." A restored session still never opens the panel. The panel's own saved visibility is a different fact: S103 saves what the user chose (`open`, height, the tool, the session of each tool), and VS Code and JetBrains both keep the panel's visibility and the active terminal across a reload. T2b read "a restored session does not open the panel" as "the panel is closed after a reload", which hid a live terminal behind a toggle with nothing to say it was there. The rule is stated again in `core/panel/README.md`, `session/README.md`, `decisions.md` (A23) and `S3a.md`.
2. **The button needs `free`.** `canTakeBack` is true for any ended and detached feed, and the lane draws the button only when the taker has gone: beside "Taken over by another tab" (the taker is alive) there is none, so two live tabs do not fight over a terminal with one press.
3. **A free or lost feed's `close()` still sends nothing to the host**, so closing a tab never ends a terminal no tab shows (the host's lease is what ends it). Say so if a free terminal's close should end it.
4. **Every replay answer is checked** (an integer `start >= 0` and `start + length === end`, else the answer is unreadable), since rejoin relies on `start` to know how many bytes to skip.
5. **The first events signal at page load** (the runtime calls a listener that subscribed before the first connection) is harmless: `rejoin` does nothing for a terminal that is not running.

## 4. The real host (facts used, measured in T2b and again by this slice's seam)

- A page whose events socket drops is a NEW window identity to the host when it reconnects (after 1 s, same client id); events told meanwhile are lost to the page for good; a blip under ~6 s leaves the terminal attached to the old identity; `AttachTerminal(id, { page_key, from_offset })` answers from a boundary at or before the offset (a gap when `start > from_offset`) and the host echoes `DETACHED taken-over` with the old number to every window.
- After a tab that took a terminal is closed (a page closed, not reloaded), the host's `requested` for the taker's attachment reached the first tab in 4 to 58 ms in both engines in the seam (the taker's `DetachTerminal` at `pagehide` got through: the WebKit drop of T2b was measured on a RELOAD); where it does not, the host says `window-retired` 2 to 4 s later and the button waits for that. No event is sent when a third tab attaches a terminal that is detached (so `free` can be stale, and pressing the button then takes it over, which is what the person asked for).
- A seam proxy (a small TCP forwarder the scenario owns) cuts the page's events socket and refuses a new one for a set time, in both engines alike.

## 7. Not verified

- The Linux CI image (the seam and the probes there), Windows, the native desktop window (the window keeps its identity across a reload), Safari itself and any engine but Playwright's, the back-forward cache.
- The seam's proxy cuts and refuses the page's events socket; the real network failures (a laptop that sleeps, a flaky link) were not tried.
- One failure was seen once in a combined parallel pass on Chromium at the blip ("0 bytes lost": the cut found no output to lose) and did not recur in seven later runs and the whole seam; the assertion now prints the proxy's counts and the offsets if it comes back.
- The words of a failed "Take it back" ("Failed to start / Couldn't start the terminal.") are the start failure's, not worded for a terminal that already existed.
- Typing during a replay is queued; a virtual keyboard's keyCode 229 text, mouse reports and wheel-to-arrow input are still dropped while a replay is applied, and a replay that never finishes leaves held typing queued; the queue keeps the first 64 Ki characters.
- The take-back guard is a check, not a claim: the race closes only with the host precondition of W8 (not built; asked).
