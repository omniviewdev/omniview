## What was built

- **Contract** (`contract/v1.ts`, minor, optional `palette` beside `panel`): `PaletteV1 = { providers?, commands? }`. A provider is `{ kind: 'match' | 'search', section, filter?, supports? }` with `match(query, scope)` (a small set held in memory: ranked by the host) or `search(query, scope, signal)` (on demand: 150 ms after the last key, aborted when the query moves on or the palette closes, 5 s, 20 rows kept, `limited`/`partial`/`message` in an answer). A row is DATA: `id`, `label`, `secondary?`, `keywords?`, a kit glyph `icon`, and exactly one of `route` (a page of the plugin's own pages) and `command` (an id in `palette.commands`, with a JSON `arg`). A command is `{ run(arg, { plugin, panel? }) }`. At most four providers a plugin, ids and section titles bounded (`PALETTE_LIMITS`).
- **Admission of the declaration** (`contract/admit.ts`): a malformed declaration is refused by name, as a malformed `panel` is (a kind this version does not know, a provider with no way to answer or with both, a fifth provider, a colon in an id). **Admission of the rows** (`contract/paletteRows.ts`, run while the palette runs): one row at a time, bounded lengths, a glyph `isIconName` knows, a route to a page the plugin has (a list page takes no parameters, a detail page needs the parameter its definition says names its object), a command the plugin registers, a JSON argument of at most 1,024 characters, no function in the row. A row that is not valid is left out with one sentence naming it; the rest of the answer, the provider and the plugin are untouched.
- **Host wiring** (`host/paletteProviders.ts`, `host/palette.ts`): a provider of the model for each the plugin declares, registered by `attach()` for every plugin that is ready and has a palette; replaced when a plugin's contribution is replaced; taken away with its pending requests, rows and the chips that narrowed the search to it (`removePlugin`, one change) when the plugin is loading again, failed or gone; kept until the last of several attaches is undone (React's double mount). A failure is said in the host's words ("Things did not answer."): the plugin's own error is the cause of the error the model logs, and reaches no screen. A late answer, an answer after the stop, a deaf provider and a provider that never answers are the model's runner's to drop or time out, and are tested through the real wiring. The host does no work on an answer that came after it was told to stop. A plugin called `host` is refused (its providers would be asked whatever the palette is narrowed to, and `removePlugin('host')` would take the host's own sources). Rows open through the tab model exactly as the host's do; a command is looked up again immediately before it runs and its failure is told in the host's words. `PluginHost` hands each plugin's panel handle (`panelHosts`) to the palette for its commands.
- **The order of the plugins' sections** (`host/palette.ts`, `syncProviders`): the plugins' providers are registered in the rail's order whatever order the plugins turned ready in, because sections that match equally keep the order their providers were registered in and what a plain Enter opens is the first row (decision 9, and "The open item"). A plugin that arrives ahead of others in the rail has them registered again after it; one that leaves, or whose contribution is replaced, disturbs nobody else's place.
- **Fixture plugin** (`fixture/src/palette.ts`): one `match` provider (a page and a command) and three `search` providers, `quick` (at once), `slow` (300 ms) and `big` (5,000 rows), each controlled through `window.__fixturePalette` (delay, size, `fail`: throw, reject, hang, garbage, a row that is not valid; `spin`: hold the thread; `listen: false`: deaf to the signal) with counters (`calls`, `aborted`, `answered`, `active`). It is QUIET until a check makes the control (every `supports` says no), so the other scenarios of the seam check are not disturbed.
- **Probe** (`palette-plugins-probe.mjs`, which runs section `plugins` of `palette-probe.mjs`; `palette-plugins.mjs`, `palette-plugins-fixture.{html,tsx}`): the host's own wiring (`createHostPalette`) over the fixture plugin, in a real shell. Parts: timeline, typing, focus, commits, shift, closed, states (axe); the seconds of each part are in the report (`report.plugins[<engine> <viewport>].seconds`). Controls (in the shard table, each runs only the part it perturbs): `slow-blocks`, `quick-late`, `focus-moves`, `extra-commit`, `plugin-shift`, `closed-work`, `stale-shown`. The section is a script of its own, and a shard of its own (shard 6), because it is about 150 s and its controls about 120 s more, which no shard has room for (see "Shard seconds").
- **Seam scenario `l`** (`ui-next/plugins/e2e/seam.check.mjs`): the real Go host, two plugins loaded from bundles built outside the tree.

## Decisions and deviations (for the lead)

1. **The member is `palette`, not `search` (C1b's spec said `search` beside `panel`).** It holds providers of both kinds and the commands they name; `search.providers[x].kind === 'match'` reads wrong.
2. **A malformed declaration is refused by name; a bad row is dropped.** The assignment says admission "drops bad ones with a per-provider problem, never a crash" for rows; for the static declaration I kept the contract's own rule for `panel` (refused by name, the `contract` failure). If the lead prefers a bad declaration to drop only that provider, it is one `checkPaletteProvider` result turned into a problem instead of a refusal.
3. **Both directions of the contract** (the assignment): an older bundle (no `palette`) is admitted and drawn as before (`admit.test.ts`, `PluginHost.palette.test.tsx`); a newer bundle on a host that predates the member is the older contract and one member more, which that host never reads (its admission has never refused a member it does not know, as for `panel`): shown in `admit.test.ts` by the same bundle without the member being admitted with the same verdicts, and by a type test that each is assignable to the other. C1b's spec said an older host "refuses by name"; it cannot, for the same reason `panel` could not (decision P1a). **Not run:** a real older host (a Go server built from `origin/main`) loading the new fixture plugins: it is a one-off by hand and the plugin vocabulary of this step makes it cheap, but it was not done here.
4. **A row's kind is derived, not declared:** a row with a command is a command; a route row is a page for a `match` provider and a resource for a `search` provider. The accessible name says it ("Page: …", "Resource: …"). A noun of the plugin's own ("Pod") and `into` (the step inward that makes a chip) are NOT in this contract: they are what the resource search needs next (below).
5. **The plugin's name is among the words a `match` row is found by**, as the host's own pages' are.
6. **Problems of rows go to `report`** (default: the console, `[palette] <plugin>:<provider>: <sentence>`), once for each distinct sentence for a provider and at most eight; the status band says nothing of them (the mock has no state for it). If a visible state is wanted, `partial` is the model's existing one.
7. **`supports(scope)`** is in the contract (C1b's spec had it): a provider may decline a scope; the model asks it with a frozen copy of the scope (plugin, chips below the plugin's own, kind).
8. `ui-next/shell/index.ts` gained one type export (`PaletteAnswer`): the host reads the model's answer type.
9. **The plugins' sections tie in the rail's order, whichever plugin loaded first.** The model keeps sections that match equally in the order their providers were registered in, and the host registered the plugins in the order they turned ready, a race between two loads. `syncProviders` now registers in the rail's order (`railOf`, `compareRail`: a total order that does not depend on how the plugins were listed or loaded) and registers again, behind a plugin that arrives ahead of them, the plugins after it; a plugin that leaves, or is replaced, disturbs nobody else's place. This changes what a user sees only where two plugins' sections match equally: the rail's order decides, on every run.
10. **`ASSERTION_OFF=<regex>` in `palette-probe.mjs`** drops the failures whose line matches, so a negative control can be shown undetected with its assertion removed (the rule for a control) by running it with its own `expected` pattern.

## The open item: cause and fix

**What was seen.** In scenario `l` of the seam check (the real Go host), plain Enter on the first row of the results opened the plugin's page in the tab on screen (one tab) in most runs, and in some runs opened it in a new tab beside (two tabs, the new one on screen). WebKit failed in the first full run and Chromium in the second; repeating the scenario alone on a loaded machine (load 7 to 55, eight busy loops added) it failed within its first four runs every time, about one run in three, and the same on both engines.

**What it was not.** Not the engine (both did both), not the key (the trace shows `{"how":"smart","source":"search"}` from the plain Enter every time), not the tab model: it decided as its rule says (`open.ts`: smart open navigates the tab on screen when it is in the SAME plugin and scope, else it opens a tab, a preview one when it came from search results). Not a pointer: no `pointermove` reached the page (only the boundary events a browser sends when rows come under a pointer at rest, which the palette does not read).

**What it was.** The destination of the failing run was the OTHER plugin's page (`fixture-b-dup`, the copy), while the tab on screen was the first plugin's. The two fixture plugins bring rows that read alike and match equally, so their sections tie, and a tie keeps the order the providers were REGISTERED in. The host registered a plugin's providers when the plugin turned ready, and the two plugins load at the same time: on a loaded machine the copy was sometimes ready first, so its section led, and Enter opened ITS row. The check could not tell (the rows' accessible names and the sections' headings are the same for both plugins).

**What a user gets on a plain Enter** (the rule, unchanged): the first row opens by smart open. A page that a tab already shows is shown (that tab comes forward). Else, when the tab on screen is in the same plugin and the same scope as the row's page, that tab goes to it (a new step in its history). Else a new tab opens beside the one on screen, a preview tab when the row came from a search (it is replaced by the next preview, and a tab the user keeps stops being one). Alt Enter always goes in the tab on screen, Command or Control Enter opens a background tab, Command or Control Shift Enter a new tab that is shown. What is first: the section that holds the best match; equal sections in the order Recent, Tabs, Go to, Commands, Settings, then the plugins'. **Now the plugins' are in the rail's order on every run.** Host rows have no such race (the host's own sources are registered first, in a fixed order): scenario `j` of the seam check (Enter on a host page row, one tab asserted) passed in every full run of both engines.

**The tests.** Red first: `palette.test.ts` (three: the order a plugin's turn gives, a plugin that arrives ahead of the others in the rail, and a plugin that leaves or reloads) and `PluginHost.palette.test.tsx` through the real PluginHost (a plugin that is ready first and one that is ready after it, the rail's first plugin on screen: Enter must stay in the tab, and it opened a second one). The seam check now names which plugin leads (the ids of the rows), restores the absolute tab counts (1, 2, 2, 3), and `SEAM_PROVIDERS_REPEAT=<n>` runs the scenario alone n times.

## For the Kubernetes plugin

**The provider to register FIRST: one `match` provider for the kinds and pages.** It is cheap (a list the plugin already holds from its catalog and its sidebar skeleton), needs no backend, no connection and no network, and gives every kind and page a palette entry (SE1: "an item of that list that the palette cannot find is a defect"):

```ts
palette: {
  providers: {
    kinds: {
      kind: 'match',
      section: 'Kinds',                      // "Kubernetes · Kinds" in the palette
      match: (_query, scope) => KINDS.map((kind) => ({
        id: kind.page,                       // the sidebar's page id: stable
        label: kind.plural,                  // "Deployments"
        secondary: kind.group,               // "Workloads" (the group the sidebar puts it in)
        keywords: [kind.singular, ...kind.shortNames].join(' '),   // "deployment deploy" "po" "svc": what kubectl calls them
        icon: kind.glyph,                    // the kit glyph the sidebar already uses
        route: { page: kind.page, connection: scope.chips[0]?.id, params: {} },   // the list page; the connection when the palette is narrowed to one, else the tab's (the host completes it)
      })),
    },
  },
},
```

Why this one and not "every resource": it is a static list of a few dozen rows, returned as the same array each call (the host reads at most 1,000 rows of a `match` answer, and re-reads them on every keystroke: a few dozen cost nothing); it touches no cluster, so it cannot fail, be slow or be forbidden; and the model ranks it (title 6, keywords 3, context 1: `po` finds Pods by prefix and `svc` by keyword). The Kubernetes kinds are the plugin's vocabulary and live in the plugin, never in the host. A row's `label` is at most 120 characters, its `id` at most 256.

**What resource search needs from Q0's steps** (`proposals/Q0-bounded-query.md`):

- **Q4 `searchResources` in `@omniviewdev/runtime/ui/v1`** (a FUNCTION, not a hook: a `search` provider is a plain function with a signal; Q0 section 5.3) is the one thing the provider needs on the host side, and it is on the plugin's side of the seam: this step's `search(query, scope, signal)` is what calls it. `signal` is the palette's own; Q4's cancel-to-`CancellablePromise` mapping is what makes "the query moved on" stop a backend call.
- **Q3a and Q3b (the identity representation and the name index, plugin Go)** answer the question the provider asks: names that begin with or hold the text, for one kind and a few namespaces, at most 20, with a count (`limited`) and a coverage reason (`partial` and `message`: "Building the Pods index"). Without them a search would scan the API per keystroke, which Q0 section 7 rejects.
- **Q1 (counts)** is not needed by the palette, but its size gate is the provider's answer to "should an unscoped search ask every kind?" (Q0 section 9, question 3): until the user names a kind (a type chip) the provider can decline an unscoped search with `supports`, and ask only the kinds whose count is under the threshold.
- **Q6 is the provider itself**: `search: (text, scope, signal) => Promise.all(kindsOf(scope).map((type) => searchResources({ type, text, namespaces, limit: 20 }, { signal })))`, merged by rank, each row `{ id: row.key, label: row.name, secondary: 'namespace · Kind', icon, route: { page: <detail page of the kind>, connection, params: { name, ...the page's other identity parameters } } }`. The host requires the parameter the detail page's `identity.name` names; a resource whose name is longer than 120 characters needs a shortened `label` and its full name in the route. `limited` comes from `total`; `partial` and `message` from `coverage.reason`; a kind that throws is one failed source (the palette's own line and Retry), not an empty result.
- **What this contract does not yet have, and Q6 will want:** `into` on a row (the step inward `→`, which makes a chip: connection, then type, then resource, so `scope.chips` reach the provider), and `Into.kind: 'plugin'` for a host plugin home. Both are additive minors of this same member; none is built here (the assignment's row shape has no `into`).
- Recents of a plugin's rows are remembered as pages (the host records what the tab model made of the open) and are not yet persisted (`createPaletteSaver` is still not wired to the session slot: C1b's list).
