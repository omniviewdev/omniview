## Decisions

1. **One deck, no remount, the document in the screen's order.** `PanelBody` still maps the mounted bodies, but `panes/order.ts` (`deckOrder`) lays a group out in the document as it lies on screen: the panes of the group take the places its members hold in the mounted order, in the group's order, and each sash is keyed by the pane it comes before and sits just before it: pane 1, sash, pane 2, sash, pane 3, so the Tab key walks the screen (WCAG 2.4.3). A split makes a NEW session, mounted last, which takes the place of a member after it: React inserts the new body and its sash and moves none (`Panes.test.tsx` observes the deck's child list: nothing removed, the same nodes in the same order; the probe's `panes.keep` and `panes.order` do it in a real engine; `PaneEmulators.test.tsx` counts the fake emulator's constructions: 3, 4 after a split in the middle, none disposed). No CSS `order` is used. A close removes a node. *The one case that moves a node:* a session that no pane shows replacing the active pane's session (a tab chosen; the model's rule), where the replacing body, already mounted elsewhere, takes its pane's place in the document.
   A sash is one component for the pane it precedes, so a split or a close puts it between other panes without making another: the controller reads where it is NOW (`place()`), not where it was made (a first version kept the boundary of its first render: ArrowRight on the second sash moved the first pane after a split in the middle).
2. **`isShown` is true for every pane of the shown tool's group** (`core/panel/selectors.ts`), by one lookup in the group, not a layout per body: with hundreds of mounted bodies a change would otherwise build hundreds of layouts. Each pane is a real `TerminalBody` with its own emulator and its own `visible`: a pane that is not shown (the tool or the panel hidden) follows the existing hide rules (`screen.hide()`: parse without rendering, the GPU context kept, not recreated).
3. **The sash is the shell's, not the kit's.** The kit has no splitter or sash (checked: `packages/kit/src/components`); the panel's own top-edge handle (`Panel.tsx`, `splitter.ts`) is the precedent, so `panes/PaneSash.tsx` is a separator with a CSS Module, a hit area 3 px wider than its 1 px line on each side, `tabindex=0`, an accessible name, `aria-orientation` by axis, `aria-valuenow` the line's position in percent. The panel's `data-resizing` rules were scoped to `='y'` so that a pane drag (`'x'`/`'y'`) does not paint the panel's handle.
4. **What a drag costs** (the panel splitter's rule, HLT-34): a move writes no state; one animation frame writes `flex-grow` on the two bodies beside the sash; the model is told once, on release (`moveSash`); the inline value is handed back in a layout effect once React has drawn the committed shares; Escape or a cancelled pointer puts the shares back and tells nobody. The deck is measured when the gesture starts and **again at release** (found by the probe: a window narrowed mid-drag left a pane at 47 px, the commit being read against the old length), never per frame.
5. **80 px in pixels.** `PANE_MIN_PX` and `minRatio(extent, n)` of the model, with `extent` the deck's length less its sashes. Held in the drag (per frame), the keys, the release, and by `fitPanes` from the deck's `ResizeObserver` (a window made narrower, the panel maximised) and when the number of panes changes. A split is refused for want of room by `roomForPane` (the model's function, which the registry asks before it asks the host for anything and the toolbar asks to say why it cannot).
6. **Split terminal** is the fifth button of the Terminal toolbar (icon `columns`), in the body of each pane. It asks the deck for the length the panes would share with one more sash, and `terminals.splitHere(session, extent)` opens a NEW terminal through the same path as "New terminal here": the feed's `directory()` is the host's fact (`ChannelTerminalCwd`), the new target starts there and the registry opens it with `split: { extent }` (`TerminalSessions.open`), which is `store.splitPane` (a new session, never a copy). Refused with no room: nothing is asked of the host, nothing starts; a refusal after the process started closes it again and warns. The button stays focusable and says why it cannot (no room, outside a deck, a terminal that cannot say where it is) in its description and tooltip.
7. **The active pane is marked** (found while looking at the screenshots: nothing said which pane the keyboard is in): a 2 px accent line along the top of the active body (`data-pane-active`), only in a group.
8. **Not decided here:** the focus ring of a pane, the chord that splits, and the column layout's UI (the model and the deck draw it; no control asks for it yet).

## What is proved, and how

Page tests against the invented stream bodies (`panes/Panes.test.tsx`: **no emulator**; jsdom has no layout, so the deck's length is given: 800 px, a sash of 5), the Split button against the real registry and screen with a **FAKE emulator** (`terminal/TerminalSplit.test.tsx`), the registry (`TerminalSessions.test.ts`, `terminals.test.ts`).

**The real emulator** (the product's own xterm, DOM renderer where text is read and the GPU's where contexts are counted) is the probe's: `terminal-panes-probe.mjs` (`PART=panes` of `terminal-probe.mjs`, sections in `terminal-panes.mjs`), against the probe's own host, which now records the directory a terminal was asked to start in and every directory it was asked for. In WebKit and Chromium at 1440x900 and 1280x800:
- `panes.split` a second terminal under another id, asked to start in `/home/user` where the host said the first is; `panes.equal` two panes equal within 1 px, each at least 80, and with the sash filling the deck; `panes.focus` the keyboard in the new pane; `panes.cols` each emulator's columns are its pane's, within one column (the host's own record of the sizes it was told); `panes.three` three equal panes and two sashes;
- `panes.sash` a Tab stop with a hit area wider than its line; `panes.drag` a drag of 150 px moves the line by 150 px and the emulators follow; `panes.min` a drag far past either end stops at 80 px; `panes.reset` a double click equalises; `panes.keys` 16 px, Shift 64, Home, Enter;
- `panes.fit` a window made narrower brings every pane to at least 80 px, nothing overflows; `panes.drag-resize` also when the window changes mid-drag; `panes.full` a narrow window takes as many panes as fit and then Split terminal says why it cannot and starts nothing; `panes.gl` three panes hidden and shown ten times hold no more WebGL contexts than terminals and the count does not grow; `axe.panes` no violation.

Controls, both halves: the probe's table (`PANES_CONTROLS`, 11, unit `terminal-controls-panes`: faults of the page in a real engine) and `docs/ui-next/status/T6-panes-layout/controls.sh.txt` (19 faults of the code against the tests, with the second half enforced by a `SOLE` list). The second script puts each fault in the real file and puts it back (a scratch copy of the panel would not be the code the page tests draw, because the shell's own tree renders the real panel); do not edit those files while it runs.

Looked at (screenshots of three panes, `SHOTS=<dir>`): both engines at both viewports. The panes sit side by side with a 1 px line between them, each with its toolbar (five buttons); the active pane has the accent line on its top edge and the solid cursor.
