## Why this shape (for the reviewer: a page kind is hard to change once plugins ship it)

1. **A new kind, not an optional `identity` on the detail page.** The detail page is the page of ONE object everywhere it appears: the route needs its identity parameter (`paletteRows.ts` refuses a route without it), the tab is `{name} · {Kind}` (`detailIdentity.ts`), the back path leads to its list, `describeDetail` reads `identity.name`, and admission refuses it as a landing. Making `identity` optional changes the meaning of each of those for every existing detail page and asks every reader to branch on "unless there is none"; a type error does not find a branch that should have been written, it finds a read that no longer type-checks. A new member of the `PageV1` union touches none of them: old plugins and old pages are what they were, by construction, and the rule at the head of `v1.ts` (additive, optional, older bundles drawn as before) holds without argument.
2. **The detail anatomy is reused unchanged; the host's new code is one component and two small functions.** The mock's Overview IS that composition (header, tabs, OVW1 sections), so `OverviewContribution` (about 45 lines with its comment) makes a definition for the existing `DetailPage` (`overviewAsDetail`: `kind` = the page's title, one internal parameter holding the connection's name) and draws it. No new component of the page, no new style, no new kit prop, no new section kind, no new view type: the hook answers `DetailPageViewV1`.
3. **The heading is the connection's NAME, and the host owns that.** The host already knows the name of the connection a route carries (the lane's, else the one the window learned: `ConnectionNames`), and the key must never be drawn (HM2). So the plugin states no heading, and a plugin has no way to draw a key as one. A page that is read in no connection is headed by its title.
4. **The smallest definition.** `{ title, tile, tabs }`: no `identity` (the route names a scope), no `list` (nothing leads back above a landing), no `kind` (the page is named by its title), no route parameters (`RouteV1.params` is empty, as a list's). Everything the host draws more (state chip, facts, commands, summary, sections, states) is the detail source's, so a plugin that wrote a detail page already knows how to write this one.
5. **Both ways of compatibility are tested, not argued.** Old plugins on the new host: every existing admit, palette, contribution and fixture test is unchanged and green (two assertions that quote the list of kinds in a message changed their words on purpose). A new plugin on an old host: the old admission reads `kind` as `list` or `detail` and nothing else, so it refuses the bundle at admission by naming the page: `pages.overview.kind is "overview", and this version draws "list" and "detail" pages` (the first new admit test run on the unmodified code printed exactly this, with four more problems because the old check then reads the definition as a list's). That is the loader's `contract` failure: a typed refusal, never a crash, never drawn wrong. **The cost is real and is the plugin's choice**: a plugin whose `home` is an overview has no list-only contribution to give an older host, so the whole contribution is refused there (the same cost the detail page had, and the reason a plugin states the host version it needs). A second export or a runtime fallback would mean two builds of one plugin for hosts that, on the feature channel, update together with their plugins.
6. **What it deliberately does not do.** It adds no way to link to a list with a quick filter (below), no command of the host's own, no dashboard of numbers (a tile with a count and a link would be a new section kind, and the mock's cards do not need one: its rows are rows), no usage graph. Each is additive later under the same rule.

### Questions for the reviewer

- The name. `overview` is also the word of the detail page's first tab (OVW1) and of this page's in-page tab. The user's word for the page is "Overview" (the mock, the sidebar), and a kind that says what it is for beats a kind named for how it is drawn; say if you want `scope` or `landing`.
- A one-tab strip. The detail page draws its strip always, so a page with one tab shows a lone "Overview" pill under the header (seen in `status/HM3/overview-landing-webkit-void-1440x900.png`). It is the detail page's behaviour for every one-tab page; hiding it is a separate decision for both kinds.
- The synthesized definition (one internal route parameter, `OVERVIEW_SUBJECT`) against a small branch inside `DetailPage` for "no identity". The first keeps `DetailPage` (and its tests and probes) untouched at the price of one internal indirection; the second moves the indirection into a page every detail view depends on.
- The default words of a `not-found` state read "Overview north doesn't exist here" (the detail page's, `detailView.ts:81`): a plugin gives its own `message` for the state, as `DetailState` allows. Changing the default means changing `DetailPage`.
