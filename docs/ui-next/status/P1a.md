## Decisions to confirm (owner)

- **Contract rule (3) of a minor addition cannot hold by the letter for a new member.** `panel` is a new optional member of `ContributionV1`; an older host that validates the shape strictly would reject a plugin that brings it. The header of `contract/v1.ts` says so. Options: keep the member (an older host ignores unknown members today: it does), or version the whole contribution (`contributionV2`). I kept the member.
- **The height follows the mock: re-clamped on load and on resize** (was: stored as chosen and never rewritten, so a regrown window gave the user's size back). CodeRabbit pointed out that this was a deviation from the mock with no recorded approval. The model now has `fitHeight(viewport)` (run by `Panel` when it mounts and when the window height changes) and `restorePanel(..., { viewport })`, as the mock's `panelClamp` is run by `persist.clamp` on load and on `resize` (shell-core.js, S103); `resolveHeight` stays the draw-time clamp, as the mock's `solve` has it. If the owner prefers the user's size back after a regrow, it is a decision to record, and the change is to drop the effect in `Panel.tsx`.
- **A plugin's `open` that throws is logged and shown to nobody.** `newSessionOf`'s `start` catches it and logs `[panel] <plugin> could not start a session in <tool>` to the console (the panel's existing channel: a card that cannot describe itself and a refused open do the same); the app has no notification or error-history surface yet, so the user sees no message. The host needs one (lead: a row, not P1a's).
- **The status bar's toggle draws its own button** (`StatusBar.module.css`, as the rail and the strip's navigation buttons are host composition too); a review comment asked for the chrome in the kit. It moves with the `StatusBar` kit part (the doc comment on `StatusBar` says it should become one), not as a one-button capability now.
- **Every tool is a "sessions" tool** in this step (the singleton kind of Problems/Operations is not built); the tool registry has no count limit (the strip scrolls); a plugin brings at most 2 tools.
- **A plugin opens sessions by pull** (`PanelToolV1.newSession.open()`, called by the host on `+`); there is no plugin → host handle yet (P1b needs one: see the spec).
- The toggle chord is Cmd/Ctrl+J (the app menu binds neither it nor the close chord); the close-session chord only acts inside the panel and is handled in the capture phase so it does not also close a page tab.
- `docs/ui-next/optimisations.md` HLT-32 (every drawer tab stays mounted) is carried: a streaming session keeps its buffer, so a session body stays mounted after first shown. The cost is memory for every session ever shown; P1b decides the cap policy.

- **The card's buttons are 28 px high, as the mock draws them (`button.small`); the chapter and the mock's own comment say 24.** The probe follows the mock, the acceptance reference. Errata (row N10): the written 24 px against the drawn 28 px.
- **The shell keeps the arrow cursor on its buttons and tabs, as the tab strip and the rail do; the mock's are `pointer`.** The splitter's `row-resize` is compared.
- **A session tab is named by its title and scope, and by its state when it is not running ("stream-beta, ended"); the mock appends the target's detail and says "running" as well.** Written in `words.ts` before this resume; the spec (X33) asks only that a failed session says "failed".
- **The mock leaves a strip of many sessions scrolled to its start (the selected tab off screen); the shell scrolls the selected tab into view.** The probe scrolls the shell's strip to 0 to read both alike.
- **The kit's `KeyValue` is a size container only with 2 or 3 columns** (it was always): the first consumer in a box that is as wide as its content (the session card). A kit behaviour change, tested in `KeyValue.test.tsx`; the kit and detail probes pass.
- **Opening the panel pins the tool on screen as the user's** (`arrange.ts` `show`): a tool a plugin registers later never takes the panel by sorting first. Written with its test, not red first.
- **A late tool in an open panel moves the strip's own content** (the separator and `+` by the new tab's width): inherent in a strip that grows; Chromium's layout shift for it is 0.008 to 0.009. Closed, it is 0.
- **Two small tests (`saver.ts`, `splitter.ts`) were written together with their fixes, not red first.**

## P1b — the log viewer as a panel tool (exact spec)

**Goal.** The log viewer becomes the host's own tool in the bottom panel (`Logs`, a host tool id with no colon), drawn by the host, over sessions that plugins open. A plugin renders nothing in it; it opens sessions (`panel.sessions.logs.card` for the card) and names resources.

**Engines to carry from `docs/ui-next/optimisations.md` §3** (the register 3.1 rows; each keeps its test and its measure): HLT-1 virtual list (measured rows, `estimateSize` 18, overscan 30); HLT-2 row memo (identity comparator on the entry, six display flags, `searchMatches`, `currentMatchOffset`); HLT-3 static row CSS; HLT-4 one mutable buffer in a ref, one flush per frame, capped at 100,000 lines with head eviction; HLT-5 ingest parses each line once (one event per batch); HLT-6 the pause buffer is bounded (**a defect in the old code: bound it and say what is dropped**); HLT-8 the last 100 stream events and a separate ready flag; HLT-9 follow/pin (scroll pin in a layout effect, released by the user's scroll); HLT-10/11/12 incremental, bounded search (10,000 matches, 100 ms budget, `matchesByLine` once per matches change); HLT-13 binary search by time; HLT-14 single-pass ANSI parser at ingest; HLT-15 level detect by lookup; HLT-16 source selection as a `Set` with a 300 ms debounce; HLT-17 windowed source list above 50; HLT-18 copy visible = O(window); HLT-20 `tailLines` default 1000; HLT-32 a session's body stays mounted (the panel already does this); HLT-33 memo boundaries per session; HLT-34/35 splitter cost (done in P1a). Terminal rows (HLT-22..31, 36..40) are the terminal tool's step, not P1b.

**Runtime hooks a log session needs that `@omniviewdev/runtime/ui/v1` lacks.** `ui/v1` exports connection and resource hooks, types and errors only (`src/ui/v1.ts`); log sessions live in `src/logs.ts` (`CreateSession`), `src/logSessionEvents.ts` (`PrepareSessionEvents`, `SubscribeSessionEvents`) and `src/hooks/logs/useLogSession.ts` (`useLogs().createLogSession`), none of them curated. Add to `ui/v1` (names to confirm, shapes below): `useLogSession(request)` (create with a reserved id, subscribe, expose `{id, state: starting | running | ended | failed, cause, lines subscription}` and close on unmount), a `LogSessionRequest` type (plugin, connection, resource target, source, `tailLines`, follow), `useLogSources(target)` (the sources a resource offers), and a **plugin → host handle** in the contract (`PanelHostV1` or a `ctx.panel`): `openSession({tool, title, scope, route, state})` returning a session handle with `update({state, cause, title})` and `close()`, so a plugin's own button ("View logs") opens a host session without the host calling the plugin (the pull `newSession.open()` of P1a stays for the `+`). The host's viewer, not the plugin, subscribes to line events; the plugin only names the target.

**Backend catalog items**: see the previous section.

**Acceptance for P1b.** The log tool draws a session of the fixture-like neutral log source at 10,000 lines and 100,000 lines in WebKit and Chromium: mounted rows ≤ window + overscan, one React commit per frame while streaming, follow pin holds, search over 100,000 lines stays within its 100 ms budget, a hidden session keeps its buffer, the pause buffer is bounded, drag-resize with logs open adds 0 commits, copy visible is O(window); axe clean; the old bench rows HLT-g1..g5 have a new-tree equivalent (`panel-probe.mjs` is extended, or a `logs-probe.mjs`), and a CI step runs it.
