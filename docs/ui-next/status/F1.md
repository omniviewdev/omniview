## (a) `internal/builtinplugins/grafana` `TestDeniedAndShutdownCancellation`

**CI.** Run 44620965637, job 135902184855 (Go checks, attempt 1, PR #544): `provider_test.go:264: shutdown did not cancel query`, `--- FAIL ... (0.00s)`. The only failing test of the run.

**Verdict: PRODUCT ordering bug, not a test race.** The test asserts the right thing: after `Provider.Close()` an in-flight `QueryResources` must return an error. The provider sometimes returned a nil error and a response with every metric `failed: context canceled`.

**Cause.** `QueryResources` told a cancelled call from a failed source with `call.Err()` (`query.go:139`, before the fix). `call` learns about provider shutdown only through `context.AfterFunc(p.lifetime, cancel)` (`config.go:391`), which runs `cancel` in a new goroutine. The request, however, is cancelled through the connection generation (`config.go:249`, a plain child of `p.lifetime`, so cancelled synchronously inside `p.cancel()`) and its own `AfterFunc(t.generation, cancel)` in `transport.get` (`transport.go:57-58`). Two goroutines are started by one `Close()`; when the request one wins and `client.Do` returns before the `call` one has run, `call.Err()` is still nil, the error is folded into `fail("failed", ...)` (`query.go:147`) and `QueryResources` returns `out, nil`. It needs the goroutine that cancels `call` to be delayed, which is what a busy CI runner does and an idle machine almost never does.

**Evidence.** A scratch probe (not committed) printed the response when the nil error occurred: `nil error; result="failed: context canceled" lifetime.Err=context canceled`, 14 of 300 runs at `-cpu 2` under contention.

**Reproduction.** `-race`, 500 runs per setting, 36 busy loops:

| `-cpu` | before (origin/main) | after the fix |
|---|---|---|
| 1 | 1 / 500 | 0 / 500 |
| 2 | 23 / 500 | 0 / 500 |
| 4 | 11 / 500 | 0 / 500 |
| no contention, `-count=200`, default `-cpu` | 0 / 200 | n/a |

Larger after-fix sample (2000 per setting, same contention): `-cpu 1` 0 / 2000, `-cpu 2` 0 / 2000, `-cpu 4` 0 / 2000 (6000 runs, 0 failures; the same three settings failed 35 / 1500 before).

**Failing test first.** `TestQueryFailedByShutdownIsCancellationNotSourceFailure` (`provider_test.go`) puts the provider in the state `Close()` passes through (lifetime cancelled, `closed` not yet set, `call` not yet cancelled) with `GOMAXPROCS(1)`, so the goroutine that cancels `call` cannot run before `QueryResources` returns. It is red on `origin/main` 2000 / 2000 (quiet) and 2000 / 2000 (36 busy loops): `err=<nil> response=...Status:failed ... Message:context canceled`. After the fix 0 / 2000 and 0 / 2000. No sleep, no retry; it can only miss the bug, never fail on correct code.

**Fix.** `Provider.stopped(call)` (`config.go`): the call's own error, else `p.lifetime.Err()`. The lifetime is set before any goroutine it starts can run, so it is the one place that cannot lag. `QueryResources` uses it instead of `call.Err()`. Nothing else changes: `TestProviderConnection` and `GetDataSources` return `get`'s error directly, so they already surfaced the cancellation.

**Not changed, noticed.** Deleting or replacing a connection while a query is in flight cancels only that connection's generation, so the query still ends as `failed: context canceled` with a nil error (deterministic, not flaky, and arguably right: the source was retired, the call was not). Left alone.
