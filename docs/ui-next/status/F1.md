## (a) `internal/builtinplugins/grafana` `TestDeniedAndShutdownCancellation`

**CI.** Run 44620965637, job 135902184855 (Go checks, attempt 1, PR #544): `provider_test.go:264: shutdown did not cancel query`, `--- FAIL ... (0.00s)`, the only failing test of the run. Same line on 2026-11-09 (run 42695593598) and 2026-11-19 18:09 (run 44584824392).

**Verdict: PRODUCT ordering bug, not a test race.** The test asserts the right thing: after `Provider.Close()` an in-flight `QueryResources` must return an error. The provider sometimes returned a nil error and a response with every metric `failed: context canceled`.

**Cause.** `QueryResources` told a cancelled call from a failed source with `call.Err()` (`query.go:139`, before the fix). `call` learns about provider shutdown only through `context.AfterFunc(p.lifetime, cancel)` (`config.go:391`), which runs `cancel` in a new goroutine. The request is cancelled through the connection generation (`config.go:249`, a plain child of `p.lifetime`, so cancelled synchronously inside `p.cancel()`) and its own `AfterFunc(t.generation, cancel)` in `transport.get` (`transport.go:57-58`). One `Close()` starts two goroutines; when the request's goroutine wins and `client.Do` returns before the `call` one has run, `call.Err()` is still nil, the error is folded into `fail("failed", ...)` (`query.go:147`) and `QueryResources` returns `out, nil`. It needs the goroutine that cancels `call` to be late, which a busy CI runner does and an idle machine almost never does.

**Evidence.** A scratch probe (not committed) printed the response when the nil error occurred: `nil error; result="failed: context canceled" lifetime.Err=context canceled`, 14 of 300 runs at `-cpu 2` under contention.

**Reproduction** (`-race`, original test, 36 loops, 500 runs per setting):

| `-cpu` | before | after |
|---|---|---|
| 1 | 1 / 500 | 0 / 500 and 0 / 2000 |
| 2 | 23 / 500 | 0 / 500 and 0 / 2000 |
| 4 | 11 / 500 | 0 / 500 and 0 / 2000 |
| no contention, `-count=200` | 0 / 200 | n/a |

**Failing test first.** `TestQueryFailedByShutdownIsCancellationNotSourceFailure` (`provider_test.go`) puts the provider in the state `Close()` passes through (lifetime cancelled, `closed` not yet set, `call` not yet cancelled) with `GOMAXPROCS(1)`, so the goroutine that cancels `call` cannot run before `QueryResources` returns. Red on `origin/main` 2000 / 2000 quiet and 2000 / 2000 under 36 loops: `err=<nil> response=...Status:failed ... Message:context canceled`. After the fix 0 / 2000 and 0 / 2000. No sleep, no retry; it can only miss the bug, never fail on correct code.

**Fix.** `Provider.stopped(call)` (`config.go`): the call's own error, else `p.lifetime.Err()`. The lifetime's error is set before any goroutine it starts can run, so it is the one place that cannot lag. `QueryResources` uses it instead of `call.Err()`. `TestProviderConnection` and `GetDataSources` return `get`'s error directly, so they already surfaced the cancellation.

**Noticed, not changed.** Deleting or replacing a connection while a query is in flight cancels only that connection's generation, so the query still ends as `failed: context canceled` with a nil error. That is deterministic (not a flake) and arguably right: the source was retired, the call was not.

## (b) `backend/pkg/plugin/metric` `TestLegacyMetricBindingsRetainActualWindowRealm/subscribe/owner`

**CI.** Run 44204556280 attempt 1 (PR #534's branch `ui-next/n19d-delete-scaffolding`) and run 42568339182 attempt 2. The test binary panicked, so the package failed with no failing test named:

```
panic: runtime error: invalid memory address or nil pointer dereference
resource.(*appEmitter).Emit        emitter.go:28
metric.(*controller).handleStreamOutput   controller.go:362   (data event of an owned subscription)
metric.(*controller).ensureStream.func3   stream_state.go:188
  ... while unwinding, the deferred endStream: controller.go:359, the same panic again
```

**Verdict: TEST.** `ServiceStartup` binds the emitter to `application.Get()` (`controller.go:163`); a test has no Wails app, so `appEmitter.app` is nil and the first emission dereferences it. In `subscribe/owner` the stream's first sample arrives 0.1 to 0.3 ms after `Subscribe` returns (measured, five runs); the test passes only if its own `cancel()`, the `state.done` check and `Unsubscribe` finish before that, which a descheduled test goroutine misses. Other tests of the package that subscribe replace the emitter (`reference_admission_test.go:187,320`); this one did not.

**Evidence.** A scratch probe with the same fixture that only holds the subscription for 3 s panics every time, within the first 0.05 s of the test, with the CI stack. Contention (`-race`, 54 loops, `-cpu 2`, 40 processes x 25 runs of that subtest): 4 panics in 967 runs; the whole test, 36 loops: 1 crashed process in 100.

**Fix.** `window_context_test.go`: after `ServiceStartup`, `ctrl.emitter = hostresource.NoopEmitter{}`; the test asserts who may subscribe and who owns the stream, not events. After: 0 panics in 2000 runs (same loops, 80 processes x 25).

**Not changed, considered.** Making `NewAppEmitter(nil)` or `ServiceStartup` fall back to `NoopEmitter` would also stop the panic, but it would silence events in a host that was wired wrongly; in production the app exists when `ServiceStartup` runs.

## (c) Windows job `backend/pkg/plugin/resource`

**CI.** Every failure is the same error on a different request:

```
Received unexpected error: {"type":"omniview:resource/timeout","title":"Timed out","status":408,"detail":"The operation exceeded its deadline.","code":"TIMEOUT",...}
--- FAIL: TestAuthoringIdentityChangesRejectStaleExpectations (0.33s)      (0.26 to 0.71 s in the four runs; SchemaStates 0.55 s, ResponseIsBounded 0.31 s)
```

**Verdict: TEST.** `CompletePredicate` applies `resourceauthoring.DefaultPolicy().Deadline`, 250 ms (`policy.go:46`; "P01: 250ms", an interactive budget), to every request (`authoring_service.go:83-86`). The authoring tests ran under it although only `TestAuthoringDeadlineAndCancellation` is about it. On a loaded runner the request that is first for a new connection (`conn-2`, a new type, a new schema) takes longer than 250 ms; the elapsed times above are the deadline plus the test's own work. The tests assert identity, staleness and bounds, so a time budget is not what they mean to assert.

**Reproduction on macOS** (the Windows job cannot be run here): `-cpu 1`, 144 loops (8 per core), non-race, 150 runs of each of four authoring tests: 6 failures in 600 (`TestAuthoringIdentityChangesRejectStaleExpectations` 2, `TestAuthoringResponseIsBoundedForLargeSchemas` 2, `TestCompletePredicateOverTheServiceWrapper` 2), all `TIMEOUT 408` after 0.26 to 0.32 s, the CI signature. Unloaded the same tests take 10 to 20 ms.

**Fix.** `newAuthoringController` (`authoring_transport_test.go`) builds the test controller with the default policy and `Deadline = 0` (the policy says "Zero disables it" and that the deadline "may be zero in tests that supply their own context"); `newAuthoringHarness` and `TestActualSDKChildCompletion` use it. `TestAuthoringDeadlineAndCancellation` still sets its own 100 ms deadline and proves it against a provider that never answers. This is not a wider timeout: the tests no longer depend on the speed of the machine at all, and a hang is caught by `go test`'s own timeout. After, same loops and `-cpu`, 600 runs of each of the four tests: 0 failures in 2400.

## Dev tools

Nothing here is committed except `scripts/go-test-failures.mjs` and its test; the rest live in `/tmp/f1` and are reproduced here.

- `loaded.sh N CEILING -- command...`: N (at most 18) `perl` busy loops around a command, recorded in a pid file, killed by a trap on EXIT/INT/TERM/HUP, and each loop also exits when the script dies (parent change) or after the ceiling (`alarm`):

  ```bash
  N=$1; MAX=$2; shift 3; [ "$N" -gt 18 ] && N=18
  PIDFILE=$(mktemp /tmp/f1/loaded.pids.XXXXXX)
  cleanup() { [ -f "$PIDFILE" ] && { while read -r p; do kill "$p" 2>/dev/null; done < "$PIDFILE"; rm -f "$PIDFILE"; }; }
  trap cleanup EXIT INT TERM HUP
  for _ in $(seq 1 "$N"); do
    /usr/bin/perl -e '$pp = getppid(); alarm shift; for ($i = 0;; $i++) { exit if $i % 500000 == 0 && getppid() != $pp }' "$MAX" &
    echo $! >> "$PIDFILE"
  done
  "$@"
  ```

  (The earlier runs used a helper that backgrounded the loops and killed them in a second command; see the Log.)
- `runtest.sh BINARY REGEX COUNT [CPUS]`: runs `go test -c` output with `-test.run`, `-test.count`, `-test.cpu` and `-test.v`, prints runs and `--- FAIL` lines. `crashrate.sh BINARY REGEX MARKER PROCESSES COUNT [CPU]`: the same for a test that kills its process (a panic): runs many processes and divides crashes by runs started. Both are 10-line `grep -c` wrappers.
- Scratch probes, deleted: the Grafana response printer, the metric first-sample probe (holds the subscription 3 s), the gated-provider probe of the connection policy test.
- CI census: `gh run list --workflow "PR Checks" --limit 400`, `gh api repos/omniviewdev/omniview/actions/runs/ID/attempts/N/jobs` for every attempt, `gh api --allow-escape-sequences repos/omniviewdev/omniview/actions/jobs/ID/logs` for each failed Go checks or Windows job, read with `scripts/go-test-failures.mjs`.
