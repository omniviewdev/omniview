## 1. What is built

**A. The capability.** `Launch.Channel`; `CreateTerminal` answers `Session.Cap` (32 `crypto/rand` bytes, base64url, 43 characters) once and in no other answer; the manager keeps it as a `capability` type whose every formatting verb prints a placeholder and compares it with `crypto/subtle` against every capability it holds, with no early exit. A channel terminal has no record in the exec controller's index, no owner, no window and no event: `live()`, `Ack`, `find`, `ListSessions`, `List`, the tombstone lookups by id and the dismissal by id all refuse it with the same not-found as an id that never was. New bound calls, additive: **`CloseChannelTerminal(capability)`, `ChannelTerminalBusy(capability)`, `ChannelTerminalCwd(capability)`, `ListChannelTerminals(capabilities)`, `DismissChannelTerminal(capability)`**, each answering the one `omniview:session/not-found` (`terminal.ChannelNotFound()`, whose words hold nothing the caller sent). `ListChannelTerminals` answers only for the capabilities given, in the order given, by id, at most 1,024. All five are pinned `deny` in `internal/auditgate/policy.json` and in `TestDangerousMethodsStayDenied`; `/wails/stream/ws` was already denied by path and stays so.

**B. The channel.** `app.HandleStream("terminal", exec.TerminalStreamHandler(execController))` in `main.go` (both builds, one handler; a test pins that it is the only stream registered). `terminal.Channel` (`Send` blocking, `Recv` ordered, `Close`, `Done`); `streamChannel` adapts `*application.StreamConn`. The first frame is `attach{v:1, cap, from_offset?}` and nothing is read before it; anything else gets the single frame `not-found` and a close. Frames, handshake, gap and lost semantics, lease, takeover, errors and a worked example are in `docs/ui-next/terminal-channel-protocol.md`. Replay and live output are **one read of the ring** (so there is no join to get wrong); the connection is the holder; a stream that ends detaches the terminal and a new stream with `from_offset` takes it again byte for byte; a second stream takes it and the first is sent `taken-over`, then closed, and cannot type. **Decide and act is one step under the terminal's lock**: input is admitted to the terminal's queue under the lock that decides the holder.

**C. The hidden-page policy.** `terminal.Limits` states `channel_ring_bytes` (8 MiB), `channel_high_bytes` (1 MiB), `channel_low_bytes` (256 KiB), `channel_stall_ms` (2,000), `channel_inflight_bytes` (1 MiB), `channel_frame_bytes` (64 KiB), `channel_max_input_bytes` (1 MiB); the manager's copies are fields a test sets. The pump reads into the ring whatever the page does; the ring overwrites its oldest bytes and counts them (`overwritten`). Each stream has one sender that reads the ring in frames of at most 64 KiB and calls the blocking `Send`; on return it advances `sent` and `progressAt`; if the ring overwrote what it had not sent it emits `gap{from,to}`. The pump waits only while the holder is alive (progress within the stall, on the manager's injected `clock`) and more than the high mark is unsent, until the low mark; with no progress for the stall, or no holder, it does not wait. `ack` frames cap the in-flight bytes once a page has acknowledged. The legacy credit (`flow.go`, the watchdog, `DeliveryReporter`) is untouched and unused for channel terminals.

### Decisions

1. **While detached the reader is not held for a channel terminal.** The brief says both "detaches the terminal (T2's lease: reader held ...)" and "no holder: the pump does NOT wait". The second is Main's decision for the hidden page and wins: a detached channel terminal keeps running into the ring (bounded, counted overwrite) and the lease keeps its meaning.
2. **A new channel terminal is on its lease from the moment it is made**; the first stream ends it. A page that dies before it opens the stream leaves no shell.
3. **The end of a channel terminal that ended by itself is kept** (the events lane's tombstone, shared limit of 16, freed at the lease), reached only by the capability; a terminal the host closed leaves nothing.
4. **`ready` carries the session** (without the capability) and `lease_ms`; there is **no `lease` frame** (no lease runs while a stream holds the terminal, and nobody is there to tell when it ends).
5. **A channel terminal uses no window at all**: not admitted to the realm, not released by a retirement, and a create from no window is allowed.
6. **An id is held in every lane** (M4 of the review of 6052c031). A channel terminal has no record in the index of the events lane, so the check for an id in use did not see it. Every lane now decides under the one lock of the controller from the one predicate (`idHeldLocked`): the index has a record of the id, a channel terminal is being made with it (`channelMaking`, from the check to the manager's own hold), or the manager holds a terminal with it (`Manager.HoldsID`). A create that names the id of a channel terminal is refused `ALREADY_EXISTS` whatever lane it comes from: `CreateSession` is refused before it asks a plugin, and again when the plugin answers (the plugin's session is closed with its plugin); and a plugin's frames under that id are dropped as those under the id of a terminal of a window are (finding A of the second review: `heldByAnother` takes `channelHeld`, asked under the lock the record is read under). The id is a label, never a capability.
7. **Input that finds the queue full waits** (M1). A write that blocks in the kernel (a program that does not read its terminal) keeps its bytes in the queue's count, and the input of the stream that holds the terminal is never dropped: it waits for room and the stream's right to type is looked at again at every change (a stream that lost the terminal is refused). While an input waits the stream's later frames, acknowledgements included, wait with it: a page that has typed more than the shell reads sees its acknowledgements held up until the shell has read. This is stated in the protocol document.
8. **A page that acknowledges holds a window, and the output is cut to its credit** (M2, M3). The host counts the bytes of a frame from the moment it hands the frame to the transport (an acknowledgement can come before the Send returns, and is kept), the first acknowledgement (of nothing, if the page likes) turns the window on, and a frame is cut to the credit that is left, so a page that acknowledges when it holds a whole window is always given one.

### 2d. The real route (`backend/pkg/plugin/exec/streamroute`, `-tags server`)

`TestTheRealRouteOfTheTerminalChannel`: a Wails application in server mode on a free loopback port, the host's own controller (and so its terminal manager) behind `app.HandleStream("terminal", TerminalStreamHandler(controller))` as `main.go` registers it, and a `coder/websocket` client that speaks the frames of the protocol document to `/wails/stream/ws?name=terminal` (in the server build a stream is a plain WebSocket and each binary message is one frame; the frame table is written out again by hand in the test). It is a package of its own because `application.New` keeps the first application of a process in a global. Four subtests, all pass (2.3 s):

1. A capability that opens nothing (43 characters of `A`), a first frame that is not JSON and one that is not an attach each get **the one `not-found` frame, and the host closes the stream with a normal closure**.
2. The right capability gets `ready` first (`v` 1, `start` 0, `end` 0, a lease stated), and **its input comes back as output**: `hello\n` typed is `hello\r\nhello\r\n`, the terminal's echo and then `cat`'s own, on one run of offsets from 0.
3. **A stream dropped with no frame detaches the terminal** (`ListChannelTerminals` says it is not attached and has a lease), the shell goes on writing into the ring meanwhile (`NextOffset` goes past the dropped stream's offset), and **a new stream with the capability and `from_offset` resumes byte for byte**: `ready.start` is the offset, `ready.lost` is 0, no gap, and `first\r\n` then `second\r\n` are what the two streams have.
4. **A stream that never reads does not block the shell**: a shell that writes 23,986,176 bytes (366 blocks of 64 KiB, in raw mode) with nobody reading finishes in 2.2 s after the stream attached (the 2 s of the stall, and the flood), and the page that then reads is told by one gap what the ring overwrote: **9,223,177 bytes of output and one gap make the offset 23,986,185** (the bytes plus `MARK-END\n`). Wait for an event only: the application serving, a frame, the host noticing that a stream is gone, the file the shell writes when it is done, each bounded.

A measurement that mattered for this test: a pty on macOS passes about **1.4 MB/s** to the fastest reader when a program writes through the line discipline's output processing or in small pieces (9,000,026 bytes of `yes | head -c 6000000` in 6.34 s read by a Python loop, load average 8), so a first version that used `yes` took 28 s and measured the pty. The shell writes in raw mode and in blocks now.
