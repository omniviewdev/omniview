## What was built (plugin, PR #275)

- `ui/src/palette/kinds.ts`: `kindsProvider`, one `match` provider, section `Kinds` (the palette shows "Kubernetes · Kinds"), in `paletteV1 = { providers: { kinds } }`, the contribution's new `palette` member. One row for each kind of the registry that the connection serves, in the sidebar's order: `id` the kind's page id, `label` the plural the sidebar shows, `secondary` the group the sidebar puts it in (Workloads, Config, Network, Storage, Access control; **Cluster** for Nodes and Namespaces, as the mock's `group()` does for its top level), `icon` the kind's tile glyph, `route` `{ page, connection, params: {} }` (a list page takes no parameter). The array is the same one while nothing changed (the host reads it on every keystroke).
- **What a row is found by.** `keywords` = the Kind (`Pod`), `list`, then the short names (`po`). The first two are the mock's: its `connectionRows` give each kind the keywords `[type.kind, type.plural, 'list']` (shell-kubernetes.js:622; the plural is the title here). **The short names: the mock has none, and the plugin's data does not carry them to the interface** (the catalog's `ResourceType` has `type`, `displayName`, dimensions and capabilities, no `shortNames`; the Go side drops `APIResource.ShortNames` at `pkg/plugin/resource/native_catalog.go:156`). So `ui/src/palette/shortNames.ts` holds them (21 of the 29 kinds have one), and `shortNames.test.ts` compares the table, kind by kind, with the API discovery documents of a real server (`ui/src/palette/fixtures/discovery.json`: `kubectl get --raw` of the nine group versions the plugin lists, Kubernetes v1.34.0, resources only), so a kind whose short name the server says and the table lacks, or the other way round, fails. Source of each: `kubectl api-resources`' SHORTNAMES column, which is that discovery field.
- **Which kinds a connection serves**: `ui/src/palette/useKnownKinds.ts`, called by `useSidebarNodes` (the one hook the host runs for the plugin on the rail, whatever page is on screen) with the connection the pages read: once the connection is connected, it publishes the connection and the types of its catalog to `known.ts`, which `match` reads as a function. It reads the catalog as `useSidebarCounts` does (the same request: the runtime reads it once). A kind whose reads are refused (FORBIDDEN) is still in the catalog and still a row; its page says it was refused. **No connection, a connection that is not connected, or a catalog that has not answered: no row** (the mock: `if (!scope || !catalog?.types?.length) return []`). When the sidebar goes away (another plugin is on the rail) what was published stays, so the palette still goes to the plugin's lists from there.
- **Scope**: a chip of kind `scope` (the palette narrowed to a connection) names the connection; with none, it is the connection the sidebar is for. For a connection other than the known one the catalog is not known and every kind is a row. **Namespace scope: there is no namespace menu yet** (the lists and the sidebar read every namespace, `sidebar/scope.ts`) and a list page's route takes no parameter, so a row carries none. When a namespace menu exists the route needs a way to carry it (a contract question, below).
- `README.md`: one paragraph. No Go, no kit change.

## Decisions and findings for the lead

1. **Two lists of the same pages.** The host's own "Go to" already lists every page of a plugin's sidebar ("Kubernetes · Config" rows: C1b's `pagesOf`), so with this provider `pod` shows PodDisruptionBudgets and HorizontalPodAutoscalers twice (Go to, then Kubernetes · Kinds), and Pods itself is the tab on screen, a Go to row and a Kinds row. The mock has ONE: its kinds are rows of Go to ("Pods · prod-eu · Workloads"). What this provider adds over Go to: the short names, and the connection in the route. If the lead wants one list, the host's pages provider should leave out the pages a plugin's `match` provider says again (by route), or the plugin's rows should be the only kinds (the host drops the plugin's sidebar leaves from Go to). **Not decided here.**
2. **Plain Enter after `pod` does not open the Kinds row.** The model's order is Tabs, Go to, ..., the plugins' sections; the first row is the Pods tab or the host's own Go to Pods. The Kinds row is reached with the arrow keys (or the mouse), and the proof does that. This is the host's ranking, untouched.
3. **A short name of two letters does not rank its kind first.** Typed in the real host, against "Kubernetes · Kinds": `po`, `deploy`, `svc`, `cm`, `pvc`, `netpol`, `quota`, `limits`, `hpa`, `ing`, `pdb` give their kind first; `ns` gives DaemonSets, EndpointSlices, Namespaces; `sts` DaemonSets, ReplicaSets, StatefulSets; `ds` Pods, PodDisruptionBudgets, DaemonSets; `sa` StatefulSets, ServiceAccounts; `sc` HorizontalPodAutoscalers, IngressClasses, Secrets, StorageClasses (the kind is always in the section, and not always first). The cause is in the model's matcher (`core/palette/match.ts`): a TITLE may match loosely (its letters in order inside one word), and that outweighs a whole-word match in the keywords (weight 3 against the title's 6). It is the host's ranking, which this step does not change; if kubectl's short names should win, the model could score a whole keyword match above a loose title one. `/Users/joshuapare/Notes/omniview/ui-migration/status/C1d-assets/palette-aliases.mjs` prints the order for sixteen short names.
4. **The connection is the sidebar's.** There is no connection menu (tier C): "the current connection" is the one the plugin's pages read (the route's, else the plugin's first). A second connection, opened by its address (`#/kubernetes/deployments?connection=<id>`), makes the rows open that one (proved, below).
5. **Enter on a Kinds row opens a tab beside** (a list page's face has no identity, so the tab model's smart open creates a tab); Alt Enter would put it in the tab on screen. The host's rule, as C1c describes it.
6. **A row's `secondary` is the group only.** The mock adds the connection when the palette searches several ("prod-eu · Workloads"); this provider knows one connection, so it does not.
7. **Admission**: the plugin's rows pass the host's row admission (lengths, glyph, route to a list page with no parameters): the unit test holds the plugin to the same limits, and no `[palette]` problem report reached the console of either engine while `pod`, `svc`, `ns`, `zzz` and the empty query were typed on the real host.
