## 2. The design, and why it is the smallest sound one

**Done: one build of each kind for each shard, made by whichever process of the shard asks first.** No new job, no artefact, nothing restored from a cache: the directory is under `$RUNNER_TEMP` of the shard's own job, so a build cannot outlive a job, and it is named by a key anyway (section 3.2), so that it could not be stale if it ever did. The code is `probe-builds.mjs` (key and lines, 108 lines), `build-cache.mjs` (the helper the five call sites share, 80 lines), and 69 changed lines of the engine; each call site went from 8 to 10 lines of its own stamp logic to one `sharedBuild` call. The first process of a shard to need a kind pays its build in its own seconds, so which unit pays depends on the packing; the margin of a unit (a quarter, or 60 s) is larger than the longest build (about 19 s).

**Not done: a build job (or the plan job) that builds every kind once per run and uploads it.** The artefacts are small (1.5 to 3.6 MB each), so the upload is not the cost; the cost is a job. Counting from main's logs: every shard spends 23 to 35 s on `task packages` (370 s a run), 10 to 15 s on the ui-next build in 9 shards (102 s) and, after this change, one build of each kind it uses (7.3 s for the shell fixtures on the runner, 35 builds and 259 s in a run); a build job would do all three once and the shards would download instead. It would cost a job of its own (container start 24 to 55 s, checkout, install, the builds, the upload: about 150 to 190 s of runner time) and put it before every shard (about +2 to 3 minutes on the critical path, which the queue hides, but the queue is what the lead is paying for). Net about 470 s a run: the 381 + 109 s of `task packages` and the ui-next build and the 259 s of fixture builds that remain, 749 s, less a job of about 190 s and 15 downloads of about 6 s. That is a second mechanism (artefact names, a download in every shard, a path that must match) for a gain smaller than the one this change makes, and the in-shard sharing already removed the part that scales with the 219 controls. Left as a follow-up with its numbers.

## 3. Soundness

### 3.1 Rule 1: where each control plants its fault (the data)

Four readers read the code of all 219 controls (probe by probe: `N27/controls-classification.tsv`, one row each, with the line where the perturbation is applied and what it is) and wrote how `ASSERTION_OFF` is taken out for each probe (`N27/assertion-off.md`); I read a sample of the odd ones myself (`strip` `slot-width` is `addStyleTag`, `slot-undeclared` a query the clean fixture reads, `tour` `slot-wide` an `addStyleTag`; `late-list`, `slow-open`, `idle-timer`). **217 controls perturb the page** (an injected stylesheet, a script run in the page or before it, an input the probe sends, a query the clean build's own fixture reads) **and 2 perturb what the probe reads** (`copy-no-source`, `clear-miscount`: a number edited in the probe's own process before the check); **none plants its fault in the source or at build time, none writes to or reads from the build directory** (no probe writes a file but its report, pictures and the stamp that this change removes), and **no source under `ui-next/` or the packages reads `NEGATIVE_CONTROL`** (a test scans for the variables the build reads). So every unit of controls says `plants: 'page'`. `check` makes the answer mandatory (a unit of controls without it, with another word, or a unit that is not of controls with one fails, naming the unit), refuses a unit that sets `BUILD_CACHE`, `FIXTURE_DIST` or `FIXTURE_DIST_DEV` (the runner sets the first and no unit names a build of its own), and refuses a unit that says `'build'` and sets `DIST`. No unit says it today: a control that does must split into its own unit and give its fault to the build in a variable of its own, because the build is blind to the control (3.2).

### 3.2 Rule 2: the key, and what a stale build would need

The directory is `<runner temp>/probe-builds/<first 16 hex digits of the key>`, the key a SHA-256 of: every file of the repository except `node_modules`, `.git` and the root's own `dist` (the lockfile among them; a package's `dist` IS in, because the fixtures import the built kit), node's version, platform and architecture, and every variable of the build (`OMNIVIEW_*`, `WAILS_*`, `VITE_*`, `VITEST*`, `NODE_ENV`, `NODE_OPTIONS`, `BABEL_ENV`, `BROWSERSLIST*`). `FONT_DELAY_MS` is not in it because it is not baked in: the static server reads it when a font is asked for, and a test scans the whole tree for a build source that reads it. Another test scans every source a build reads (`vite.config.ts`, the Vite plugin, the packages, `ui-next/` without its probes) for `process.env.X` and fails, naming X, when X is not a variable the key carries (ten today, all `OMNIVIEW_*`, `WAILS_*`, `VITE_*` and `VITEST`). The key is computed once per shard, from the shard's environment, before the first unit runs (0.1 to 0.5 s for 5,100 files, 73 MB). **The control cannot reach a build**: `NEGATIVE_CONTROL` and `ASSERTION_OFF` are taken out of the environment `sharedBuild` hands the build function, and a test reads the five call sites and fails for `...process.env` in any of them or a `mkdtempSync` of their own (mutants killed in all five).

## 6. Risk: what a wrong key would let through, and what guards it

A key that left out an input would let a probe or control read a build made from something else: **a probe would prove a property of an old or different page** (a regression in the kit passes), and **a control would be run against a different page than the probe's** (it can turn inert, or be detected for the wrong reason). What guards it: nothing is restored across jobs or commits (the directory is under the job's own temp), so staleness needs the tree to change inside a job, which no probe does (none writes a file in the tree); the key hashes every file and every variable the build reads, each of which has a mutant; a test fails when a build starts to read a variable the key does not carry; the control cannot reach a build, so a shared build is the same for every control; the seven builds are byte-identical whoever asks; a build is published whole by a rename (a failed or killed build is never read; two builders keep the first's); and an inert control is red in every ordinary run, because a control that is not detected exits 1 and fails its shard, which `Kit probes` requires. What a run does NOT check is rule 28's second half (the assertion removed, not detected): that is what the both-ways run of 3.3 is for, and it is a scratch tool, not a step of the workflow.
