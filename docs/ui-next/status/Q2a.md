# Status: Q2a (the sidebar's count slot and its open groups: the host half of step Q2, sidebar counts for the Kubernetes plugin)

- Agent: SidebarCounts
- Goal: the Kubernetes plugin's sidebar draws a count on each entry (`exact` as the number, `estimate` as `~` and the number, nothing for `unknown`, loading or a refused kind) and asks for the counts of the entries that are on screen only. Two things stood in the way in the host and are not the plugin's to change (Main's ruling: option A, the agent owns this host PR): `ShellTreeNode.count` was `number` (`registration.ts:15`, `admit.ts:56`, `Tree.tsx` printed `{count}`: no `~`, no grouping, no held slot, so a label gave way when a count arrived), and the plugin could not see which groups of its tree were open (the tree keeps them in `useState`; `NodesSource` passed `useNodes` only `{ plugin, route, panel }`). This PR adds both, as ADDITIVE minors of `contributionV1`. The plugin half (Q2) and the host pin follow (below).

The design reached, tests first:
   - `ui/src/sidebar/count.ts`: `Count` to the node's count: `exact` a number, `estimate` `{ value, approximate: true }`, `unknown`, absent, a value that is not a canonical decimal or beyond the safe integers: `null`.
   - The skeleton (`kinds/index.ts` `sidebarNodes()`) declares `count: null` on every kind (the slot is held from the first frame; the golden in `index.test.ts` and `entry.test.ts` changes deliberately); `contributionV1.sidebar.useNodes` is added (`entry.test.ts` pins its absence today).
   - Reads: `useResolvedResourceTarget({ pluginID, route, type, scope, enabled })` then `useResources({ pluginID, request: { targetId, request: { target, pageSize: 1 } }, collection: false })`, `resources.data.sourcePage.count`; a 403 is `parseAppError(error).code === 'FORBIDDEN'` (or status 403): no count, the row stays usable. The rules of hooks forbid a hook per kind in a loop and the runtime has no batched count hook (Backend catalog), so a pool of four slots (the backend's `CountConcurrency`), written out as four calls, is driven by a framework-free store (`store.ts`: wanted kinds in row order, due when absent or older than 60 s, at most four in flight, settle frees a slot and takes the next, a kind no longer wanted is dropped and its read cancelled); a 60 s timer re-plans (the backend keeps an answer 30 s, so no request is repeated inside it).
   - Wanted = the kinds of `CLUSTER` (always on screen) and of the groups in `context.open`; none while the connection is not `connected` (a read never connects, plan D4); only kinds the catalog serves; a namespace scope (`scope.ts`: all, or `oneOf`) as one constraint, for namespaced kinds only (`queryDimensions` has `namespace`); several namespaces are `unknown` from the backend and so draw nothing. There is no namespace menu yet, so the sidebar's scope is all namespaces, the same the lists read.
   - The open list: `useKindPage` publishes its count (`complete` ? exact `rows.length` : the first page's `sourcePage.count`) to a small registry (`openCounts.ts`, keyed plugin, connection, type; withdrawn on unmount); a kind with a published count is not read at all (no second request) and its row follows the list live.
   - The refused list: `kinds/source.ts` `failed()` for `denied` gives `{ kind: 'failed', message }` with NO `retry` and the plugin's own sentence naming the kind and the scope ("You do not have permission to list Roles in all namespaces."; cluster-scoped: "…in this cluster."), never the runtime's `detail` (the host's text for FORBIDDEN is fixed: `The operation could not be completed.`, `parseAppError`), so no Retry and no plugin prose from the wire; other kinds are untouched.
   - Cost test with a fake runtime (29 kinds, every group open: exactly 29 count reads, never more than four at once, then 0 for 30 s; collapsing a group cancels its reads; opening one reads only its kinds; the open kind is not read).
