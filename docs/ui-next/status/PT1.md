## 3. Decisions (what is the source of truth for each tool)

1. **Problems is a list of conditions fed by four sources, all of them producers that exist today**: the window's plugin entries (failed, not "starting again"), the connection store (a start that failed, by class; `disconnected` is a normal state and is never a problem, S94), the plugin ALERTS of the activity service (`firing`, and `unknown` shown as **Not confirmed**: the host does not know, and a list of what is true now must not hide what may be), and the activity observation itself: while the runtime's provider says it cannot observe the service there is one warning, `Activity isn't available` (without it a failed observation would look like a quiet system). A condition is not a notice, has no unread state and is never a toast. The model is `ui-next/shell/panel/problems/model.ts`; the adapters are in `ui-next/plugins/host/conditions.ts`.
2. **The alerts bridge is small and is built here**: the host side needs only the records the provider already holds. The window's leaf `ActivityTap` (inside `ActivityProvider`) hands them to a feed, and the two models read the feed. No second subscription to the activity service is made (each one is a producer lease), and the host is not re-rendered by a progress tick.
3. **Operations is the activity service's tasks** (`kind: 'task'`), through the same feed. Cancel is drawn only for `cancellation: 'available'`, and then calls the host's `RequestCancellation`; `requested` says "Canceling..."; the dot on the tab follows `visibility.read` and a record is read when the tool has shown it for a second (the notification centre's rule, S81).
4. **Singleton tools in the panel model**: no change to `core/panel`. The host registers the two tools as tools of the host (`registerTool`, orders 30 and 40) and the bindings say which tool draws without sessions (`renderTool`) and what each tab carries (`badges`). A singleton has no session strip and no `+`.
5. **Row activation goes to the row's subject** and is also a button in the row (rows are not Tab stops): a plugin goes to its own page (the page that says what happened, with the Retry), a connection is chosen the way Home and the picker choose one (`connections.actions.go`: it starts the connection first), an alert goes to its connection when it names one, else to its plugin. A subject that cannot be opened (the plugin stopped or was uninstalled while its record remains, the connection did not start) says why in a notice (`Couldn't open <name>` with the host's own sentence): a row is never a control that does nothing.
6. **Columns that need a fact no producer states are not drawn**: Since (Problems) and Duration (Operations), Target of an operation that names no connection says "—" with the reason. Each is a catalogued gap.

## 5. Backend catalog (AGENTS rule 22)

1. **TANGENTIAL, WIRE to fix: a task has no finish time.** `sdk.Record` has `createdAt`, `updatedAt`, `observedAt` and no `finishedAt` (`plugin-sdk@v0.22.1/pkg/activity/activity.go:55-68`), and `updatedAt` moves with every commit, `SetPresentation` (the read flag) included (`backend/pkg/activity/service.go:242-250`, `observations.go:181`). So a finished task's duration is not derivable. The record is decoded with `DisallowUnknownFields` (`service.go:514`), so a new field is a wire change. Interim: no Duration column.
2. **TANGENTIAL, WIRE: no producer says when a plugin or connection condition began.** `plugin/unloaded` carries the plugin and the cause only (`backend/pkg/plugin/events.go`), `PluginInfo` has no failure time (`backend/pkg/plugin/types/plugin_record.go:30-45`), `connection/status` carries nothing. An alert's `observedAt` is the last observation, `createdAt` the first ever (a record that fires again keeps both meanings stale). Interim: no Since column; a window that begins listening after the failure cannot tell.
3. **TANGENTIAL (plugin): the Kubernetes plugin posts no alert for `kubernetes.unavailable_api_groups`.** `git grep UpsertAlert origin/feature/ui-next` finds none; the fact is a connection metadata string (`pkg/plugin/resource/native_catalog_heal.go:137`). The host is plugin-agnostic and cannot read a plugin's fact key, so the producer states the condition by posting an alert keyed by connection and group set through `Activities().UpsertAlert` and resolving it when the heal loop clears the fact (SDK0 N1). Until then the condition does not reach Problems. The bridge from alerts to Problems is built here and proven with the fixture plugin.
4. **TANGENTIAL (host): a lost producer's alert stays `unknown` for ever.** `retire` turns a firing alert `unknown` (`observations.go:274-300`); `eligible` prunes only a resolved alert (`service.go:139-141`) and `admitRecordLocked` counts every alert that is not resolved against the producer's 128 (`service.go:560-592`). A plugin that crashes with alerts and, after it recovers, reports under other keys keeps the old ones as "Not confirmed" until they are resolved by their key. [INFERENCE: not run; the fixture proves the `unknown` state, not the limit.]
5. **TANGENTIAL: no task the new UI can see is cancellable.** A reporter's tasks begin with `cancel == nil`, so their `cancellation` is `unsupported` for good (`observations.go:352`); only a task the host starts for a resource action carries a cancel (`backend/pkg/plugin/activities.go:49`), and the new UI starts no resource action yet (the B-34 family). The Cancel button is built and tested against records and a fake feed; it was not exercised against a real producer.
6. **TANGENTIAL: `navigate-resource` is an old-shell address.** A record's resource source is `ResourceNavigationIntent{pluginID, targetId, route, reference, representation}` and the new tab model's routes are `{plugin, contribution, params}`; nothing maps one to the other, so a row goes to its plugin or its connection.
7. **NOTE: the runtime's provider polls.** `ActivityProvider` renews its producer lease with a 10 s interval (`packages/omniviewdev-runtime/src/activity/ActivityProvider.tsx:70`). It is the provider's, existed before this step and is not on the data path of the tools, which read the records it holds.
8. **TANGENTIAL (host), proposed event: a connection start that fails by error is told to no one but its caller.** `StartConnection` in `backend/pkg/plugin/resource/controller.go` returns the provider's error at `:571-575` (and the borrowable-start refusals at `:562-564` and `:576-578`) without emitting anything; the one emit of the start is `c.emitter.Emit(EventConnectionStatus, ...)` at `:607` and runs only when the provider answered with a status. `ConnectionStatusPayload` (`:48-53`) is `{pluginID, connectionID, status, name}`: no reason and no class. A window that did not make the start (a second window, or a start the host makes itself) never hears that it failed; seam scenario `v` saw a start made by the harness's own call never reach the page, and `GetAllConnectionStates` then answers FAILED, found only by asking [the answer's shape is the seam sub-agent's reading; the lines above are mine, read on `e70aa2ce`]. Proposed: emit `connection/status` with `status: "failed"` (or the class the error maps to: unreachable, unauthorized, forbidden) and one sanitized sentence as the reason, from the error branch before it returns, so every window's connection store, and Problems with it, learns of the failure by event (B-07: a raw `%v` of the error leaks through `ConnectionStatus.Details`; the reason must be the safe sentence). Interim: Problems lists the states the window reads and the start the window made itself; seam scenario `v` starts the connection from the page (its two refused 422s are the scenario's `RUNTIME_ALLOW` entry).
9. **TANGENTIAL (runtime): the provider's `error` is wider than a failed observation and is never cleared.** `useActivities().error` also carries `notify` and `openDetails` failures and `activity/observation-error` events (a host action whose updates could not be recorded), and the provider never clears it (`packages/omniviewdev-runtime/src/activity/ActivityProvider.tsx:219`; read by the host-wiring sub-agent, not by me). Today only a failed subscribe or heartbeat reaches it from the new UI, so Problems shows `Activity isn't available` for those; an observation-error event would keep the row for the page's life. A runtime step should separate the observation's state from per-call failures and clear it on recovery.
10. **NOTE (host wiring outside this step): discarded `ActionResult`s.** Home's `go` (`PluginHost.tsx` ~877, `homePage.tsx:26`) and `switchTab` (`PluginHost.tsx:827`) drop the result a refusal comes back in; this step handles it for its own rows only.
