## 1. What was wrong

`main.go` creates the main window with `app.Window.NewWithOptions`, in the server build too, and the window service creates every other window the same way. Wails runs a window that is created that way when the application runs (`App.Run` runs `pendingRun`), in the server build as well, and from then on `EventIPCTransport.DispatchWailsEvent` gives it the JavaScript of every event: one `fmt.Sprintf` string per event, queued for the window (`WebviewWindow.DispatchWailsEvent`, `enqueueEventJS`).

Nothing takes those strings out in the server build. The pages are in browsers, which read the events from the socket, and the window has no page of its own. The queue has a bound for goroutine emitters, but `serverApp.isOnMainThread()` is `true` in server mode ("there's no main thread concept") and `enqueueEventJS` never blocks a main-thread emitter, so the bound never engages. I did not trace which of the queue, the batch being run or the native side holds the strings; the heap profile and the measurement below show that a window that runs keeps them, and that one that does not run keeps nothing.

## 2. The change

1. **The server build does not run the windows the host creates** (`webview_window_server.go`). `NewWebviewWindow` creates the window with `application.NewWindow` and registers it with `app.Window.Add`; it never calls `Run`. A window that has not run takes no event (`DispatchWailsEvent` returns at once when it has no platform window), and the registry still answers for it: `getTargetWindow` gives a call with no client id the first window of the registry (the e2e fixture and the seam rely on it), the window service keeps its entry, `GetByName` finds it.
2. **`Activate` does nothing in the server build** (`wails.go`, `runsNativeWindows`): `Show` runs a window that has not run, which would start the queue again for the window service's `Focus` and `OpenSettings`.
3. **One place creates a window** (`webview_window_native.go`, `webview_window_server.go`): `main.go` and the window service call `NewWebviewWindow`. The native one is `app.Window.NewWithOptions(options)`, the same call as before. `TestEveryWebviewWindowIsCreatedThroughTheFactory` reads every Go file of the repository (not `_test.go`) and fails for a call of `Window.New`, `Window.NewWithOptions` or `application.NewWindow` outside the two factory files, so a new window cannot bring the queue back.

## 4. Not verified, and limits

- **The window never reports "runtime ready" in the server build.** `main.go` calls `runtimeReady()` (the development-control lifecycle's `markRuntimeReady`, which publishes `host-ready`) from the main window's `WindowRuntimeReady`, an event of a native page. A window that does not run has none. The development-control readiness in a server build therefore stays at its earlier value; the e2e fixtures accept `backend-ready` or `host-ready` (`e2e/scripts/application.mjs:47`, `e2e/tests/fixtures/workspace.ts:44`). I did not run a development-profile server instance before and after to see what it published; CI's e2e-application job is the check.
- A registry-only window reports `IsVisible() == false` and empty `Bounds()`, so the window service lists the main window of a server build as not visible. Not run against the UI; the pages of a server build do not use native windows.
- **A client that stops reading still grows the host.** Wails' per-client mailbox in the server build is unbounded (the 11.4 GiB of the T1-go review, two clients, one stalled). This change removes the cost of the window, not that one; it is Wails' queue or a limit in the host, and a separate row.
- Not run on Linux or Windows native builds; Windows vet only. The seam and e2e jobs run the server build on Linux.
- The retention test measures live heap, the end-to-end run RSS. The test's bound (16 MiB) is a third of the events' size (47 MiB); the old behaviour grew 141 MiB.
