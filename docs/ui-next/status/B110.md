## 1. What was wrong

`main.go` creates the main window with `app.Window.NewWithOptions`, in the server build too, and the window service creates every other window the same way. Wails runs a window that is created that way when the application runs (`App.Run` runs `pendingRun`), in the server build as well, and from then on `EventIPCTransport.DispatchWailsEvent` gives it the JavaScript of every event: one `fmt.Sprintf` string per event, queued for the window (`WebviewWindow.DispatchWailsEvent`, `enqueueEventJS`).

Nothing takes those strings out in the server build. The pages are in browsers, which read the events from the socket, and the window has no page of its own. The queue has a bound for goroutine emitters, but `serverApp.isOnMainThread()` is `true` in server mode ("there's no main thread concept") and `enqueueEventJS` never blocks a main-thread emitter, so the bound never engages. I did not trace which of the queue, the batch being run or the native side holds the strings; the heap profile and the measurement below show that a window that runs keeps them, and that one that does not run keeps nothing.

## 2. The change

1. **The server build does not run a window the host creates** (`webview_window_server.go`). `NewWebviewWindow` creates the window with `application.NewWindow` and registers it with `app.Window.Add`; it never calls `Run`. A window that has not run takes no event (`DispatchWailsEvent` returns at once when it has no platform window), and the registry still answers for it: `getTargetWindow` gives a call with no client id the first window of the registry, and a call that names a window (the e2e fixtures send the name of the settings window with every call, `bindWindowContext`) finds it by name.
2. **The windows of the window service are `registryWindow`s in the server build** (`createWindow`'s guard). Each is in Wails' registry, never run. `Activate`, `Hide` and `SetPosition` do nothing, `IsVisible` is false, `Bounds` is empty, and `Close` does what the closing hooks of `createWindow` do for a window that exists: the settings window hides (`windowVisibilityChanged(false)`) unless the host is shutting down, any other window is taken out of the registry and reported closed (`windowClosed`), on the caller's goroutine like the service's own fake. `Activate` of the main window does nothing either (`Show` runs a window that has not run).
3. **One place creates a window** (`webview_window_native.go`, `webview_window_server.go`): `main.go` calls `NewWebviewWindow`; the native one is `app.Window.NewWithOptions(options)`, the call that was there. `TestEveryWebviewWindowIsCreatedThroughTheFactory` reads every Go file of the repository (not `_test.go`) and fails for a call of `Window.New`, `Window.NewWithOptions` or `application.NewWindow` outside the two factory files, so a new window cannot bring the queue back.

**What the first two versions got wrong.** (a) The first registered the service's windows without running them and left `Close` to Wails; the independent review of #691 found that Wails' `Close` returns at once for a window that has no platform window, so `Service.Close` succeeded and the service kept the entry and the saved state of a window that was gone. Emitting the closing event through Wails to repair it is not possible: `NewWindow` registers a closing listener that calls `impl.close` on a nil `impl`, which is fatal (the process dies; seen in a `-race` run). (b) The second made those windows headless (no Wails window at all) and failed CI's `e2e-application`, `navigation.spec.ts` "header opens one retained Settings window": the page of the Settings window addresses its calls to the window by name, Wails answers "window 'settings' not found" for a name that is not in the registry, and the test only attaches the page once the service lists the window. So the final version keeps the windows in the registry and gives them their own `Close`.

## 4. Not verified, and limits

- **The e2e-application job is the check of the registry windows.** The first head (plain registry windows) passed it; the headless head failed it (section 2); the final head is the first with their own `Close`, and I did not run the e2e suite locally.
- **The main window never reports "runtime ready" in the server build.** `main.go` calls `runtimeReady()` (the development-control lifecycle's `markRuntimeReady`, which publishes `host-ready`) from the main window's `WindowRuntimeReady`, an event of a native page; a window that does not run has none. The development-control readiness in a server build therefore stays at its earlier value; the e2e fixtures accept `backend-ready` or `host-ready` (`e2e/scripts/application.mjs:47`, `e2e/tests/fixtures/workspace.ts:44`), and the independent review found no consumer in a server build that waits for `host-ready`. I did not run a development-profile server instance before and after.
- A registry-only window reports `IsVisible() == false` and empty `Bounds()`, so the window service lists the windows of a server build as not visible, and `OpenSettings` or `Focus` show nothing. The pages of a server build do not use native windows.
- **A client that stops reading still grows the host.** Wails' per-client mailbox in the server build is unbounded (the 11.4 GiB of the T1-go review, two clients, one stalled). This change removes the cost of the windows, not that one; it is Wails' queue or a limit in the host, and a separate row.
- The `Pods cluster check` job failed on the first head with "failed to listen on 127.0.0.1:34204: bind: address already in use" while starting a host (`scripts/ui-next-pods`): a port collision of the harness, unrelated to the change.
- Not run on Linux or Windows native builds; Windows vet only. The seam and e2e jobs run the server build on Linux.
- The retention test measures live heap, the end-to-end run RSS. The test's bound (16 MiB) is a third of the events' size (47 MiB); the old behaviour grew 141 MiB.
