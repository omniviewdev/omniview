## Why the old measurement came out short

The old assertion (`kit-probe.mjs`, `busy`) already read `performance.now()` in the page, not the automation protocol's wall clock: it took `loader - icon`, where both are MutationObserver records. A record is delivered when the task that made the mutation ends. React runs the passive effect that starts the timer inside that task (the parts page mounts every example in one commit), so the timer starts BEFORE the icon is seen, by the rest of the task: `loader - icon = delay - lateness`. Measured with a wrapper on `setTimeout` (same page, same clock):

| engine | timer set | icon seen | timer fired | loader seen | old `loader - icon` |
|---|---|---|---|---|---|
| WebKit | 286 | 308 | 1287 | 1288 | 980 |
| WebKit | 191 | 218 | 1192 | 1192 | 974 |
| Chromium | 123.5 | 138.7 | 1126.8 | 1127.5 | 989 |
| Chromium | 105.9 | 120.1 | 1115.2 | 1115.7 | 996 |

On a quiet machine the lateness is 14 to 27 ms; the lower bound of 900 leaves 100 ms. A runner that takes more than 100 ms to finish the commit task (897 and 898 ms in CI: 103 and 102 ms) fails a correct product. The timer itself is never early: timer set to fire was 1000 to 1009.6 ms in every sample. The earlier P1b-2 note (799 to 885 ms) and the `ExampleStage` mitigation in `LogView/ExampleStage.tsx` reasoned to the same mechanism without measuring it; the mitigation is not needed for this probe any more and was not touched (not my file).

## The fix

`busy` records, in the page and on `performance.now()`: the call of `setTimeout` made while the busy button shows its icon (a wrapper installed by `addInitScript`; it calls the native one with the same arguments), the timer's firing, and the glyph changes (MutationObserver). `judgeLoader` asserts:

- the timer that ended in the loader (the longest that fired before the loader came) was followed by the loader within `1000 - 1` to `1000 + 300` ms of being set. The lower bound is the product's second less one clock step (WebKit's `performance.now()` is whole milliseconds); it was 900 against an icon time that was late. The upper bound is unchanged (300 ms) and is the only place a late timer can show: it can only lengthen the measured delay, never shorten it;
- the timer was set no later than 300 ms after the icon was seen (a product that started its second late would otherwise pass: the timer's own delay would still be one second).

`ONLY=busy` runs the section alone (for repeated runs). The report now carries the recorded timers.
