## What was wrong

Two fixture plugins (`fixture-a-ok` "Streams", `fixture-b-dup` "Streams copy") bring a tool of the same `order` (40). The panel model sorted the tools by `order` and broke a tie by `Tool.seq`, "the order of registration", and `syncPlugins` gave a tool its `seq` the first time it saw it. The host calls `syncPlugins` on every change of the plugin store, so `seq` was the order the plugins' loads ENDED in: on the runs in which the copy finished first its tool took the first place after the host's own, and the strip read `Logs, Streams copy, Streams`. The rail, the palette and every other list were already in the rail's order; the panel was the one kind that still took its order from the moment a plugin arrived. (The old code had a third order too: when both plugins arrive in one render it took the plugin store's, the plugins' ids; the test's two plugins have ids that sort the other way round from the rail so that the three can be told apart.)

## The rule, and the one place

**A list the window makes from what several plugins contribute is in the order of the rail**: the plugins that contribute first, in the order the rail draws them (`railOf`: what they declare today, what the person arranges later), the others after them as they were listed. A plugin that finishes loading late takes the place the rail gives it; it is not appended. Nothing is ordered by when a plugin arrived, by the order the plugin store lists plugins in, or by how long a load took. Within a plugin the order is the plugin's own declaration.

- **One place: `inRailOrder(entries)` in `ui-next/plugins/host/rail.ts`** (new). `panelPluginsOf` (the panel's tools), `syncProviders` (the palette's providers) and `pagesOf` (the palette's Go to rows) take their order from it, and `railOf` itself is what it is made from, so the day the person arranges the rail it is the one function that changes.
- **The model keeps the caller's order.** `PanelStore.syncPlugins(plugins)` now keeps the ORDER of the list it is given in `PanelState.live`, and a plugin's tools tie among themselves by that place (`visibleTools`): the order is `order`, then the host's own tools, then the plugins in the order they were listed, then the order a plugin declared its own tools in (`Tool.seq`, now the position in the plugin's own list, no longer a count of registrations: `registered` counts the host's tools only). A tool of the host leads a plugin's tool of the same `order` whenever the host registered it (before, it depended on which was registered first).

**The mock's rule for panel tool order, quoted** (`aws-wails-native-lab/app/OmniviewNativeLab/frontend/mock`, tree `c8e44a44`, the pinned mock):

```
shell-regions.js:244  function visibleTools() { ... .sort((a, b) => a.order - b.order || a.seq - b.seq); }
shell-regions.js:222  registerTool: ... order: Number.isFinite(def.order) ? def.order : 100 + toolSeq, seq: toolSeq++, plugin: def.plugin || 'host'
shell-regions.js:238  declaredTools (a plugin's panelTools[], at most 2): ... order: Number.isFinite(t.order) ? t.order : 200, seq: 1000, plugin: def.id
shell-panel.js:2524-2527   the host's four tools: terminal 10, logs 20, problems 30, operations 40
shell-core.js:1078    Shell.plugins.list(): [...defs.values()].sort((a, b) => (b.id === 'host') - (a.id === 'host') || a.name.localeCompare(b.name))
```

So the mock sorts on the tool's own `order` FIRST (one number for every tool, the host's included, which is how a plugin puts a tool between two of the host's), and settles a tie by `seq`: the host's tools were registered before any plugin's, all the tools a plugin declares have the same `seq` 1000, so a tie between two plugins' tools is settled by the stable sort over `Shell.plugins.list()`: the host first, then the plugins BY NAME. The mock's rail is that same list, so in the mock the rail's order and the name order are one. **The panel follows the mock**: the tool's `order` first, then the host's tools, then the plugins in the order of the rail (the rail is the host's `rail.order`, then the plugin's name, which is the mock's name order wherever no plugin declares a place), then the plugin's own order. That is not the "plugin first, then its own order" of the general rule, and the mock decides it (the contract says the same: `PanelToolV1.order` is "where the tab sits among the tools").

## What a late plugin does to what the person is on

The open item (P1a, "a late tool with the panel open shifts the strip"): what happens, now and before.

- **The tool on screen and its session never change.** Opening the panel makes the tool on screen the person's (`arrange.ts` `show`), so a tool that arrives later and sorts before it does not take the panel; a chosen tool and its session stay, and so does the body, the same element, still counting (model test; `PluginHost.order.test.tsx` "takes its place in the panel's strip..."; seam h2 asserts it in both engines: the same body element, `aria-selected` on the same tool and session, its count not started again).
- **The tabs after the new one move right by its width; nothing else does.** Before R2 a tool that tied with the others was appended, so it moved nothing that was there (and was in the wrong place); now it takes its place, so when it sorts ahead of the person's tool that tool's tab moves right by the width of the new one. The seam's h2 measured it in Chromium at 1440 x 900: the copy's tab moved 100.6 px (the width of the "Streams" tab), the tool, the stream and the body on screen did not change. P1a measured the strip's own content at layout shift 0.008 to 0.009 for a late tool in an open panel, 0 with the panel closed. The panel probe of this run (host fixture, `late`, both engines, both viewports, report `panel-probe.json`) says the same in rectangles: closed, `layoutShift` 0 and the tab strip and drag lane of the top row move by the new page tab (`208 -> 240` px wide, as before R2); open, the tool strip grows `213.41 -> 344.3` px (the width of the new tab, 130.9 px), and the separator and the sessions strip move right by the same; the panel's body and the frame do not move.
- **The mock allows exactly this.** `Shell.on('plugin:contribution', ...)` (`shell-regions.js:943`) redraws the whole open panel when a plugin turns live, and `declaredTools` / `visibleTools` put the tool at its sorted place; nothing is held back, and the tool on screen is the window's own `panelTool`, which a new tool does not change. The host does the same, and the tool on screen is pinned where the mock has it as a state.
- The mock shows a plugin's tool only while the tab on screen is that plugin's (`visibleTools`: `t.plugin === 'host' || t.plugin === current || the tool has sessions`); the host shows every live plugin's tool (P1a's "a tool's visibility by the active tab's plugin" is still a later row). A late plugin therefore moves the strip in the host where the mock would show nothing for a plugin of another tab. Not changed here.

## Findings, not changed here

1. **The rail and the sidebar are not held when the inventory arrives after the window mounted.** `PluginHost` holds the rail and the sidebar until every plugin has settled once (`settledOnce`), but `coming` reads `entries`, and `PluginHostScreen` hands the plugins to the store in a LAYOUT effect, after the host rendered the commit in which `inventory` became `ready` with an empty store: that render has `coming` false and sets `settledOnce`. The screen draws the host once the session is read, beside the inventory, so which comes first decides it; when the inventory comes second, the window shows the rail with the plugins that are ready so far (`["Second plugin"]`, its sidebar) and then `["First plugin", "Second plugin"]` with the first plugin's sidebar when the rail's first plugin arrives: the entries and the sidebar follow the completion order for the time the plugins take. The final state is the rail's order and the probes' fixtures hand over the plugins in the same batch as the inventory (so they hold). Reproduced with the `open()` of `PluginHost.order.test.tsx` (the screen's sequence), before and after R2 alike: the rows were `loading: no rail`, `Second ready: rail ["Second plugin"], sidebar "Second navigation"`, `both ready: rail ["First plugin", "Second plugin"], sidebar "First navigation"`. The fix is small and belongs to the screen (pass `loading` to the host until the layout effect has handed over the list) or to the host (`coming` also while the inventory is not yet handed over); it is a change to when contributions are DRAWN, outside this row's defect (the final order), and it changes the commit sequence every window test and probe sees, so it is the lead's to schedule.
2. **A plugin tool with no `order` sits after every tool that has one** (`UNORDERED`); the mock gives a plugin's tool with none the number 200 and a registered tool 100 plus its registration. They differ only for a plugin tool that declares an order above 200.
3. The old tests that say "registration breaks a tie" (`store.test.ts`, the tools of the HOST) stay true: a tool of the host takes the next place when it is registered.

## Mutation check (the fix, one exact replacement at a time; `mutate.mjs`)

- `load-runs.sh` (kept in `~/Notes/omniview/ui-migration/status/R2-assets/`; the whole script is below): n runs of h and h2 per engine under at most one busy loop per core, one script, the loops its own background jobs ended by a `trap`, nothing killed by name.
- `run-units.mjs` (same folder): runs units of `scripts/ci/probe-shards.mjs` (a probe, its controls) one after the other from a clean environment (`PATH`, `HOME`, `TMPDIR`, `LANG`, `USER`, `OMNIVIEW_UI=next`, `FONT_DELAY_MS=40`, `RUNNER_TEMP`), `uptime` before each, one log a run.

```bash
#!/usr/bin/env bash
# R2: repeat the seam's panel scenarios h and h2 under CPU load, per engine.
#   load-runs.sh <runs> <busy loops> <engine>...      e.g.  load-runs.sh 20 12 webkit chromium
# At most one busy loop per core (the script refuses more). The loops are this script's own background jobs, ended by the trap on exit, interrupt and termination: nothing is killed by name.
set -u
runs=${1:?runs}; loops=${2:?busy loops}; shift 2
[ "$#" -gt 0 ] || { echo "no engine" >&2; exit 2; }
cores=$(sysctl -n hw.ncpu 2>/dev/null || nproc)
[ "$loops" -le "$cores" ] || { echo "$loops busy loops is more than the $cores cores" >&2; exit 2; }
root=$(git rev-parse --show-toplevel)
pids=()
stop() { for pid in "${pids[@]}"; do kill "$pid" 2>/dev/null; done; wait 2>/dev/null; }
trap stop EXIT
trap 'exit 130' INT
trap 'exit 143' TERM
for _ in $(seq "$loops"); do
  ( while :; do :; done ) &
  pids+=("$!")
done
echo "load at start: $(uptime | sed 's/.*load averages*: //')  ($loops busy loops, $cores cores)"
status=0
for engine in "$@"; do
  log="${TMPDIR:-/tmp}/r2-load-$engine.log"
  started=$(date +%s)
  if SEAM_PANEL_REPEAT=$runs ENGINES=$engine node "$root/ui-next/plugins/e2e/seam.check.mjs" > "$log" 2>&1; then verdict=PASS; else verdict=FAIL; status=1; fi
  echo "$engine: $verdict, $(grep -c ' ok$' "$log") of $((runs * 2)) scenario runs ok in $(( $(date +%s) - started )) s, load at end $(uptime | sed 's/.*load averages*: //')  (log $log)"
done
exit $status
```
