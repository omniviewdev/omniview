# PF2: the bounds of `ctx.panel.ports.forward` (S4 and S5 of the review of PR #710)

Step PF2 of the Ports work, before any real plugin uses the contract member. The independent review (`reviews/host-710-ports-contract.md`, S4 and S5) found that the member trusted its caller in three ways, and the lead ruled on each (2026-11-25). This file says what was built, the numbers and why, what was measured, the differences from the mock, and what is catalogued instead of built.

## 1. What was built

| Rule | Where | What it does |
|---|---|---|
| **A user action starts a forward** | `ui-next/plugins/host/portForward.ts` (the HOST side of the contract, not the plugin) | The first thing `forward()` does, before it reads the request, is read `navigator.userActivation.isActive` (an injectable dep). `true` goes on. `false` is refused `FORBIDDEN`: `A forward can only be started from a user action: a click or a key press.` An engine without the API is refused too (fail-closed: `This window cannot tell a user action from a script, so it cannot start a forward.`). `stop()` asks for no gesture. |
| **A cap on what a plugin holds** | `host/portLedger.ts` | At most **64 forwards per plugin and connection** and **128 per window** (`MAX_FORWARDS_PER_CONNECTION`, `MAX_FORWARDS_PER_WINDOW`). The count is taken synchronously at the call (a place is reserved before the host is asked), so 1,000 calls made while the host answers end at exactly the cap and the rest are refused at once, without a call to the host. Refusal: `RESOURCE_LIMIT` with the number on the error (`error.limit`, 64 or 128) and in the words (`This plugin already holds 64 forwards in this connection. Stop one first.` / `This window already holds 128 forwards. Stop one first.`). A place is given back when the start fails, when `stop()` has closed the forward, when the host says the forward is closed, and when the plugin stops (the host sends nothing for a plugin that dies: W-PF2). The ledger listens to the two feeds only while it holds a place (idle = 0 listeners). |
| **Every string is bounded** | `host/portSize.ts` | `resourceId` 1024 characters, `resourceKey` 256, each text of the reference 1024, `resourceData` 64 KiB serialised, the whole request 128 KiB, nesting 64 levels (a cycle is a refusal). The size is measured by a walk with a byte budget that stops at the first excess, so a 20 MiB body is never serialised. Refusal: `INVALID_REQUEST` naming the field and the number. A refused call never reaches `networker.start`. |
| **The tool shows what the producer states** | `ui-next/shell/panel/ports/**` | The SDK's session states `local_port` and no host. The Mapping reads `port 8081 → :8080/TCP` (`Auto → …` while unassigned). **Open in browser is disabled for every forward the producer gives no host for**, with the reason `Where this forward listens is not stated, so it cannot be opened from here.` (button, tooltip, row menu; a press asks nothing). Copy becomes **Copy port** (writes `8081`, `Port copied`). A session that DOES carry `local_host` (the SDK addition W-PF7, not yet made) turns it back on: a loopback host (`127.0.0.1`, `::1`, `localhost`) is shown, Open goes to `http://<host>:<port>` and Copy address writes `<host>:<port>`; any other host is shown and Open says `This forward listens beyond this computer, so it is not opened from here.` |
| **The contract no longer asserts a host** | `contract/v1.ts` | `PortForwardSessionV1.localHost` is optional and absent (the host answers `{ sessionId, localPort, stop() }`). `PortForwardErrorV1.limit?: number` is new. Both additive: nothing used the member yet. |
| **The Pods cluster check's ports** | `.github/workflows/ui-next-pods.yml`, `scripts/ui-next-pods/unavailable.test.mjs` | The check started its hosts on fixed ports 34201 to 34204, inside the Linux ephemeral range (32768 to 60999), and run 45538393171 died with `failed to listen on 127.0.0.1:34204: bind: address already in use` (an earlier step's outgoing connection held the port as its source port). The four ports are now 24201 to 24204 (11 lines). |

Order inside `forward`: the gesture (read synchronously at the call), the request's shape, the bounds, the cap, then the host. A refusal at any step never reaches `networker.start`.

### The numbers, and why

- **64 per connection.** A person can read 64 rows; the review measured that a plugin with `ulimit -n 256` ran out of descriptors at 242 forwards (one listener plus two descriptors per relayed connection) and then could not serve its own connections. The prior art states no number: VS Code remote forwarding, Codespaces and JetBrains document no cap (VS Code's Remote Tunnels document 10 tunnels per account, which is not forwarded ports; a VS Code issue reports about 1,000 SSH forwards degrading the window); `kubectl port-forward` is one invocation for any number of ports; `ssh -L`'s `MaxSessions` (default 10) counts shell sessions, not forwards; a browser's six connections per host are HTTP/1.x requests. So the number is Omniview's own, and one constant to change. The soft descriptor limit is 256 under launchd on macOS and commonly 1024 on Linux; Go raises it toward the hard limit since 1.19, so a Go plugin may have more, but a plugin in another language may not.
- **128 per window.** Twice a connection's: a window may have two connections full. It counts the forwards the window started through its plugins' handles. The host has no window owner (W-PF1), so another window counts its own and a reloaded page starts again from zero: the cap is what one window's life can ask for, not what the host holds.
- **1024 for an id**, 256 for a key: the SDK's own text limits (`connection_metadata.go` keys 256 bytes, error messages 1024 bytes) are the nearest precedents. **64 KiB** for a body: a body is the plugin's way to hand the forwarder what it needs; no forwarder needs more than a descriptor.
- The activation lasts **5 s** in WebKit 27.2 and Chromium 156 (measured: the page's own timer sees `isActive` flip at 5005 ms and 5027 ms after a real click). It is the window's, not the handler's: an effect that runs within 5 s of ANY user action passes. That is what transient activation proves (a person acted a moment ago), and it is what the lead decided. A plugin that awaits slow work between the click and the call can lose it. **Playwright's `page.evaluate` itself carries activation in both engines** (`isActive` is true inside it while the page's own timers say false), so a script cannot stand in for 'no gesture' in the seam: the fixture's `Forward after 6 seconds` makes the call from the page's own timer.

## 2. Decisions taken in this step (the lead may flip each)

1. **Fail-closed without `navigator.userActivation`.** The lead decided gesture-only; an engine that cannot tell cannot start a forward. WebKit 27.2 and Chromium 156 have the API. [INFERENCE] the oldest macOS WebView the app supports is not checked.
2. **A plugin that stops gives its places back** (a dep, `plugins: { running, subscribe }`), because the host emits no `closed` for a dying plugin (W-PF2); otherwise a plugin that crashed holding 64 forwards could not forward again for the window's life.
3. **The window cap's words say `This window`** (the count spans plugins); when both caps are full the connection's is reported, the one a person can act on.
4. **`limit` is set only on the cap's `RESOURCE_LIMIT`**; the bound refusals state their number in words.
5. **Open in browser is DRAWN and DISABLED on every row** until the SDK states a host (the lead: 'disable Open with words'). A column of disabled buttons is a visible cost; the alternative, not drawing Open while nothing can enable it, is smaller and says less. Awaiting the lead.
6. **Copy is Copy port** (a port is what the producer states; an address would assert a host). With a stated host it is Copy address again.
7. **`LOOPBACK` is gone** from the tool and the contract: nothing asserts `127.0.0.1` for a forward. The fixture page still says `on 127.0.0.1:<port>`: the fixture plugin KNOWS where its own forwarder listens (the contract says a plugin that needs the address has to know it of its own forwarder).

## 5. Where a forward listens: what the host could verify, per OS (decision 3 of the lead; NOT built in PF2)

The lead asked that, until the SDK states `local_host`, the host verify itself that a forward is loopback-only, or else show `port N` and disable Open with words. Verification is feasible but is not a small step, so the second was built. Researched (the host's tree and the SDK v0.22.1 sources; nothing was run on the three systems, so the per-OS costs are [INFERENCE] where marked):

- **The host knows the plugin's process**: `ExternalBackend` keeps the go-plugin client's `ReattachConfig().Pid` (`backend/pkg/plugin/types/external_backend.go:33-55`); `GetPluginProcesses()` fences the identity (`backend/pkg/plugin/processes.go:31-100`); `internal/processinfo` reports observations, not sockets. **gopsutil is not a dependency of this repository**: the collectors use `golang.org/x/sys` (`/proc` on Linux, sysctl on macOS, process handles on Windows: `internal/devsession/processes_{linux,darwin,windows}.go`). Admitting it is a dependency decision for the lead.
- **Linux**: join the links of `/proc/<pid>/fd` (`socket:[inode]`) with the rows of `/proc/<pid>/net/tcp` and `tcp6` in state LISTEN (local address and port). No cgo, no binary. Needs same-user access to the plugin's `/proc/<pid>/fd` (normal; `hidepid` or ptrace restrictions can deny it: the answer must then be `unknown`, never `loopback`).
- **macOS**: `proc_pidinfo(PROC_PIDLISTFDS)` then `proc_pidfdinfo(PROC_PIDFDSOCKETINFO)` per socket descriptor (libproc through cgo with native structures, no spawned binary), reading the TCP state and the IPv4 or IPv6 local address; the alternative is `lsof -nP -iTCP -sTCP:LISTEN -a -p <pid> -F` (an external binary, slower, parsed). Same-user inspection needs no privilege; a sandboxed host cannot do it.
- **Windows**: `GetExtendedTcpTable` twice (AF_INET and AF_INET6) with `TCP_TABLE_OWNER_PID_LISTENER`, filter the owner pid, decode the local address (`golang.org/x/sys/windows` is a dependency; the table structures need a small wrapper; no cgo, no elevation).
- **Recommendation**: one on-demand method, `VerifyPortForwardListener(ctx, sessionID) (ListenerVerification, error)` on the networker service (`backend/pkg/plugin/networker/`, delegated through the existing `ServiceWrapper`), result `{ sessionId, observedAt, status: 'loopback_only' | 'non_loopback' | 'unknown', addresses: string[], reason }`, the process identity fenced before and after the observation; a wildcard or non-loopback listener means `non_loopback`; no listener found, no permission, UDP, or a shared or delegated process mean `unknown`. It is three platform files with native structures, three CI systems to prove them on, and a Wails binding with its generated client. An observation cannot prove that the socket is THE session's (the plugin may hold other listeners on the port family) nor that it stays loopback later: it is evidence, not a guarantee, which is why the SDK stating it (W-PF7) is the better source and the verification a belt for plugins whose SDK does not.

## 7. Not verified

- Four tool tests (three of the body, one of the menu) were written after the code, not seen red: they assert strings that did not exist before.
