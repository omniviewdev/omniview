## 1c. How a window's KIND selects what the frontend draws (read, with file:line)

- **The old UI** decides per window before it draws: `ui/main.tsx:38-45` awaits `resolveCurrentWindow()` (`ui/features/windows`: the runtime's `Window.Name()` and the window service's `List()`) and draws the shell of that window's kind; kind `settings` draws `SettingsWindowShell` (`ui/features/windows/SettingsWindowShell.tsx:15-90`: the old Settings page in a router, `GetSettingsState()` and the `settings/state` event, `HideSettings()`, Cmd/Ctrl+W, `content-visibility: hidden` while hidden).
- **The host** makes every native window with `options.Name = spec.Name` and `options.URL = "/#/"` (`backend/window/wails.go:60-64`: "The frontend asks Wails for its window name; a URL query would be lost when the window reloads"), so the URL cannot carry the kind and the name is the identity. For kind settings it sets the title, no frame (macOS: a hidden title bar and hidden window buttons, `wails.go:70-81`), a minimum of 960 x 600 (`:82-84`), and cancels the close into a hide (`:97-103`). `OpenSettings` (`backend/window/settings.go:12-58`) registers the entry of kind `settings` BEFORE it creates the native window (1060 x 640, centred on the work area) and focuses an open one (`native.Activate()`): one instance.
- **The new UI before this turn** had NO branch: `ui-next/main.tsx` drew `PluginHostScreen` in every window, so the native Settings window would have drawn the whole shell (a second main window).
- **The decision:** the same identity as the old UI and as the new UI's own session (`ui-next/shell/session/window.ts`, `resolveWindowName`): `Window.Name()` and the service's `List()` give the kind (`windowKind.ts`). A browser has no native window, so it draws the shell at once with no wait (`isNativeWindow()` is false: `WindowKindScreen`); a native window draws nothing until the host has answered (the shell's own first frame waits for the same service about its session, so no wait is added that the shell was not in). Any failure draws the shell (a window a person can leave). **No Go change was needed**: the kind is already registered and the title, the frame, the size and the one instance are the host's.

What is proven: the content and the branch in engines on the real host (`?screen=settings-window` stands in for the window: the same component, the host's window service and events); the kind resolution with fakes (`windowKind.test.ts`, `WindowKindScreen.test.tsx`); the window's follow of the host's requests (`window.test.tsx`: 7 tests, subscribe-before-read, show refetches, a key already used is not taken); the Go side's one instance, hide-not-destroy and requests (`GOWORK=off GOTOOLCHAIN=local go test ./backend/window/... -run Settings -race`: ok). What only a native run shows: the window's chrome (title, no traffic lights on a Mac, the draggable caption moving it), 1060 x 640 centred, Cmd+, (AppKit's accelerator: JavaScript never sees it), and the focus of the open window.

**The manual check (5 steps):**
1. Build and launch the desktop app with the new UI on the feature channel (`OMNIVIEW_UI=next`; `task dev` with it is not verified, AGENTS.md "Not verified").
2. Press Cmd+, (or Omniview > Settings..., the gear in the top row, or the palette's "Settings"): ONE window opens, 1060 x 640, centred, titled Settings, with a caption (title, Close at the right) and the pages and a page, and NO rail, tabs, panel or status bar; the main window behind still responds to clicks (the window is not modal) and no sheet opens in it.
3. Press Cmd+, again and click the gear of the main window: the same window comes forward; there is never a second one.
4. In Settings pick Terminal and flip Cursor Blink; open Developer Settings, type 70000 in Host profiling port and press Enter: the host's words ("Enter a whole-number port from 0 to 65535.") show in the row and the typed text stays; quit and relaunch: Cursor Blink is as it was left.
5. Press Escape, reopen (Cmd+,), press Cmd+W, reopen, press the Close: each hides the window and the app keeps running; the reopened window shows the same page at once; drag the caption: the window moves, and the Close still closes.

**Two-window truth.** Proven in server mode on the real host: a change in the window page reaches the sheet of the main page, and the reverse, through the host's `settings/changed` event, in 22 to 31 ms (WebKit and Chromium; the seam scenario `s` asserts it). Natively the main window's new shell reads no setting yet (its theme, density and text size take props, decision 5), so a change made in the window has nothing in the main window to reach until the Appearance step; the mechanism is the same events.

**Realm slots (64 live windows).** The native Settings window is made once and recycled: `OpenSettings` reuses `entry.native` (`settings.go:46-58`) and a close is cancelled into a hide (`wails.go:97-103`), so opening and closing it any number of times takes ONE slot for the life of the app and never another. In server mode a page of the window's screen is a browser window of the realm, retired about 3.4 s after it closes (INV2); the seam scenario `s` opens and closes one 100 times.

**Popups inside the sheet (checked in WebKit and Chromium on the real host).** The tooltip of Reset (the kit's popover) is shown (`:popover-open`) above the open dialog and is not inert; the kit `Select` is a native select, which sits inside the dialog (its popup is the operating system's), so there is no hosted popover to be inert.

**Scrim.** The mock's dialogs have `.scrim { background: #0000004D }` (`mock/core.css:1479-1489`), and the palette's `.scrim:has(.palette)` is `transparent` (`:1491`); the kit has NO scrim or veil token (searched `packages/kit/src` and `tokens`: only the sheet's own comment names it), so the sheet draws no veil (the kit gap: a token such as `--ov-bg-scrim`, nine themes, is the proposal).
