## 1c. How a window's KIND selects what the frontend draws (read, with file:line)

- **The old UI** decides per window before it draws: `ui/main.tsx:38-45` awaits `resolveCurrentWindow()` (`ui/features/windows`: the runtime's `Window.Name()` and the window service's `List()`) and draws the shell of that window's kind; kind `settings` draws `SettingsWindowShell` (`ui/features/windows/SettingsWindowShell.tsx:15-90`: the old Settings page in a router, `GetSettingsState()` and the `settings/state` event, `HideSettings()`, Cmd/Ctrl+W, `content-visibility: hidden` while hidden).
- **The host** makes every native window with `options.Name = spec.Name` and `options.URL = "/#/"` (`backend/window/wails.go:60-64`: "The frontend asks Wails for its window name; a URL query would be lost when the window reloads"), so the URL cannot carry the kind and the name is the identity. For kind settings it sets the title, no frame (macOS: a hidden title bar and hidden window buttons, `wails.go:70-81`), a minimum of 960 x 600 (`:82-84`), and cancels the close into a hide (`:97-103`). `OpenSettings` (`backend/window/settings.go:12-58`) registers the entry of kind `settings` BEFORE it creates the native window (1060 x 640, centred on the work area) and focuses an open one (`native.Activate()`): one instance.
- **The new UI before this turn** had NO branch: `ui-next/main.tsx` drew `PluginHostScreen` in every window, so the native Settings window would have drawn the whole shell (a second main window).
- **The decision:** the same identity as the old UI and as the new UI's own session (`ui-next/shell/session/window.ts`, `resolveWindowName`): `Window.Name()` and the service's `List()` give the kind (`windowKind.ts`). A browser has no native window, so it draws the shell at once with no wait (`isNativeWindow()` is false: `WindowKindScreen`); a native window draws nothing until the host has answered (the shell's own first frame waits for the same service about its session, so no wait is added that the shell was not in). Any failure draws the shell (a window a person can leave). **No Go change was needed**: the kind is already registered and the title, the frame, the size and the one instance are the host's.

## 4. Decisions and deviations for the lead

1. **Superseded by the owner's ruling (2026-11-22): the window natively, the sheet in a browser.** The first turn built the sheet (reversible; section 1: "sheet" is ambiguous); the content is now one component in two containers. The old window's size, the pages left and the page right hold in both.
2. **No Save, no Apply, no unsaved-changes question**: the written rule is apply-on-change (S125, quoted in FM1); the sheet closes by Escape or its Close at any moment and loses nothing. A scrim press does not close (04: a form's backdrop does not discard a draft on an accidental click).
3. **Not drawn in this slice** (each recorded in the adapter with its reason): `appearance.theme` and `terminal.nativeApplication` (their editors are pickers the old window registers, `ui/pages/settings/CoreSettingsPage.tsx`), a setting marked developer-only, the types multiselect, colour and date-time, a secret whose presence the host does not state. No sections (the host declares none), no status slot in the page heading, no page menu, no Copy key, no search, no Plugins group, no Notifications, AI Tools or Updates pages (the old window has the last two as custom pages). **Search** is not drawn because it is not built; it can be real over the model (labels, descriptions, ids).
4. **Nav without glyphs.** The host names glyphs as `LuSettings2`, `LuPaintbrush`, `LuSquareTerminal`, `LuCode`, `LuBeaker`, `LuActivity`; the kit has two of six, and a nav that draws two would look unfinished. Glyphs the icons step needs: `paintbrush`, `square-terminal`, `code`, `beaker` (the host's page glyphs, Lucide), `settings` (the mock's gear for the top row, `LuSettings`; `settings-2` is used now), `rotate-ccw` (the mock's reset, `LuRotateCcw`; the kit's `undo` is used now).
5. **Appearance, Editor, Terminal and General persist real values the new shell does not read yet** (its `ThemeProvider` takes props; the old shell reads them). They are the host's own settings and apply in the product that shells them; binding the new shell's theme, density and text size to them is the Appearance step.
6. **Palette over the sheet**: while the sheet is open the window's tab, panel and palette chords are taken from the page behind it (the sheet is a modal); the sheet's own Command K (focus its search) comes with the search.

7. **The gear, the palette's "Settings" and the chord open the HOST'S WINDOW natively** (`WindowClient.OpenSettings('')`, one instance: a second ask focuses it) and the SHEET in a browser; the control falls back to the sheet when the host cannot show its window (never trap). On a Mac Cmd+, is AppKit's menu accelerator: the menu's Settings... already opens the window and JavaScript never sees the key, so the chord this tree handles is the browser's.
8. **The window opens on the page the host names**: its default request is `/settings?category=general` (`backend/window/settings.go:30-35`), so the first open lands on General, while the sheet (no request) opens on the first page, Appearance. Not unified: the host's default is the host's (a Go change if the lead wants Appearance first).
9. **One assertion of `scripts/ui-flavour.test.mjs` changed (a shared file, outside my paths; veto it if you want another fix).** The `next` build has its first lazy chunk with rules of its own (`Body-*.css`, `window-*.css`), so "the output holds one stylesheet" became "the page links exactly one stylesheet, and each stylesheet, appended to the entry's, passes the same checker as the entry's alone" (layer order once, every rule in a declared layer, every token read is defined, no `!important`). The alternative (`cssCodeSplit: false` in `vite.config.ts`) would put every future lazy surface's CSS in the entry.
10. **Identity by the host's window service, not by URL, and no Go change** (section 1c). A native window draws nothing until the host says which it is; a browser draws at once. `?screen=settings-window` is a development screen like `?screen=parts` (the seam and the probes open it).
11. **The window's page is kept while it is hidden** (as the original's): drafts, scroll and the page stay; a show refetches what the host holds. Close, Escape and Cmd/Ctrl+W hide it; nothing destroys it but quitting.
12. **The 100 window pages cost about 50 s per engine** in the seam, and the realm cannot be reached by them: the Settings window page calls only `GetSnapshot`, `GetSettingsState` and `HideSettings`, and the realm admits a window for activity, resource, exec, networker, logs and metric calls (`main.go:790-796`), so a Settings page takes no realm slot and there is nothing to release; the check still reads the rows 100 times, keeps `List()` at its baseline and looks for "window realm refused" in the log. Keep 100 (the lead's ask) or cut to 20 to save about 40 s per engine.
13. **An interactive popover opened from inside the sheet would take no pointer.** The kit's popovers (tooltip host, menus) are hosted outside the dialog, and a modal dialog makes the rest of the document inert: the tooltip IS drawn above it (proved from pixels: `document.elementFromPoint` ignores inert content, so it answers the row under the tooltip) and a tooltip needs no pointer; a menu or a hover card would. Settings uses only tooltips and native selects, so nothing here is affected; the sheet part is where it has to be solved before a sheet holds a menu.
14. **The window paints before the host has said it is shown** (`window.tsx`: `visible` starts true and `GetSettingsState` corrects it): harmless natively (the window is shown by the host that made the request), a flash only for a window the host never asked to show.
15. **The pages follow the focus** (an arrow moves to a page and shows it; Home and End the same): the probe found the first version moved the focus only, and VS Code's settings contents and JetBrains' settings tree agree on selection following the arrow (the standing rule). `Nav.tsx` selects on focus.
16. **No draft outlives its field (S125, written, beats the mock's code):** the page entered is started from what the host applied, so a value the host refused when the page was left is not waiting on the way back; a valid draft is applied when the focus leaves the field (the press on another page). `Body.tsx` `dropRefused`.
17. **One surface for the navigation and the page (the mock's), not the original's lighter sidebar**: the probe found the nav column on `--ov-bg-window` (38,40,44) against the page's (25,26,28); the mock's sidebar and page share one surface and the original's is only slightly lighter, so the column is the container's own with a separator (`Nav.module.css`). The old window's picture is the comparison for size, not for that fill.
18. **The page's heading is one level under its container's title:** h3 under the sheet's h2, h2 under the window's h1 (axe found h1 then h3 in the window on every page and all nine themes).
19. **Tab order in the sheet is Close, the pages (one stop), the controls, then back to Close** (the header comes first in the document, as the mock's `.sheet > .hd`): my brief to the probe said "Close last" and was wrong; the dialog wraps, so nothing is trapped.
20. **The probe's five findings were fixed in the UI, not worked around:** the page's scroll pane starts each page at the top (keyed by the page), the heading is the mock's 48 px (a 28 px title lane, 4 px, a one-line description with an ellipsis), the group label is 13/600 in the text colour in a 24 px row, the failed state's sentence is 12 px and centred, and the heading levels above; the controls' `base` repairs that held the clean run silent while those were open were removed.
