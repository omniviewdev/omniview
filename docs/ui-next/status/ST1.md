## 1c. How a window's KIND selects what the frontend draws (read, with file:line)

- **The old UI** decides per window before it draws: `ui/main.tsx:38-45` awaits `resolveCurrentWindow()` (`ui/features/windows`: the runtime's `Window.Name()` and the window service's `List()`) and draws the shell of that window's kind; kind `settings` draws `SettingsWindowShell` (`ui/features/windows/SettingsWindowShell.tsx:15-90`: the old Settings page in a router, `GetSettingsState()` and the `settings/state` event, `HideSettings()`, Cmd/Ctrl+W, `content-visibility: hidden` while hidden).
- **The host** makes every native window with `options.Name = spec.Name` and `options.URL = "/#/"` (`backend/window/wails.go:60-64`: "The frontend asks Wails for its window name; a URL query would be lost when the window reloads"), so the URL cannot carry the kind and the name is the identity. For kind settings it sets the title, no frame (macOS: a hidden title bar and hidden window buttons, `wails.go:70-81`), a minimum of 960 x 600 (`:82-84`), and cancels the close into a hide (`:97-103`). `OpenSettings` (`backend/window/settings.go:12-58`) registers the entry of kind `settings` BEFORE it creates the native window (1060 x 640, centred on the work area) and focuses an open one (`native.Activate()`): one instance.
- **The new UI before this turn** had NO branch: `ui-next/main.tsx` drew `PluginHostScreen` in every window, so the native Settings window would have drawn the whole shell (a second main window).
- **The decision:** the same identity as the old UI and as the new UI's own session (`ui-next/shell/session/window.ts`, `resolveWindowName`): `Window.Name()` and the service's `List()` give the kind (`windowKind.ts`). A browser has no native window, so it draws the shell at once with no wait (`isNativeWindow()` is false: `WindowKindScreen`); a native window draws nothing until the host has answered (the shell's own first frame waits for the same service about its session, so no wait is added that the shell was not in). Any failure draws the shell (a window a person can leave). **No Go change was needed**: the kind is already registered and the title, the frame, the size and the one instance are the host's.

## 8. Producer brief: `Snapshot.Revision` (the host's settings snapshot and its change events)

Ready to build. It would let the client drop all request numbering and detect a missed event.

**What.** A monotonic `revision` (uint64) on the host's settings state: `Snapshot.Revision` (`json:"revision"`; it is also in `CommitResult.Snapshot`), and the `settings/changed` event payload `{ kind: 'host', revision: N }` (today `{ kind: 'host' }`, `internal/bootstrap/bootstrap.go:24`). A new `GetRevision(scope)` returns the integer alone.

**Rules.** (1) Incremented once, under the store's lock, by every commit that changes a stored value, in the same transaction that writes it, and persisted with the values (`settings.db`), so it never goes down across a restart: a client that sees a lower revision than it holds has a bug, not a restart. A refused commit, a commit that changes nothing and a validation do not move it. (2) `GetSnapshot` reads the revision and the values in the same critical section: a revision names exactly the state it came with. (3) The event is emitted after the write (as `service.go:336-338` does now) with the revision that write made. (4) One counter for each scope (the host, each plugin).

**What the client deletes** (`ui-next/shell/settings/model/session.ts`, `view/Body.tsx`): (a) the request numbering (`asked`, `mine`, and the rule that drops an answer that is not the newest question's) is replaced by "apply an answer only if its revision is at least the one held", which stays right when the HOST answers two calls out of order (the numbering cannot see that, and says so); (b) the `inflight` / `epoch` / `wantsRefresh` / `ASKS` machinery that keeps a snapshot taken before the page's own commit from being applied: the commit's result carries its revision, so any snapshot below it is dropped and nothing is asked again; (c) a missed event is detected, not guessed: an event whose revision is above held + 1 means one was lost, and the page asks, with no reconnect signal needed for that case; (d) what it still asks "in case" (the page looked at again, the events connection back) becomes one `GetRevision()` call (an integer) and a full snapshot only when it is higher, instead of a snapshot for every look; (e) the retry after a lost question (F2) keeps its waits but re-asks for the revision, which is cheap. What it keeps: the retry bound, the draft rule, the secret rules. `onEventsReconnect` stays: it is what makes the page ask.

**Tests, Go** (`backend/pkg/settings`): the revision rises once for each commit that changes a value, and not for a refused one or a no-op; 100 concurrent commits give 100 distinct increasing revisions under `-race`; a snapshot taken while a commit runs is consistent (values and revision of one state); the event carries the revision after the write; plugin scopes count apart; a restart keeps it (persisted). **Tests, TypeScript:** the session's B1 and F2 tests rewritten over revisions (an answer with a lower revision is dropped, with the host answering out of order), and the seam's jittered burst. **Compatibility:** a new optional JSON member the old UI ignores; bindings regenerated (`task check:bindings-check`).
