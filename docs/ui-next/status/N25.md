## 1. Controls by change

### The rule

`scripts/ci/probe-select.mjs` (pure functions, no dependency, tested without an install). A pull request on its first attempt runs every probe and the controls its changed paths reach; the order of the rules for each changed path is:

1. a path that is not plain (a control character, a backslash, a `.` or `..` segment, an absolute path): every control (it is not classified);
2. a unit's declaration file, `scripts/ci/probe-units/<probe>.mjs`: the controls that file declares (a pull request that adds or changes a control proves it), and no others;
3. what every control depends on (`EVERYTHING`): every control. The shared harness (`packages/kit/probes/probe-lib.mjs`, `serve.mjs`, `mock-screen.mjs`, `ui-next/shell/probes/harness.mjs`, `build-fixture.mjs`), `scripts/ci/**`, the probe workflow, `.github/ci/**` (the image), every `package.json`, the lockfile, `pnpm-workspace.yaml`, `.npmrc`, `.tool-versions`, the kit's tokens (`packages/kit/tokens/**`, the generated `tokens.css` and `tokenNames.ts`), its layers, base styles and fonts (`src/styles/**`), its theme provider (`src/theme/**`), its font files, its `Text` and `Stack` primitives and `src/shared/**`, and the kit's own build (`vite.config.ts`, `tsconfig*.json`, `scripts/**`);
4. a path whose class `changes.mjs` calls `other` (anything that is not documentation and not the new UI: Go, the old UI, the root `vite.config.ts` and `tsconfig*`, `Taskfile.yml`, the runtime package, any other workflow): every control, with the reason "its class is unknown here";
5. documentation (`docs/**` Markdown, the status directory), Markdown anywhere, the tests of vitest (`*.test.*`, `*.spec.*`): selects nothing;
6. a path that a control unit's globs match: that unit;
7. any other path of the new UI: selects nothing, and is listed in the summary as "declared by no unit" so that a reviewer sees it.

Everything else is a full run: the event is not a pull request (a push to main, the nightly run, a dispatch, a merge-queue run, an event nobody named), the attempt is above 1 (a re-run), the attempt cannot be read, the diff cannot be read (Git failed), or there is no changed path. The job summary of the plan lists every control unit with whether it ran and the path or the rule that decided it (one line each), the paths that forced everything, the paths declared by no unit, and the seconds skipped.

### What a unit declares

Each unit has `paths`: globs (`*`, `?`, `**`, `{a,b}`; brackets are refused; the matcher is tested against the runtime's own `path.matchesGlob` on a corpus). **Probes' globs are broad** (the source directories their fixture's bundle holds: the shell probes hold `ui-next/shell/**`; the kit probes the kit's whole `src/` or the components they stage), because a later step may gate the probes by change and must not gate one on a narrow list. **Controls' globs are focused** on the code the control perturbs: the probe's own files (its script, its fixtures, its mock reference and measurer), the directories of the feature it checks, and the frame files the perturbation lives in. The test of the table fails when a glob matches no file of the tree, when a unit does not list its own probe script, when a fixture page a probe script opens (or the module it loads) is outside the globs of any of its units, and when a `.mjs` a probe script imports from its own directories is outside its globs and not in the shared harness. The bundle of each fixture was read from a production build (`vite build`, the rendered modules of each entry) to write the probes' globs: for example the notices fixture holds `ui-next/shell/{notices,core/notices,panel,palette,tabs,core,…}`, the host fixture also `ui-next/plugins/{host,contract,loader}` and the runtime package.

### What it lets through, and what main does when it finds it

A pull request can now merge a change **outside a control's declared globs that makes that control prove nothing**: a primitive of the kit that no control unit lists (a `Button` that stops taking the class a control's CSS targets), a file only a fixture's import reaches that is in none of the globs of the controls that use the fixture. The old scheme ran every control on the pull request and saw it there; this one sees it on the next push to main and in the nightly run, both of which run every control. What stops it earlier, mechanically: the fixture pages, the probe's local imports and the unit's own script are checked against its globs; the shared harness and the foundations run everything; any path it cannot classify runs everything.

When main's full run finds one, `Kit probes` is red on the commit, and the aggregator says so in words of its own (`::error title=Kit probes (full run)::a push to main, the nightly run or a dispatch failed: these runs check every probe and every control, and a pull request checks the controls its paths reach, so ...`) before it names the shard and the job. Who is told: the push to main is red for **the person who merged** (GitHub's own failed-workflow mail and the check on the commit, as for any red main) and the nightly run for **the person who last edited the cron line of the workflow** (the same, GitHub's rule for schedules); a dispatch tells whoever dispatched it. Nothing else is notified: there is no bot, no issue and no channel in this repository for a red main (`grep` for `slack`, `workflow_run` and `issues: write` finds none), and I did not add one: a failing issue bot is a decision for the lead (below).

## 2. Shards computed, not hand-packed

### The table is a directory of small files

I chose **one file for each probe in `scripts/ci/probe-units/`** (`panel.mjs`, `notices.mjs`, …: 20 files, 35 units), each exporting `units`: the unit that runs the probe and the units that run its controls. A unit is `{ id, name, script, env?, controls?, seconds, paths }`. Why a directory and not a sorted list: a pull request that adds a probe **adds a file**, which cannot conflict with another pull request that adds a file; a sorted list still conflicts when two pull requests insert at the same place (two appends to the end do), and a number that the drift check asks a pull request to update lives in the unit's own file, where only a pull request about that probe touches it. A unit has no shard: no pull request chooses where a unit runs, and moving a unit is not a change. Each file keeps the comments that described its units in the old table (what each probe checks, what each control perturbs). Before: the 787-line `probe-shards.mjs` held 10 shards, 33 units, `MEASURED_SECONDS` and a 60-line balance note that grew with every pull request, and was edited by every probe pull request (21 of the last 39 commits that touched `ui-next/` or `packages/kit/` changed it, per N24-D1).

`scripts/ci/probe-shards.mjs check` (the first thing the plan and every shard run) fails, one line each with the file named, for: a probe script that no unit runs (as before), a probe that runs twice, a control in two units or twice in one (a probe's controls may now be several units; each runs once), a script that does not exist, an id or a name used twice or an id that is not a lower-case word with hyphens, `NEGATIVE_CONTROL` set by hand in `env`, seconds that are not whole and positive or are over the limit (the message says "split it"), a unit with no `paths`, a glob that cannot be read, **a glob that matches no file of the tree** ("the path moved or was mistyped, and a control that is never selected proves nothing"), a unit that does not list its own script, and a unit file that does not load, exports no `units` or is not an `.mjs`. 35 units, 15 control units, 20 probe scripts, none by hand.

### The packing

`scripts/ci/probe-pack.mjs`: the selected units (id and seconds) into the fewest shards under `LIMIT_SECONDS` = 432 (not raised: the wall budget of 9 minutes less the 90th percentile of the setup; over the 70 shard jobs of seven runs the setup is median 87.5 s, p90 105 s, so 108 holds), **exact where it can be, first fit decreasing where it cannot**: an exhaustive search over the units, longest first, trying each shard once for each load and giving up a branch when the work left cannot fit the room left, for each count from the lower bound (the work over the limit, rounded up) to the one first fit gives; the search is bounded (400,000 placements; a run has about 35 units and needs a few hundred); then the shards are evened out (longest unit first onto the shortest shard, then moves and swaps that shorten the longest while neither ends over the limit). It depends only on ids and seconds, not on the order given: units are sorted by seconds, then id, and shards numbered from the longest. Tested against an oracle (dynamic programming over subsets, which shares nothing with it) on 400 random instances of up to 12 units, and on four instances (found by searching 20,000) where first fit decreasing needs one shard more than there is; the longest shard of 60 random instances is within the smallest unit of the best over every assignment. For the 10 sample pull requests and the full run the number of shards is the lower bound every time.

### The plan job

`Kit probes plan` runs first on `ubuntu-24.04` (no container: it does not pull the CI image, which is on the critical path of every shard), `fetch-depth: 2` (`HEAD^1` is the base of the merge commit), Node from `.tool-versions` (`actions/setup-node` with `node-version-file`, which reads the `nodejs` line: one home for the pin, as the workflow's guard requires), then `check` and `plan --base HEAD^1`. Measured: 17 s in the full run. It writes `matrix=<json>`, `shards=<n>` and `mode=` to the job output and the summary above to the job summary. The shard job is `needs: plan` with `matrix: ${{ fromJSON(needs.plan.outputs.matrix) }}`: `{ include: [{ shard, units, seconds, dist }] }`, the units as ids joined by commas, `dist` whether one of them reads the ui-next build (the build step is `if: matrix.dist == true`, the plan step of the shards is gone). The matrix reaches the command through `env` (`SHARD`, `UNITS`), never through its text; the dispatch input reaches the plan the same way. `Kit probes` is `needs: [plan, shard]` and green only when both succeeded: a plan that failed skips the shards, and the aggregator says it was the plan, and names no shard.

**Concurrency.** The group is the pull request's number for a pull request, with `cancel-in-progress` (a newer push to it cancels the older run, as before), and `run-<run id>` for every other run, never cancelled: a push to main's run is the only full run of its commit and a newer push must not throw it away (they queue for runners, which is what the pool is for). There is no group that serialises two main runs behind one another: a pending run is replaced by a newer pending run in a shared group, which would lose a commit's only full run again.

**Nightly.** `schedule: cron "41 2 * * *"` (a minute that is not the top of an hour), the same workflow with the same plan (a schedule is a full run). **A dispatch** is a full run; with `changed_paths` (one path per line) it rehearses the pull request that would change them (`gh workflow run ui-next-kit-probes.yml --ref <branch> -f changed_paths="$(cat paths.txt)"`): the same selection and packing on the runner, said to be a rehearsal in the summary. I used it for the measurements below.

**The path filters** of the workflow gained `scripts/ci/probe-units/**`, `scripts/ci/probe-*` (the engine, its tests and data), `scripts/ci/changes.mjs` and `scripts/ci/check-image.mjs`, which the plan and the shards read.

## 4. The drift fails the shard

After a shard has run, each unit's real seconds (its runs added up; a unit with a run that failed is left out, as K3's warning did) are compared with the unit's `seconds`. **A unit that took more than a quarter, or 60 s, whichever is more, over its seconds fails the shard**, and the message has what to do:

```
::error title=Kit probe unit seconds (shard 4)::Probe the command palette ... (palette) took 340 s on this runner, 261 s in scripts/ci/probe-units/palette.mjs (+79 s, 30 percent; a unit fails past a quarter and 60 s over): put `seconds: 340` there, and the next run packs the shards with it
```

A unit that took more than that **under** its seconds only warns (`::warning`, "put the new number there so that the planner can use the room"). A unit the table does not have fails (the plan and the table disagree). The job summary of every shard has a second table, one row for each unit: its seconds in the table, on this runner, and the difference. The drift is checked after the probes ran, so a probe that failed and a drift that failed are both in the log and both fail the job.

**The values.** Every unit's `seconds` is run 44929041191's real seconds (the rows of its shard summaries, a control's row one run, a unit the sum of its rows: 4,379 s, the number of L4.md's table), and the two units that run did not have, the rate at open (20 s) and its control (12 s), are the runner's first run of #650 (L4.md). The split units are the sums of the per-control rows of the same run. A test holds them (`probe-shards.test.mjs`: every unit equals that run's value).

**The margin, from data.** A single run is one sample, and the controls of a unit are many short runs that each build the fixtures: they move with the machine. Seven runs of this workflow on the ten-shard table (the run above, #647's push to main 44930354641, #653's run 44932913868 and its push to main 44934408252, #650's 44932365922 and 45037646536, and 45037417413), 235 unit runs with the units as they are now, against run 44929041191's seconds:

| a quarter and 45 s | 0 (the nearest, `log-controls` 166 s for 121 s, is exactly at it) |

It is a table that is held to what the runner measures, not a hard wall on a shard's seconds: the limit is a plan (432 s of table seconds in a shard, a job of 9 minutes when the setup is as slow as 1 in 10), and the table stays true, so a plan made from it is. The `timeout-minutes: 20` of the shard is the wall.

### The one rule

**A bound in milliseconds is the claim's bound on the reference machine times how much slower this page is than that machine, which the page measures in the same engine just before it measures the claim, never under x1 and never over a hard cap (x3); every sample, the calibration, the scale and the bound are printed; where the claim is a count (a commit for a notice, the listeners a closed centre holds) no millisecond is used and nothing is scaled.** The calibration is the median of nine samples, each the mean of eight runs of a fixed piece of DOM work (50 rows of 8 cells built, attached, laid out and read), after three warm-ups: the work the open does (elements, style, layout), at a size that does not depend on the page, long enough that WebKit's 1 ms clock is a few percent of a sample. The reference is the same number on the machine where the claim was made.

Measured, in the same page, locally (macOS arm64, Playwright's engines, three series of 6 to 10 trials per engine at load averages of 5 to 12): Chromium calibration 1.59 to 1.65 ms, open 3.4 to 3.8 ms (ratio 2.1 to 2.3); WebKit calibration 3.25 to 3.5 ms, open 9 to 11 ms (ratio 2.7 to 3.1): the calibration does not move with the load of the machine more than the open does, which is the point. References: **1.6 ms (Chromium) and 3.3 ms (WebKit)**. On the runner (the full run 45044160208 of this branch): the calibration reads Chromium 2.8 to 3.15 ms and WebKit 7.13 ms (x1.75 to x2.16), the open 7 to 7.5 ms and 18 to 20 ms, so the ratio of open to calibration is 2.4 to 2.8 there (2.3 to 2.9 locally): the calibration tracks the open across a machine twice as slow. A slow VM like the one that failed #650 calibrates about x4 against the reference and is capped at x3: a bound of 100 ms, and the open there was 38.

## Risks, plainly

1. **A control gone inert through a change outside its declared globs merges on the pull request and is caught on main.** The class of regression the old scheme caught on the pull request and this one does not: a change to code that a control perturbs, in a path the control's globs do not name (a primitive of the kit that no control lists, a helper only a fixture's import reaches). It is caught by the push to main's run and the nightly run, which run every control; those fail `Kit probes` on the commit. Mitigations that exist: the unit's own script, the fixture pages its probe opens and the probe's local imports are checked against its globs by a test; the shared harness, the kit's foundations and every path of an unknown class run everything; the controls' globs are focused on the code they perturb and include the frame files their perturbation lives in. What does not exist: a check that a glob list covers a fixture's whole import graph (the shell fixtures bundle the whole shell, so such a check would make every shell control depend on all of `ui-next/shell/**`, which is what this step removes), and a way to tell the author of the pull request that merged it: a red main is the merger's.
2. **The selection is as good as the globs, and the globs are a judgement.** They were written from each probe's table comment, each control's perturbation and each fixture's bundle (read from a production build), and checked against 13 real pull requests; a probe that is later changed to exercise a new directory needs a glob for it, and the first sign that it did not get one is a red main. A unit file that changes selects its own controls, so the pull request that changes the globs proves the controls it changed.
3. **A pull request that touches the CI scripts or the workflow runs everything and costs what it cost before.** `scripts/ci/**` is in `EVERYTHING` on purpose (the engine is what selects), so the probe engine's own pull requests, this one included, are full runs.
4. **The plan job is a new single point of failure** (17 s, no container, `ubuntu-24.04` with Node from the toolchain pin): if it fails no shard runs and `Kit probes` is red with "the plan job finished as ...". It does not read the diff of a forked pull request differently from the others.
5. **The runs are not cheaper at the top end.** A change that touches what everything depends on runs every control: 11 shards, 13 jobs, more runner seconds than the ten-shard table's run (see Numbers): the old table was 4,167 s of units against a runner that measured 4,379 s, so it was one shard short.
6. **The drift gate is a table held to the runner, not a wall.** A slow machine can put a shard 30 percent over its table without a unit passing the margin (see 4 above); the 60 s floor is data from seven runs, and an eighth that is worse will fail a shard on a unit whose value is right: the message says the number, the author reruns the job (a re-run is a full run) or raises the number once.
7. **Nothing here changes what a probe or a control asserts**, except the one ms bound of the centre open, which is scaled, and its control, whose fault is longer.
