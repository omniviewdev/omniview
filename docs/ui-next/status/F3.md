## Cause

**What the two ids are.** View generations (`HostSourceViewEvent.ViewGeneration`, `source_view.go:37`), not view ids. A view id never changes: the test opens one view (`source_coordinator.go:701`) and one source (the fixture closes `stopped` once; a second open would panic on the second close). A second view, a retry or a second source is therefore not what happened.

**When a generation starts.** `syncLocked` (`source_view.go:434-452`) sets `v.generation = uuid.NewString()`. It has two normal callers: the session, for every view, when the first snapshot of the source is complete (`source_session.go:807-809`); and the client's request, `SyncSourceView` (`source_coordinator.go:749`). While the session has no snapshot the client's call returns at `source_view.go:437` and sends nothing. After it, the view is already synced, so `syncLocked("resync")` calls `resetLocked` (`source_view.go:443-445`), which emits a `reset` event that names the old generation, and then starts a new one and queues the whole snapshot again. A `changes` event takes the generation current when it is queued (`nextLocked`, `source_view.go:66-69`).

**The order that fails.** The test calls `OpenSourceView` and then `SyncSourceView` back to back. The source stream (gRPC open, first frames) takes roughly 0.5 to 1 ms to deliver its snapshot (stall probe below). If the test goroutine is delayed by more than that between the two calls, the session syncs the view first (generation A: `snapshot`, `snapshotEnd`), the emit loop publishes both, and the client's sync then resets (A) and starts B. `waitSourceView` scans the recording from its start, so `initial` and `end` are A's events; the file change is queued under B; line 140 compares A with B. Forced on purpose, the stream is exactly:

```
snapshot gen=A seq=1 / snapshotEnd gen=A seq=2 / reset gen=A seq=3 (resync) / snapshot gen=B seq=1 / snapshotEnd gen=B seq=2 / changes gen=B seq=3
```

If the sync lands between `snapshot` and `snapshotEnd` of A, `end` is B's and line 136 fails instead (`initial` against `end`): the one natural failure here was at 136.

**Evidence.**

- Stall probe (scratch, not committed): the unmodified test with `time.Sleep(d)` between the two calls, 200 runs each, machine not quiet: d = 0: 0 failures; 250 us: 1; 500 us: 63; 1 ms: 196; 2 ms: 200; 5 ms: 200. A stall of a millisecond fails nearly every time, so a CPU-starved runner needs no rare event.
- The late order forced without sleeps (the red commit on the wip branch): 300 of 300 fail with the CI message; the early order 0 of 300.
- Alone against in the package: the test alone ran 4,100 times plain with 0 failures; the whole package (once plain, twice with `-shuffle=on`) passed with it in. With the stall probe at 300 and 400 us, C02 failed as often alone (2, 9, 1, 2 of 100) as in a process that first ran the 26 subtests #551 added to the package on 11-19 (1, 1, 0, 0 of 100), so that PR did not make it flakier (a process that has already run gRPC tests is faster, not slower). The package has no `t.Parallel()`, and each run builds its own controller, provider and file, so there is no shared global between tests.

**Verdict: TEST bug, not a product bug.** The test asserts an ordering the product does not promise: that the generation of the first `snapshotEnd` is the one a later change carries, whatever else happens. The product promises the opposite and the client is written for it: a `reset` ends the generation it names and the next generation starts at sequence 1 (`sourceView.ts:175-199`, `accept`), and the client keeps the records it holds through the reset (`sourceView.test.ts:152`, "retains current records through reset until the next generation ends", the same event order). The second sync cannot be avoided in the host: the client subscribes (`Events.On`, `sourceView.ts:239`) after `OpenSourceView` has returned, so anything the host published before that is lost, and `SyncSourceView` (`sourceView.ts:273`) is how it gets the snapshot again.

**What a user could have seen.** Nothing wrong. The host never handed the UI a view id that was not the live one, and no event carried a generation that the client would accept as live and that was not: a change is queued under the generation current at that moment, a sync drops the queue (`releaseQueueLocked`), and one goroutine emits the events in order, so a stale event always precedes the `reset` that retires it. In the late order a list that had subscribed in time receives its snapshot twice at open, `view.viewGeneration` that `useResources` hands to its callers changes from A to B once, and records that did not change keep their object identity (`replaceEqualDeep`, `sourceView.ts:212-216`), so no row is rebuilt. The cost is a second snapshot of whatever the source held in the first millisecond, a small list for a new session. A session that already holds its snapshot never takes this path: its views get one sync, from the client.

## Failing test first

`TestC02SourceViewLifecycle` now runs the lifecycle twice, once for each order of the client's sync, and the fixture provider holds its first snapshot until the test lets it go (a channel, no sleeps), so which order a run gets is no longer a race:

- `sync before the first snapshot`: Open, Sync (the session has no snapshot: it sends nothing), release the source. One generation, never reset.
- `sync after the first snapshot`: Open, release the source, wait for `snapshotEnd`, then Sync. A `reset` that names the first generation, the snapshot again under a second one, and the change carries the second.

Red commit (wip branch, `40149ba0`: the new structure with the old assertions, the change compared with the first `snapshotEnd`): `sync after the first snapshot` fails 300 of 300 with `source_c02_integration_test.go:160: Not equal: expected: "ecec48f3-..." actual: "96100d5e-..."` (the old line 140); `sync before the first snapshot` 0 of 300. It can only miss the bug, never fail on correct code: the product is unchanged.

## Fix

The change is compared with the live generation: the first one in the early order, the one after the `reset` in the late order (`live`). The late order also asserts the `reset` (reason `resync`, naming the first generation) and that the second generation carries the snapshot again; the early order asserts that no `reset` was emitted. Files: `backend/pkg/plugin/resource/source_c02_integration_test.go` and this file. No product, SDK or workflow file is touched, so nothing of the credential-broker track (connection lifecycle, `profilesMu`) is.
