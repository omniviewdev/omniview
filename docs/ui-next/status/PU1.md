## Goal

A plugin that was loaded and then stopped (its process crashed, it was reloaded, uninstalled or turned off) must leave the window: its sidebar, pages, palette providers and panel tools go through the paths that already handle a plugin that failed to load, its open tabs say so, the sessions of a host-owned panel tool stay (A21), and a plugin that comes back loads again with no reload of the window and with one of everything.

## What the host said before, and what it says now

The assignment expected the window to get no signal at all. It got signals, but none a window could act on: `plugin/state_change` (every phase change; its `reason` is the host's text and holds the error of a failure, `lifecycle/machine.go:logTransition`), `plugin/crash` (the plugin's last log line; the first crash of a cycle only, `manager.go:333-344`), `plugin/enablement_changed` (a literal, not a declared event, `catalog.go:300,327`), `plugin/inventory_changed` (no payload), and for a reload nothing but `state_change` (the three `plugin/dev_reload_*` events are declared and never emitted). `ui-next` listened to none of them. What each trigger sent, from the red Go tests (`unloaded_event_test.go`, before any change), and what it sends now:

| Trigger | The window was told (events in order, before) | Now, in addition: `plugin/unloaded` with |
| --- | --- | --- |
| process crash | `plugin/crash`, `state_change`, `state_change`, `crash_recovery_failed` | `{pluginID, cause: "crashed"}` (`manager.go handlePluginCrash`: every crash, not only the first of a cycle) |
| reload (`ReloadPlugin`, a dev rebuild, a retry, the recovery of a crash) | `state_change`, `state_change` | `reloaded` (`loader.go reloadPluginLocked`, after the unload and before the load) |
| update or reinstall from an archive | `install_started`, `state_change` x2, `inventory_changed`, `install_finished` | `reloaded` (`archive_transaction.go unloadArchivePlugin`); relinking a development plugin: `installer.go unloadForReinstall` |
| uninstall | `state_change`, `inventory_changed` | `uninstalled` (`installer.go unloadForReinstall`, from `uninstallPlugin`) |
| turn off | `enablement_changed`, `state_change` x2 | `disabled` (`catalog.go SetPluginEnabled`, next to `enablement_changed`; turning on tells nothing) |

A plugin the manager does not hold (a first install) is not told of. The event is `plugin/unloaded`, payload `{pluginID, cause}`, cause one of four words and no other member (`UnloadedPayload`; a test pins the wire and fails on a third member). **A plugin that runs again** is not a new event: the window reads the declared `plugin/state_change` with `to: "Running"` (the signal `docs/development-plugin-lifecycle.md` gives consumers for it, and `connectionReadiness.ts:158` already reads the same way).

## The declared names, and why a new one

Quoted: `EventStateChange` (`events.go:15,41`, payload `StateChangePayload` with `Reason` free text and no cause); `EventCrash` (`:30`, `PluginErrorPayload.Error` is the plugin's last log line, sent once per cycle); `EventReloadStart/Error/Complete` (`:22-24,54-56`, payload `*config.PluginMeta`, one trigger, and the old shell listens to `dev_reload_complete`, `ui/features/plugins/core/PluginService.ts:763`, so emitting them would change the shipped product); `EventInventoryChanged` (`:29`, `application.Void`). None carries a cause code without text for all four triggers, so `plugin/unloaded` is new. Its cost: the Wails bindings are regenerated by `task bindings` (5 generated files, `eventcreate.ts` renumbers its constructors), a rule in `internal/auditgate/policy.json` (allow: id and code, no text) and a section in `docs/development-plugin-lifecycle.md`.

## What the window does (`ui-next/plugins/`)

- `host/lifecycle.ts` (new): two handlers, `plugin/unloaded` to `PluginStore.unload(id, cause)` and `plugin/state_change` to Running to `PluginStore.revive(id)`; it reads an id, one of four words and a phase name and nothing else (the `reason` of a state change is never read); `PluginHostScreen` starts it and removes both handlers with the screen.
- `PluginStore.unload(id, cause)`: a crash or a reload keeps the plugin as a failed entry of the new kind `unloaded` with the host's own sentence (the mock's words: crashed "The plugin process stopped unexpectedly, so its pages can't load data." and reloading "The plugin is starting again. The page opens when it is ready."); an uninstall or a turn-off forgets the entry, as a window opened now would not have it (the tab then says the existing "This plugin is not installed, or is turned off."). Modules are dropped, an answer of a load in flight is dropped, the first cause stands (the recovery of a crash reloads the plugin and the host says so: crashed stays). `revive(id)` loads a plugin that was gone again from its files; ready, loading and failed-on-their-own entries are left alone.
- Through the paths that handle a failed plugin: rail (`failedOf`: "Acme, stopped" with the error glyph, "Acme, starting again" with the plugin's own), tab face and availability (`contributions.ts`), the empty window's caption (`NoTabs.tsx`), the panel (`panelPluginsOf` already treats a plugin that is not ready as gone: tools leave, A21 keeps the sessions of the host's Logs tool), the palette's providers. Mock rule quoted: ch16 PO1 ("a plugin that is off contributes nothing ... Its tabs keep route and state and draw the glyph of the plugin's state ... the error glyph of S19 for one that failed") and S89 (failed: Retry; starting: no retry). A crashed plugin's tab offers the Retry the existing failed state has (it reloads the interface); a reloading plugin's tab draws the loading state with no Retry (`PluginHost.tsx HostPage`).

## Decisions for the lead

1. A new event name, `plugin/unloaded` (above), instead of a declared one. Alternative with no bindings or policy change: the window derives the cause from `state_change` plus the inventory (racy; no cause for a reload).
2. Uninstalled and turned-off plugins are FORGOTTEN, not kept as failed entries (no rail entry; the tab uses the existing not-installed sentence). Uniform failed entries are one line in `PluginStore.unload` plus a word in `failureWords` if you prefer them.
3. A reloading plugin's tab draws the loading state with no Retry (the mock's starting state); a crashed one keeps the failed state's Retry, which reloads the INTERFACE (the host recovers the process itself).
4. "Controls in the shard table": the seam is not run by any workflow, needs the Go host build and is not a probe script of `PROBE_DIRS`, so scenario n's controls are in `seam.check.mjs` (`PROCESS_CONTROLS`), as k's and m's are. A CI-run proof of the same chain needs the host fixture of the shell probes (`ui-next/shell/probes/host-fixture.tsx`, `window.__plugin.unload`, which still drives `store.retry`): not mine; replace it with `listenForLifecycle` over a fake `Events` and add its controls to a shard.
5. Scenario n costs about 60 s per engine: the host's health check ticks every 30 s and there is no faster path for a plugin with no resource stream.
