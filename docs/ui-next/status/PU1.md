## Goal

A plugin that was loaded and then stopped (its process crashed, it was reloaded, uninstalled or turned off) must leave the window: its sidebar, pages, palette providers and panel tools go through the paths that already handle a plugin that failed to load, its open tabs say so, the sessions of a host-owned panel tool stay (A21), and a plugin that comes back loads again with no reload of the window and with one of everything.

## What the host said before, and what it says now

The assignment expected the window to get no signal at all. It got signals, but none a window could act on: `plugin/state_change` (every phase change; its `reason` is the host's text and holds the error of a failure, `lifecycle/machine.go:logTransition`), `plugin/crash` (the plugin's last log line; the first crash of a cycle only, `manager.go:333-344`), `plugin/enablement_changed` (a literal, not a declared event, `catalog.go:300,327`), `plugin/inventory_changed` (no payload), and for a reload nothing but `state_change` (the three `plugin/dev_reload_*` events are declared and never emitted). `ui-next` listened to none of them. What each trigger sent, from the red Go tests (`unloaded_event_test.go`, before any change), and what it sends now:

| Trigger | The window was told (events in order, before) | Now, in addition: `plugin/unloaded` with |
| --- | --- | --- |
| process crash | `plugin/crash`, `state_change`, `state_change`, `crash_recovery_failed` | `{pluginID, cause: "crashed"}` (`manager.go handlePluginCrash`: every crash, not only the first of a cycle) |
| reload (`ReloadPlugin`, a dev rebuild, a retry, the recovery of a crash) | `state_change`, `state_change` | `reloaded` (`loader.go reloadPluginLocked`, after the unload and before the load) |
| update or reinstall from an archive | `install_started`, `state_change` x2, `inventory_changed`, `install_finished` | `reloaded` (`archive_transaction.go unloadArchivePlugin`); relinking a development plugin: `installer.go unloadForReinstall` |
| uninstall | `state_change`, `inventory_changed` | `uninstalled` (`installer.go unloadForReinstall`, from `uninstallPlugin`) |
| turn off | `enablement_changed`, `state_change` x2 | `disabled` (`catalog.go SetPluginEnabled`, next to `enablement_changed`; turning on tells nothing) |

A plugin the manager does not hold (a first install) is not told of. The event is `plugin/unloaded`, payload `{pluginID, cause}`, cause one of four words and no other member (`UnloadedPayload`; a test pins the wire and fails on a third member). **A plugin that runs again** is not a new event: the window reads the declared `plugin/state_change` with `to: "Running"` (the signal `docs/development-plugin-lifecycle.md` gives consumers for it, and `connectionReadiness.ts:158` already reads the same way).

## The declared names, and why a new one

Quoted: `EventStateChange` (`events.go:15,41`, payload `StateChangePayload` with `Reason` free text and no cause); `EventCrash` (`:30`, `PluginErrorPayload.Error` is the plugin's last log line, sent once per cycle); `EventReloadStart/Error/Complete` (`:22-24,54-56`, payload `*config.PluginMeta`, one trigger, and the old shell listens to `dev_reload_complete`, `ui/features/plugins/core/PluginService.ts:763`, so emitting them would change the shipped product); `EventInventoryChanged` (`:29`, `application.Void`). None carries a cause code without text for all four triggers, so `plugin/unloaded` is new. Its cost: the Wails bindings are regenerated by `task bindings` (5 generated files, `eventcreate.ts` renumbers its constructors), a rule in `internal/auditgate/policy.json` (allow: id and code, no text; `TestRegisteredEventNamesAreClassified` in `main_audit_policy_test.go` fails without one for a registered event) and a section in `docs/development-plugin-lifecycle.md`.

## What the window does (`ui-next/plugins/`)

- `host/lifecycle.ts` (new): two handlers, `plugin/unloaded` to `PluginStore.unload(id, cause)` and `plugin/state_change` to Running to `PluginStore.revive(id)`; it reads an id, one of four words and a phase name and nothing else (the `reason` of a state change is never read); `PluginHostScreen` starts it and removes both handlers with the screen.
- `PluginStore.unload(id, cause)`: a crash or a reload keeps the plugin as a failed entry of the new kind `unloaded` with the host's own sentence (the mock's words: crashed "The plugin process stopped unexpectedly, so its pages can't load data." and reloading "The plugin is starting again. The page opens when it is ready."); an uninstall or a turn-off forgets the entry, as a window opened now would not have it (the tab then says the existing "This plugin is not installed, or is turned off."). Modules are dropped, an answer of a load in flight is dropped, the first cause stands (the recovery of a crash reloads the plugin and the host says so: crashed stays). `revive(id)` loads a plugin that was gone again from its files; ready, loading and failed-on-their-own entries are left alone.
- Through the paths that handle a failed plugin: rail (`failedOf`: "Acme, stopped" with the error glyph, "Acme, starting again" with the plugin's own), tab face and availability (`contributions.ts`), the empty window's caption (`NoTabs.tsx`), the panel (`panelPluginsOf` already treats a plugin that is not ready as gone: tools leave, A21 keeps the sessions of the host's Logs tool), the palette's providers. Mock rule quoted: ch16 PO1 ("a plugin that is off contributes nothing ... Its tabs keep route and state and draw the glyph of the plugin's state ... the error glyph of S19 for one that failed") and S89 (failed: Retry; starting: no retry). A crashed plugin's tab offers the Retry the existing failed state has (it reloads the interface); a reloading plugin's tab draws the loading state with no Retry (`PluginHost.tsx HostPage`).

## What an open tab shows when its plugin is gone

The tab stays where it is, with its route and the face it had (ch16 PO1: "Its tabs keep route and state"; the model keeps the face of a plugin it no longer has). What its island shows depends on the cause, always in the host's words and never an end-less state or an action that could not work:

| Cause | The tab's island | Retry | Spinner |
| --- | --- | --- | --- |
| crashed | the kit's failure notice, "Couldn't load <plugin>": "The plugin process stopped unexpectedly, so its pages can't load data." (the mock's failed plugin, S89); the rail says "<plugin>, stopped" with the error glyph | yes: the failed state's Retry, which reads the interface again (the host recovers the process itself) | no |
| reloaded | the loading state, until the host says the plugin runs (the mock's starting plugin: no Retry, S89); the rail says "<plugin>, starting again" | no | yes, and it ends at `plugin/state_change` to Running (see PU1-02 for a reload that fails) |
| uninstalled, disabled | the kit's failure notice, "Couldn't load <plugin>": "This plugin is not installed, or is turned off." (the words the host already draws for a tab restored from a session whose plugin is not there); no rail entry | no: nothing could work, the plugin is not there | no |

`PluginHost.unload.test.tsx` tests each (the notice, the sentence, no `aria-busy` anywhere, no Retry where it is not offered); nine mutations of the window's rules (a Retry on the gone tab, the reload special case off, an ignored `plugin/unloaded`, an ignored Running, the first cause not standing, modules and late answers kept, the old rail word, the error glyph for a reload, an uninstalled plugin kept as failed) each turn their tests red. Not the mock's: the glyph of a gone plugin's tab (the mock draws the neutral glyph of the plugin's state, PO1) stays the page's own, and the mock's recovery component (heading "<plugin> is disabled", "Enable it to open its pages.", an Enable or Start action) is not built in `ui-next`; both are the plugins page's and the recovery page's work.

## Backend catalog

- **PU1-01, TANGENTIAL, `backend/pkg/plugin/loader.go:622-628` and `:187-196`:** a reload whose load fails validation leaves the plugin with NO record: `unloadPluginLocked` deleted it (`loader.go:681`) and `validateForLoad` returns before `storeFailedRecord`, so `RetryFailedPlugin` answers "Plugin 'x' is not currently loaded" (404) and the plugin vanishes from `ListPlugins`; only `LoadPlugin` brings it back. Found in scenario n (the binary lost its execute bit). Interim: the check loads it with `LoadPlugin`.
- **PU1-02, TANGENTIAL, `backend/pkg/plugin/loader.go:245-249` and `:622-628`:** a reload that FAILS leaves the window on "starting again" (the loading state, no Retry) for ever: the host sends `plugin/unloaded` (`reloaded`) when it stops the plugin, but a failed load sends nothing, because the new record's state observer is registered only after the load succeeded (`registerStateObserver`, `loader.go:245-249`), so no `plugin/state_change` to Failed reaches the window. Fix: emit a state change (or an event of its own) from `storeFailedRecord` (`loader.go:393-403`), or have `ui-next` turn a plugin that is "starting again" into the crashed state after a deadline. Not done: the lead's ruling was to catalogue only the record loss (PU1-01); this one is the same path.
- **PU1-03, not told:** `StopDevPlugin` (`managed_lifecycle.go:110-144`) and a stop that fails (`unloadPluginLocked` returns an error, the plugin is `Failed`) send no `plugin/unloaded`; the window still hears `state_change` and does nothing with it.
- B-22 (log sessions of a plugin that restarts retire with no signal) is answered for the window only: the window now unloads the plugin, so A21 ends and keeps its sessions; the host's own log index (`logs/controller.go:431-490`) is unchanged.
