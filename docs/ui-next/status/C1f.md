## The rule, and where each case is decided

A row says the connection by its display NAME, taken from where the shell already knows it, and never a route parameter's raw value; where no name is known the row says no connection (never the key).

- **Where the name is known.** The page publishes its frame when it is drawn (`FrameV1`, the host's `frames`, by `routeKey`), and the frame's `scope` is the lane the shell draws above the page: faces of `{label, icon, text}`. The face labelled **Connection** says the connection's name (`Connection: kind-kind`). The contract does not name that face; the plugins and the design lab's lane label it so, and a plugin that labels it otherwise has no name here (a question below). `host/palette.ts`, `connectionNameOf`.
- **The tab on screen (case 1, a route that carries a key).** The page's own lane names it: `Gadgets | kind-kind · Group`, `Namespaces | kind-kind`, and the Tabs row `Deployments | kind-kind · Current tab`: once, because the crumb the host makes from the key (a detail page's path) and the scope's label, which is the key too, are both said by the name, and a place named twice is said once.
- **The tab on screen, a route that carries none (case 2, the ordinary flow).** DECIDED: the rows of that plugin say the connection its lane names. The mock's rows read `prod-eu · Workloads` (`shell-kubernetes.js` `connectionRows`: `where = text => (label ? `${connectionId} · ${text}` : text)`, `label` true when the palette offers the kinds of more than one connection); the host cannot count a plugin's connections, but the lane is exactly the shell's knowledge of the connection the page is read in, and a page opened from that tab opens in it (the plugin reads its own when the route names none, and its lane says which). So the ordinary flow reads `kind-kind · Workloads` and the top-level pages (no group) read `kind-kind`, where they read the plugin's name before.
- **A plugin that is not on screen.** Its pages open at the connection the plugin was last shown in (`remembered`, unchanged: the route carries the key), and a row says that connection by the name the lane of that last-shown route said, which the frame store still holds. If that page was never drawn in this window (a restored session shows one page), no name is known and the row says no connection: the group alone, the plugin's name for a page with no group. **With no tab of the plugin open and nothing remembered**: the same, no connection.
- **The chips that narrow the palette.** The scope chip's label is the name and its id stays the key (what a plugin's provider is asked with, `SearchScope.scope.id`). With no name known the palette is narrowed to the plugin alone: a chip would have to say the key, and a provider is then asked with no connection (it was asked with the key before; the plugins that name their lane are not affected).
- **Recent.** What the model is told of a place (`describe`) says the name where the host made the scope and a detail page's path crumb from the key, and says nothing where no name is known. A route that carries no key has nothing made from one, but its lane says which connection it is read in, and Go to and Tabs say it, so Recent says it too (`Acme · kind-kind`), in a scope that has no key (CodeRabbit's comment on the PR; the first version left it out). Recents saved by an older build carry their old text until the plugin describes them again.
- **A page published after the palette opened** is said at once: the palette listens to the frames while it is open (as it does to the tabs, the plugins and the sidebar nodes).
- **Unchanged:** a page that sits in no group says the connection alone, chip or none, and the plugin's name when no name is known (C1e, ruling 4); the host makes no group up (`Cluster` is the plugin's to say); rows of two plugins that read alike are told apart by the plugin's name.

## Other places that draw a route's connection parameter raw (listed, not fixed here)

The root is `plugins/host/contributions.ts`: the tab's FACE is made from the route, so its scope label, a crumb of a detail page's path and a facet are the key. Everything that reads those draws the key.

| `plugins/host/contributions.ts:73` and `:122` (`describeDetail` path; a list page's path when its hook published none) | the route's connection as a crumb: `[plugin, <key>, list, name]` | the status bar's crumbs and the detail page header's crumbs |

That changes the tab model's identities and the strip's qualifiers, so it is a step of its own (the lead's call), and the palette would then need no lane reading of its own.

## Questions for the lead

1. **Which lane face is the connection?** The contract (`FrameV1.scope`, `DetailPageViewV1.scope`) says "at most two faces" and nothing of which says the connection; the host reads the face labelled Connection, a convention of the plugins and the design lab. A plugin that labels it otherwise (a translated label, `Cluster`, `Account`) has no name here, and its palette says no connection. Either the contract names the face (a `connection` marker on the face, or the connection's name beside the key in the frame) or the convention is written into the contract as it is.
2. **A top-level page with no group** reads the connection alone (C1e ruling 4); a plugin that wants `Cluster` there needs a group or a label of its own on the node, which the contract does not have.
3. **The shared fix** in `contributions.describe` above.
