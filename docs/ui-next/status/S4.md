## Goal

A plugin whose process negotiates a plugin protocol the host does not run is refused by a decision the host makes from the NUMBER (never from error text), told to the window as the cause `incompatible` with the two numbers, and shown in words with both versions and no Retry. The host still runs exactly what it ran before (protocol 1): no dual-read, no second protocol.

## How the decision is made

1. **One declared value.** `types.OldestProtocolVersion` and `types.CurrentProtocolVersion` (both 1) are the only place the accepted range is written; `AcceptedProtocols()` reads them. The offer to go-plugin, the decision, the facts and the host's sentence are derived from it. The dual-read step edits `CurrentProtocolVersion`, the flip edits `OldestProtocolVersion`. (The five utility controllers' `switch version { case 1: ... default: error }` are per-protocol client code, not the range: they change at that step too.)
2. **Offer every protocol up to a ceiling.** go-plugin's plugin picks the highest number both sides list and, when none matches, announces its lowest anyway, which the client refuses with a string and no type. The loader offers protocols 1 to 16 (`offeredProtocolCeiling`); those the host runs carry the capability clients, the others an empty set.
3. **Decide by number, kill, never dial.** `handshake(client, cmd)` = `Start()` (process and handshake line), `admitProtocol(NegotiatedVersion())`, and only then `Client()`. A refused plugin gets NOTHING: no client is dispensed and nothing is dialled. (The first version of this step called go-plugin's `Kill()` on a refused plugin and wrote here that the only traffic it gets is a graceful-exit request, so that it left no socket behind. Both claims were wrong, and the review of #659 measured it: `Kill()` dials the plugin, mutual TLS, then `Shutdown` with no deadline, `StreamStdio`, `StartStream`, which a plugin that does not answer holds for ever, and the plugin left its socket.) `refuseProcess` ends the process instead: `cmd.Process.Kill()` (SIGKILL), removes the socket the plugin advertised (`unlinkAdvertisedSocket`: only a unix socket, directly in the directory the plugin was told to use, named `plugin` and digits, that `Lstat` says is a socket and not a link, so a plugin's own word cannot name another file), and waits for go-plugin's reaper (`client.Exited()`, polled every 2 ms, at most 2 s so that a process that cannot be killed does not hold the load). `createBackend` then returns the typed error without `Kill()`, which would dial a socket that is gone and leave a gRPC connection and its goroutines behind (a test counts them). The host does not start a plugin in a process group of its own (go-plugin's runner sets none; only the devserver and the supervisor do), so there is no group to kill: a process the plugin started is out of reach, as it is whenever the host kills a plugin.
4. **Typed.** `*IncompatibleError{Incompatibility{PluginProtocol, Accepted{Oldest, Newest}}}`, found with `errors.As` through the AppError wrap. `loadFailureCause` reads the type first (`incompatible`), then `Timeout()` (`timeout`), else `failed`. A refusal is never a timeout however long the plugin took to answer (`createBackend`).
5. **Where the facts go.** The event `plugin/unloaded` gains one optional member, `incompatibility` (two numbers, set for `incompatible` only); the plugin's `ListPlugins` entry gains `incompatible` (the same). The event serves the windows that are open, the inventory the ones that open later (the same two paths `failed` already has: the phase). No text travels with either.
6. **The words.** The host's sentence for its log and the old shell's page (`LastError`, the AppError detail) is composed from the numbers: "This plugin was built for a different version of Omniview. It uses plugin protocol 2; this Omniview accepts protocol 1." The AppError has its own title ("Plugin is not compatible with this version of Omniview", 422) instead of "Failed to initialize plugin RPC" (500): nothing is broken, the pair is not one the host runs. The window words the same numbers itself (`failure.ts`); a Go test and a window test write the one sentence out.
7. **No retry.** `refusedForGood` ends the crash-recovery loop at a refused plugin: one attempt, no further backoff, no timer; `crash_recovery_failed` carries the host's sentence. The window's tab draws no Retry (`canRetry`) and the store asks the host for nothing.

### A protocol past the ceiling: option A (decided by the lead)

A plugin more than 16 protocols ahead of the host is refused by go-plugin itself, with `incompatible API version with plugin. Plugin version: 400, Client versions: [...]`: a string, no type. The number the host would need for `incompatible` exists only in that library's text, and the host does not read a library's text for a fact (the owner's ruling: a fact the producer knows is stated by the producer; a consumer never guesses or matches error text). So no exception is made: **the cause stays `failed`**, with a Retry, no two numbers. What changed in round 2 is what the page and the record say for it:

- the text go-plugin wrote lists the protocols the host offered in the order of a Go map, a different one on every run, and (for a plugin that died at once) the plugin's path, mode and owner. It reached `LastError` and the AppError detail, which the old shell's page shows. It is now the host's own sentence for a handshake that failed, fixed: "The plugin started, but its process did not complete the handshake with Omniview. The details are in the host log." (`handshakeError`, `load_failed.go`; it wraps go-plugin's error, so `errors.As` and `Timeout()` still read it);
- go-plugin's words go to the host's log only (`go-plugin refused the handshake of the plugin's process`, field `error`, once for each load); the log sink redacts, as it does for every caller (`manager_log_redaction_test.go`);
- the new window never showed `LastError`: it words each cause itself (`failure.ts`, `failed`: "The plugin could not start, so its pages can't load data."), so nothing on the new page changes. `controllerFailure` is not on this path: it words the failure of a capability controller's start (a provider's typed error, which it passes through `apperror.ForResource`; any other error it returns unchanged), while a handshake that fails is the error of `createBackend`, which the load wraps as the AppError "Failed to initialize plugin RPC" (500) whose detail is the error's text, now the host's sentence; the old shell's page shows `LastError`, which is that text;
- the class is "a process that started and whose handshake go-plugin refused" (it exited at once, wrote something that is not a handshake line, speaks a protocol past the ceiling, among others), not this one case, so that no case is recognised by its words. A process that could not be started keeps the system's own words ("fork/exec ...: exec format error"), and a timeout keeps go-plugin's fixed "timeout while waiting for plugin to start", which the old page shows and the window words itself;
- tested (`TestAProcessBeyondTheProtocolsTheHostOffersFailsWithTheHostsSentenceAndGoPluginsWordsGoToTheLogOnly`, protocols 17 and 400, six loads each): the cause is `failed` on every load, no `incompatible` member, no typed decision, `LastError` and the AppError detail are the same sentence word for word on every run and carry neither the number nor "Client versions", and the host log holds go-plugin's words with the number, once for each load. Seen red against the raw go-plugin error: the text differed on every run (`Client versions: [3 9 11 13 15 4 6 ...]`, then `[2 7 8 10 12 ...]`);
- the cost, said plainly: a developer who reads the old shell's page no longer sees go-plugin's hint ("This usually means the plugin was not compiled for this architecture ...") for a plugin that died at start; it is in the log, which the sentence names. The cure for the number is the producer's: S4-01 below, the plugin stating its protocol (and its SDK version) where the host reads it BEFORE go-plugin's check, which also lets the ceiling go.

The mock's rule (ch16 S88, S89, S135; `mock/shell-page-plugins.js`): health state **Update required** (incompatible), notice "**Update required.** This plugin was built for Omniview {max} or older; this is {HOST_VERSION}. Those words are about Omniview VERSIONS from the plugin's `max-ide-version`; the host decides on PROTOCOL numbers and does not know which Omniview version a build was for. So:

- the sentence is the one this step was given, "This plugin was built for a different version of Omniview.", with no direction (older or newer), followed by the two versions: "It uses plugin protocol 2; this Omniview accepts protocol 1." (a range reads "protocols 1 to 2");

## Backend catalog

- **S4-01, WIRE, an SDK candidate: the plugin states its protocol and its SDK version where the host reads them BEFORE go-plugin's check** (`pkg/v1/lifecycle`, `proto/v1/lifecycle/lifecycle.proto` `GetInfoResponse`, `pkg/sdk/plugin.go:34,244-248,294`; owner's ruling: a fact the producer knows is stated by the producer). Today the plugin's protocol is stated in exactly one place the host reads before it dials, go-plugin's handshake line (`core|app protocol|network|address|grpc|cert|mux`), and go-plugin checks it against what the host offered and refuses with a string when nothing matches: that is why the host offers 16 protocols (so go-plugin names the number) and why a plugin past the ceiling is `failed` with no number (option A above). `GetInfo` states more (`plugin_id`, the plugin's own `version`, `sdk_protocol_version`, `host_connections_version`) but only to a host that dials, and a refused plugin is never dialled (decision 3). Nothing states **the SDK module version, the resource wire version (`resourcev2.WireVersion`, 3), the digest, or the protocols the plugin can serve**. So the facts of a refusal stay numbers only, and the ceiling stays. The producer-side change, for the SDK step to choose the carrier of (all are read with no go-plugin and no dial): (a) `plugin.yaml` stamped by the SDK's packaging from the compiled constants (today `sdk_protocol_version` there overrides the compiled constant, no host reads it, and a manifest can lie: this step's fixture uses exactly that); (b) the binary's build info (`debug/buildinfo`, as `internal/devsdk/binary.go` does) for the SDK version, plus a release table the SDK's CI generates at tag time for the protocol it speaks; (c) a describe mode of the executable (a flag that prints `{sdk_version, plugin_protocol, supported_protocols, resource_wire_version, wire_digest}` and exits), run under a deadline and ended by the same hard kill the refusal uses. With any of them the host can decide `incompatible` BEFORE it starts the plugin's process, for every protocol and not only those up to a ceiling, and the ceiling, `handshakeError` for this case, and the kill of a started process can go.
- **S4-02, BLOCKER for "Update the plugin"** (`ui-next/plugins`, `service_wrapper.go:35`): the new window has no update action, so the incompatible page states facts only. Only hosts built after this step are typed; the marketplace's `min_ide_version` is what keeps a protocol-2 build away from them. A plugin more than 16 protocols ahead is untyped on every host.

- **S4-07, BLOCKER on the host's own next step, FOUND BY THE REVIEW OF #659 (origin/main too; not fixed here, it is not the same two lines)**: `ExternalBackend.Stop()` is go-plugin's `GRPCClient.Close()` and `ExternalBackend.Kill()` is go-plugin's `Kill()`, which closes the client the same way: each asks the plugin to shut down (`GRPCController.Shutdown`) with a context that has no deadline. Measured (`TestAnAcceptedPluginThatNeverAnswersShutdownBlocksStopAndKillUntilItsProcessEnds`: a protocol-1 plugin whose `Shutdown` never answers, which the loader accepts as it should): `Stop()` AND `Kill()` were each still blocked after **60 s on origin/main `77ce06f8` and on this change** (`S4_OBSERVE_STOP=60`); killing the child by pid released them. The callers are `shutdownBackend` (`loader.go`), from `shutdownPlugin`: the unload, the reload (so the retry and the recovery of a crash), the uninstall, the cleanup of a start that failed after the process started, and the host's own `Shutdown`; the call that was made does not return, so neither does the operation that made it. It is the same wait that held the load of a refused plugin before round 2, on the other side of an accepted plugin. The shape of the fix, for whoever owns the lifecycle: a deadline on the request, and on expiry the hard kill the refusal uses (`cmd.Process.Kill()`, reaped, socket removed); it needs the process handle go-plugin keeps private (`Client.runner`; `ReattachConfig().Pid` is the pid, with the pid-reuse care `pidTracker` already takes) and a decision on what a plugin that is killed mid-stop loses, so it is a change to every running plugin's stop, not a refusal's. The test is written to fail when either call is bounded, and is then to become the test of the bound.

- **S4-09, TANGENTIAL**: a plugin that is hard-killed leaves its socket behind (`plugin<N>`, in `PLUGIN_UNIX_SOCKET_DIR`, else the plugin's `TMPDIR`, else `/tmp`): only the plugin's own close of its listener removes it.
