**Real data through the entry.** The fixture's Items page has a Connections column whose cell calls `useConnections({ plugin: 'fixture-a-ok' })` from the shared entry. The check asserts the bundle's `useConnections` is the registry's, and that the cell leaves `reading` for `0 connections`: the call ran in the host's QueryClient and activity provider, went over the Wails runtime to the real Go host and came back. **What blocks more:** the seam check's plugins are a `plugin.yaml` and `assets/`; a connection list or Pods need a plugin backend (the Kubernetes plugin and a cluster, or a plugin binary built with the SDK; `e2e/fixtures/testbench` exists and I did not look into whether it could serve one), which is not cheap here. The real-cluster parity check (`.github/workflows/ui-next-pods.yml`, kind) reads real Pods through the scaffolding, which now imports only the curated entry; **it was not run locally** (no kind or kubectl run); its result is on the PR.

**The `422 /wails/runtime`: found.** With the check printing the request and the answer of every unexpected 4xx, each is a `POST /wails/runtime` for `github.com/omniviewdev/omniview/backend/pkg/activity.FrontendService.Attach`, `.Heartbeat` or `.Unsubscribe`, answered `{"message":"activity session unavailable","kind":"RuntimeError"}`. The message is `backend/pkg/activity/frontend.go:105` (`FrontendService.session`: the session id is unknown, or bound to another window than the caller's, `session.window != invocation.IdentityOf(window)`); Wails turns any binding error into HTTP 422 (`wails/v3@v3.1.0/pkg/application/transport_http.go:406`). The calls are the `ActivityProvider`'s session traffic (`packages/omniviewdev-runtime/src/activity/client.ts:53,66,68`), mounted by `PluginHostScreen`. It appears in server mode, and not on every run (the first run after my change had none; the four later runs had 3 to 4 per engine). **Inferred, not instrumented:** in server mode the caller's window is `GetBrowserWindow(clientId)` when the page's WebSocket has registered, and otherwise the first window (`wails/v3@v3.1.0/pkg/application/messageprocessor.go:137-155`); `Subscribe` fires at mount, before the socket registers, binds the session to the first window, and the later calls arrive as the browser window. A native window sends no client id, so this path would not apply there [also inferred]. **Not fixed:** the owner of the activity service and the Wails server transport decides (the session could bind to the client id, or the provider could wait for its socket); the check now prints each one with its call, so it cannot go unnoticed or be mistaken for the plugin seam.
