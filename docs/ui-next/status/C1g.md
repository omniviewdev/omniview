## The rule, and the one place

The shell says a connection by its NAME. It never builds a string a person reads from a route's connection parameter (the key); where no name is known it says no connection.

- **One place: `contributions.describe`** (`plugins/host/contributions.ts`) makes the FACE of every tab from a route, and every surface of the shell reads the face (the tab model's `identity`, `selectors` and the breadcrumb, which the strip, the tooltip, the accessible name and the status bar read). The face says the name where one is known: the scope's `label` is the name and its `id` stays the key (it tells places apart, `sameScope` and the tab's key use it, and it is never drawn); a crumb of the path and a facet that would be the key are the name, or are left out. `describeDetail` (the detail page's face, also read by the detail page's header) takes the name as an argument and builds nothing from the key but the scope's id and the route of its list crumb.
- **Where the name comes from** (`plugins/host/connectionName.ts`, new, the module the rule lives in):
  1. the scope lane the page published for the route (`FrameV1.scope`, the host's `frames`): the face the plugin MARKED as the connection (`role: 'connection'`), else, for a plugin built before the marker, the first face labelled Connection (case and white space do not matter). A lane that is not what the contract says names nothing (a plugin's data is not trusted);
  2. else the name this window has learned for that plugin and key (`ConnectionNames`, per window, nothing saved): learned from every lane `describe` reads, and from the faces of restored tabs that hold a name. That is how a tab whose page was never drawn in this window (a restored one, one opened in the background) says its connection;
  3. else none: the scope's label is empty, no crumb, no facet.
- **Where the rule is held** (`connectionName.test.ts`, "the files that read a route's connection parameter"): a source scan lists every file of `ui-next` that reads a route's `connection` parameter (`connectionOf(`, `params.connection`, `params?.connection`, `params['connection']`, a destructuring of `params`; the pattern has a test of its own), and the list is an allow-list with the reason of each reader (`contributions.ts` makes the face, `PluginHost.tsx` tells a hook which connection it is read in, `palette.ts` opens a place in the connection it was last used in, `panel.ts` addresses a route, `connectionName.ts` scrubs a saved face). A new reader fails the test until its author says why it is one; a file that stopped reading it fails the test too, so the list stays true. The shell's own surfaces are not on it: none of them reads the parameter.

## The marker on the contract, and the one line the Kubernetes plugin changes

`ShellScopeFace` (`shell/registration.ts`, re-exported by the contract) has a new optional member, `role?: 'connection'`: this face's text is the NAME of the connection the page is read in, whatever its label. It is minor on the terms the contract's head comment gives (`plugins/contract/v1.ts`, the paragraph "The connection marker (C1g)"): nothing is removed or renamed, a face with no `role` is what it was, every bundle written before it is admitted and drawn as before, and a host that predates it draws a marked face as a face.

- A lane that marks a face is read by the mark alone: a face labelled Connection beside it is not the connection, and a marked face with no text says no connection (the plugin said which face it is, and it has no name yet).
- The convention of C1f stays as the fallback, so a plugin built before the marker keeps working: with no marked face, the first face labelled Connection says the name. Both readings are tested (`connectionName.test.ts`, `contributions.test.ts`, the window's `PluginHost.names.test.tsx`, the palette's tests); the fixture plugin marks its face, the tests' shared plugin (`plugins/testing.ts`) is written as a plugin was before the marker, and the plugins probe's page marks a face labelled Cluster, which the label would not have found.
- **The one line the Kubernetes plugin changes:** in the scope lane its pages publish, the face labelled `Connection` (its text is the connection's display name) gains `role: 'connection'`: `{ label: 'Connection', icon: 'server', text: name, role: 'connection' }`. Nothing else in the plugin changes. It needs the contract types of a host that has this change (the plugin takes them from the host's `contract/v1`, at the pin its `ui-next` build uses); until it does, the label reads it, as it does now.

## Session restore

A tab restored from a saved session is drawn before its plugin has loaded: the plugin source answers a stand-in (`provisional`) and the tab keeps the face it was saved with. A build before C1g saved the key in that face (the scope's label, a crumb of the path, a facet), and so would have drawn it until the plugin loaded.

- **`Contributions.restoreFace`** (new, optional, `shell/core/tabs/types.ts`; guarded by `plugins.ts` like every host hook: one that throws or answers what is not a face leaves the face as saved). `persist.ts` `readTab` runs it on the saved face of EVERY restored tab, before the plugin is asked, so what the window learns from a saved face is there when the plugin describes the tab. `connectionName.ts` `restoredFace` is the host's: a saved face that holds the key loses it (the scope's label is the name this window knows, or empty; a crumb or a facet that is the key becomes the name, or is dropped), a saved face that holds a name keeps it and teaches it to the window, and a face that holds neither is returned as it came.
- `shell/core/tabs/face.ts` `scopeOf` keeps an explicit empty label empty (a scope with no label used to read as its id, which is the key): an absent label is still the id.
- What it comes to: while a plugin is loading, no tab draws a key (a tab of a session from an older build has the accessible name `Widgets`, of one from this build `Widgets, north`); when the plugin has loaded, the page on screen publishes its lane and every tab of that connection says the name, the ones whose pages were never drawn included. `PluginHost.names.test.tsx` runs it through the real window in both cases, scanning every text and every `aria-label`, `title`, `alt`, `placeholder` and tooltip attribute for the key.

A plugin whose key IS its name (`north`) reads like an unknown name in a saved face (the key and the name cannot be told apart), so its restored tab says nothing of the connection until its page has published; after that it says `north`.

## Review: what the six comments asked and what was done

4. **A page or resource label that equals the key** (a key `Widgets`, a path `[Acme, Widgets]`, a restored detail face with a `Widgets` list crumb and resource facet) was replaced by the name. 5. **A background tab earlier in the strip kept an empty name** when the tab whose page names the connection came later: the tab model describes the tabs in order in one pass, and the name was learned only when its own tab was described. `createContributions.subscribe` now subscribes a learner to the published frames before the tab model's listener (`Published.entries`, new, reads every frame), so every name is learned before any tab is described again. A test through the tab model holds it.
6. **A saved scope label is clipped to 24 characters** (`LIMITS.scopeLabel`) before `restoredFace` sees it, so a key longer than that arrived as `<prefix>…` and was learned as a name, and drawn. `isScopeKey` takes the key and the key clipped by the tab model's own `clip` for the key, and only those (a name `prod…` is not the clipped form of the key `production`); the clip and the limit are exported by the shell for it. Tests restore a 39-character key and a short one.
