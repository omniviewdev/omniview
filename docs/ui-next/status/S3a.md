## 1. Where the session is stored (evidence)

**The host's window service, slot `session`** (`backend/window`, bound as `WindowClient` in `@omniviewdev/runtime/api`). No Go was added.

- The OLD shell keeps its window state there: `ui/features/windows/windowState.ts:16-23` (`GetState(window name)` once at boot, before the first render), `:57-59` (`SaveState(name, slot, json)`), `:7` and `:62-75` (400 ms debounce), `:77-85` (flush on `beforeunload`, `WindowTabDragProvider.tsx:18`); the slots are `pages` (`workspaceController.ts:58,171`) and `drawer` (`BottomDrawer/provider.tsx:248,441`); the window is named by `Window.Name()` and checked against `WindowClient.List()` (`identity.ts:35-40`); a failed restore falls back to empty tabs (`ui/main.tsx` boot).
- The Go side: `backend/window/service.go:387` `GetState` (a window's slots), `:404` `SaveState` (one slot, any non-empty name, valid JSON: `:690`), persisted to `windows.json` in the state root (`persistence.go:14`, session path `main.go:872`), written atomically with mode 0600 (`persistence.go` `writeSessionFile`), flushed at shutdown, a corrupt FILE moved to `windows.json.bak` (`persistence.go:88-120`; whole file only, so a slot's own damage is for the session module).
- **Per window**: slots are keyed by window name. **Per channel**: the state root is (`feature-ui-next` has its own). **Survives a packaged restart natively**: it is the host's own file, flushed by the host.
- Run against the real host in server mode (browser, no cgo): `Window.Name` answered `main` with no connection header; `GetState("main")` answered `{}`; `SaveState` by id and by name was persisted to `home/.omniview-feature-ui-next/windows.json` (`{"windows":[],"states":{"main":{"session":...}}}`); SIGTERM left the slot on disk.
- **Rejected: `localStorage`.** Keyed by origin, which every window of every instance shares (a key per window and channel would be invented, and the state root's isolation would not apply); the web view writes it when it likes ([INFERENCE] a quit may find the last writes pending) where the window service is the host's own and flushes at shutdown; and the old shell keeps no window state there.
- The remote audit gateway denies `GetState`, `SaveState` and `ListStates` (`internal/auditgate/policy.json:215,218,225`): a view-only browser starts the shell empty and saves nothing, which is what an unreadable place does.
- **A page served to a browser** (server mode: development, the seam check) is named `browser-N` by the host, which the service does not know: the page keeps its session in the main window's slots (`resolveWindowName`). Every such tab of one instance therefore shares one session; that is not a product case.

## 2. The module and the rules

`ui-next/shell/session/` (its README is the guide): one versioned document `{ version, tabs, rail, panel }` (the tab model's and the panel model's own snapshots, each with its own version and `migrate`), saved by the shell's saver (400 ms after the last change; also written on `pagehide` and when the page is hidden, which covers the main window that hides when it closes), read before the window draws (`loadSession`, bounded by `READ_DEADLINE_MS`, never rejects).

- **Quarantine, never deleted**: not JSON, not a document, no whole-number version, a NEWER version, or a part that cannot be read: the text is kept whole as the slot `session.invalid.<time>` (a record: the text exactly, when, why), the window starts empty (a part that can be read is used), a console note says so, and the window then replaces `session` with a session of this version so the next start does not find it again. When it cannot be kept aside, nothing is ever written. A place that cannot be read (or does not answer in 2 s): empty window, a note, **no saving**.
- **A tab whose plugin has not loaded**: restored with its saved face (a `provisional` description, the stand-in the host makes for a loading plugin, never replaces a face a tab has: core/tabs, test first), its page the kit's loading state while the list of plugins is on its way, the plugin's page when it registers. When the list was read and the plugin is not in it: the kit's failure notice "This plugin is not installed, or is turned off." under the plugin's saved name, and the tab stays. A failed list: the notice with Retry.
- **Panel sessions** come back `ended` (the panel model's cause), never running; the panel does not open because sessions were restored (S116), and comes back as it was when it held none; height and tool are kept.
  - **2026-11-24, T2d (decision A23): superseded for the open flag, which comes back as it was left.** S116 as written says "Sessions restored at startup, adopted from another window, or re-created by Retry do not open it (today's quiet-tab rule)", and why: "a restored terminal must not cover the page". That is about a SESSION opening the panel. It does not say that the person's own saved panel (S103: `open`, height, tool, the session of each tool) is to be dropped, and it was written when every restored session was dead; S3a read it as "a panel that holds sessions stays closed". Since T2b a terminal is alive again after a reload, and one behind a closed panel waited unseen, though VS Code and JetBrains both restore the panel's visibility and the active terminal across a reload. So the panel now comes back open when it was open and closed when it was closed, with its tool and the session of each tool. What stays: every restored session is `ended` with the panel model's cause until the Terminal tool attaches it, a restored session opens no panel that is closed and is never revealed, focused or moved (the registry's `reveal: false`), and a session the person starts opens the panel.
- **Start-up rule** (replaces "first plugin by order"): `Contributions.home()` for the window is gone from the host (`firstPlugin`, `holdHome`, `release` deleted); a saved session brings its tabs back, and with none the window is the empty window (decision A17). The tab model's own generic rule (an empty window opens a home when its host offers one) stays: its tests are the model's, and the host offers none.
- **The rail** waits for every plugin to settle once (`held`: its track and the sidebar reserved empty, no lane), then chooses; the restored rail choice stands until the tab on screen changes.
- Host: `PluginHost` takes `session`; `PluginHostScreen` reads it through `loadSession(windowStorage(...))` beside the inventory and draws the host once it has it.

## 2b. A plugin that did not load, from an empty window (CI finding, `Pods cluster check`)

The product question: the empty window already LISTED a plugin that did not load (its row says "Did not load"), but the rail drew nothing for it. It now has an entry (`failedOf`, `ShellRailEntry.problem`): the error glyph, named `<name>, did not load`, the cause in its tip, after the plugins that contribute; it has no sidebar, so choosing it opens the plugin's page in a tab (the named failure and its Retry) and the current entry and sidebar stay. Tests first (shell, host), the seam check asserts the four entries and the tip and the opened page, and the bundle-absent control asserts the rail entry, its tip and the page it opens.

## 3. What is deliberately NOT restored (and why)

Scroll positions, the selection, the search and filters of a page, expanded rows: a page's state is plain data the model keeps for the window's life and never saves (S32), a saved offset is wrong after the data changed and races the page's first load, and a plugin's page owns its own state. The sidebar's open groups (a component's state, not a model's). The closed-tab list (Reopen closed tab), a tab's unsaved flag and attention cue (they mean "now"), reveal requests. Which pages are mounted (only the tab on screen; the others when shown). The output and the state of a panel session. The main window's size and position (the Go side keeps bounds only for the other windows).
