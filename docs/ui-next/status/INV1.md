## Who is affected (read this first)

**SERVER mode only** (`-tags server`: the browser-hosted build the seam, the probes and the agents' browser verification use). The native app is **believed unaffected, by reading the code, and was not run**: a native call carries the window's id (`x-wails-window-id`) and no events socket exists (`websocket_server.go`: `GetBrowserWindow` returns nil when there is no broadcaster), so the identity a session is bound to never changes. What a user of server mode lost before the fix: for up to about 10 s after a page load the page had no valid producer capability, so toasts (`notify` / `PublishMessage`) and task reports (`BeginTask`, `ReportTask`, `FinishTask`) were refused with `activity session unavailable` (measured: refused at +3 s, accepted after the provider re-subscribed at +10 s), and in one order of events the view was not attached until the provider reconnected. The provider recovered by itself.

## The defect

`ActivityProvider` subscribes on first paint. In server mode stock Wails v3.1.0 names a call's window by the page's events WebSocket (`messageprocessor.go:138-142`, `websocket_server.go:84-93`): a call that arrives before that socket is accepted resolves to `windows[0]`, the host's main window, and once the socket is accepted the same page's calls resolve to a new `BrowserWindow` (another id and Go type). `FrontendService.session()` (`backend/pkg/activity/frontend.go:104`) binds a session to `invocation.IdentityOf(window)`, so a session made before the socket was refused afterwards (`422 activity session unavailable`: `Attach`, `Heartbeat`, `Unsubscribe`, producer calls). Measured on macOS arm64 (3 Chromium seam runs and 1 WebKit seam run show nothing, because their three calls all went out before the socket and answered 200; a bare page: Chromium 6 of 6 loads, WebKit 4 of 6; the socket delayed 1.5 s: deterministic in both). Linux CI shows it in Chromium only because Chromium there sends the first call before the socket and WebKit does not. A reload makes a new client id and a new socket, so it races again.

## Decision: hold the call (chosen) against binding to the page's client id (evaluated)

**The alternative:** bind the session's ownership check to the page's client id (`x-wails-client-id`, sent on every call, before and after the socket) in server mode and leave native on the window identity.

- *Does it weaken the check?* The check (`frontend.go:28-31`) keeps document reloads and different webviews from renewing each other's report-only work; the session id is also an unguessable capability. In server mode the client id is chosen by the page (`nanoid()`, `@wailsio/runtime` `runtime.js:53`) and any script of that page, or any local HTTP client, can send any value; but after the socket is accepted Wails already derives the server-mode window from that same id, so binding to it is no weaker than the rule that applies to every call after the socket, and it is stronger than the rule before it (all pages share the main window's identity). Wails' own comment (`stream_transport.go:137`) says client ids "are not a capability". So: not a weakening of what the check enforces in server mode, but a second rule beside the native one.
- *Does native keep its rule?* Yes, if the id reaches the service only through something the server build adds.
- *What it needs:* the id is not in the call's context (the context holds only `application.WindowKey`, `messageprocessor_call.go:136`). It needs the same asset-chain middleware as the hold fix, to put the id into the request context; a new identity type in `invocation`; a change in `session()` and in `FrontendService.Subscribe`; and, to remove the race for the other window-bound services (`invocation.WindowRealm` scopes: source observations and operation handles, `plugin/resource/graph_observation.go:124`, `plugin/metric/finite_service.go:32`, `extensiondiagnostics/host`), the same change in each of them. Done for the activity service alone the others keep the gap.
- *What it would also fix:* the socket's **reconnect** (see below).

**Chosen: the hold, because** it removes the race where it is made (Wails resolves the call before the socket exists), for every window-bound service at once, with one middleware, no change to any service's ownership rule (rule 9: nothing about consent, pinning, epoch fencing or call binding is touched) and no new notion of identity to review. Cost: a bounded wait in server mode only. The page-identity binding is the better long-term shape and is recorded under "Backend catalog" below, with what it would have to change.

### The hold, and its bound

`EventsSocketMiddleware` (`internal/hostruntime`, server build; the native build returns nil) is in the asset chain inside the development policy (a refused request is never held). It holds a `POST` that carries `x-wails-client-id` **and** an `Origin` header (a browser document sends both; the seam's own `tryBound`, curl and the dev gateway send no `Origin` and are never held) until `application.GetBrowserWindow(clientID)` is non-nil, polling every 5 ms.

- **Why 1 s.** Measured here, the socket is registered 1 to 20 ms after the page's first call in both engines (`/tmp/inv1/repro.mjs`, 20+ loads, load average 26 to 78); a second is about fifty times the largest gap and is also the most a single call can lose.
- **When the socket never registers** (blocked, refused, a client that is not a page): after 1 s the call **proceeds**, as it did before; it is never refused. The page then keeps one identity for all its calls (the main window's), so its sessions stay valid, which is what a refusal would break. Tested (`TestEventsSocketGivesUpAfterTheBoundAndServesTheCall`).
- **When the caller goes away while held:** the call is dropped, not served (`TestEventsSocketDropsACallWhoseCallerWentAwayWhileHeld`).
- **Not held:** no `Origin`, no client id, not a POST, a call that **names its window** (`x-wails-window-name` or `x-wails-window-id`), or the socket is already up (tests). The last-but-one was added after the first push: the application e2e suite (`e2e/tests/fixtures/wails.ts`, `bindWindowContext`) stands in for a native window by rewriting every runtime call to the fixed client id `e2e-native-window-context` plus `x-wails-window-name`; that id never registers a socket, so the hold made every call of that page wait the full second and the Settings page of `Navigation › header opens one retained Settings window` did not draw its search box within 5 s (`PR Validation`, `e2e-application`, run 44888784609). It is also the live proof of what a client that sends an `Origin` and a client id but never opens a socket costs under this fix: one second per call.
- **A socket that drops and returns** (Wails' `custom.js` reconnects after 1 s): calls made in the gap are held up to 1 s each, then proceed; see the backend catalog entry for what is **not** fixed.

## What changed in the seam (the hardening)

`seam.check.mjs`: every request any page of the run makes that answers 4xx or 5xx is recorded with the phase it happened in (`watchRequests`, wrapped round `browser.newPage` so the pages of scenarios n and p are covered too), and each phase (`phase(...)`: healthy, rail, panel, logs, palette, twins, providers, kept, identity, toasts, session, process, failed-load) fails unless each failure is in `RUNTIME_ALLOW`, each entry with its reason and the phases it is expected in:

| Entry | Phases | Reason |
|---|---|---|
| `400 /_/plugins/fixture-d-missing/assets/entry.js` | all | a plugin with no bundle is a named state (scenario e); every page load asks for each installed plugin's bundle |
| `422` body `omniview:plugin/load-failed` | `process`, `failed-load` | n and p take the plugin's process down or make its load fail; the page asks for its connections and the host answers with the load failure |

The check used to print the 4xx it saw in scenario a to f and not assert; the old `rest` line and the `failedDetails` print are gone. Console errors: the browser's `Failed to load resource` line is the same event as the failed response and is not counted twice; any other console error stays each scenario's own assertion (they already assert their page errors).

**Negative control** `runtime-4xx` (in `CONTROLS`, so the workflow runs it in both engines with no change): a page that loads clean (asserted first, in words the control's pattern does not match), then one 422 planted from the page (`FrontendService.Heartbeat` with a session the host never issued, with the page's client id); the assertion of the phase must fail with ITS words, the planted failure is forgotten and the assertion must pass again. `SEAM_REMOVE=runtime-4xx` leaves the assertion out and the planted 422 must pass undetected.

## Backend catalog

- **TANGENTIAL** `backend/pkg/invocation/window_realm.go:22` (`IdentityOf`), used by `backend/pkg/activity/frontend.go:104`, `plugin/resource/graph_observation.go:124`, `plugin/metric/finite_service.go:32`: in server mode a **reconnect of the events socket** gives the page a new `BrowserWindow` (new id), so every window-bound capability issued before it is refused (measured: the socket's server side closed at 2.0 s, `custom.js` reconnected at 3.0 s, the next heartbeat at 10 s answered 422 `activity session unavailable` and the provider re-subscribed). The hold does not touch this. The fix is the alternative above: a page identity (the client id) carried in the call's context by the server build's middleware and used by `IdentityOf`'s callers in server mode, with native unchanged; wider (every window-bound service) and needs the ownership review of the alternative above. Interim: the provider's heartbeat recovers within 10 s. Upstream, Wails should hold or refuse a call whose client id has no socket instead of giving it to `windows[0]`. Not run on native.
- Inference, not run: two browser tabs of one server-mode host shared the main window's identity before the first socket opened, so each could renew the other's session; the hold closes that gap too.
