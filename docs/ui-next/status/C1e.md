## The lead's rulings on this step, and where each is held

1. `aliases` in the model, not a raised `keywords` tier: accepted; the reason is in `ui-next/shell/core/palette/README.md` ("Aliases are not keywords (C1e), and why") and in the first bullet below.
2. Go-to rows read `<connection> · <group>`, or `<group>` under a scope chip, and the plugin's name only with neither: accepted, built.
3. Two rows that would read alike get the plugin's name, on exactly those rows, in the text drawn and in the accessible name: built (third bullet below), tested with the seam's two fixture copies.
4. A top-level page with no group reads the connection alone; the host invents no group. **Recorded here as asked:** the mock says `Cluster` on such a row. A plugin that wants `Cluster` (or any word) there needs a group of its own for those pages, or a label of its own on the node; the contract has neither, and this step adds neither. A later contract question.
5. Before the push: the mutation check, the quiet-machine runs, the flake rates, the screenshot's theme, the rebase and the shard table: under Verification.

## What the mock says, and what the host now does

- **Ranking (ch16 SE1, `shell-search.js` header):** "inside the list an exact or prefix match on an object name outranks a substring or loose match in a command or page title". The mock's code weighs title 6, keywords 3, context 1 and has NO aliases (nor short names); its keyword weights are tested as the oracle (`match.test.ts`). **The mock agrees with the rule for a NAME and is silent on keywords**, so the rule is implemented for a new field of the model, `aliases` (`Candidate.aliases`, space-separated): a word that is a whole alias scores 100 x 6 (an exact title match), a word an alias begins with 88 x 6 (a title prefix); any other match of an alias is a keyword's (x 3); never loose; never drawn (the mock draws a keyword nowhere: "a word that matched only a keyword is drawn nowhere"; nothing is invented). Ties keep the deterministic tie-break (order, shorter title, title and key by code unit). **Why not raise `keywords` as the assignment worded it:** the host's own keywords carry the plugin's name (a tab's keywords are `<plugin> <page>`); with the tier on them, typing a plugin's name makes its open tab tie with its home row (600 each) and the Tabs section, which leads equal sections, would put the tab ahead of the home: a plain Enter would activate a tab where the mock opens the home. Aliases are explicit names a plugin chose. `ns` before: DaemonSets 348, EndpointSlices 234, Namespaces 228 (the keyword); now Namespaces 600 (`rank.test.ts` has it with neutral titles).
- **Row text (mock `connectionRows`, `shell-kubernetes.js:610-632`):** `where = text => (label ? `${connectionId} · ${text}` : text)`, `label` true only when the palette offers the kinds of more than one connection (`targets.length > 1`: no scope chip and several connected connections), so with one connection or a scope chip a row reads `Workloads`; the screenshot (two connections) reads `prod-eu · Workloads`. The plugin's name is never on a grouped row (`Connections` says the plugin's name only because it has no group). **Host now:** context = the connection the page opens in (the tab on screen's when the plugin is on screen, else the one the plugin was last used in) unless a scope chip narrows the palette (it says it), then the groups (`Workloads`, `Inventory › Storage`): `<connection> · <group>`, or `<group>` under a chip. A page that sits in no group reads the connection alone, chip or none (`prod-eu`), and the plugin's name when there is no connection either. The host makes up no group for it: the mock's `Cluster` is a word only the plugin knows (ruling 4). The plugin's name stays a word the row is found by. **What changed:** rows read `<scope> · <group>` / `<group>` where they read `<Plugin> · <Group>` (with a connection `north · Things`).
- **Two rows that would read alike (ruling 3):** the same title and the same words under it, of two plugins of two names (a same-titled page in a same-named group with no connection; or the same connection): the plugin's name goes first on exactly those rows (`Acme · Things`; with a connection `Acme · north · Things`), in the text drawn and in the accessible name, as a session tab's scope is said only when two tabs read alike. It is judged on the rows the source lists, never on the query. A name does not tell apart two plugins that declare one name, nor two pages of one plugin, so such rows read as they did. Tests: `host/palette.test.ts` ("two rows that would read alike", with a second plugin of its own name, and the cases that must not be told apart) and `PluginHost.palette.test.tsx` (through the window); the seam, in both engines: scenario `j` keeps the two fixture copies at one declared name (they are one source, and the other scenarios need rows that read alike to test the order told by ids), where both read `Page: Crash, Things`, and scenario `j2` (`checkTwins`) asks the page, before the bundles load, for the name each copy's rail entry says (`window.__fixtureOwnNames`, read by the fixture's entry), where they read `Seam Fixture · Things` and `Seam Fixture Copy · Things`.
- **One route, one row (`gotoCandidates` `seen`):** a leaf the sidebar names twice is one row (first label and context, the keywords of both); the leaf that opens the plugin's home is not a row, its keywords go to the home row. **Tabs and Go to keep both** (`tabCandidates` is another source; the screenshot shows Pods under Tabs and again under Go to): `host/palette.test.ts` holds it.

## For the Kubernetes plugin (the step after this one, mechanical)

1. Drop the Kinds provider: delete `ui/src/palette/kinds.ts`, `known.ts`, `useKnownKinds.ts` (with their tests), `paletteV1` in `entry.ts` and the `useKnownKinds(plugin, connection)` call in `ui/src/sidebar/useSidebarNodes.ts`. Keep `shortNames.ts` and its discovery test. **Which hosts keep kind search:** a host that predates this change loads the plugin (admission is tested both ways) and ignores the `keywords` member, so once the provider is gone it finds the plugin's pages by their labels but no longer by a Kind or a short name (`Pod`, `po`). The plugin may therefore drop the provider only where every host it supports reads sidebar keywords: either the plugin's pin in this repository (`KUBERNETES_PLUGIN_REF`, step 4) moves with the plugin, so the host this repository builds always has this change when it loads the plugin it pins, or the plugin keeps the provider as a fallback until its older hosts are gone. **A decision for the lead; this PR takes neither** (it changes nothing in the plugin).
2. Put the words on the nodes: in `ui/src/kinds/index.ts`, `entryOf` becomes `({ id: kind.page, label: kind.nouns.other, icon: kind.tile.icon, count: counts?.get(kind.page) ?? null, keywords: [kind.kind, ...(SHORT_NAMES[kind.type] ?? [])] })` (the Kind, `Pod`, then `po`: one word each, at most 8, no `list`: as an alias it would be an exact name of every kind). The skeleton and the hook's nodes both come from `entryOf`. Vendor the contract (`hack/vendor-host.sh`) first so `keywords` type-checks.
3. What the rows read: opened from a Kubernetes tab (palette narrowed to the plugin and its connection) `Workloads`, `Config`, ...; narrowed to the plugin alone or unnarrowed `<connection> · Workloads`. The top-level Nodes and Namespaces have no group, so they read the connection alone (`prod-eu`), chip or none, where the mock says `Cluster` (ruling 4: a group or a label of its own on those pages is a later contract question). Pods is the plugin's home, so it is the home row (`Kubernetes`, context `Pods`), which carries `po`; `ns`, `svc`, `sts`, `ds`, `sa`, `sc` put their page first. Resource search (`Kubernetes · Resources`) stays a later provider.
4. The pin (`KUBERNETES_PLUGIN_REF`) needs a bump after both this PR and the plugin PR merge.
