## 2. The rule

A session belongs to the window that opened it. A local terminal is held by the terminal manager (`Manager.Authorize`): the window that opened it, or the page that attached it with its key (T2-go); a terminal that is detached belongs to nobody until a page attaches it. A session of a plugin is held by the window that created it, as the controller's session index records it.

- **Not found, not forbidden.** A window that does not hold a session is told what is told of an id that never was. A call that comes from no window holds nothing.
- **A plugin session outlives its window and then belongs to nobody** (`ReleaseOwnedTerminals` orphans it). Any window lists it, reads its facts, ends it (`CloseSession`) and the one that attaches it holds it from then on; it can do nothing else with it (no input, no resize) until it attaches. Ending it is allowed because attaching is, and because a window that is told a session is there and then told it is not found is a contract that lies: the e2e teardown (a client that is not the page that made the session) lists the sessions a retired page left and ends each one, and CI failed on it (`CloseSession failed: 422 session/not-found`) before this. That keeps the legacy restore (`planDrawerRestore`: the main window adopts the sessions that survived a reload; in server mode the reloaded page is a NEW window, so only "attach claims an orphan" finds them). A session made by a call that came from no window is an orphan from the start. Sessions of a window that is still live are not the e2e client's to list or end (it is another window): the e2e `appPage` fixture closes what its page opened as that page (`closePageSessions`: the client id is read from the page, as the seam runner does), and the client `e2e` finds what no window holds.
- **An offer moves a session between live windows** (`OfferSession`, 60 s, used once). The legacy UI moves a terminal tab in three ways and in all of them the target window attaches the session when its drawer mounts the tab, while the source still holds it: the menu "Move to window", the tear-off to a new window, and the drag to another window. The source offers first: `moveTabToWindow` and `moveTabToNewWindow` before the move, and the drag at the DROP (`createWailsTabDragTransport().drop`, in line with the drag's calls, right before `EndDrag`, which is when the target gets the drop and attaches): an offer made as the drag began was gone after a minute for a long drag and was left open by every drag that was cancelled. A failed offer stops the move (the session ended, or this window does not hold it): the source tab stays, the menu and the tear-off tell the person through `showAppError`, and the drag is cancelled (`CancelDrag`) and resolves `null`. A tab whose status is `expired` has no session and moves as before. An offer is a right to attach and no access: nobody else can use the session meanwhile, only its holder offers it, and the window that lost the session is told on `DETACHED` (T2-go). The old window's late `DetachSession` (the legacy "handed off" mark exists to avoid it) is now refused, which is harmless. **A move that does not happen takes the offer back** (`RevokeSession`: only the window that holds the session, none open is no error, the same words as an id that never was for any other window): the drag revokes when `EndDrag` rejects or no window accepted the tab, and the menu and the tear-off revoke in the `catch` of a move that failed after the offer; a failed revoke is logged and swallowed, because the offer runs out by itself, **after `terminal.OfferTTL` (60 s)**, and is used once. The binding is denied to the audit browser and pinned in `TestDangerousMethodsStayDenied`.
- **A tombstone is dismissed by the window that attached it.** T2-go says `CloseSession` dismisses the end of a terminal that ended while detached; at the exec lane it could not (the terminal's CLOSE had taken it out of the index, so the call was not found before it reached the manager). #675 made the call reach the manager; this adds the owner: the manager keeps the end for the window that attached it (or that held the terminal when it ended), and only that window dismisses it. The test of #675 for the same call is folded into the ownership version (`TestTheEndOfATerminalThatEndedWhileDetachedIsDismissedBy...`), which also ends the detached shell by a signal from the test instead of a sleep that races the detach.
- **A right is read and used in one step** (the three races of CodeRabbit on #677, each with a forced-order test for both orders). (a) *Publication*: a window that retires while the plugin makes its session found nothing to orphan, and the session was then recorded as the retired window's; the session is guarded from before the window is admitted (`GuardSessionCreate`, `createGuard`): a retirement (`orphanSessionsOf`) marks every guard of the window under `c.mu`, and the session is recorded as no window's when its guard was marked (a retirement before the admission is refused by the realm; after it, until the session is recorded, it is the guard's; the wrapper subscribes to the realm's retirement signal before it admits the window, because one that fell between the two on the wrapper's first call was lost to the guard: CodeRabbit on #677, `TestASessionIsLeftToNoWindowWhenItsWindowRetiresRightAfterItsAdmissionOnTheFirstCall`). The first version asked the realm again after the plugin answered; the realm forgets a closed window after a minute (`window_realm.go`) and a plugin has no deadline, so a slow create re-admitted a dead window and stranded the session (CodeRabbit on #677). (b) *Close*: `CloseSession` checked the window on a copy of the record and asked the plugin later (the lookup of the connection sits between): the right is read again in `commitClose`, under `c.mu`, where the record is marked as being closed, and `claimSession` refuses a session whose end is decided (a close that the plugin answered with an error stays decided: the SDK's close that times out still ends the session). A local terminal and the end a terminal leaves go through `Manager.CloseOwned`: the window is checked and the fate is set under the session's lock, `dismissEnded` forgets an end under `m.mu` only for the window that holds it, and `Attach` hands an end over only while it is still kept. (c) *Retirement*: `release` set nothing, so a window that claimed an offered terminal between the decision to end it and the end had it ended by the window that retired; `release` now sets the fate under the lock that reads the owner and `Claim` does not take a terminal whose end is decided. The manager's offers read its clock (a test moves it; the sleeps of the offer and of the refused write are gone). The tests hold a call at the instant the other must land: `Manager.beforeEnd` and `Manager.beforeTransfer` (fields that no one sets but a test), and, in the exec lane, the plugin's create and close and the lookup of the connection, which exist already.
- **Every call that names a terminal by its id decides and acts in one step** (decided with the lead after the first review: it was "check, then act" for the calls below, and the window that gave the terminal away a moment earlier could still land one). `Manager.WriteOwned`, `ResizeOwned`, `AckOwned`, `BusyOwned`, `CwdOwned`, `GetOwned`, `DetachOwned` and `AttachOwned` read who holds the terminal and act under the session's lock (`withHeld`; the order of the locks stays `emitMu`, `Manager.mu`, `mu`, `outMu`, `flow`). Input and resizes are decided by their admission to the terminal's input queue: the hand-over is under the lock, the wait for the shell is not, so the input of the window that claims the terminal follows what the window that gave it away had in line and nothing the old window sends after the claim reaches the shell. `AttachOwned` claims (the offer), resets the credit and marks the terminal attached in one step. A session of a plugin: the input is sent under `c.mu` in slices of 20 ms (`sendHeld`), and the window is checked again after each slice, so a claim is not held up by a plugin that takes no input and the input of a window that no longer holds the session is refused, not sent. The calls the plugin answers over RPC (resize, detach, the facts, attach) are fenced by the session's gate (`sessionIndex.gate`, `gated`): a call holds it, shared, from its check of the window to the plugin's answer, and a claim that takes the session from another window takes it exclusively, so it waits for the call that was on its way (the check is made again with the gate held, of the record as it is, and a call that comes after the claim is refused). The gate comes before `c.mu`; a plugin that does not answer holds up the claims of that one session and of no other. The exec controller calls nothing else of the terminal manager by a bare id.
- **A session whose end is decided is no one's to list, read or end** (CodeRabbit on #677): `claimable` and so `listable`, `visible` (`GetSession`) and the second check of `commitClose` leave out a session of a plugin that is being closed, or whose close the plugin answered with an error (the end stays decided). The window that holds it keeps listing and using it until its CLOSE comes.
- **Acknowledging an ended session** is told only to the window that had it (the manager's memory of ended sessions keeps the owner).

Code: `backend/pkg/terminal/ownership.go` (`Authorize`, `Claim`, `Offer`, `Revoke`, `SessionsOf`, `withHeld` and the `*Owned` calls), `backend/pkg/plugin/exec/ownership.go` (`holds`, `visible`, `claimable`, `listable`, `claimSession`, `OfferSession`, `RevokeSession`, `GuardSessionCreate`, `orphanSessionsOf`, `sendHeld`).

## 3. What a plugin UI in the same page can still do

**Everything its page can.** A window is the only boundary this change draws. A plugin's UI is JavaScript that runs inside the page of a window (`importPlugin.ts` `import()`s the bundle into it), and its calls reach the host through the same Wails runtime with that window's identity: it holds what the page holds, including the local shell (`CreateTerminal`, then `WriteTerminal` on its own terminal), and the key the page keeps in `sessionStorage` (T2-go). Another window's sessions are out of its reach; its own page's are not. This is decision R10 (plugins are trusted code in the host realm), not something this change weakens.

**Is the boundary "do not export the exec calls to the plugin shims"? No, and it is not built.** Checked:

- Nothing shipped imports `ExecClient` from a plugin: the Kubernetes plugin UI (`omniview-plugin-kubernetes` at `d06f24e`) imports `ResourceClient`, `MetricClient` and `DataClient` from `@omniviewdev/runtime/api` and opens its shells through the host's `createExecSession` (the drawer bridge); the containers plugin imports none.
- But taking a name out of `packages/omniviewdev-vite-plugin/shims/_omniviewdev__runtime__api.mjs` only changes what a plugin BUILD may name. At run time a plugin gets the whole module: `window.__OMNIVIEW_SHARED__['@omniviewdev/runtime/api']` in dev (`devSharedExporter.ts`), the `shared://` import map in production (`shared_dependencies.ts`), and the raw Wails runtime (`window._wails`, or a POST to `/wails/runtime` by method id) needs no module at all. A shim edit would look like a boundary and would not be one.
- The real boundary is a separate realm for plugin UI (a sandboxed frame or worker with a message API) whose calls the host tags with the PLUGIN's identity and checks per plugin (the `invocation` package already has host-issued principals). That is a design of its own (R10 puts hostile plugin code out of scope); until it exists, a plugin UI and its page are one trust domain.

## 4. Why the events are still broadcast, and what would fix it

The output, `CLOSE` and `DETACHED` events of a session go to every window by id (and, in server mode, to every connected page). Read in `wails/v3@v3.1.0/pkg/application`:

- Server mode: `WebSocketBroadcaster.DispatchWailsEvent` sends every event to every client (`websocket_server.go:150`); `BrowserWindow.DispatchWailsEvent` is a no-op ("dispatched via WebSocket broadcast, not per-window", `browser_window.go:38`) and `BrowserWindow.EmitEvent` is an app-wide `Event.Emit` (`:42`). There is no per-client send, and `wailsEventListeners` is unexported.
- Native: `WebviewWindow.EmitEvent` is an app-wide emit with a sender (`webview_window.go:260`). `WebviewWindow.DispatchWailsEvent` reaches one window, but it serializes and runs JS on the main thread (`ExecJS`, as `transport_event_ipc.go` warns), so calling it from a terminal's reader goroutine would pace the shell by the UI thread; and no native window can be run here to prove that nothing regresses in the shipped app.

What this change does about it: a window that learns an id from an event (it can) still cannot attach, type into, resize, close or read the facts of that session. It can read the session's live output while the event bus carries it. To close that: (a) a Wails change (an addressed emit and a per-client send), or (b) a host-owned per-window event route, or (c) a pull stream (`ReadOutput(id, offset)`) with a content-free notification. (a) is the smallest. Not built.

This change does not touch what it reads; it is stated and not hidden.
- An offer is open for 60 s to ANY window that attaches the session (not to a named target: a tear-off does not know its target's identity when it offers). It is used once. It is taken back by `RevokeSession` when the move does not happen, and by nothing else before the 60 s run out; a revoke that fails (the host is unreachable) leaves it to run out.
- A plugin UI in the page holds what the page holds (3).
- The logs service's bare-id calls (`LogsClient.GetSession`, `CloseSession`, `ListSessions`) are not changed: they are not terminal or exec bindings.
- Windows: `go vet` only; no session exists there.
- **The gate makes a claim wait for the plugin**: the claim of a session of a plugin by another window (an offer that was used, or an orphan adopted) waits for the calls to the plugin that were on their way for the window that held it, and a plugin that hangs on a resize holds up the claims of that one session (the claimer's own attach would wait for the same plugin). `ListSessions` of a plugin and the recorded facts are read, not fenced (see below).
- **Sequenced input that waits ahead of its number is applied in sequence order**, as the terminal's input queue orders it (the queue is the terminal's, not the page's): a call of the window that gave the terminal away that was taken in while it held it is applied in its place, and the numbers a window that never sent the missing ones waits for are given up after the queue's gap wait. Nothing that the old window sends after the claim is taken in.
- **Reads of facts are not part of the step**: the listing and `GetSession` of a session of a plugin read the record, and a session can change hands the instant after; what a window is shown is what it held or could attach when it asked.

## 7. Decisions for the lead

1. **Orphans are adoptable by any window.** It keeps the legacy restore after a server-mode reload (a new window identity); the cost is that a plugin session whose window left is open to the first window that attaches it.
2. **Offers are open, not addressed, for a minute.** The alternative (an offer to a named window) needs the target's identity before it exists (tear-off) and a way to resolve a window name in the exec lane.
3. **The events need a Wails change** (or a host event route); say which, and I build it.
4. **The plugin boundary is a design, not a shim edit** (3).
5. **CLOSED (decided with the lead): the other bare-id calls decide and act in one step** (`WriteTerminal`, `ResizeTerminal`, `AckTerminal`, `IsBusy`, `GetCwd`, `DetachSession`, `AttachSession`, `GetSession`, `WriteSession`, `ResizeSession`): see 2. It is not a generation number carried from the check to the use but the check and the use under one lock, and for input the admission to the input queue, which orders the new holder's input after what was taken in. The calls to a plugin are fenced by the session's gate (2).
6. **A close that the plugin answered with an error stays decided** (the SDK's close that times out still ends the session, `TestASessionTheHostClosedLeavesNoRecordWhenItsCloseComes`): the session is not handed to another window meanwhile. If the plugin's close can fail and leave the session alive for good, its window can still use it and move it no more.
7. **An offer is taken back by `RevokeSession` and runs out after `terminal.OfferTTL` (60 s)** (decided with the lead): the drag revokes at a refused or failed drop, the menu and the tear-off in the `catch` of a move that failed after the offer. The binding is denied in the audit policy and pinned.
8. **A session whose end is decided is no one's** (see 2): it is not listed to a window that does not hold it. If the close of a plugin can fail and leave the session alive for good, the session is out of every list but its window's.
