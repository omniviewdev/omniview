## What changed

1. **One job became five.** The job `probes` ("Kit probes", one VM, 16 probe steps one after another, 26 to 34 minutes) is now the matrix job `shard` (`Kit probes shard 1` to `5`, `fail-fast: false`, 30 minutes each) and a job `probes` that keeps the name `Kit probes`. Each shard does the setup the single job did (checkout, Node, pnpm, Task, store cache, `pnpm install`, `task packages`, browser cache and the bounded, retried install of #557), builds `ui-next` into `$PROBE_DIST` only when one of its probes reads it, and runs its probes.
2. **The shard table is `scripts/ci/probe-shards.mjs`.** A unit is a step of the old workflow: its name (verbatim), the probe script, the env it had (`DIST`, `REPORT`, `FONT_DELAY_MS=40` on the two palette steps) and, for the negative-control steps, the list of controls (one run each with `NEGATIVE_CONTROL` set, as the shell loops did). A probe and its controls are in one shard (the check enforces it). The old step comments went into the table next to the unit they describe.
3. **The runner runs every probe of a shard, even after one fails.** The old job stopped at its first failing step (the push of main at `e32cd86e` ran one probe of 16 because the loader-timing check of the parts probe failed; the other 15 were skipped). A shard now runs all its units, folds each in a log group, prints an `::error` line naming the failed probe and the shard, then the last 40 lines of its output outside the group, and writes the seconds of every probe to the job summary. It exits 1 when any run failed. The verdict is the one the steps had: a probe passes when it exits 0 (the negative controls exit 0 when they see what they perturb).
4. **`Kit probes` is the aggregating job** (`needs: shard`, `if: ${{ !cancelled() }}`, one step, no checkout): green only when the matrix result is `success`. A shard that failed, timed out (cancelled) or was skipped fails it, and so does an empty or unknown result. The matrix result is one word for all five shards, so the step names the ones that did not succeed from this run attempt's job list (`gh api .../actions/runs/$ID/attempts/$N/jobs`, `actions: read` on that job only): `::error::Kit probes shard 3 finished as failure: <url>`. If the list cannot be read the check is still red and says so. A cancelled run (a newer push) does not run it, as in `UI checks` of N24-U1.
5. **Completeness** (below), and the matrix line `shard: [1, 2, 3, 4, 5]` must equal the table's shard ids.

Per-shard setup that is repeated (steps of run 44773679493, seconds): job setup 3, checkout 5, Node 4, pnpm 2, Task 1, store cache 5, install 1, `task packages` 23, browser cache 6, browser install 51 (58 to 78 in the other runs), ui-next build 8: about 110 s, 120 to 160 s with the new check step and post steps.

## Completeness: a probe cannot be left out

`node scripts/ci/probe-shards.mjs check` is the first command after `pnpm install` in every shard (a few seconds). It fails, one line per problem, with the path named (and as a `::error file=...` annotation in CI), when:

- a probe script under `packages/kit/probes`, `ui-next/shell/probes` or `ui-next/page/probes` (a file named `<thing>-probe.mjs` or `<thing>-probe-<suffix>.mjs`; `probe-lib.mjs`, fixtures, helpers, mock measurers and dev tools are not) is in no shard and not listed in `BY_HAND`: `ui-next/shell/probes/x-probe.mjs is a probe script and no shard runs it: add a unit for it to a shard ...`;
- the units of one probe script are in two shards, a script is in a shard and in `BY_HAND`, a unit's script does not exist, a probe directory does not exist (a renamed directory must not turn the scan into an empty one);
- a unit name is used twice, a shard has no unit, a unit has no name or script, controls are empty or repeated, a control is set in `env` instead of `controls`, an env value is not a string;
- the matrix line of the workflow lists a shard the table lacks, or the table has a shard the matrix lacks (its probes would never run), or the line cannot be found.

`scripts/ci/probe-shards.test.mjs` also holds `STEPS_AT_THE_SPLIT`, the 16 steps of the single-job workflow with their script, env and controls. Each must be in exactly one shard with its script, every env entry and every control; a step may gain, not lose, so deleting a probe from CI means deleting its line there, where a reviewer reads it.

## What the single job shared across steps, and what the split breaks (audit of the 12 probes in CI and the libraries they import)

Nothing the split breaks. The state one step could leave for another on the one VM was:

- **The ui-next build in `$PROBE_DIST`**: read by `kit-probe`, `table-probe`, `fonts-probe`, `tooltip-probe` and `log-probe` (and its controls), which is every unit whose env names `$PROBE_DIST`. The plan step reads that off the units and writes `dist=true|false`: the build step runs in a shard that has such a unit and is skipped in one that has none (shard 1, the panel probe, builds its own fixtures). A unit that names `$PROBE_DIST` in a shard that did not build it fails at once with `$PROBE_DIST is not set` (tested), it does not fall back to a build of its own.
- **Fixtures**: `harness.mjs` and the page `lib.mjs` build the shell and page fixtures into `mkdtemp` directories of their own on every run; the controls rebuild them too, as before. `FIXTURE_DIST` and `FIXTURE_DIST_DEV` (reuse a build) are not set in CI.
- **Ports**: every static server in the probes and their libraries listens on port 0 (`serve.mjs`, the page `lib.mjs`). The fixed ports (49231, 49455, 49472 to 49475) are in the `mock-*-measure.mjs` generators, which CI does not run.
- **Reports**: each probe writes only its own `$RUNNER_TEMP/<name>-probe.json`; none reads another's. The artifact is now one per shard (`kit-probe-reports-<shard>`): upload-artifact v4 refuses two uploads under one name.
- **Env**: `OMNIVIEW_UI=next` stays workflow-level; `FONT_DELAY_MS=40` is in the env of the palette units, which is where it was; `DIST` and `REPORT` as before. `FONT_DELAY_MS` is read when `serve.mjs` is imported, so it applies per process, as before.
- **Timing probes**: each still runs alone on a VM of the same type (ubuntu-24.04, 4 vCPU) with the probes of its shard one after another; the load on a probe is what it was. The loader-timing check of the parts probe (the flake behind main's failed runs at `d5ecf57c` and `e32cd86e`; #590 is open to fix it) is in shard 5 with the strip probe.
- **Caches**: the pnpm store and browser caches are restored by every shard. When a key misses, all five shards try to save it and one wins; the others log "Unable to reserve cache", a warning.

The work every shard repeats (about 70 s of the 110 to 160): store cache 5 and `pnpm install` 1 (a warm store; `node_modules` is not a thing to ship between jobs), `task packages` 23 to 34, ui-next build 8 to 11, browser cache 4 to 6 and install 51 to 78. The browser install runs apt for the WebKit libraries and cannot be an artifact; the plan's I1 and B1 (a CI image with the browsers) are the fix, and are not part of this step.

What could be built once is `task packages` and the ui-next build: 4.4 MB in 532 files (840 kB and 427 kB compressed), measured locally. A build job would have to finish first (about 60 s: setup 25, packages 25, ui-next 9, upload), then each shard would download and unpack it (about 5 s) instead of building (about 35 s). So the artifact saves 30 s in each shard and puts 60 s in front of all of them: the wall time is longer by about 30 s even before the second queue wait a dependent job pays, and the runner time is shorter by 1 to 3 minutes. See the measured variant below.
