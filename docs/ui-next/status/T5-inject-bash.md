## Decisions (to repeat in the pull request)

- **bash: its own login emulation, started as `bash --rcfile <dir>/bashrc -i`, no `-l`.** bash ignores `--rcfile` under `-l` (`prior-art.md` pitfall 1). The script runs `/etc/profile` and then the first readable of `~/.bash_profile`, `~/.bash_login`, `~/.profile`, once, at the top level, as a login shell does; `~/.bashrc` runs only if the user's login file sources it. The shell is started once (no second start of the user's files); the relaunch without the integration (step 2) starts it as before, `-i -l`. Not emulated: `~/.bash_logout`, `shopt login_shell` (it cannot be set; a profile that tests it sees a non-login shell), `$0` of `-bash`. **What a real login runs, and what this runs, with the system files.** A real login bash reads `/etc/profile` and then the first user file; it does not read the compiled-in system bashrc (`SYS_BASHRC`). Here bash is not a login shell, so it reads `SYS_BASHRC` itself before the rcfile (seen on Debian 13: `PS1` was already `${debian_chroot:+($debian_chroot)}\u@\h:\w\$ ` when the rcfile began), and then the script runs `/etc/profile`. On Debian and Ubuntu `/etc/profile` sources `/etc/bash.bashrc` when `PS1` is set and bash is not `/bin/sh`, so `/etc/bash.bashrc` runs twice, the first time before `/etc/profile` and not after it. Whether twice changes state: with the stock Debian 13 file (read here) no: it assigns `PS1`, sets `checkwinsize`, reads `debian_chroot`, defines `command_not_found_handle`, and touches neither `PATH` nor `PROMPT_COMMAND`, so the second run assigns the same values. Ubuntu's file is the same in kind [INFERENCE: not on this machine]. Fedora and RHEL define `SYS_BASHRC` as `/etc/bashrc`, which their `/etc/profile` does not source (their `~/.bashrc` does, and it runs only if the user's login file sources it): there it runs once from bash and once more through the user's `~/.bashrc`, where the file's own `BASHRCSOURCED` guard is what keeps it from repeating; and a file that tests `shopt -q login_shell` sees a non-login shell [INFERENCE: not read on this machine; to check on a Fedora].
- **`shopt -q login_shell` is false under the integration.** The shell is started without `-l` (the line above), and `login_shell` is a read-only option that only bash's own start sets, so the script's emulation of the login (`/etc/profile`, then the first of `~/.bash_profile`, `~/.bash_login`, `~/.profile`) cannot set it. A user file that branches on it (`if shopt -q login_shell; then ... fi`) takes the non-login branch, and so does a program that asks the shell whether it is a login shell. The profile files themselves do run: the seam's scenario r2 asks for that (`SEAM_PROFILE_RAN`, set by the `.bash_profile` of the check's home) and no longer asks `login_shell`. VS Code's bash integration has the same limit [INFERENCE: its `shellIntegration-bash.sh` is sourced from `--init-file` under a shell that is not started with `-l`, and I did not read the script for this]. The opt-out `terminal.shellIntegration=false` gives a real login shell, started with `-l` as before.
- **The version is asked, not guessed.** `Manager.bashVersion` runs the bash with `-c` and an environment of its own (no `BASH_ENV`), 2 s at most. Before 4.1 (macOS's system bash is 3.2: the script holds a descriptor in a variable) the fact is `skipped{bash-too-old}` and the shell starts as before; a probe that fails is `skipped{bash-version-unknown}`. The probe costs a process per bash start (about 5 ms here).
- **The nonce** is read with `read -u 3` into `__omniview_nonce`, a shell variable that is not exported; the descriptor is closed at the end of the script (`ready` is written first). A child of the shell has no nonce in its environment, a nested bash has no function of ours and no nonce. While the user's login file runs, descriptor 3 is open in its children (the other end is the host's, and there is nothing left to read from it): the same residue as fish's, and inert after `ready`.
- **`PROMPT_COMMAND` is kept, in the middle.** A string becomes `first \n <user's> \n last` (newlines, not `;`, so a user's trailing `;` cannot make `;;`); an array (bash 5.1) becomes `(first <user's elements> last)`. `first` reads `$?` before anything, prints the end mark (`D;<status>`) and hands `$?` on, so the user's prompt command sees the status of the command; `last` prints the directory marks, wraps `PS1` with `A` and `B` (once) and arms the DEBUG trap. A user who assigns `PROMPT_COMMAND` after the script has run replaces it: the marks stop, and the fact stays what it was.
- **The DEBUG trap is chained, the user's first.** A preexec library (bash-preexec's form) installs `trap '... "$_"' DEBUG`; the new trap is the user's string, a newline, then ours, so that the library sees `$_` as it expects. Ours does anything only for the first simple command after the prompt was armed.
- **The line is read from the history, and only when the history took it.** `$BASH_COMMAND` is the first simple command with aliases resolved, not the line, so the script reads `history 1` and strips its number. `HISTCMD` inside a command is the number the command has: equal to what the prompt showed when the history took the line, one less when it did not (`HISTCONTROL=ignorespace` or `ignoredups`, no history). When it did not, the command has the `C` mark and **no line** (never another: `TestAHistoryThatDoesNotHaveTheLineGivesNoLineAndNeverAWrongOne`); a repeated command under `ignoredups` therefore has none. A multi-line command is one history entry, its lines joined by `; ` (`cmdhist`): the line recorded is that entry, not the lines typed.
- **No `[[ =~ ]]`** in the script (it would clobber the user's `BASH_REMATCH`), and `xtrace` is put out in the hooks that touch the nonce (`set +x`, back at the end), so a user's `set -x` never prints it; the top level of the script tests the nonce without expanding it.
- **A hangup during the hooks still hangs up the jobs.** bash runs `PROMPT_COMMAND` and trap strings as a non-interactive shell (`SEVAL_NONINT`), and a non-interactive shell does not hang up its jobs: a SIGHUP in the millisecond of the hooks left `sleep 587 &` running (seen: `TestClosingHangsUpTheBackgroundJobsOfABashShell` failed 5 of 8 runs, because it closes the instant the job is named). While the hooks run, and only then (a HUP trap that stays keeps bash from handling a hangup in readline: seen, 4 of 6 left the job), a handler gives each job's process group SIGHUP and SIGCONT and lets the hangup take its course; a user's own HUP trap at the time of the script is never touched. **Known gap, with its size.** The hangup is lost to the jobs when it arrives between two events: (1) the end of the user's command (or the start of the DEBUG trap before a command), when bash starts the prompt commands as non-interactive, and (2) the moment `__omniview_hup_on` has run `builtin trap` in the first hook, which is one DEBUG-trap call, one function call and, on bash 5.3, a `${ }` read of the traps: tens of microseconds, not measured separately; on bash before 5.3 the fork is in it too. An earlier version asked bash with `$(trap -p HUP)` inside that window; the fork (78 microseconds) made `TestAGracefulShutdownHangsUpTheBackgroundJobsOfEveryShell/bash` fail 4 of 20 runs (7 of 20 for the reviewer), and 0 of 20 after it was taken out. What is lost is a `kill` of the background jobs of that shell (they keep running, as with `nohup`); the shell itself ends. It is not closed in the product: a handler that is there before the prompt commands would be there while bash waits in readline, where it keeps bash from handling the hangup (seen). The trailing edge (between `builtin trap - HUP` and the end of the prompt commands) is microseconds.
- **The user's HUP handler is read from bash, with no fork on bash 5.3, and the script defines no `trap` function.** (A first version kept the answer itself through a function named `trap`: it broke `RETURN` traps, which fired twice, and it missed `builtin trap`, `command trap` and a handler set by the user's prompt command. It is gone.) The hooks look at what bash has before they put their handler, and take theirs away only if it is still theirs: bash 5.3 reads it in the shell with `${ builtin trap -p HUP; }` (the same `$BASHPID`, no fork); an older bash has no such form (a syntax error there, so it is defined through `eval` only on 5.3 and later) and asks with `$(builtin trap -p HUP)`, a fork of some 80 microseconds in the window, which makes the gap on bash before 5.3 about 0.1 to 0.2 ms per prompt. The older path is tested here by an overlay that makes the version test false (the tests of bash and the graceful shutdown pass on it), not on a real bash before 5.3 (there is none on this machine).
- **An empty line and Ctrl-C at the prompt run no command.** The prompt commands run again, and the armed DEBUG trap sees `__omniview_precmd_first` as its first command. It is taken for the user's command only when the history has grown since the prompt: bash does not call the trap for a subshell `(exit 7)` or similar, and for those this is the first command it sees (a fix that drops every such command, `if BASH_COMMAND = __omniview_precmd_first`, loses `(exit 7)`: seen). A command that the history did not take (a space first) and runs without the trap has no marks at all.
- **A line of only a comment is no command.** bash does not call the DEBUG trap for it, and the first prompt command would then be taken for it (the history grew): when the line the history has begins with `#` the trap takes it for nothing, no mark (`TestACommentLineIsNotACommand`).
- **The user's DEBUG status is kept (extdebug).** The composed trap is `<user's>`, `__omniview_rc=$?`, `__omniview_debug`, and `__omniview_debug` returns that status on every path: with `shopt -s extdebug` a DEBUG trap that returns non-zero skips the command. The status is the user's except for our own hooks (`__omniview_precmd_first` and `_last` as the command, and every command inside one of our functions: extdebug makes the trap follow into functions, `FUNCNAME[1]` is ours), which it must not take away (`TestAUsersDebugTrapThatRefusesOurHooksDoesNotTakeThemAway`). A command the user's trap skips (non-zero with extdebug) is no record: the trap sees it, notes it, and the prompt command that follows is not taken for it (`TestACommandThatTheUsersDebugTrapSkipsIsNotRecordedAsRun`). Our own functions are matched by exact name (a user's `__omniview_mine` is theirs: `TestAUsersFunctionNamedLikeOursIsStillTheirs`), and the trap does nothing in a subshell (`BASH_SUBSHELL`): with extdebug or `set -T` a subshell, a command substitution and the parts of a pipeline inherit it, and it printed its marks, the nonce among them, into the user's file or variable (`TestTheDebugTrapOfASubshellNeverWritesIntoTheUsersData`, both options). Not handled: a user's DEBUG trap that refuses the commands of the script's own installation (it runs after the user's files, under their extdebug), which would leave the shell without the hooks (the fact is `unconfirmed` only if `ready` is refused too). Not tested: a non-zero status under `set -e`.
- **pwsh's prompt gets the `$?` of the last command.** The wrapper's own statements replace `$?`, which cannot be written; the statement before the call to the user's prompt leaves the right value (`$null = $true`, or `Write-Error ... -ErrorAction Ignore`, which is no error record).
- **The suite skips real-bash tests on a bash before 4.1** (`integrationShellSkip`: "NOT RUN", as for a missing shell); the dedicated tests of the fallback stay on.
- **Every mark is written to `/dev/tty`, in bash and zsh (a second nonce leak, found by review).** The hooks printed to stdout, which is the terminal only by default: bash fires the DEBUG trap inside a compound command's redirect (`for ...; done > f`, `if ...; fi > f`, `while read l; do ...; done < in > out`, `{ ...; } > f`), and a user's `exec > file` redirects the shell's own stdout for good, so `ESC]633;E;<line>;<nonce>` and the other marks landed in the user's file (`TestTheMarksNeverLandInAFileThatTheUserRedirectsTo`; the same for zsh's `exec > file`, `TestTheMarksOfZshAndFishAndPwshNeverLandInAFileThatTheUserRedirectsTo`). The preferred fix, a private descriptor to the terminal, does not work in bash: it does not close the descriptors it opens with `{var}` on exec (seen: a child had fd 10 to the pty), so every child would hold one; `/dev/tty` is opened for each write and kept by nobody (`TestNoDescriptorOfTheHooksIsInheritedByAChild`). The cost: a shell with no controlling terminal writes no marks (the host always gives one: the pty is the shell's controlling terminal). Audit of the same class: fish and pwsh pass the tests (fish's handlers run on events, not inside a redirect, and the shell cannot `exec >` itself; pwsh writes with `[Console]::Write` and its `>` applies to a command's output stream, not to the console), and zsh's `preexec` runs once before the line, so only `exec > file` mattered there.
- **The pwsh transcript holds no nonce.** `Start-Transcript` (or a policy that turns transcription on) records what `prompt` returns, and the end mark, `OSC 7` and `633;P` (the nonce and the directory) were in that string. They are now written to the console before the prompt returns; the string holds only the prompt marks `133;A` and `133;B` (they carry neither the nonce nor a path, and the transcript then has those two control sequences around each prompt: noise, no secret). `TestPwshTheTranscriptHasNoNonceAndNoMarkWithADirectory`; control `pwsh-marks-in-the-prompt-string`. The command line mark (`633;E`, with the nonce) was already written with `[Console]::Write`, which the transcript does not record (the test holds it to that).
- **pwsh calls `Microsoft.PowerShell.Utility\Write-Error`** (a user's `function Write-Error {}` would otherwise succeed, and the prompt would see a failed command as a success: `TestPwshAUsersWriteErrorFunctionDoesNotMakeAFailureLookLikeSuccess`, control `pwsh-write-error-not-qualified`). The other cmdlets the script calls are not qualified; a user who redefines one of them changes what it does.
- **`set -e` and `set -u`.** errexit is put out in the first hook and back in the last, which returns 0: `return` of a status that is not zero ends a shell that has `set -e` (`! true` was enough). The user's own prompt commands run with errexit off. `set -u` was already safe (the script uses `${var:-}` everywhere); it is pinned by a test.
- **The test waits for an observable event, not time.** `TestClosingHangsUpTheBackgroundJobsOfABashShell` closes after the integration's second input-start mark (`OSC 133;B`: the first is the first prompt, the second is the prompt drawn after the job's command, which is after every hook ended); without the integration (a bash before 4.1) there is no window and no wait. `TestAHangupDuringThePromptCommandsStillHangsUpTheJobs` waits for a file the prompt command writes, and holds the close inside a `sleep` that is running. It waits for the pid of the prompt command's own `sleep` to be written (it is then running, the shell is in `wait`), and no test of this file sleeps for a fixed time to force an order.
- **pwsh: `pwsh -Login -NoLogo -NoExit -Command ". '<dir>/integration.ps1'"`.** The profile has run when the script does, so the user's prompt is the one wrapped. `prompt` is wrapped (end mark with the status, `OSC 7`, `633;P`, `133;A`, the user's text, `133;B`); `PSConsoleHostReadLine` is wrapped (as VS Code does) so that `633;E` and `133;C` come after the line was accepted and its newline echoed. The nonce comes from file descriptor 3 as a socket: `System.Net.Sockets.Socket` on a `SafeSocketHandle` made from descriptor 3 (it owns it and closes it at the end), which pwsh 7.5.1 on Linux does; `ready` is sent on it. The nonce lives in `$global:__omniview_nonce`: a variable of the session, not an environment variable.
- **pwsh's status.** `$?` is false for a failed cmdlet and for a native command with a non-zero code. The script says 0 for true; for false, 1, or the native code when the last error record is the one from before the command (a new one is a cmdlet's failure) and `$LASTEXITCODE` is a non-zero integer. Best effort: it is the exit code of the last native command in that case, which pwsh can only tell by this; the exit code is never what the nonce vouches for.
- **pwsh is given 4 s to say `ready`** (`pwshReadyWait`), bash, zsh and fish 500 ms: pwsh takes about a second to start here, and the fact would be `unconfirmed` for every start. A pwsh that ends within the 4 s is still started once more without the integration. The cost is paid by `Start` only while the shell has not said `ready` and has not ended.
- **The arguments.** For pwsh the allowed arguments are `-Login` and `-NoLogo` (the shell contract's); `-Command` and its prefixes, `-File`, `-EncodedCommand` are `skipped{command}`; any other is `skipped{arguments}`.
- The runtime models of the bindings carry the two reasons (`task bindings`).
- The fact's reasons added: `bash-too-old`, `bash-version-unknown`.
