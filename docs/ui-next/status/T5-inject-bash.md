## Decisions (to repeat in the pull request)

- **bash: its own login emulation, started as `bash --rcfile <dir>/bashrc -i`, no `-l`.** bash ignores `--rcfile` under `-l` (`prior-art.md` pitfall 1). The script runs `/etc/profile` and then the first readable of `~/.bash_profile`, `~/.bash_login`, `~/.profile`, once, at the top level, as a login shell does; `~/.bashrc` runs only if the user's login file sources it. The shell is started once (no second start of the user's files); the relaunch without the integration (step 2) starts it as before, `-i -l`. Not emulated: `~/.bash_logout`, `shopt login_shell` (it cannot be set; a profile that tests it sees a non-login shell), `$0` of `-bash`. **What a real login runs, and what this runs, with the system files.** A real login bash reads `/etc/profile` and then the first user file; it does not read the compiled-in system bashrc (`SYS_BASHRC`). Here bash is not a login shell, so it reads `SYS_BASHRC` itself before the rcfile (seen on Debian 13: `PS1` was already `${debian_chroot:+($debian_chroot)}\u@\h:\w\$ ` when the rcfile began), and then the script runs `/etc/profile`. On Debian and Ubuntu `/etc/profile` sources `/etc/bash.bashrc` when `PS1` is set and bash is not `/bin/sh`, so `/etc/bash.bashrc` runs twice, the first time before `/etc/profile` and not after it. Whether twice changes state: with the stock Debian 13 file (read here) no: it assigns `PS1`, sets `checkwinsize`, reads `debian_chroot`, defines `command_not_found_handle`, and touches neither `PATH` nor `PROMPT_COMMAND`, so the second run assigns the same values. Ubuntu's file is the same in kind [INFERENCE: not on this machine]. Fedora and RHEL define `SYS_BASHRC` as `/etc/bashrc`, which their `/etc/profile` does not source (their `~/.bashrc` does, and it runs only if the user's login file sources it): there it runs once from bash and once more through the user's `~/.bashrc`, where the file's own `BASHRCSOURCED` guard is what keeps it from repeating; and a file that tests `shopt -q login_shell` sees a non-login shell [INFERENCE: not read on this machine; to check on a Fedora].
- **The version is asked, not guessed.** `Manager.bashVersion` runs the bash with `-c` and an environment of its own (no `BASH_ENV`), 2 s at most. Before 4.1 (macOS's system bash is 3.2: the script holds a descriptor in a variable) the fact is `skipped{bash-too-old}` and the shell starts as before; a probe that fails is `skipped{bash-version-unknown}`. The probe costs a process per bash start (about 5 ms here).
- **The nonce** is read with `read -u 3` into `__omniview_nonce`, a shell variable that is not exported; the descriptor is closed at the end of the script (`ready` is written first). A child of the shell has no nonce in its environment, a nested bash has no function of ours and no nonce. While the user's login file runs, descriptor 3 is open in its children (the other end is the host's, and there is nothing left to read from it): the same residue as fish's, and inert after `ready`.
- **`PROMPT_COMMAND` is kept, in the middle.** A string becomes `first \n <user's> \n last` (newlines, not `;`, so a user's trailing `;` cannot make `;;`); an array (bash 5.1) becomes `(first <user's elements> last)`. `first` reads `$?` before anything, prints the end mark (`D;<status>`) and hands `$?` on, so the user's prompt command sees the status of the command; `last` prints the directory marks, wraps `PS1` with `A` and `B` (once) and arms the DEBUG trap. A user who assigns `PROMPT_COMMAND` after the script has run replaces it: the marks stop, and the fact stays what it was.
- **The DEBUG trap is chained, the user's first.** A preexec library (bash-preexec's form) installs `trap '... "$_"' DEBUG`; the new trap is the user's string, a newline, then ours, so that the library sees `$_` as it expects. Ours does anything only for the first simple command after the prompt was armed.
- **The line is read from the history, and only when the history took it.** `$BASH_COMMAND` is the first simple command with aliases resolved, not the line, so the script reads `history 1` and strips its number. `HISTCMD` inside a command is the number the command has: equal to what the prompt showed when the history took the line, one less when it did not (`HISTCONTROL=ignorespace` or `ignoredups`, no history). When it did not, the command has the `C` mark and **no line** (never another: `TestAHistoryThatDoesNotHaveTheLineGivesNoLineAndNeverAWrongOne`); a repeated command under `ignoredups` therefore has none. A multi-line command is one history entry, its lines joined by `; ` (`cmdhist`): the line recorded is that entry, not the lines typed.
- **No `[[ =~ ]]`** in the script (it would clobber the user's `BASH_REMATCH`), and `xtrace` is put out in the hooks that touch the nonce (`set +x`, back at the end), so a user's `set -x` never prints it; the top level of the script tests the nonce without expanding it.
- **A hangup during the hooks still hangs up the jobs.** bash runs `PROMPT_COMMAND` and trap strings as a non-interactive shell (`SEVAL_NONINT`), and a non-interactive shell does not hang up its jobs: a SIGHUP in the millisecond of the hooks left `sleep 587 &` running (seen: `TestClosingHangsUpTheBackgroundJobsOfABashShell` failed 5 of 8 runs, because it closes the instant the job is named). While the hooks run, and only then (a HUP trap that stays keeps bash from handling a hangup in readline: seen, 4 of 6 left the job), a handler gives each job's process group SIGHUP and SIGCONT and lets the hangup take its course; a user's own HUP trap at the time of the script is never touched. **Known gap, with its size.** The hangup is lost to the jobs when it arrives between two events: (1) the end of the user's command (or the start of the DEBUG trap before a command), when bash starts the prompt commands as non-interactive, and (2) the moment `__omniview_hup_on` has run `builtin trap` in the first hook, which is one DEBUG-trap call and one function call: tens of microseconds, not measured separately. An earlier version asked bash whether the user had a HUP handler with `$(trap -p HUP)` inside that window; the fork (78 microseconds) made `TestAGracefulShutdownHangsUpTheBackgroundJobsOfEveryShell/bash` fail 4 of 20 runs (7 of 20 for the reviewer), and 0 of 20 after it was taken out. What is lost is a `kill` of the background jobs of that shell (they keep running, as with `nohup`); the shell itself ends. It is not closed in the product: a handler that is there before the prompt commands would be there while bash waits in readline, where it keeps bash from handling the hangup (seen). The trailing edge (between `builtin trap - HUP` and the end of the prompt commands) is microseconds.
- **No fork in the window: the script keeps the user's HUP handler itself.** `__omniview_hup_user` is read once after the user's own files ran, and a shell function named `trap` (this shell only: not exported; `builtin trap` and `command trap` bypass it) reads it again whenever a command of the user's names `HUP`, `SIGHUP` or `1`, in the shell or in a file it sources. The hooks put their handler only when the user has none, and the user's is never replaced or removed (`TestTheHooksLeaveNoHUPHandlerAtThePromptAndNeverReplaceTheUsers`). The cost is that `type trap` says it is a function.
- **An empty line and Ctrl-C at the prompt run no command.** The prompt commands run again, and the armed DEBUG trap sees `__omniview_precmd_first` as its first command. It is taken for the user's command only when the history has grown since the prompt: bash does not call the trap for a subshell `(exit 7)` or similar, and for those this is the first command it sees (a fix that drops every such command, `if BASH_COMMAND = __omniview_precmd_first`, loses `(exit 7)`: seen). A command that the history did not take (a space first) and runs without the trap has no marks at all.
- **`set -e` and `set -u`.** errexit is put out in the first hook and back in the last, which returns 0: `return` of a status that is not zero ends a shell that has `set -e` (`! true` was enough). The user's own prompt commands run with errexit off. `set -u` was already safe (the script uses `${var:-}` everywhere); it is pinned by a test.
- **The test waits for an observable event, not time.** `TestClosingHangsUpTheBackgroundJobsOfABashShell` closes after the integration's second input-start mark (`OSC 133;B`: the first is the first prompt, the second is the prompt drawn after the job's command, which is after every hook ended); without the integration (a bash before 4.1) there is no window and no wait. `TestAHangupDuringThePromptCommandsStillHangsUpTheJobs` waits for a file the prompt command writes, and holds the close inside a `sleep` that is running. It waits for the pid of the prompt command's own `sleep` to be written (it is then running, the shell is in `wait`), and no test of this file sleeps for a fixed time to force an order.
- **pwsh: `pwsh -Login -NoLogo -NoExit -Command ". '<dir>/integration.ps1'"`.** The profile has run when the script does, so the user's prompt is the one wrapped. `prompt` is wrapped (end mark with the status, `OSC 7`, `633;P`, `133;A`, the user's text, `133;B`); `PSConsoleHostReadLine` is wrapped (as VS Code does) so that `633;E` and `133;C` come after the line was accepted and its newline echoed. The nonce comes from file descriptor 3 as a socket: `System.Net.Sockets.Socket` on a `SafeSocketHandle` made from descriptor 3 (it owns it and closes it at the end), which pwsh 7.5.1 on Linux does; `ready` is sent on it. The nonce lives in `$global:__omniview_nonce`: a variable of the session, not an environment variable.
- **pwsh's status.** `$?` is false for a failed cmdlet and for a native command with a non-zero code. The script says 0 for true; for false, 1, or the native code when the last error record is the one from before the command (a new one is a cmdlet's failure) and `$LASTEXITCODE` is a non-zero integer. Best effort: it is the exit code of the last native command in that case, which pwsh can only tell by this; the exit code is never what the nonce vouches for.
- **pwsh is given 4 s to say `ready`** (`pwshReadyWait`), bash, zsh and fish 500 ms: pwsh takes about a second to start here, and the fact would be `unconfirmed` for every start. A pwsh that ends within the 4 s is still started once more without the integration. The cost is paid by `Start` only while the shell has not said `ready` and has not ended.
- **The arguments.** For pwsh the allowed arguments are `-Login` and `-NoLogo` (the shell contract's); `-Command` and its prefixes, `-File`, `-EncodedCommand` are `skipped{command}`; any other is `skipped{arguments}`.
- The runtime models of the bindings carry the two reasons (`task bindings`).
- The fact's reasons added: `bash-too-old`, `bash-version-unknown`.
