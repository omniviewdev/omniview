## 1. What changed

1. **A failed connection start reaches every window (PT1 catalog item 8, closed).**
   - Host, `backend/pkg/plugin/resource/` (`connection_start_failures.go`, `controller.go`, `connection_change.go`, `profile_invalidation.go`, `types.go`): when `provider.StartConnection` returns an error, or answers a failure status (UNAUTHORIZED, FORBIDDEN, FAILED, ERROR, BAD_REQUEST, NOT_FOUND, TIMEOUT, UNAVAILABLE, REQUEST_ENTITY_TOO_LARGE), the host keeps why, per connection of the plugin's list, and announces it with ONE `connection/status` event: status FAILED (or the answered status) and a new `error`, the public error. The error is the one every provider error already passes (`apperror.ForResource`: the class's words, the provider's sentence only after `PublicText`; the raw error is dropped); an answered status is worded by its class alone (UNAUTHORIZED, FORBIDDEN, INTERNAL for the rest, which reads `failed`) and its own `Error` and `Details` are never read. `GetAllConnectionStates` reads FAILED with that `readinessError` while the record stands (whatever the provider reports, except CONNECTED); a later answer, a stop, the connection leaving the plugin's list, a plugin init or unload clear it, so the map never holds a connection that is gone. A start the host refuses itself (a caller that gave up, a retired generation, a route that changed) announces nothing and keeps nothing. PENDING, DISCONNECTED and UNKNOWN answers are not failures.
   - Runtime: the generated binding gets `ConnectionStatusPayload.error`; the old shell's `useConnectionReadiness` (`connectionReadiness.ts`) takes the event's error for FAILED, so the class does not depend on whether the event or the rejection arrives first (measured on the real host, 40 failed starts in each engine: the event came before the answer in 15 (WebKit) and 22 (Chromium) of 40; both orders are handled). A patch changeset.
   - UI: the connection store (`ui-next/plugins/host/connections/store.ts`) keeps no memory of failed starts of its own (the consumer-side stand-in is deleted with its tests): the event makes every window read the list again, the list says FAILED with the host's reason, and Problems shows the row through the existing `connectionConditions` adapter. A start that fails keeps `connecting` until the re-read lands, so after a failed start Home, the picker and Problems say "Connecting…" for one round trip and then what the host says. `connect()` still answers its caller from the rejection or the answered status.
   - Seam scenario `v`: a start made by the harness (a node-side call, not the page's) makes the Problems row appear by the event, with the tab count and the host's public sentence; the fixture's new connection mode `unreachable-path` fails with a sentence that names a path under a home directory, which the public-text rules refuse, so any leak of the plugin's own words is told apart. 26 controls with their `ASSERTION_OFF` pairs (3 new: `conn-told`, `conn-count`, `conn-public`).

## 3. Decisions the lead may overrule

- Answered failure statuses other than UNAUTHORIZED and FORBIDDEN are worded as class INTERNAL, which the UI reads as `failed`; `PROVIDER_ERROR` is a 502 that the UI's `classOf` reads as `unreachable` ("Not responding"), which would be wrong for a generic failure. One `return "INTERNAL"` in `answeredFailureCode` flips it. The SDK's TIMEOUT, UNAVAILABLE and REQUEST_ENTITY_TOO_LARGE are failure words too and got the same treatment.
- The old shell's readiness hook handles only FAILED events with an `error`; an answered NOT_FOUND event carries an INTERNAL error, and applying it would turn that connection's phase from `not-found` to `error`, so the hook leaves the other statuses to their own words.
