## What the host does now (the producer says, the consumer never guesses)

- **Go lane** (`backend/pkg/plugin/logs`, `replay_markers.go`): the lane is the ONLY party that sets `omniview.log.replay-markers`. Every `omniview.*` parameter a window sends is dropped before anything reaches the plugin (create, update and the headless read; names logged at Warn, never values; the caller's map is never changed), and on the window's create the lane asks itself (`ParamReplayMarkers` = `1`). The reply's fact (`LogSession.replay_markers`), the line's `replay` and the caught-up event (kind 7) reach the window as the plugin sent them (tests: `replay_markers_test.go`). The lane does NOT reorder lines against events (it batches lines, 50 ms or 100, and sends events at once, so a caught-up event can overtake the lines before it; the stream counts a line by its own flag at acceptance, so that is harmless).
- **Runtime stream** (`openLogStream`, `@omniviewdev/runtime/ui/v1`): typed facts. A line has `replay: boolean` (the backend's flag as sent). A source has `replay: 'replaying' | 'live' | 'unknown'`. The snapshot has `markers: 'pending' | 'yes' | 'no'` (the answer to the create call, or the first marker, which is the backend's word that they come; `yes` is never taken back). `stats().live: number | undefined` is the count a rate may be made of: lines NOT flagged replay from a source that is `live` and still going, counted when the stream ACCEPTS them (so a hidden or slow view does not change it); `undefined` while no source that is going is live. A source is `replaying` while markers come and its word is not in (and again after `SOURCE_ADDED`, `RECONNECTING` or `RECONNECTED`), `live` from its caught-up event, `unknown` when the session has no markers.
- **Kit model** (`LogViewModel`): the rate is `LogFeedStats.live` over the wall clock, last 3 s (L1's mechanism, the series restarts when a view comes back; L3's paused and quiet rules unchanged). No count: the rate is unknown and the strip says **`No rate`**, not `0.0 lines/s` (a live source that writes nothing is `0.0`). `LogFeedStats.live` is optional (additive: a plugin's own feed written before it still is a feed and shows no rate).
- **The words.** The mock's log strip has no placeholder (it reads `0.0 lines/s` for a seeded backlog it does not count: `shell-panel.js:1995-2001`). The mock's words for an absent rate are elsewhere: `cat-msg-c-eventbridge4.js:91`, `['Rate', r.rate ? `${M.nf(r.rate)}/s` : EB.none('No rate')]`, where `EB.none` is `H.none` (`core.js:898-900`: a dash with `aria-label="No rate"`), and `H.none('No data', 'No data')` (`core.js:984`). The strip says those words. **Decision for the lead:** the kit's `MissingValue` says the design draws the dash and never a phrase; the dash with the accessible name "No rate" in the strip is a change of `NO_RATE` (`log/statText.ts`) and the strip's span.
- **A source that is never marked** (the plugin's interim `MaxInt64`, or a plugin that cannot count in time) stays `replaying`, so the strip says `No rate`, for as long as the session lasts. Decided from the SDK contract (an unmarked source is unknown; "never an error or a spinner"): the UI never says more, there is no timeout, and nothing turns it live by waiting (a test advances ten minutes with 20,000 flagged lines and the probe has a control that invents the timeout). A timeout that said "this source will not be marked" would be a guess; the producer's own word for it is the SDK follow-up (`ErrReplayUnknown`, below).
- **Why the host's clock skew is no longer relevant:** the rate reads no time on any line and no gap, only what the source says is live, so no clock (this host's, the backend's, a node's) enters it.
