## What changes for users (plugin PR #272 and its finish commit)

1. Every connection ID changes, from the context name to `<slug>-<10 hex>` (at most 59 characters, `[a-z0-9._-]`; the hash is of the kind of source, the cleaned absolute path of the kubeconfig and the exact context name). It shows in logs, spans, the pprof label, routes, Logs targets, the agent's `connection_id` and palette routes. Moving or renaming the kubeconfig, or renaming a context, changes the ID; editing the file otherwise does not.
2. The UI says the NAME (`Connection.name`: the exact context name, or what the user renamed it to): the scope lane chip, the status-bar path, the Pod page and the scope of a Logs session (its card's Connection row and the tab's qualifier). Two kubeconfig files that both define `prod` now give two live connections (before, the plugin listed none: the SDK rejected the duplicate ID), told apart by a second word, `prod · config` and `prod · other`.
3. One kubeconfig file reached by a symlink, a hard link, a case variant (on a file system that ignores case) or listed twice is one source: one connection for each context, and the first spelling in the configured order keeps its ID. The plugin never reads `KUBECONFIG`: the order is that of its `kubeconfigs` setting (default `~/.kube/config`), stored as a list, so IDs do not flip between starts while that list keeps its order.
4. Saved tabs, sessions and Logs targets reset once. A restored tab that holds an old ID reads the plugin's first connection, and the chip says which one by name; nothing prints the stale ID.
5. A connection that names no kubeconfig context cannot connect: it fails with `INVALID_REQUEST` ("Invalid request"; the plugin's sentence reaches the user once an SDK tag with SDK #79 is adopted, v0.20.0 drops it).
6. **What is lost without the migration below: host overrides, removed connections and auto-connect choices, and the agent's per-connection policy** (next section).

## The design of the one-time host migration (not built)

**Who supplies old to new.** The plugin. `pkg/connid` belongs to the plugin's module and the host is plugin-agnostic (decisions A13, A16), so the host cannot call `connid.FromLegacyID(legacyID, kind, locator)` and must not copy the format. The plugin already exports the pure function; what is missing is the call. Recommended: a question on the resource provider, `MigrateConnectionIDs(ctx, stored []StoredConnection{ID, Data}) -> map[oldID] newID | ambiguous | unknown`, carried by the SDK (a WIRE change: an SDK tag is the owner's) and answered by the plugin from `FromLegacyID(old, KindFile, FileLocator(clean absolute path of the stored data.kubeconfig, runtime.GOOS))` for a stored profile (the plugin stores the tilde-expanded path, so it must be cleaned) and from its current inventory (`data.context == old`) for state with no data (the agent policy). If the SDK cannot carry it in time, the fallback is one field of the connection the plugin lists (`LegacyIDs`), from which the host maps without any plugin knowledge. A copy of the format in the host is the last resort; `TestIDGoldenVectors` (plugin `pkg/connid`) is then the shared corpus.

**Fail closed.** An ID that maps to nothing, or to more than one connection (two files that now define the same context), is never dropped silently. For the agent's policy: a `blocked` entry that is ambiguous blocks every candidate; an entry that maps to nothing is kept as it is; and until the migration has succeeded for a plugin whose IDs changed, the agent treats every connection of that plugin as blocked (the guard is a marker, the store's scheme version, not the absence of an entry). For profiles: an ambiguous override is kept and shown as needing the user, never attached to a guess.

**Steps** (size: S under half a day, M one to two days, L three or more):

1. Decide the supplier and write its contract (SDK method or `LegacyIDs`), with the plugin side on `FromLegacyID`. Plugin: S. SDK and its tag: M (WIRE; the SDK tag is the owner's).
2. A migration runner in `backend/pkg/plugin/resource/connection_profiles.go`, run once per plugin and store version inside `replayConnectionProfilesLocked`, after native discovery (`source.NativeConnections`) and before `ApplyConnectionOverlay` (`:332`), under `profilesMu`: versioned marker (`connection-profiles-v1` to a document that records the ID scheme), idempotent, atomic write, a copy of the old document kept (`.pre-ids`), rolled back on error. M.
3. The profile store: rewrite `configuration.id`, add `configuration.data.context` to a migrated override (or it cannot connect), rewrite `disabledIDs`; auto-connect rides in the profile. M.
4. The agent's policy: re-key `Connections[plugin]` through the same mapping, with the fail-closed rules above and the start-up guard. M.
5. The window session and the old UI's stores: map through the same function or reset once (accepted); first audit the stores marked not audited. S to M.
6. Tests first: a host test with a stored profile and a blocked agent policy under the old ID and a plugin that lists the derived one (after the migration the derived ID is blocked and the profile has `data.context`); an ambiguous ID; a migration that fails (the agent stays blocked, the profile document is untouched); the second run changes nothing. M.
7. The flip's release note and sequence: the migration runs before the first start of the flipped plugin. S.

Interim until it exists: anyone who runs the plugin from `feature/ui-next` with saved overrides sees the failing duplicates, and anyone who blocked a connection for the agent must block it again. The lead asked for this to ride with the flip (condition 5).
