## The window close (5 of the task, the priority)

**Observed.** In the packaged app, `OMNIVIEW_UI=next`, channel `feature-ui-next`: the red light, Cmd+W on the empty window and Cmd+Shift+W each ended the process within 2 s (`ps` empty, plugin child gone, the log says `host services shutting down`; no `windowVisibilityChanged`). Captures: `32-fullscreen-after-cmd-w-window-hidden.png` (no window), `36-desktop-after-cmd-shift-w.png`, `45-pre539-desktop-after-red-light.png`, `47-old-ui-desktop-after-red-light.png`.

**Is the hook installed? Yes.** `backend/window/wails.go:48` calls `attachMainWindow`, `wails.go:126` registers a `WindowClosing` hook that cancels the close and calls `mainWindow.Hide()` (unless `shutdownStarted()`). The same hook makes the JS `Window.Close()` (`messageprocessor_window.go:139`, `window.Close()`, which only emits `WindowClosing`) a hide.

**Why the process still exits.** `main.go:300` (before this PR) `Mac: application.MacOptions{ApplicationShouldTerminateAfterLastWindowClosed: true}`. Wails answers AppKit's `applicationShouldTerminateAfterLastWindowClosed:` with that value (`wails/v3@v3.1.0/pkg/application/application_darwin_delegate.m:31-34`); hiding the only window (`orderOut`) makes AppKit ask, and the answer ends the app. **Proof, by the single variable:** a trial build of the same commit with the option `false` (one-line change, the only difference): red light, Cmd+W on the empty window and Cmd+Shift+W all left the process alive with the window off screen (`41-…`), and the Dock brought it back (`37-…`, `39-…`, `42-…`, `43-…`).

**Regression or pre-existing? Pre-existing.** The red light quits in: (a) the commit before #539 (c89c3299), `OMNIVIEW_UI=next`, same channel stamp (`44-…`, `45-…`); (b) current main with the OLD UI, `OMNIVIEW_UI` unset (`46-…`, `47-…`). History: the option comes from the Wails v3 migration (a0ec1de8); the hide-on-close hook came later with multi-window (c4f02318) and has never worked on macOS for the last window. The chord and menu item #539 added only made it reachable by keyboard.

**The rule.** VS Code and JetBrains on macOS: the red light and Cmd+Shift+W close the window, the app stays in the Dock, Cmd+Q quits; decision A17 says hide and the Dock brings it back.

**Fix (this PR).** `window_options.go` `macApplicationOptions()` returns `ApplicationShouldTerminateAfterLastWindowClosed: false`, used at `main.go:300`; the test `TestMacApplicationStaysRunningWhenTheLastWindowCloses` (`window_options_test.go`) was written first (red: `undefined: macApplicationOptions`) and passes. **Verified natively on a build of this branch (the packaged flavour, plus a read-only overlay that is not in the commit):** red light with two tabs open: process alive, no window (`51-…`), a real Dock click (pointer to the screen's left edge to reveal the auto-hidden Dock, click on the icon) restores the window with both tabs and the scroll (`52-…`; the earlier trial used the Dock's `AXPress`, same result); Cmd+W twice (the two tabs close) and a third time on the empty window: hidden, alive, Dock restores (`53-…`); Cmd+Shift+W: hidden, alive, Dock restores (`54-…`, `55-…`); Cmd+Q on a visible window and on a hidden app: the process and its plugin child exit.

**Not covered.** Windows and Linux: the option is macOS-only; the hide hook still leaves a hidden main window with no way back there (S2a Backend catalog item 1, still open). Settings and other windows are untouched by the option [INFERENCE: not run].

## Known native-only defects, re-checked and diagnosed

All numbers are from the read-only overlay (Ctrl+Alt+M, `S2b/s2b-debug.ts.txt`, built into a diagnostic binary, not committed), page coordinates, panel closed.

1. **Last visible table row "clipped by the footer": the geometry is correct; it is the scrollport cutting a partial row.** The Pods table's scroll region (`DataTable.module.css:11-22`, `.region`, `height: 100%; overflow: auto`) is `y204 h535 b739` and its footer (`CollectionFooter`, `y739 h33`) starts at `739`: they touch, nothing overlaps. Rows are 40 px, the sticky header 25 px, `scrollH 985` (= 25 + 24 x 40). At scrollTop 0 the region shows 510 px of rows = 12.75 rows, so the 13th row (`kube-apiserver…`, top 709, bottom 749) is cut by 10 px at the region's bottom edge, exactly what any scrollable list does when the viewport is not a multiple of the row height. At the end of the list (scrollTop 450 = max) the last row (`unschedulable`) ends at 739: `cut 0`, gap 0 (`57-…`). Why Playwright "never" showed it: the same arithmetic gives region height = inner height - 274 (809 - 274 = 535 here), rows window = region - 25: at 1440 x 900 that is 601 px = 15.03 rows (aligned, so no visible cut) and at 1280 x 800 it is 501 px = 12.5 rows (cut), [INFERENCE] by calculation, the Playwright probes were not run here. Not fixed: removing the partial row would be a design change (row snapping, which the mock does not do either), not a small repair.
2. **Extra scrollbar track at the sidebar's right edge: not a defect of the port; the mock does the same, and the OS makes it visible.** `Tree.module.css:15` (`overflow-y: scroll`) is the mock's `.side-navigation` (`mock/core.css:186`), and the page's scroll owner `PageHost.module.css:10` (`overflow-y: scroll`) is the mock's `#mainscroll` (`core.css:151`). With a mouse connected macOS draws classic 17 px scrollbars, and `overflow-y: scroll` paints the empty track permanently: the overlay reads `[role=tree] w244 client227 scroll227 ovY scroll sbw 17` (the sidebar loses 17 px of its width) and the empty `Home` page shows the same track at the island's right edge (`31-…`). Headless browsers and trackpad-only Macs have overlay scrollbars (0 px), which is why Playwright never shows it. The fix (a gutter that paints nothing until there is something to scroll) is a design decision against S15 and the mock: left for the lead. Seen once, not reproduced: a WHITE track at the page's right edge in `09-…` (a not-found page right after the Pod was deleted); the same page in `30-…` and everything after paints dark.
3. **1280 x 800 asked, 1280 x 808 given.** `main.go:77-78` `MinWebviewWidth 1280`, `MinWebviewHeight 800`. Accessibility `set size {1280, 800}` and `{1280, 792}` both end at a 1280 x 808 frame (`winlist`), and the page reads `inner 1281 x 809` (the web view is 1 px larger than the frame in both directions, `docEl client 1281 x 809`). Cause [INFERENCE, not run apart from the sizes]: Wails sets the minimum twice (`webview_window_darwin.go:405-412`): `setContentMinSize:` from `contentRectForFrameRect` of a 1280 x 800 frame, computed with the plain 28 pt title bar, and `setMinSize:` 1280 x 800; the window then gets the unified compact toolbar (`macTitleBar()`, `window_options.go:23`) that makes the chrome about 8 pt taller (the 38 pt bar of `N22b`), so the content minimum is honoured at 772 + 36 = 808. Consequence for the shell: the smallest native viewport is 1281 x 809, one pixel and nine larger than the A15 test viewport, so the 1280 x 800 probes are a stricter case than any native window can reach. A fix is a Go change in the window options (`MinHeight` of 792, or setting the content minimum after the toolbar is attached), not made here: it changes the shipped window's minimum.
