## Decision rules, written before any table code and before any measurement (2026-11-16)

### (a) The row layout

**The question.** Plan 3.3 item 2 chooses a native `<table>` with spacer rows above and below the mounted window. The previous sprint measured "fixed rows in normal flow" as live-update p95 +22.5% and layout +20.9% and reverted it (T-03; `bench/app/README.md:835-838`; host #470 comment), and the shipped table positions every row absolutely and moves it with `transform: translateY(var(--_dt-row-offset))`. Those numbers came from the old CSS grid and flex markup, in Chromium, from two samples per side ("screening only, not acceptance"). Whether a native table with `table-layout: fixed` behaves differently is `[INFERENCE]`. So the choice is made by measurement under live updates, not by static scroll.

**Candidates**, all on the same components: the same TanStack Table row model with the adaptive sorted model, the same virtualizer adapter (fixed row height, overscan and step from the same constants), the same memoised row and cell components, the same plain text cells (the layout is measured, not the cells), the same columns, rows and data:

- **S, spacer.** Native `<table>` with `table-layout: fixed` and a `<colgroup>`; sticky header cells; the `tbody` holds a top spacer row, the mounted window in normal flow, and a bottom spacer row (both `aria-hidden`); `aria-rowcount` on the table and `aria-rowindex` on each mounted row. No per-row custom property, no `position: absolute`.
- **A, absolute.** The shipped technique rebuilt on the same components: rows `position: absolute`, `transform: translateY(var(--row-offset))` with one custom property per row, row display grid or flex with the column sizes from the table, the body `position: relative` with the total height. Overriding `display` on table parts drops the table semantics in some engines, so A carries explicit `role` attributes on every table part (`table`, `rowgroup`, `row`, `columnheader`, `cell`) and `aria-rowindex`; their cost is part of A.
- **R, reference (not a candidate).** The previously shipped table itself (the library `DataTable` of `@omniviewdev/base-ui` 0.17.3 with its virtual body, as the host and the Kubernetes plugin use it), mounted in the same bench page with the same rows, plain text cells and the same driver, in both engines. It is what the new table must not be slower than ("no regression against the product"). If R cannot be mounted in the page within the step's time box, A stands in for "the previously shipped layout" and the report says R was not measured; the sprint's recorded numbers are quoted as quoted, never as ours.

**Workloads** (5,000 rows from the kind corpus unless said; the narrow column set; comfortable density, 40 px rows):

- W0, static scroll: wheel input from Node at 1,200 px/s, 60 events a second, for 5 s after a 3 s warm-up that scrolls the same path (B2).
- W1, live-update scroll: W0 with the seeded sparse-update workload at the row level (5 events a second, 2 rows per event, every tenth touch a delete and a recreate under a new key; `bench/render/fixtures/updates.ts:133`, `--updates sparse`), 1x CPU in both engines, and 4x CPU in Chromium (CDP throttling; WebKit has none, so that cell is not measured there).
- W2, live updates at rest: the same updates with no scroll, 10 s: commits per update, rows rendered per update, comparator calls (G-T1, G-T2).
- W3, mount and sort: mount to the first row at 25, 1,025 and 5,025 rows; bulk re-mount of a 60-row window (B1); sort by Name from a click to the next painted frame at 5,025 rows.
- C, control: the same driver on a page with a scroller of 5,000 plain `div` rows (no table). It fixes the floor of the machine and the engine: idle rAF cadence, and the p95 an empty windowed scroller gets.

**Design of a measurement.** Candidates run INTERLEAVED in pairs (S, A, R, S, A, R, ...), the order rotated each round, so that machine drift hits every variant equally (the baseline of row N8 was taken at a load of 7 to 14 on 18 cores and states that differences under about 15% are noise; the machine here is shared with other agents' sessions too). At least 9 trials per variant, workload and engine; every trial in a fresh page; the load average is read before and after every trial and a trial with a 1-minute load above 12 is repeated. Frame intervals are requestAnimationFrame deltas (nearest-rank percentiles, a real frame, never interpolated). "Frame work" is the time from the start of a rAF callback to the next message-channel macrotask, which spans the callbacks, style, layout and the main-thread part of paint in both engines. Chromium also records CDP `Performance.getMetrics` (layout, style, script and task durations; layout and recalc counts), long tasks, and the React Profiler counts (`react-dom/profiling`); WebKit has no CDP, so for it only the rAF and frame-work signals and the React counts exist.

**The rule**, in order:

1. **Veto: accessibility.** A candidate is out in an engine if, in that engine, its accessibility tree (Playwright aria snapshot in both engines, plus the engine's own tree through CDP in Chromium) does not expose a table with its row count, rows, column headers with their sort state, and cells; or if rows become Tab stops; or if axe-core reports a serious or critical issue. Explicit `role` attributes that restore the semantics pass, and count their cost.
2. **Primary: W1 at 1x, 5,000 rows, rAF interval p95, paired.** In each engine count the interleaved pairs in which X's p95 is lower than Y's (ties split half). X BEATS Y in an engine when it wins at least 7 of 9 pairs (the same share for more trials) and its median p95 is lower by more than 5%. X is WORSE than Y in an engine when Y beats X there.
3. **Choose** the candidate that is not worse than the other in either engine and beats it in at least one. When the engines disagree (one candidate beats the other in one engine and is beaten in the other), take the candidate whose worst engine result is better (minimax on the relative difference of the median p95), because the product ships on WKWebView, WebView2 and WebKitGTK.
4. **Tie** (neither beats the other in either engine): compare the median frame work on W1 in both engines; a difference under 10% is a tie again, and a tie goes to **S**: native table layout, no per-row custom property, no role overrides, fewer lines of code (owned code wins ties, R5).
5. **S loses.** If A beats S in at least one engine and A passes the veto in both, the previous sprint's finding reproduces: choose A with its roles, record that the plan's spacer pick was overturned by measurement, and carry the ladder only if a budget is still missed. If A does not pass the veto, keep S and run the ladder (3.3 item 6) on S; a budget still missed after one week is trigger T1.
6. **Not a layout question.** Whatever is chosen must still meet B1 to B7 (3.3) on the chosen layout; the rule only chooses, the budgets accept. The overscan (6) and the range step (the old 4 rows, with overscan 8 so that a step of 4 exists) are measured on the chosen layout as a small sweep ({6/3, 8/4, 10/4}) on W1 before they are fixed (T-02: 4 is the measured value and a different window logic must beat it).
7. The numbers, the raw files and the exact command go to `docs/ui-next/baseline/`; the losing layout stays in the git history of this branch (the commit is named in the baseline file) and is deleted from the kit (no dead code). The bench keeps the ability to rerun R.

### (b) What B2 refers to, and whether it is kept

**B2 as written** (plan 3.3): "scroll at 1,200 px/s over 5,000 rows for 5 s: rAF interval p95 at most 16.7 ms, composite cadence p95 at most 33.4 ms, 0 coverage holes", read from the frame diagnostics of `bench/app/README.md:444-448`. It names one workload: a static list, no live updates. The old table's recorded numbers are different things: **33.4 ms** is the whole old app, unthrottled, healthy metrics, NO resource updates, frame interval p95 after the sprint's fixes ("still miss[es] the 20 ms frame goal", `bench/app/README.md:931-942`); **66.7 ms** is the same candidate WITH sparse live updates (`:945`), and under 4x CPU the input stalled (966.6 ms). Both are Chromium, headless, in-page backend, metric cells included.

**Reading I take** (proposal, for the lead to approve or amend; nothing below changes a budget by itself):

- **B2a (kept as written).** Static scroll W0 at 1x CPU, rAF interval p95 at most 16.7 ms, in both engines, on the new table with real rows. 16.7 ms is the 60 Hz slot: at most 5% of frames miss one. It is deliberately stricter than the old table's 33.4 ms (a rewrite, at most 21 elements per narrow row, no per-row subscription); an old-table miss against it is not a regression against the product. This is the number trigger T1 refers to.
- **B2b (split out, proposed).** The same scroll with the sparse live-update workload W1 at 1x CPU. The plan has no budget for it and the old table recorded 66.7 ms. Proposal: at most 33.4 ms, i.e. live updates may cost the table no more than the old table's frame p95 WITHOUT updates. Until the lead decides I report W1 against both 16.7 and 33.4 and against R measured in the same harness.
- **B2c (report only).** W1 at 4x CPU in Chromium: the old table could not complete it, so no number is held; it is reported to show what a slow machine does.
- **Composite cadence** (the second number of B2) is not a page-visible signal: rAF deltas are not compositor output (`bench/app/README.md:278` says so). WebKit exposes no way to read it; in Chromium it needs a trace. Not measured unless a trace is cheap to add; written as not measured.
- **Trigger T1, precisely.** T1 fires when B2a is still missed in either engine on the reference machine after one week of the ladder (fewer default columns, flatter cells, less overscan, no per-row effects), OR when B2b exceeds R's own W1 result measured in the same harness (a regression against the shipping table), OR when a B3 to B7 count is missed. A B2b result between 33.4 and R's is a recorded miss of the proposal, not T1. A B2c result never fires T1.
- **The machine floor.** Headless Chromium paces frames at a virtual 60 Hz and headless Playwright WebKit may not; both engines run under software rendering on a shared machine. So every B2 number is reported with the control C beside it, and when C itself is above 16.7 ms in an engine the B2a verdict in that engine is the relative one (table p95 not above C's p95 by more than one rAF interval); that relative reading is also part of the proposal.
- **Why not simply amend B2.** B2a needs no amendment if the table meets it. If it does not after the ladder, amending a budget needs the lead's approval: the status file will carry the proposal with the measured numbers, and the PR will say it plainly.
