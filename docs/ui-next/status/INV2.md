## Who is affected (read this first)

**SERVER mode only** (`-tags server`: the browser-hosted build the seam, the probes, the audit gateway and the agents' browser verification use). The native app is **not exposed to the stall** (reasoned from the code and from a run that pins one window identity; not run natively): a native window's scope is retired by Wails' `WindowClosing` and it takes 64 live native windows to fill the realm; one long-lived window opening and closing many tabs left every counter flat (below).

## The cause

The window realm (`backend/pkg/invocation/window_realm.go`) keeps one scope for each window and **refuses a window when it already holds 64** (`:65` at `2a1924ce`). A scope leaves it only when Wails fires `WindowClosing` for the window (`:70-81`), which also calls `RetireSourceOwner` and so closes the owner's source interests, sessions and views. In server mode a page's window is Wails' `*BrowserWindow`, and its `OnWindowEvent` is `return func() {}` (Wails v3.1.0 `browser_window.go:85`): nothing ever fires, so **the scope of a closed page, and everything it owns, stay for the life of the host**. Every page load and every reconnect of a page's events socket makes a window. The main window holds one slot: **the 64th window is the first one refused**. Every call a page then makes through the resource service is answered `422` `Access denied` (`FORBIDDEN`) in 1 to 4 ms (an empty principal, refused by `Boundary.Admit`, made generic by `apperror.ForResource`); nothing is logged; the page says `Couldn't load <Kind>` / `No connections`; both processes are up and idle (264 host goroutines and 427 plugin goroutines, none on a mutex), which is all K2b-2 and K2c-1 saw. A call with no page (a script with a client id and no socket) is attributed to the main window and is still answered.

It also leaks, for every page that closes: its source sessions and views in the host and **an informer with its watch in the plugin** (+3 host goroutines and +6 plugin goroutines a page for a list, one API-server WATCH for each session; memory and file descriptors do not move). It was already written down as a bound of the audit gateway's first design (`docs/development-audit-gateway.md`, "a host that serves many sessions [needs] a restart now and then") and never connected to B-44.

## The fix

`WindowRealm` asks Wails itself whether a server-mode page is still there. A window that names a page (`ClientID()`: only Wails' `BrowserWindow` does) is kept with its client id; while the realm holds one, a timer runs every 2 s: a client id with no events socket registered (`application.GetBrowserWindow`) on **two sweeps in a row** has its scope retired exactly as a closing native window's is (removed, remembered as closed for a minute, `onRetire(owner)` outside the lock). It stops when no page is left. Native windows are untouched; the cap is still 64, now of **live** windows; no service, no `main.go`, no ownership rule changes.

Per client id and not per window, on purpose: a page whose socket reconnects gets a new window (a new identity) and its old identity stays until the page is gone, so nothing a connected page can still use is closed (the reconnect itself is a separate, existing defect: below).
