## The seam's settings-slots wait: NOT reproduced, not fixed

The failure (PR #705, Seam webkit, run 45466782774): scenario s, part `slots`, one of the 100 Settings window pages never showed its rows or the failed notice in 30 s (`page.waitForFunction`, `seam.check.mjs` `read`). The same job's first attempt had passed that scenario and was cancelled in the controls step; the third attempt passed.

Tried: the slots part alone (new `SEAM_ONLY=settings-slots`, clean) in WebKit, from `env -i`, the host cross-built for Linux (`CGO_ENABLED=0`, the CI's tags): (a) the CI image `omniview-ci:local` (amd64, under emulation, 2 CPUs): 1 of 1 passed, 7.9 s a page; (b) a Playwright 1.64.1 noble image with Go and pnpm, arm64 native, `--cpus 2`: 3 of 3 passed, 0.48 to 0.52 s a page (a 4th was lost to my stopping the container). The 20 of 20 asked for was not reached, because no failure was ever seen to fix. The registry's CI image could not be pulled (private; the token has no `read:packages`).

What the code says (inference, not shown): the page's first Settings load (`load()` in `ui-next/shell/settings/model/session.ts`) asks the host with no deadline, where every later question has one (`ASK_DEADLINE`, then `RETRY_WAITS`); a first question that is never answered leaves the page on "loading" with no failed notice, which is what the wait saw. Not changed here: no run showed that the host did not answer.

Changed so the next failure names its cause: the wait is the same (event-waited on the page's own state, bounded at 30 s); when it is lost the failure now says the page number, what the page showed (text, state, row count) and how many windows the host listed. `SEAM_ONLY=settings-slots` runs the part alone.
