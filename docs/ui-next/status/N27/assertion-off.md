# How the assertion of a control is removed (ASSERTION_OFF), by probe: read from the probes' code by four readers (N27); nothing here was run

No control of the slice writes a file or spawns a child; the only builds are `buildUiNext()`/`build()` when DIST is unset (serve.mjs:22, row-menu-probe.mjs:66; the control name never reaches them). With DIST set all four probes only read it (serve.mjs:50 `readFileSync(file)`; row-menu-probe.mjs:81). The probes write only SHOTS/REPORT.

- form-probe.mjs: `ASSERTION_OFF=says` sets `OFF = control.says` (the regex of the control's entry, line 780); any other value is `new RegExp(value)` (:47); OFF filters in `fail()` (:56) in the clean and planted run alike. The `says` regex is NOT printed (only in source). Lines: `detected: <c> (<fault>): <planted[0]>` exit 0; `NOT DETECTED: <c> (<fault>); <section> said: nothing` exit 1; `INVALID: <c> (<fault>) trips assertions it is not named for: a | b` exit 2; `INVALID: <c>: the clean run is not silent, so the control proves nothing:\n  <lines>` exit 3. Unknown control: thrown Error (node exit 1, no printed line). Chromium 1440x900 only, two runs (clean, planted).
- log-probe.mjs: NO ASSERTION_OFF at all (grep: none). Independence is by `expect` regex (+ optional `says` string, axe only: 'button-name') per control (:163-170), checked by controlProblems (:1112): baseline must make the assertion and agree, perturbed must fail it. Lines: `detected: <c> fails <id> (<where>) and the same assertion passes without it` exit 0 (process.exitCode); `NOT DETECTED: <c>\n  <problem>...` exit 1 (problems: `setup error without/with the perturbation: ...`, `the assertion <regex> was not made without the perturbation`, `the assertion does not pass without the perturbation: <key> (<outcome>)`, `the perturbed run did not fail <regex>[ with "<says>"]`). Up to 20 `DIFF <where> <id>: mock .. kit ..` lines first. No INVALID, no exit 2/3. Unknown control: Error thrown at load (:180). Regex not printed except inside the problem lines. Default engine chromium, viewport 1440x900.
- row-menu-probe.mjs: `ASSERTION_OFF=<regex>` (:55) must match the failure line `<where>: <what>` where where=`chromium 1440x900`; use the control's `expected` regex source: trigger-not-expanded `top mouse: aria-expanded on \[\], aria-controls on \["Actions for worker-1"\]$`, expanded-twice `top mouse: aria-expanded on \["Actions for worker-1","Actions for worker-2"\], aria-controls on \["Actions for worker-1"\]$`. `says` is not supported (value `says` would be the regex /says/, matches nothing). Not printed as a pattern; the failure line is printed inside `detected (...)`. Lines: `NEGATIVE CONTROL "<c>": detected (1 failure, <line>)` exit 0; `NEGATIVE CONTROL "<c>": NOT DETECTED (<n> of the failures are the one named, <m> other failures[: a | b])` exit 1; `NEGATIVE CONTROL "<c>": SETUP ERROR, the opening failed before the perturbation (<n>): ...` exit 1 (no INVALID). OFF applies to the baseline too. Unknown control: thrown Error (:662).
- sheet-probe.mjs: `ASSERTION_OFF=says` sets `OFF = control.says` (:409), e.g. / trap: /; other value is a RegExp (:39). `says` not printed. Lines (printed per engine): `detected: <c> (<engine>; <fault>): <planted[0]>` exit 0; `NOT DETECTED: <c> (<engine>; <fault>)` exit 1; `INVALID: <c> (<engine>; <fault>) trips assertions it is not named for: a | b` exit 2; `INVALID: <c> (<engine>): the clean run is not silent, so the control proves nothing:\n  <lines>` exit 3; exit = max over engines. ENGINES is not set by the unit env (only DIST), so the default `webkit,chromium` makes runControl run BOTH engines at 1440x900 (:411), though the unit text says Chromium. Also prints `uptime: ...` first (:433).


## ui-next/shell/probes/logs-open-probe.mjs (logs-open-controls)
- ASSERTION_OFF is any regex (`new RegExp(...)`, logs-open-probe.mjs:47), NOT validated; it is tested in `fail()` against the line `${name} [${engine}]: ${text}` (:97-100), for the clean AND the perturbed run, so the control's own assertion vanishes from both.
- Set it to the printed pattern: the probe prints `its assertion, to remove with ASSERTION_OFF: ^${named.replace('.', '\\.')} ` (:155), i.e. `^rate\.max ` (counted-replay), `^rate\.unknown ` (no-wait), `^never\.unknown ` (timeout-live); note the trailing space. Printed on detected and on NOT DETECTED alike.
- Detected: `NEGATIVE CONTROL "<c>": detected (<first perturbed failure line>)`, exit 0 (:154,:158). Needs clean run has no `named` failure, perturbed has one, and every perturbed failure starts with an `allowed` name.
- Not detected: `NEGATIVE CONTROL "<c>": NOT DETECTED (clean: N <named> failures; perturbed: M; others: <lines joined by " | ">)`, exit 1. No INVALID line: a clean-run failure of the named assertion = NOT DETECTED too.
- A bad NEGATIVE_CONTROL name throws before any browser (:46). Runs one engine (chromium unless ENGINES is set), clean and perturbed side by side.

## ui-next/shell/probes/logs-probe.mjs (logs-controls-feed, logs-controls-toolbar)
- ASSERTION_OFF must equal the control's own `expected` regex source exactly: `OFF.source !== PERTURBATIONS[CONTROL].expected.source` or no control throws `ASSERTION_OFF must be the pattern of the active negative control's own assertion (NEGATIVE_CONTROL=<c>, its pattern is <source>)` (:120). Empty string = unset (:118).
- The pattern is NOT printed in a normal run (no `its assertion, to remove` line); take it from PERTURBATIONS (:67-98) or from that error message. Dropped in `fail()` (:121-124), tested against `${where}: ${what}`, e.g. `^hidden .*: the feed emitted`.
- Detected: `NEGATIVE CONTROL "<c>": detected (N differences, e.g. <line>)`, exit 0 (:1811,:1819). Before it: `what the probe saw with the perturbation "<c>": N differences` plus the failure lines.
- Not detected: `NEGATIVE CONTROL "<c>": NOT DETECTED (N other failures)`, exit 1.
- Toolbar controls only (TOOLBAR_CONTROLS, :102): detected but with other failures prints `NEGATIVE CONTROL "<c>": FAILED, N other failures (a control trips only its own assertion): <first other>` and exits 1 (:1814-1817). With the assertion off it should print NOT DETECTED with 0 other failures.
- No INVALID line. Baseline guards fail with their own line (`close-twice: the baseline is ...`, `second-stream: the baseline is ...`, `the control lone-scope found no tab ...`, `the control same-name found no two tabs ...`) which the control's regex does not match, so result is NOT DETECTED.
- A section that ran in no engine fails only with no control (:1804). Sections run: control's `sections` only, chromium, 1440x900.

## ui-next/shell/probes/notices-probe.mjs (notices-controls-toast, notices-controls-centre)
- ASSERTION_OFF is any regex, NOT validated (:85); tested in `fail()` (:86-89) against `${where}: ${what}`. Use the control's `expected` source, which the probe prints (:2743) after the result line: `its assertion, to remove with ASSERTION_OFF: <expected.source>` (e.g. `^geometry [^:]* info: toast 1\[w\]`), also on NOT DETECTED.
- Detected: `NEGATIVE CONTROL "<c>": detected (N differences, e.g. <line>; M other failures)`, exit 0 (:2740-2744). Other failures do not fail it.
- Not detected: `NEGATIVE CONTROL "<c>": NOT DETECTED (N other failures[, e.g. <first>])`, exit 1.
- No INVALID line, no baseline guard: a failure that matches `expected` from an unperturbed fault counts as detected. Unknown control name throws (:729).
- Chromium 1440x900 unless ENGINES/VIEWPORTS set (:2677-2679); production is always built (:2670); development only when (perf||centre) and parts undefined or including `commits` (:2672): in this slice only centre-second-commit.


## palette-probe.mjs / palette-plugins-probe.mjs (the wrapper sets process.env.SECTIONS='plugins' and imports palette-probe.mjs; same code)
- ASSERTION_OFF is a REGEX, not a control name: `const OFF = process.env.ASSERTION_OFF === undefined ? undefined : new RegExp(process.env.ASSERTION_OFF);` (palette-probe.mjs:58). `fail(where, what)` builds `line = \`${where}: ${what}\`` and drops it when `OFF.test(line)` (59-62). An invalid regex throws in `new RegExp`; no other validation.
- The pattern to use is the control's own `PERTURBATIONS[<name>].expected` (palette-probe.mjs:616-640, header text line 14-15: "run with its own pattern (PERTURBATIONS[<name>].expected) here, and it must then print NOT DETECTED"). The probe NEVER prints that pattern; there is no "to remove with ASSERTION_OFF" line. Take `.source` from the table, e.g. `^geometry .* empty: frame\[w\]` or `^[^:]+: plugins typing: a key pressed while the slow provider worked waited`.
- Failure line shapes the pattern sees: geometry/paint `geometry chromium 1440x900 empty: frame[w]: mock .. shell .. (off by ..)`; keyboard `keyboard chromium 1440x900: <what>`; plugins `chromium 1440x900: plugins <part>: <what>`.
- Printed at the end (control mode, palette-probe.mjs:724-728): detected -> `\nNEGATIVE CONTROL "<name>": detected (<n> differences, e.g. <first matching line>)`, exit 0. Not detected -> `\nNEGATIVE CONTROL "<name>": NOT DETECTED (<n> other failures)`, exit 1. No INVALID state. With ASSERTION_OFF=<expected.source> the desired result is the NOT DETECTED line (exit 1).
- The control mode prints no list of the failures (unlike strip/tour); only the first matching line. A thrown error (build, timeout, bad NEGATIVE_CONTROL: "NEGATIVE_CONTROL must be one of ...") is an uncaught exception, non-zero exit, none of the lines above.
- Control mode runs Chromium 1440x900 only unless ENGINES/VIEWPORTS are set (657-659).

## panel-probe.mjs
- NO ASSERTION_OFF support: the string does not occur in the file; the variable is ignored. A control cannot have its assertion removed by env.
- Control mode (1634-1638): detected -> `\nNEGATIVE CONTROL "<name>": detected (<n> differences, e.g. <first matching line>)` exit 0; else `\nNEGATIVE CONTROL "<name>": NOT DETECTED (<n> other failures)` exit 1. No INVALID line; the expected regex of PERTURBATIONS (1573-1592) is not printed. Failure lines are `<where>: <what>` where where = `geometry|shift|held|twins|twin-rules|a11y|drag <engine> <viewport> ...`.
- Surprise: control mode does NOT narrow engines/viewports (the loops at 1602 and 1604 use engineNames and viewportNames, both engines and both viewports by default, not Chromium 1440x900 as the header says) unless ENGINES/VIEWPORTS are set in the env.

## strip-probe.mjs

## tour-probe.mjs
- ASSERTION_OFF=<control name> (an exact key of PERTURBATIONS, else throws `ASSERTION_OFF must be one of ...`, tour-probe.mjs:51-52). It is independent of NEGATIVE_CONTROL: `REMOVE` skips the control's assertion (names 139,147,165; titles 253,264; twins 309,318-319; memory 363). Set ASSERTION_OFF=<same name> with NEGATIVE_CONTROL=<name>.
- The pattern is the name itself, so there is no printed pattern line. Output in control mode (391-396): `\nwhat the probe saw with the perturbation "<name>": <n> differences\n  <each failure line>`, then `\nNEGATIVE CONTROL "<name>": detected (<n> differences, e.g. <line>)` exit 0, or `\nNEGATIVE CONTROL "<name>": NOT DETECTED (<n> other failures)` exit 1. With ASSERTION_OFF the wanted outcome is NOT DETECTED (exit 1). No INVALID state. Unit tour-controls sets BUILD_CACHE (shared build already, harness.mjs buildFixtures).

## ui-next/shell/probes/settings-probe.mjs (+ settings-controls.mjs, settings-lib.mjs); units settings-controls-*
- Set: `ASSERTION_OFF=says` (settings-probe.mjs:110 `state.off = spec.says`, applied to the clean AND the planted run); or any other value = a regex (`:50` `state.off = new RegExp(...)`), matched against the failure line `"<id> <where>: <message>"` (settings-lib.mjs:46-47). `says` without NEGATIVE_CONTROL throws `ASSERTION_OFF=says needs NEGATIVE_CONTROL` (:51). The control's own name is not used.
- Header: `control <name> (<fault>):` then `  clean:   N failures, N of the control's assertion` and `  planted: N failures, N of the control's assertion, N others that are new`.
- Verdict, exit code (precedence in this order, :124-135): `INVALID: <name>: the clean run already trips <regex source>, so the control proves nothing: <line>` exit 3; `INVALID: <name> trips assertions it is not named for: <up to 3 lines joined by " | ">` exit 2; `NOT DETECTED: <name> (<fault>)` exit 1; `detected: <name>: <first tripping line>` exit 0.
- Always printed last, on every branch (:137): `its assertion, to remove with ASSERTION_OFF: <spec.says.source>  (ASSERTION_OFF=says does it)  [<n> s]`. Detected = exit 0; with `says` the expected result is `NOT DETECTED` exit 1. Final `process.exit(code)` (:143). REPORT is not written in control mode.
- Build: only `buildFixture('production')` (settings-lib.mjs:63-75, settings-probe.mjs:87), into BUILD_CACHE/production + stamp `.built`; no development build; the control name/env reaches no build, file write or child process (only `uptime` and the build, which is the same for clean and control). No control writes or reads in the build dir.
- `plant()` (settings-lib.mjs:297-302) = `page.addStyleTag` (css) and/or `page.evaluate(js, arg)`, called by a section AFTER `openFixture` returned (goto `load` + ready selector + font normalise). No control uses an init script: NONE plants before the page loads. Stages: default `ready` (after drawn, at the section's call site, see the evidence column); `rows` (rows-order only, after goToPage, settings-page.mjs:196; the `ready` call at :33 skips it); `start` (settings-perf.mjs:63) is used by no control. perf-open-* plant after load, with the loading line on screen, before `window.__release()`.
- Fixture URL flags (ui-next/shell/probes/settings-fixture.tsx:26-31,113): `case` (sheet|window), `host` (ok|held|failed|down|empty), `values`, `stored`, `theme`, `request` via URLSearchParams(window.location.search). They are the probe's own scene queries, the same in the clean and the planted run; no control sets one. Window globals the controls use are set by the fixture (:34-127): `__host`, `__stops`, `__hold`, `__release`, `__windows`, `__control`; `window.__step` is set by settings-sheet.mjs:372-388.
