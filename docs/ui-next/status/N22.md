## Result in one paragraph

A WKWebView preference reaches it: Wails v3.1.0 exposes `WKPreferences.tabFocusesLinks` as `MacWindow.WebviewPreferences.TabFocusesLinks`. Set once on the shared window template, it makes Tab reach every control in the new UI and in the old one, with the macOS setting untouched. No kit change (option (b), `tabindex="0"`, is not needed). The traffic-light offset from the same finding list is split out to a draft PR (branch `ui-next/n22b-traffic-lights`, `docs/ui-next/status/N22b.md`) because it also moves the shipped old UI's lights and is not verified for full-screen, double-click maximise and the Settings window.

## 2. The fix and why

Order of preference from the assignment: (a) a WebKit preference on the native webview; (b) `tabindex="0"` in kit parts.

(a) is reachable:

- `application.MacWindow.WebviewPreferences` (`wails/v3@v3.1.0/pkg/application/webview_window_options.go:640-641`), type `MacWebviewPreferences` with `TabFocusesLinks optional.Bool` (`:772-775`).
- Applied when the webview is created: `getWebviewPreferences()` copies it into the C struct (`webview_window_darwin.go:1574-1576`), and `config.preferences.tabFocusesLinks = *preferences.TabFocusesLinks` (`:143-145`). The purego build does the same (`webview_window_darwin_purego.go:895-896`).
- The field is `optional.Bool` from an `internal` package, so the repo cannot name the type; it sets it by method on an addressable variable (`window_options.go`, `macWebviewPreferences`).
- It is set on the one window template (`main.go:850`). Every window starts from that template: the main window (`main.go`), and the window service's secondary windows copy it (`backend/window/wails.go:55-61`; the Settings window overrides only `Mac.TitleBar`, `wails.go:76`). So old and new UI both get it.
- The public name says "links", but in WebKit this switch also turns on Tab to buttons: I did not rely on the name, I ran it (experiment 1, then the final build): same window, same setting, Refresh and the top-row tab button became stops.

Why not (b): it changes three kit parts and leaves every other plain `<button>` (old UI, plugin UI, third-party widgets) skipping the Tab order on a default Mac. (a) is one place, covers all of them, and costs no kit API change.

Not changed: Windows (WebView2) and Linux (WebKitGTK) already Tab to buttons; the option is a macOS-only struct field.

Roving groups stay roving (`RovingGroup`: one Tab stop per group, arrows inside), as in VS Code toolbars and JetBrains tool windows; "every control is a stop" is met at the group's entry point.

Test: `window_options_test.go` (`TestMacWebviewPreferencesTabToEveryControl`). It was red first (`go vet`: undefined `macWebviewPreferences`), then green.
