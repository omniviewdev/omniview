# T2b: a Terminal tab survives a window reload

**Status: for review (see the PR).** Branch `ui-next/t2b-terminal-reattach` on `origin/main` 19935ee1 (the T2a slice #671, the Go side of reattach #674 and its follow-up #675, `next_input_seq` and the dismissal of an ended terminal, are merged; the kit's menus and Home, #676 to #684, are in). Worktree `~/Repos/omniviewdev/worktrees/ui-next-t2b-terminal-reattach`. Owner agent `TerminalTool`. One slice: the page of T2a becomes the client of the host's reattach contract (`T2-go.md`).

## 1. What this slice is, and is not

In: a page key kept in the window's state and given to every terminal the host starts; on load the page lists the terminals it left, gives each saved tab its terminal again and attaches; the replay of the host's ring is written into a new emulator with its replies muted and its size and modes applied; the live output follows byte for byte; the words for a terminal that another tab took, one that went with its window and one whose lease ran out; the detach at `pagehide`; the three leftovers of T2a (the host's tried shells in the words of the page, the refused-resize replay bug, the clipped twin tab).

Not in, and not built (the slices that follow, section 8): the panel coming back OPEN after a reload (decision 6); re-joining after the page's events socket reconnects (`from_offset` is mapped in the transport and nothing sends it, W2); a detach at `pagehide` that survives in WebKit (the runtime's call has no `keepalive`, W3); the words and a "take it back" action for a terminal whose taker has gone; titles from the program, rename, the bell mark, restart an ended terminal (`T-terminal-bar.md`).

Input numbering after an attach: the host's queue is the terminal's, not the window's, and an attach does not reset it, so a page that attaches continues the count from `Attached.next_input_seq` (host #675, T2-go 2.4 step 9: the lowest number not yet taken, at least 1 on a live terminal, 0 on one that ended), one counter for writes and sizes as before. Never from `Listed.next_input_seq` (the window that holds the terminal can write between the list and the attach) and never from 1 (after an attach that number is `SEQUENCE_STALE` whenever the page that held the terminal typed: measured). An answer for a running terminal that lacks the number is unreadable and the tab fails in words. The first version of this slice had a fallback for a host that does not say it (number 0, the host's unsequenced mode, one call in flight because the real host does not keep the send order of concurrent unnumbered calls: 26 concurrent writes were never in order); it was deleted when #675 merged, since the page ships inside the host's binary and no older host exists to talk to.

## 3. Decisions

1. **The key lives in the window's state, not in `sessionStorage`.** The contract suggests `sessionStorage`; the lead ordered the place where session restore keeps window state. The cost: browser tabs of one server share the `main` window's slots, so they share the key, and a second tab takes the terminals over (that is what "Taken over by another tab" is for). A desktop window has its own slots.
2. **The panel session id is the terminal id.** A saved panel session already has an id, and the session document restores terminal sessions `ended` and feedless; a terminal made with that id is found by it after a reload, so the registry gives the saved tab its terminal again and there is no second tab.
3. **A fresh attach only.** The page has nothing after a reload, so it asks for the whole ring (`from_offset` absent).
4. **The page leaves, it does not close.** At `pagehide` a keyed terminal is detached and not closed; the host's lease (5 minutes by default) is the time the person has to come back.
5. **Words, not guesses.** A terminal the page lost says who took it ("another tab"), and a terminal the host closed says why; none of it is read from anything but the host's typed events. A keyed feed listens to `output`, `DETACHED` and `CLOSE` only: the host's own terminal ends with a typed CLOSE (`failed` with the failure); `ERROR` is the plugin exec stream's.
6. **The panel stays closed after a reload (rule S116), and the Terminal tool does not take the keyboard.** The session restore keeps a restored terminal from covering the page (S116 was written when every restored session was dead). Now that a terminal can be alive again, a reload brings the window back as the page alone and nothing says a terminal waits; the person presses the panel's toggle and the terminal is there with its scrollback. This slice leaves S116 as it is: the saved `open` flag is the session module's and the panel model's, and a rule that says "open again when a terminal was reattached" needs both (section 8). A restored terminal that was never shown has no screen and does not read: the host pauses its shell 1 MiB past the replay (nothing is lost, no CPU is spent) and goes on when the tab is shown (measured: 1.06 s, 0.115 s after the toggle). The focus follows T2a's rule for a session the person did not just open: it stays where it was (the Terminal tool's tab) and one click on the screen gives the terminal the keyboard.
7. **One path for the input numbers: the host's.** The page continues the count from the attach answer's `next_input_seq` and has no fallback. The lead's first brief said to treat a missing number as 1; the real host answers `SEQUENCE_STALE` for 1 after an attach (measured), so the first version sent number 0 (unsequenced, one call in flight) until #675 gave the field; that code was then deleted, since the page ships inside the host's binary and no older host exists.

## 4. What the real host does (measured, `bin/Omniview-server`, server mode, WebKit, Chromium and a raw client)

The harness and every payload are in the explorer's scratch folder (`/tmp/t2b-explore`, not in the repository); the facts the page relies on:

- A keyed terminal sends output only as `core/exec/stream/output/<id>` with `{offset, data}`; events are contiguous (0 gaps in 12,198 events) and at most 1,024 bytes on macOS (the pty read size). `session.id` is the id the page gave and a live id cannot be created twice.
- Reload: the new page is ready in about 0.35 s and sees `attached: true` for 2 to 4 s, until the host retires the old window (sweeps every 2 s, two sweeps): always attach, never wait. If the new page attaches first, no retirement event follows; its own takeover comes back to it as `DETACHED taken-over` with the OLD number.
- `AttachTerminal` answers in 1 to 8 ms; the replay is the ring (at most 1.31 MB), equal byte for byte to what the old page received. With `vim` open: alternate screen, application cursor, focus events, bracketed paste, mouse tracking 3 and encoding 2 are in `modes`. A resize to the same size makes vim print nothing; a bounce makes it redraw.
- Reload during a 25.9 MB flood: the live output continues exactly at `replay.end`; six storms of 300 to 400 attaches each were byte-exact against a listener. Events covered by the replay arrive after the answer in 0 to 11 of every 400 attaches, up to 2 ms later, whole.
- Flow: the explicit credit mode survives the attach and the new page needs no first `AckTerminal(id, 0)`; it must acknowledge only bytes taken from events. A new page that attaches and never acknowledges is paused after exactly 1 MiB more.
- Input (before #675, which added the number to the answer): `WriteTerminal(id, 1, …)` after an attach is `SEQUENCE_STALE` ("the next expected is 7"); number 0 works; concurrent number 0 calls are not applied in send order. With #675 the attach answer says the number (the seam asserts that the first write after a reload carries it).
- Lease: with `lease_ms: 3000` the CLOSE `{closed_by: 'detach-timeout'}` arrives 3,004 ms after the detach at every window; the list is then empty. An attach before that cancels it.
- After a host restart the list is empty, attach and detach are `session/not-found`, and the same id can be created again.

## 7. Not verified

- The Linux CI image (the seam there, the probes' seconds on a runner), Windows (no terminal there), and any engine but Playwright's WebKit and Chromium; Safari itself, and the back-forward cache (W6).
- The desktop (native) window: a reload there keeps the window's identity, so the page attaches a terminal that its own window already holds; the host's rule for that is in the contract and is exercised by the fake host in the probes, not by a native window.
- The recording predates #675: in it every write after an attach was number 0 (146 of 146) and the shell answered; nothing on screen differs from a build that continues the host's count, which the seam asserts on the real host (section 6).
- The events socket that blips (W2): the repro was written and not run; the page fails the session in words when events were lost, it does not rejoin.
- `from_offset` (mapped in the transport, nothing sends it).
- Whether the page keeps up with a very large replay on a slow machine: measured at 1.26 MB on this laptop only (21 to 23 ms to a usable screen).
- The pointer's smoothness in the recording (its frames are 40 ms apart all through; it was judged by eye), and the one second error line the recording showed at a flood reload (every reload raises one WebKit console line "Fetch API cannot load … due to access control checks" for the `DetachTerminal` the page starts at `pagehide` and the reload cancels, W3; the session saver's own write raises the same line when it is pending; none is an uncaught error of the page's code).

## 8. Follow-ups, in the order a person would meet them

1. **The panel comes back open when it was open and a terminal reattached** (decision 6): the saved `open` flag has to reach the registry, and the registry opens the panel once an attach is running. Without it a reload looks like a loss until the toggle is pressed.
2. **A taker that has gone** (the recording, still 05c): after the tab that took a terminal closes, the first tab keeps saying "Taken over by another tab … keeps running in the tab that took it" for the whole lease. The page hears the `window-retired` of the taker (every window gets every event) and can say "The tab that took it has closed; reload this tab to take it back", and a "Take it back" action is the natural control (T2c, with restart of an ended terminal).
3. **Rejoin on an events reconnect** (W2): list and attach with `from_offset = applied`, on every reconnect of the page's socket.
4. A restored tab shows its old words for the moments before the host answers (it is `ended` until the attach starts; 7 to 31 ms while the panel is closed): a "Reattaching" state from the first frame would be exact.
5. Seen in the recording and not this slice's: a taken-over, lease-closed or exited terminal keeps a solid cursor that does not blink while input is off; a taken-over tab shares the ended tab's `i` mark (a glyph for "detached" is the icons step's); the hover card covers the last transcript line (T2a's open follow-up); the empty state of a restart offers no button (restart is T2c).
