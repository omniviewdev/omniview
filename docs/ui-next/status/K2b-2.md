## What a definition could NOT express and needed code for

Each is code in the kind's `row.ts` or `object.ts`, never in the generic page.

1. **A word that is a rule over conditions, and a state that can be absent.** An autoscaler's word is a precedence over three conditions (`AbleToScale` or `ScalingActive` False is Unable to scale, then `ScalingLimited` True is Limited, then `ScalingActive` True is Scaling active) and has NO word where the object has not reported: the mock says Scaling active for anything else. A volume's and a claim's word is the phase, or Terminating once the object is marked for deletion (kubectl's, not the mock's).
2. **Text made of two maps and a rule per key.** A quota's Request and Limit join `status.used` to `status.hard` (or the spec's while the status is empty), keep the keys of one prefix, sort them and format each by its resource (cores with no unit, bytes in the mock's units, anything else raw). An autoscaler's Targets pair `spec.metrics` with `status.currentMetrics` by resource name, in three formats (a utilisation, an average value, a type the cell cannot summarise).
3. **A product, in kubectl's order.** Endpoints: the ready addresses times the ports of each subset, address-major in the mock and port-major in kubectl, with IPv6 in brackets. EndpointSlice ports and addresses are flat lists with defaults (`*`, TCP).
4. **A selector as text.** NetworkPolicy: labels, then expressions as `key Operator (values)`, `All pods` for the empty selector, none where the policy states no selector.
5. **A cell whose tip depends on the row.** A binding's Role: the name alone with `Kind/name` in the tip when the kind is the one the binding implies, the whole otherwise.
6. **A count the API omits when it is zero, and one it sends as null.** A ServiceAccount's Secrets (an absent list is zero); a Role's rules and a binding's subjects (`null` is zero, a body that is not an object says nothing).
7. **Not expressed at all, because the contract has no place for it**, as in K2a and K2b-1: the **wide set** (PersistentVolumes Access modes and Reclaim policy, PersistentVolumeClaims Access modes, Endpoints Ready and Not ready, EndpointSlices Service, HorizontalPodAutoscalers Min pods and Max pods, PodDisruptionBudgets Min available and Max unavailable: of the sixteen kinds, a PodDisruptionBudget shows nothing but Allowed disruptions without its wide set), **facets** (PersistentVolumes and PersistentVolumeClaims Storage class), the Columns chooser, sort state, selection and Create, and a count on a sidebar entry. A **log layout** (no Name column, an Object cell that links to an object of any kind, a message clamped to two lines) is what Events needs and the contract does not have (below).

## Events: measured, not added

**Not added.** The generic list handles the VOLUME of Events and not their SEMANTICS: it needs a bounded, time-ordered read and a log layout first. Measured, then read.

**On the proof cluster** (section G of the proof): the cluster held 543 Events after its fixture (the core API and events.k8s.io hold the same objects), 66 of them Warnings, in 12 Namespaces, with 37 reasons and 1,833 emissions in all (the objects' own counters); while nothing was done to it, 2 Events were added or changed in 60 s (0.033 a second); while the live changes of C ran (about two hundred objects made, changed and deleted, 389 s) the Events grew by 113 rows and deleted): the Events grew by 113 rows  emissions (0.29 rows and 2.22 emissions a second). A kind cluster at rest is the cheapest case there is: these numbers say nothing about a busy one, which is why the scale probe below exists.

**At scale** (an Events agent, scratch plugin tree `~/Repos/omniviewdev/worktrees/kubernetes-ui-next-k2b2-events-probe`, never pushed: a throwaway Events kind of the core API on the generic list, `useKindRows` unchanged, packaged and run in the real host on its own kind cluster with N synthetic Events: 1,041 / 5,041 / 20,041 including the cluster's own; Chromium 156 and WebKit 27.2 in Playwright, 1440x900, **not** the native WKWebView; the machine's load average was 18 to 120 while it ran, so the milliseconds are noisy and the three sizes were not measured at the same load; its scripts, results and the way to repeat them are in `/tmp/k2b2-events-probe/`, not in a repository):

- **The volume is fine.** The first row stays at about 0.3 s (it is the bounded first page of 256); the table is virtualised (24 rows mounted whatever N); no long task, no frame over 50 ms in Chromium; at 20,041 once loaded a jump to the last row takes 45 ms, an 80-step wheel fling has a worst frame of 17 ms, typing in the search narrows 291 of 20,041 in 533 ms after the last key. Complete grows 0.3 to 0.5 ms an Event; a reopen within 60 s holds the view twice (host about 650 MB at 20k).
- **The first screen is wrong while the set loads.** The first 256 records are the first 256 by KEY, not by time (the API lists by key; it has no time order): at 5,041 and 20,041 they are all Node Events of the namespace `default`. The newest Event of the cluster is rank 0: the top row of the loaded page is rank 2, 19 and 200 at 1,041, 5,041 and 20,041, and none of the 14 newest are on screen at 5,041 and 20,041 until the complete set lands (0.3, 1.8 and 6.4 s later), when every visible row is replaced. The quick-filter chips count the 256 loaded (`All 256 · Warning 29 · Normal 227`, then `All 5041 · Warning 504 · Normal 4537`).
- **After it completes, rows keep moving.** The list sorts live by Last seen, so every changed Event goes to the top. With Events changed at 10, 50 and 200 a second for 30 s (at 5,041 and at 20,041) the first row changed 72 to 101 times in 30 s and a visible row had changed in 35 to 38% of 50 ms samples, for a reader who does nothing; main thread busy 7 to 10% at 5,041 and 19 to 24% at 20,041; host CPU 2 to 16%, plugin 1 to 10% of a core. (K2a's rule, that a live update never moves a row, holds only in the provisional stage.)
- **Cost.** 64 MB on the wire, 79 MB of heap and 11 CPU seconds per open at 20,041; a cluster of 100,000 Events (the default TTL is an hour) would be about five times that [INFERENCE: not measured; the probe stopped at 20,041].
- **Two Event types.** The catalog holds both `k8s:/events` and `k8s:events.k8s.io/events` (both named Event); a page reads the one its definition names, and the mock is itself split (`k8s-cluster.js:84` prefers the core API, `k8s-resource.js:274` and K60.4 prefer `events.k8s.io`).

**What Events needs before it is a list** (the first two are the plugin's backend or the host; the rest are the contract and the kit):
1. a **bounded read ordered by time** (a window of the newest N and a cursor by time): `EnumerateRequest` is `{target, pageSize, cursor}` and the one native query is a label selector, so the newest-first window has to come from the plugin's backend, which holds the Events and serves them by time (Backend catalog);
2. **not loading the whole set** at large N: a projection of an Event (object, last seen, type, reason, message), as the Secret projection does, would cut the wire;
3. a **live-order policy for a log** (hold the order and say `N new`, or insert at the top and move nothing under a reader);
4. a **log layout** in `ListPageDefinition`: no Name, Actions or selection column, an Object floor of 160 px and a Message that takes the rest, clamped to two lines (a `prose` cell and the clamp in the kit), a Reason that is fixed and uncut and **folds into the message below 880 px of list width** (the list's own box width, which the contract does not give a definition);
5. a **per-row link** from the Object cell to the involved object of ANY kind (`detail` is one fixed page per kind: a Pod's page exists, no other);
6. one decision on which Event API the list reads.
