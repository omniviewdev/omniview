## The mock's rules this step follows (quoted)

- **Which columns sort.** All of them but a sensitive one: `...(column.format !== 'sensitive' ? { sort: sortOf(column.id) } : {})`, `k8s-resources.js:554`; a metadata column (`label:<key>`) sorts as text (`:563`).
- **How a column compares.** `compareBy(kind, a, b)`, `k8s-resources.js:384-397`: `number` as numbers, `time` as `Date.parse(a) - Date.parse(b)` (ascending is oldest first), `ratio` by its fraction (`x[1] ? x[0] / x[1] : 1`) then by its total (ascending is the unhealthiest first), `quantity` by `compareQuantity`, and anything else as text, `valueText(a).localeCompare(valueText(b), undefined, { numeric: true })`: a Status sorts by its WORD as text (there is no rank in the mock: `k8s-resource-definitions.js:973` `SORT = { integer: 'number', bytes: 'number', duration: 'number', ratio: 'ratio', quantity: 'quantity', 'quantity-pair': 'quantity', timestamp: 'time' }`, every other format `text`). A missing value is last in either direction and a tie is broken by the host key, ascending, in either direction (`rowsFor`, `:415-419`).
- **The default.** `defaultSort: spec.sort ? { id: spec.sort[0], direction: spec.sort[1] } : { id: 'name', direction: 'asc' }`, `k8s-resource-definitions.js:1084`: every kind opens on Name ascending but the two Events kinds (`['lastSeen', 'desc']`, `:880`, `:884`); the default column's header says so (`sortOf`: `active: sortId === key`, `:545`).
- **The click.** `on('sort')`, `k8s-resources.js:719-723`: a press on another column sorts it ascending; a press on the column in force turns it round and back (`direction: current === key && direction !== 'desc' ? 'desc' : 'asc'`): there is no third state. The kit's `nextDirection` is the same rule and is given the default as the sort in force, so a first press on the default column turns it to descending.
- **Live updates.** The mock sorts on every render: `render` calls `rowsFor(definition, all, state, frame, observedAt)` (`:537`), which re-sorts what the read holds in the order of `state.sort`; nothing holds a row still while a value changes, and a refresh keeps the previous rows on screen until the new ones arrive (`H.swr`, `core.js:514`). So a live change moves a row only when ITS sort value changed, and the other rows keep their order (stable). The one rule of the shell about the pointer (`ch16 S111`) is about drags (a tab, a splitter) and is not a rule of a table.
- **Where the sort lives and how long.** Per tab: `put(tabId, patch)` into `[ROOT, 'tabs', tabId]` (`:59`, `:722`), and remembered for the list of that connection and kind for the session (`remember`, `:127-130`, into `[ROOT, 'preferences', viewKey]`), where a list that opens again reads it back (`:669`, `sort: saved.sort`). **Never saved across a restart**: the only path of this module that is registered for saving is `[ROOT, 'types']`, the Columns chooser's choices (`:98`).

## Known gap: list -> detail -> Back loses the sort (and everything else a page keeps)

The tab model drops a tab's `pageState` on every navigation and step (`core/tabs/open.ts` `moveTab`, `core/tabs/arrange.ts` `step`: `pageState: null`; `history.test.ts` "drops the page state when stepping to another entry"). This PR backs the page's memory with `pageState` as it is today, so the sort survives a switch of tabs, a reload of the tab, closing and reopening the tab and the eviction of a page by the keep-alive cap; it does **not** survive list -> detail -> Back. The mock keeps it (`k8s-resources.js:669` re-seeds a tab's list state only when its fingerprint changed, and `:127-130` keeps it per connection and kind). The tab model's change (history entries carry the page state of the entry they leave; `step` and `navigate` restore it) is the lead's own step after the tab strip's PR; one test of this PR is skipped with that reason and asserts the sort after list -> detail -> Back, so that step turns it on.

## What the host does now (the contract of this PR)

- `ListPageDefinition.defaultSort?: DataTableSort` (the kit's `{ column, direction: 'ascending' | 'descending' }`): the column and direction the page opens in. Optional and additive; the contract's paragraph for it is in `ui-next/plugins/contract/v1.ts`.
- `ListPage` holds the sort in force: what the person chose, else `defaultSort`, and only ever a column that declares a `sortKey` (a default or a kept sort that names no such column is skipped, not an error). It passes `sort` and `onSortChange` to the table, so the kit's header draws a button and `aria-sort` for each column that declares a key, a press sorts ascending and a press on the column in force turns it round (no third state: the mock's rule and the kit's `nextDirection`), Enter and Space work because the control is a native button, and the sort is stable (TanStack's tie-break is the source's index, in both directions; a missing key is last in both).
- **Old plugin on this host:** no `defaultSort`, columns with no key: no button, no `aria-sort`, the source's order, as before (`ListPage.sort.test.tsx`, `PluginHost.sort.test.tsx`, both with a definition of the older shape). A definition with keys and no default: sortable headers that say `none`, the source's order until a press. **New plugin on an old host:** the old host never reads `defaultSort` and passes no sort to the table, so no header sorts (`admit.test.ts`: the member is the only difference and each definition is the other's in types); the packaged proof of both pairings comes with the plugin PR, as K2c-2's did.
- The kept sort: `memory.ts`/`pageMemory.ts` (the tab's `pageState`): survives a switch of tabs, a reload of the tab, closing and reopening it, the keep-alive eviction of its page and a plugin that reloads (`pageMemory.test.ts`, `PluginHost.sort.test.tsx`); never saved to disk (the tab model saves no page state), as in the mock.

## What is lost on list -> detail -> Back today (checked; the brief for the tab model's step)

Run with the real host chain in jsdom (a list with 200 rows, a quick filter, a search, a sort and a scroll offset; a link to a detail page; Back): before `{"search":"row-1","filter":"pressed","sort":"descending","scroll":120}`, after Back `{"search":"","filter":"not pressed","sort":"ascending" (the default),"scroll":0}`. So **every one is lost**: the **sort** (the tab model drops `pageState` on every navigation and step), the **search text** and the **quick filter** (the page's own `useState`, never in `pageState`: they are lost on a reload and on a keep-alive eviction too), and the **scroll position** (`PageHost`'s scroll memory is put back when a page is SHOWN again, not when its route changes). **Selected row:** the list draws no selection column yet (1a.8), so there is none to lose; the detail page's selected tab is the page's own state too. The scroll was run in jsdom and read in `PageHost.tsx`; it was not run in a browser. Keeping all of these needs the tab model's step (history entries carry the page state of the entry they leave) AND the list page writing its search and filter to its memory as it does the sort.
