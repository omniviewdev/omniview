How the ordered calls work, exactly (`execFeed.ts`; the host's contract is `T1-go.md` 2.4):

- The first number is 1, after the create call answers; text typed before that is held and goes out after it, in order, with the first numbers.
- A paste goes in calls of at most `CHUNK_BYTES` (64 KiB, cut between characters, never inside one). A WINDOW keeps at most `WINDOW_BYTES` (512 KiB) and `WINDOW_CALLS` (32) in flight, below the host's own bounds (1 MiB, 256 operations, 64 ahead); it protects the host's bounds and does not keep the order, which the numbers keep. What does not fit waits and goes on, in order, as calls are answered. The host's limits are in the create answer; the feed uses constants (reading them is a follow-up).
- A refusal with the code `INPUT_BACKLOG` (429: the host is full, the call took no number) is sent again every `BACKLOG_RETRY_MS` (50) with the same number, until the feed closes or the session ends. A refusal that says the session is gone is quiet and ends it; any other refusal fails the session in the host's words and code; a refused size only warns, and is forgotten, so a later measure of the same size is sent again (2.3).
- A worker's throwaway model of the host's queue (random delivery delays, bursts of about 120 keys in one tick) refused 33 calls without the window and none with it.

How flow works, exactly:

- The first call, `AckTerminal(id, 0)`, goes out when `CreateTerminal` has answered; the host accepts zero (it refuses only a negative count).
- Every chunk written to the emulator acknowledges its decoded byte count from the write callback, dropped bytes included (there are none). The feed keeps ONE call in flight and sums what was parsed while it was; there is no threshold.
- A count the host refuses once flow is on stays owed and is sent again after `ACK_RETRY_MS` (250) by itself, one call at a time, and goes with the next call at the latest (one warning): a host that is paused for exactly that credit sends nothing more to carry it (2.3). A host that refuses the FIRST call has no flow control to turn on, or would not: the page stops calling and the transport's credit paces the shell (one warning). A refusal that says the session is gone stops it for good.
- A screen with no reader at all (a web view that is busy, a feed nobody reads) makes the host pause the shell at 1 MiB (plus one read of at most 20,480 bytes) and read on at 256 KiB, and loses nothing. A hidden session is not that: it reads.
- `FLOW.high` (4 MiB pending in the emulator), `FLOW.slice` (64 KiB a parse), `FLOW.frame` (512 KiB a frame shown) and `FLOW.hiddenFrame` (256 KiB a frame hidden) are the emulator's own bounds: they protect xterm (which discards past 50 MB queued) and the main thread, not the host.

How VS Code does it (the lead asked for the citation): `terminalInstance.ts` `_writeProcessData(data, cb)` calls `xterm.raw.write(data, () => { ...; this._processManager.acknowledgeDataEvent(data.length) })`, whether or not the terminal is shown; the flow constants are `FlowControlConstants` in `platform/terminal/common/terminal.ts` (high 100,000 characters, low 5,000, acknowledgements in batches of 5,000). Nothing there pauses a hidden terminal. xterm.js pauses drawing in its `RenderService` while its screen element does not intersect the viewport (`_isPaused`, an `IntersectionObserver`); section 5.1 says what was measured in a hidden xterm of this page.

## 3. Decisions (for the lead)

1. **A hidden session keeps parsing (round 2, as ordered). It costs the main thread, and the host's memory is no longer held back by it.** Measured (5.1, 5.3): about 10 to 15 ms of main-thread time per MB parsed in the probe; a 20 MB flood completes in about 1.4 s hidden. A `yes` flood saturates the main thread of Chromium (878 to 888 ms of task per second, no task over 50 ms) whether the terminal is shown or not; hiding saves only the GPU process. And the claim of round 1, "a hidden panel is bounded in host memory", is WITHDRAWN: it was true only because the page stopped acknowledging (+124 MiB hidden then); a hidden flood now grows the host's RSS like a visible one (+1750 to +1920 MiB in 25 s with `yes`, B-110). The share is per session: N sessions flooding at once cost N times (a shared budget across hidden screens is a follow-up). A terminal opened while another one floods hidden was slow to its first prompt in the demo (0.57 s, 1.10 s and 1.29 s against 0.29 s); the cause was not found. The timer beside the frame keeps a build going in a minimized window at the rate the browser grants timers there (1 Hz when throttled: 256 KiB a second at worst); a minimized native window was not tried.
2. **No page-side bound for a host that refuses the first acknowledgement** (listed for T2, as ordered): a host with no flow control (the contract says Windows answers `UNSUPPORTED`; there is no terminal there yet) would let the feed's backlog grow when the page parses slower than the shell writes (measured with every acknowledgement held back: the page's JS heap grew to 404 MiB in 25 s).
3. **`retitleSession(id, title)` in `ui-next/shell/core/panel/**`** (additive, approved by the lead): one commit per retitle; twins are told apart by the panel's A22 rule as before.
4. **One word outside the owned paths: `packages/omniviewdev-runtime/src/exec.ts` now exports `AckTerminal`.** The export list of #658 left it out (`WriteTerminal` and `ResizeTerminal` were there). The legacy UI (`ui/`) has the same need.
5. **An idle close is asynchronous.** The panel's close paths (the tab's button, middle click, Delete, the close chord) call `store.closeSession` synchronously, so the guard answers "refused" and finishes the close after the host's answer: 29 to 30 ms from the release of the button to the tab gone on the real host (`IsBusy` answered in 2 ms). A close-guard member in the panel's bindings (T1.md section 11) would let the shell wait for the answer; until then the guard moves the focus itself.
6. **The host asks are in host PR #672, merged** (it won over a second host change): an `AckTerminal` for a session that has ended answers success (for a session that is ending or among the last 256 ended; an older id can still be not-found without ever having been invalid), and `SHELL_UNAVAILABLE` carries `AppError.tried: [{ source: requested|environment|account|fallback, path, reason: not-found|not-executable|not-a-shell|other, detail? }]` beside the prose. The seam's allowance for the late acknowledgement is REMOVED (its condition was met). The page still shows the prose whole, marked `TODO(host #672)` in `state.ts`; reading `tried` (a list in the card, words for each token) is the step after T2a, as the lead ruled.
7. **The probe is two units now.** The runner measured the whole `terminal` probe at 238 s (listed 215) on the first CI run, past half a shard (216 s): it is `terminal` (`PART=view`) and `terminal-data` (`terminal-data-probe.mjs`, `PART=data`), and the controls are in more units (5.1).

### 5.3 Host memory under a flood, server mode (B-110: measured, NOT flat, still open)

The review round hardened the tool (spawn errors, child cleanup, the RSS cap, `--drain=0`, the hidden interval) and changed no number. What it says: **a page that acknowledges every parsed byte does NOT keep the host's memory flat in server mode, whether the terminal is shown, hidden or not the shown session**: RSS grows 6.2 to 6.7 times the bytes parsed with `yes` and 16 to 19 times with `seq` (reads of about 17 bytes: it looks like a cost per event; not diagnosed). B-110 stays open, as its author said (the retention is after the credit point, in the event path). Case 3 reproduces B-110's figure (+2315 MiB in 25 s against its 2.36 GiB in 60 s). After Ctrl+C and closing the terminal the RSS did not fall back within 30 s except where macOS compressed idle pages; a 25 s `--pprof` run (round 1) showed 840 MiB of live Go heap after a forced GC against 20 MiB at baseline, still there 10 s after the terminal was closed.

The page's cost per case (Chromium `yes`, round 2): main-thread busy 878 to 888 ms a second in all six cells (the thread is saturated by receiving and parsing, shown or not), 76 to 79 ms per MiB shown and hidden and 84 to 91 not shown; no task over 50 ms in any 24 s window; renderer CPU 110 to 114% of a core; hiding saves the GPU process (75% of a core shown, 0 to 1% hidden), not the parse. With `seq` hidden halves the main thread (304 to 340 ms a second against 635 shown; shown had 6 long tasks, the longest 88 ms, hidden none). A session that is not the shown one parsed 10 to 15% slower than the others in Chromium (3% in WebKit); not diagnosed. Shown again, the flood went on at 9 to 12 MiB a second.
