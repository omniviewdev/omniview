## 2. What was cut, and what it costs in coverage

1. **The negative controls leave the pull request** (probes: 46 control units, 368 controls; seam: 104 controls in 29 runs). They run on every push to main, every night (`schedule`, 03:17 and 03:47 UTC), on request (`workflow_dispatch`, default scope `full`), with the label `ci:full`, **and on a pull request that changes test infrastructure itself**: `scripts/ci/**`, `.github/**`, `ui-next/plugins/e2e/**` and `ui-next/plugins/fixture/**`, any `e2e/` under `ui-next/`, any `probes/` directory (a probe, its controls, its harness, its reference). The rule is in ONE place, `scripts/ci/ci-scope.mjs`; both workflows' plan jobs run it and read its output. **It fails closed**: a diff that cannot be read, an empty diff and an event it does not know are `full`.
   **The accepted trade, stated plainly:** a change to the PRODUCT that makes a control inert (it no longer sees the fault it plants, the probe stays green) is not caught on the pull request; it is caught on main, after the merge, by the run that opens the `ci-main-red` issue. N25's review found exactly this class (B1).
2. **One engine per pull request.** The probes get `ENGINES=webkit` (23 of the 37 probe scripts read `ENGINES`; the other 14, among them the terminal and Plugins page probes, run as they did, so the saving of this cut is less than half of the probes' seconds, and the shard's own summary says what each took), the seam runs WebKit only. Chromium runs where the controls run.
3. **Fewer, longer shards for a pull request.** The probes' plan packs the pull request's units at 1,500 listed seconds (they are the seconds of both engines) into 3 shards, the seam's phases into 2; a full run is as it was (19 probe shards of at most 432 s, the seam in 3 shards for each engine). The job count, not the wall time, is what the owner counts; the wall time is in section 4.
4. **`concurrency` with `cancel-in-progress` for a pull request only, on every workflow that checks one** (the probes, the seam, Pods, kit docs, render benchmarks, the profile; not history security, above; `pr.yml` and `pr-checks.yml` were already). A run on main is never cancelled. Not changed: `main-macos-universal.yml` (it cancels its own older run on main; it is a build and not a check, listed here so that nobody reads it as an oversight), `feature-channel.yaml`, the release and nightly publishing workflows.
5. **Duplicated or not-for-a-pull-request work.** The macOS build leaves the pull request: `main-macos-universal.yml` builds the universal binary (arm64 and amd64) on every push to main, and a darwin-only break is first seen there. The render benchmarks and the whole-app profile run on a pull request only with the label `ci:bench`; they run on main (their own paths), every night and by hand. The plan and the verdict jobs (probes, seam), the path classifier of both PR workflows and the two aggregates (`UI checks`, `e2e-tests`) run on `ubuntu-slim` (the smallest hosted runner, 1 vCPU; checked on this repository: `node`, `gh` and `git` are on it and a job ran in 17 s), and the verdicts check out only what they read (a sparse checkout of `scripts/ci`, and for the seam the check's own file), so that they need no build and are the cheapest jobs of the run.
6. **Path classes that exist stay** (documentation-only, new-UI-only). No selection of individual probes by change: the review rejected it, and this does not do it. What a pull request runs is the scope, not the diff, except for the one question "is it test infrastructure".

**Not touched: `history-security.yml`.** It belongs to another track and is path-triggered; an edit to it (even to its `concurrency`) starts it, and its Windows job has been broken since the MSYS2 image moved to OpenSSL 4.1.0 (`bench/historywindowssecurityprobe/native-windows.sh` requires OpenSSL 3; its last run before this was green on 2026-11-08). It is exactly as on main, and it keeps its `cancel-in-progress: true`.

**Required check names.** The repository has no required status check (`gh api .../rulesets/5372851`: deletion, non-fast-forward, one approving review; classic protection 404), so no name here is enforced. The aggregates keep their names: `Kit probes`, `Seam check`, `UI checks`, `e2e-tests`. Names that are gone or different: `build-artifacts (darwin/arm64)` (macOS build, section 2.5), `Seam webkit` and `Seam chromium` (N29 made them `Seam <engine> shard <n>`), `Kit probes shard <n>` (n is the plan's: 3 on a pull request, 19 on a full run).

**An aggregate does not say passed for what was not scheduled.** On a pull request `Kit probes` and `Seam check` verify what the plan scheduled (the probes in WebKit; the seam's phases in WebKit), fail closed on anything missing, cancelled or empty, and print in their own line and in their summary: `not run on pull requests: N negative controls ... were NOT RUN on this pull request (they run on main, every night, and on a change to the test infrastructure)`, with the reason the scope gave. The same reports are red against the full table (a test holds that).

## 3. Main and the nightly run do everything, and a failure there is not silent

`ui-next-kit-probes.yml` and `ui-next-seam.yml` run on a push to main (their own path filters), every night and by hand with the scope `full`: every probe and every control, both engines, the seam in 3 shards for each engine. `.github/workflows/ci-main-red.yml` runs when one of the workflows that check main ends there (the probes, the seam, Pods, the benchmarks, the profile, the macOS build): a failure creates or updates **one** issue labelled `ci-main-red` with a section for each red workflow: the first failing run, the last green run of that workflow on main before it, **the commit range between them (the first bad commit is in it)** with the subjects of its commits, and the latest failure. The same workflow going green removes its section; when none is left the issue is closed with a comment. The state is in a comment of the body, so a person can write around it. Pull requests' own runs are ignored, and so are cancelled and skipped ones.

## 5. #718 folded in (the review: MERGE, notes N1, N5, N6, N7)

- **N1** `continue-on-error` is held absent from the seam, probe and main-red workflows by a test (a job or a step).
- **N5** a shard that was cancelled (its timeout, a cancelled run) no longer uploads a report: the report and the upload steps run `if: !cancelled()`, not `always()`, so a hung shard cannot leave a report that says it passed; `Seam check` is red for the shard that did not report.
- **N6** the annotation titles have no comma (`Seam unit webkit shard 2`): the comma ended the property.
- **N7** `SEAM_PHASES` set to nothing or to commas is an error (it was a full run), and an `ENGINES` that names an engine the check does not have is an error (it ran zero engines and passed).
- The reviewer's model of two shards against three for the full seam (not faster: 19.4 against 17.9 minutes at the median, 12 percent fewer runner seconds) stands for the full run: 3 shards for each engine. For a pull request the work is the phases in one engine (about 610 s), and 2 shards is what the numbers in section 4 chose.
