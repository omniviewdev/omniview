## 2. The UI-facing contract (read this; no Go needed)

Calls are on `ExecClient` (`@omniviewdev/runtime/api`); the types are generated in `packages/omniviewdev-runtime/src/bindings/github.com/omniviewdev/omniview/backend/pkg/terminal/models.ts` and exported as the `terminal` namespace of `@omniviewdev/runtime/models`.

**Since the terminal channel (#704 on the host, #716 on the page).** A terminal made with `launch.channel` is reached by none of the calls and events of this section: by its capability and its stream only (`docs/ui-next/terminal-channel-protocol.md`). Every call here answers it as an id that never was, except a create (`CreateTerminal`, `CreateSession`) that names its id: that is refused as an id in use (409 `ALREADY_EXISTS`), which tells only that the id is taken. The new UI (`ui-next/`) makes only channel terminals. This section is the events lane, which the legacy UI (`ui/`) uses until the flip; what the page key and the capability each guard is `T2-go.md` 2.7 (with protocol version 2 of the stream, #763: watchers and `released`, the holder-only `close`, per-writer `input_applied` and `writer_known`, control frames read while input waits; see [`terminal-channel-protocol.md`](../terminal-channel-protocol.md)).

### 2.1 Calls

```ts
CreateTerminal(opts: SessionOptions, launch: { cols?: number; rows?: number; cwd?: string; env?: Record<string, string>; page_key?: string; lease_ms?: number }): Promise<terminal.Session>  // env: below; page_key, lease_ms: T2-go.md 2.1 (a terminal with a key outlives its window)
GetCwd(sessionId: string): Promise<terminal.Directory>
AckTerminal(sessionId: string, bytes: number): Promise<void>   // a terminal UI MUST call it (2.8.6); it answers success for a session that is ending or is one of the last 256 that ended (nothing is left to credit; the last acknowledgement of an exiting shell races its CLOSE) and session-not-found for any other id (an older session is not remembered)
IsBusy(sessionId: string): Promise<terminal.Foreground>
WriteTerminal(sessionId: string, seq: number, data: string /* base64 */): Promise<void>
ResizeTerminal(sessionId: string, seq: number, rows: number, cols: number): Promise<void>
CloseSession(sessionId: string): Promise<void>            // unchanged name
// unchanged for the legacy UI and for plugin sessions; on a local session they now go through the same queue (arrival order, seq 0):
WriteSession(sessionId: string, data: string): Promise<void>
ResizeSession(sessionId: string, rows: number, cols: number): Promise<void>
```

`CreateTerminal`:
- `opts` is the SDK's `SessionOptions` (it had to stay: `exec.SessionOptions` is the plugin-facing type and the generator keeps it only while a bound method names it). Read: `id` (optional, at most 128 bytes: choose it so the page can listen BEFORE the shell starts; an id that any session, local or plugin, already has is refused 409 `ALREADY_EXISTS` and the first shell is untouched), `command` (empty is the account's login shell; `[path]` an explicit shell; a program that is not a shell is refused), `labels` and `params` (kept and listed as before). Any `resource_*`, `reference` or `route` is refused `INVALID_REQUEST`. `tty` is ignored (always a tty).
- `launch.cols` and `launch.rows`: the size to open the pty at. `0` or absent means "not given": 80 columns, 24 rows, each on its own (the old default was 72 x 27). Below zero or over 1000: refused `INVALID_REQUEST`, detail names `cols` or `rows`; nothing starts. (The legacy UI passes `{ cols: 0, rows: 0 }`: every field of `launch` is optional.) The Terminal tool of the new UI passes `{ cols, rows }` as its view measured them (`ui-next/shell/panel/terminal/localShell.ts`): its feed starts the process only when it has a size, so the shell lays out its first prompt for the panel it is in, and it sends no resize after the start (`execFeed.ts`); the shell, the directory and the environment are the backend's defaults.
- `launch.cwd`: the directory the shell starts in: an absolute path to a directory that exists. Empty or absent is the user's home. Anything else is refused `INVALID_REQUEST`, detail names `cwd`; nothing starts.
- `launch.env`: extra environment for the shell, name to value, set over the launch environment the shell starts from (2.8.1): a name already there takes the value given. It is not the shell's login environment: the shell computes that itself and the user's startup files may overwrite a name given here (a login `/etc/profile` replaces `PATH`). Refused `INVALID_REQUEST` (400), the detail names `launch.env.<NAME>` (`launch.env` when the name is not a name; the detail then holds the name, quoted and cut at 64 bytes), and nothing starts, for: a name the host strips or sets (`OMNIVIEW_*`, `PLUGIN_*`, `WAILS_*`, `GOWORK`, `FRONTEND_DEVSERVER_URL`, what describes the launching terminal or multiplexer: `COLUMNS`, `LINES`, `TMUX*`, `STY`, `VTE_VERSION`, `TERM_SESSION_ID`, `ITERM_*`, `KITTY_*`, `WEZTERM_*`, `ALACRITTY_*`, `GHOSTTY_*`, `VSCODE_*`, `LC_TERMINAL*`, `TERMINAL_EMULATOR`, `WT_*`; and the ones the terminal sets: `TERM`, `COLORTERM`, `TERM_PROGRAM`, `TERM_PROGRAM_VERSION`, `PWD`, `SHELL`), the same list as 2.8.1a (`hostPrivate` and the terminal's own names: one source in `env.go`); a name that is not POSIX `[A-Za-z_][A-Za-z0-9_]*`, empty, or over 256 bytes; a value with a NUL or over 32 KiB; more than 64 names or more than 256 KiB of names and values together. The names are read in sorted order, so a request always gets the same answer, and **an error never carries a value** (only the name). `ZDOTDIR` (zsh) and `XDG_DATA_DIRS` (fish) are allowed: they are the user's variables, and the shell integration (#694) that takes them over for its start reads the value given here as the user's and gives it back (the shell sees it as given; tested with zsh).
- `opts.command` empty: the shell is the setting `terminal.defaultShell` when it names a shell the host starts (`shellenv.Check`), asked for as the "requested" source of the order in 2.8 (so it is tried first and the order follows when it cannot start), on both lanes; a value that is empty, unreadable or no longer a shell (uninstalled since Settings accepted it: Settings refuses a typo when it is typed) leaves the order to choose. A shell the caller names is never replaced by the setting, and a program that is not a shell stays refused `SHELL_UNSUPPORTED`. `ListTerminalShells(): shellenv.Shell[]` (`{name, path, default}`) lists bash, zsh, fish and pwsh found in `/bin`, `/usr/bin`, `/usr/local/bin` and `/opt/homebrew/bin` (a file that is not executable is not a shell; one file reached by two paths is listed once) and the default shell wherever it is, marked by the host with the same choice `CreateTerminal` makes. Windows has no list yet (#701).
- There is no flow option: every terminal is paced by credit (2.8.6). **A terminal UI MUST turn flow on (its first `AckTerminal` call) and acknowledge every byte it parses, dropped bytes included; without acks a flood grows the host's memory without bound** (the measured cases are in 2.8.6).
- A call that comes from no window (a script with no page) is refused 403 `FORBIDDEN`: a terminal nothing could retire would outlive everything (2.6). A window the realm refuses (limit, retired) is refused with the realm's error.
- The answer, `terminal.Session`:

```ts
{ id: string; created_at: string;            // ISO time
  pid: number;                               // the shell's process id
  shell: { path: string; name: string; requested?: string };  // absolute executable; the shell's own name ("zsh", "bash", "dash"): the file a symlink points at; `requested` only when another shell started in its place (2.8.8)
  cwd: string;                               // the directory the shell started in: launch.cwd, or the user's home
  cols: number; rows: number;                // the size the pty was opened at: the size asked for, or the default
  environment: { source: 'launch'; probe: { state: 'ok' | 'failed' | 'not-run'; message?: string } };  // where the shell's environment came from; how the host's own login probe went (2.8.1)
  limits: { max_dimension: 1000; pending_ops: 256; pending_bytes: 1048576; seq_ahead: 64; gap_wait_ms: 2000;
            flow_high_bytes: 1048576; flow_low_bytes: 262144; flow_stall_ms: 2000; flow_step_bytes: 262144; flow_stall_ceiling_bytes: 8388608;
            hangup_grace_ms: 1500; drain_cap_ms: 3000 } }
```

### 2.2 Events (every window receives them; filter by the id)

| Name | Payload |
|---|---|
| `core/exec/stream/stdout/<id>` | the bytes of one pty read, base64 (unchanged). At most 20,480 bytes; the event owns its bytes now (the read buffer is reused) |
| `core/exec/signal/CLOSE/<id>` | **an object**, `terminal.End` (it was base64 text, "Session terminated") |

```ts
type End = (
  | { reason: 'exited';   exit_code: number }                                          // the shell exited by itself; 0 is a code: the field is there
  | { reason: 'signaled'; signal: string; signal_number: number; core_dumped?: true }  // killed by a signal the host did not send: "SIGTERM", 15
  | { reason: 'closed';   closed_by: 'request' | 'window' | 'shutdown' | 'detach-timeout' } // the host ended it: CloseSession, the window went away, the host quit, or (T2-go) the lease of a detached terminal ran out
  | { reason: 'failed';   failure: { stage: 'read' | 'wait' | 'pty'; message: string } } // the pty or the wait failed; message is the system's words, nothing branches on it
) & { drain_capped?: true; dropped_bytes?: number; last_offset: number }                // on any end: see below; last_offset (T2-go.md 2.3) is the length of the output
```

Guarantees (tested): exactly one CLOSE for a session; it is the LAST event of the session (every stdout event, including what the shell wrote just before it exited, comes before it: 25 of 25 runs of a 400-line burst then `exit 4`); none before the session ends; when `CloseSession` (or the end of a retired window's shells) returns, the CLOSE has already been delivered and no event of that session follows, even from a flood, **when the wait for the sessions to be gone completes** (`awaitGone` gives up after 5 s, for example for a sink that blocks, and then the CLOSE may still be on its way: 2.6). `closed` wins over what the process died of (a closed shell is not "signaled SIGKILL"). A `failed` pty ends the shell too. There is no `ERROR` event for a local terminal. **A process that keeps the pty open does not keep the session alive:** once the shell has exited the host reads what is left for at most `drain_cap_ms` (3,000) from the exit, and for a process that holds the pty open and writes (a background job: `npm run dev &`, then `exit`) the CLOSE comes at the cap, with the shell's own exit facts and `drain_capped: true`; `dropped_bytes` counts what the host read after the cap and threw away (a lower bound: what the process writes after the host closes the pty is the kernel's). On macOS the kernel revokes the pty when the shell exits and the CLOSE comes at once. A silent job does not hold the session: one second of silence ends the drain as before.

### 2.3 The busy fact (`IsBusy`), three states

```ts
type Foreground =
  | { state: 'idle' }                                                    // the shell itself holds the foreground (background jobs do not count)
  | { state: 'busy'; pgid: number; name?: string }                       // a process other than the shell holds it; name when the platform gives it
  | { state: 'unknown'; reason: 'unsupported' | 'query-failed' | 'remote' } // the host cannot tell: ASK
```

- How: `ioctl(TIOCGPGRP)` on the pty master gives the foreground process group; it is compared with the shell's own group (`getpgid`). One call at the moment the user presses Close; **no polling, no change event** (the kernel gives none; a push would need a timer). The UI calls it when it needs it.
- The name: macOS, `sysctl kern.proc.pid.<pgid>` (the executable's name, 16 bytes; if the leader of the group has exited, the first live member of `kern.proc.pgrp`); Linux, `/proc/<pgid>/comm` (15 bytes, empty if the leader is gone while the group lives). Both are one syscall or one file read. Empty `name` with `busy` is still busy.
- `idle` is exactly "the shell holds the foreground": `sleep 60` is `busy` with `name: "sleep"`; `sleep 60 &` is `idle`. **Known limit:** a shell that `exec`s into a program is still the foreground group and reads `idle` (the host starts every shell on a tty, interactive, so the shell does its own job control; one that did not would also read `idle` for a running program).
- `unknown`: `query-failed` when the system refused the question; `remote` for a session of a plugin (the host holds no terminal for it); `unsupported` on a build that cannot run local terminals (Windows: section 3). The UI treats `unknown` as ask.
- A session that is gone: 404 `omniview:session/not-found`.

### 2.4 Order and bounds (`WriteTerminal`, `ResizeTerminal`, and the legacy calls)

Each session has ONE input queue and ONE goroutine that applies its writes and resizes, one at a time. No lock is shared between sessions: a shell that does not read stalls its own queue and nothing else (tested: another session starts, answers, resizes and closes while one is blocked inside a 16 MiB write; closing the stalled one answers its writer and stops its goroutine).

- **Order.** `seq = 0`: applied in the order the call reached the host (what `WriteSession` and `ResizeSession` do). `seq >= 1`: the host applies the operations in `seq` order whatever order the calls ARRIVE in. The transport runs unawaited calls at the same time (T1.md measured 4 to 22 inversions in 100 unawaited writes and 2 to 10 in 20 runs of 50 resizes), and a number is the only way the host can know the order they were sent in. Count 1, 2, 3, ... for the session, writes and resizes together, one number for each call.
- A call returns when its operation has been APPLIED (or refused): an error from the pty reaches the call that caused it.
- A call ahead of its predecessor waits for it, at most `gap_wait_ms` (2,000). If the predecessor has not come, the host gives the missing numbers up and goes on; the late call, if it ever arrives, is refused 409 `SEQUENCE_STALE` (never applied out of order, never dropped silently: its caller is told). A call more than `seq_ahead` (64) past the next expected is refused 400 `SEQUENCE_AHEAD`. A number already used is `SEQUENCE_STALE`.
- **Bound and flood.** At most `pending_ops` (256) operations or `pending_bytes` (1 MiB, counting what already waits: one large write is taken when nothing waits) are held per session. Past that a call is **refused at once**, 429 `INPUT_BACKLOG`; the operation was not applied and consumed no number, so the same call may be sent again. No silent drop, no unbounded buffer, no waiting without an answer.
- A resize applies as a real `ioctl` in order with the writes; resizes are not coalesced (the UI's "newest wins" is its own choice).
- `ResizeSession` and `ResizeTerminal` refuse `rows` or `cols` of 0, below 0 or over 1000 (`INVALID_REQUEST`); the old call accepted `0 x 0`.

### 2.6 Release with the window (B-88 for terminals)

The decision, with the rule it follows: **the shell is ENDED when its window is retired** (rule (a)). Why: the restored tab is rebuilt by session restore as `ended` with the cause "The session ended when the app restarted." (`RESTORED_CAUSE`, S3a: panel sessions never come back running, their output is not restored) and T1.md section 9 puts reattach in a later slice, so a shell kept alive for a bounded time would make that restored tab say something untrue and nothing could reach the shell. A21 (a host tool's sessions survive their PLUGIN's unload) is about a plugin leaving, which retires no window; it is unchanged. **T2-go (`T2-go.md`) is that later slice, and it is opt-in: this rule holds for a terminal opened WITHOUT a `launch.page_key`; one opened with a key is DETACHED when its window is retired and kept for a lease, so that the page that comes back can attach to it.**

- The owner is the window identity the realm uses (`invocation.IdentityOf`). `WindowRealm.OnRetire` fires for a native window closing (its `WindowClosing`) and for a server-mode page that is gone (INV2's sweep: about 3.4 s after the socket goes). The wrapper subscribes before it makes its first terminal and releases every shell of the retired window (`ReleaseOwnedTerminals`): a shell without a page key is ended and gets its CLOSE (`closed`, `closed_by: "window"`) before the call that ended it returns, **when the wait for the sessions to be gone completes** (`awaitGone` gives up after 5 s, as it does for a sink that blocks: then the CLOSE may still be on its way, and `Released.Ended` only counts the sessions it began to close); one with a key is detached (T2-go.md).
- A race (the window retired while its shell starts) is closed by asking the realm again once the session is registered: either the retirement finds the session or the realm refuses the window and the wrapper ends the shell itself (tested with 25 pages retired at random moments of their own create calls, then the SYSTEM's list of this process's children: zero).
- Proof: **100 terminals across 20 pages, all 20 retired: 0 shells alive, counted by the 100 pids recorded at creation (`kill(pid, 0)`), each with exactly one CLOSE `closed`/`window`; the 21st page keeps its 2 shells, untouched; the index holds exactly those 2; `ps` lists no child of the test process but the 2.** (`TestHundredTerminalsAcrossTwentyRetiredPagesLeaveNoShellAlive`, 0.65 s.)
- **Not covered (stated, not hidden):** a native window that RELOADS in place keeps its window identity, so the realm never retires it and its old shells without a page key run on until the user closes them (the restored tab says they ended); one with a key is found by its owner or its key and attached (T2-go.md). A server-mode reload is a new page (a new identity) and IS covered. Closing an unkeyed one needs a "page reloaded" signal from Wails for native windows (`WindowRuntimeReady` is the candidate) that I could not test in a native window.
- A terminal from no window is refused (2.1).
- What a closed shell leaves: 2.8.5 (SIGHUP to the foreground program and the shell first, SIGKILL after 1.5 s for what ignored it). Whether background jobs end with it is the shell's own rule, and 2.8.5 says which shells.

### 2.8 A real terminal (owner ruling, 2026-11-22)

The ruling: the terminal does not have to follow the mock exactly, but it must be an exceptional functional terminal that does what one expects in an IDE. Each point below is stated by the producer, with a test in `backend/pkg/terminal/login_test.go`.

**2.8.1 ONE environment truth: the shell starts from the environment the host was LAUNCHED with, as a login shell.** On macOS the host restores the user's login environment into its own process at start (`main.go` calls `shellenv.Restore`: it runs the user's login shell as `-i -l`, prints a marker and then `env -0`, 10 s timeout, and sets the result on the host process, keeping the keys the host owns). That restored environment is for the tools the host starts (plugins). **A terminal does not use it:** `Restore` first remembers the environment the host was launched with (`shellenv.LaunchEnvironment`: launchd's minimal one for an app started from the Dock or Finder, the caller's for one started from a terminal), and each terminal's shell starts from that, as an interactive login shell (`-i -l`), minus the host-private variables below. The user's startup files then run once, on the environment a Terminal.app window starts from. **Why not the restored one** (option B of `proposals/T-terminal-prior-art.md`, mechanism 5 and pitfall 1): starting the user's login shell on an environment that was already login-restored ran their profile on a PATH that `/usr/libexec/path_helper` had already ordered. path_helper (run from `/etc/zprofile` or `/etc/profile`) puts the system directories first and moves the user's (Homebrew, mise or asdf shims, nvm, pyenv) behind them, and a version manager's "prepend unless already present" line then declines to prepend, so `python`, `node` and `kubectl` resolve to the system copy. JetBrains shipped exactly that (YT-IJPL-200767, fixed 2025-08) and now starts its terminal on the raw process environment, `--login` only on macOS; VS Code resolves the environment once and re-applies the PATH prefixes its extensions contributed after the profile runs (`VSCODE_PATH_PREFIX`) because of path_helper (both as read in the study, not re-read here). I chose JetBrains' contract (the study's option A): nothing needs re-applying, and it is the contract of a Terminal.app window. A Linux host is not restored (`Restore` does nothing there, and the launch environment is the process environment); Windows has no local terminal (section 3). **Test:** the process PATH is a restored one with a directory only the probe knew, the launch PATH is `/usr/bin:/bin:/usr/sbin:/sbin`, and `.zprofile` and `.bash_profile` hold a mise-style "prepend unless already present" line: the user's directory is the FIRST PATH entry and the probe-only directory is absent (`TestTheShellStartsFromTheLaunchEnvironmentSoTheUsersPathOrderSurvives`, zsh and bash; on macOS path_helper runs in between, which is what breaks a shell started from the restored environment). **Stripped from the shell's environment, and why** (`hostPrivate` in `env.go`): `OMNIVIEW_*`, `PLUGIN_*` and `GOWORK` (the host's own configuration; `GOWORK=off` keeps the host's plugin builds apart from the user's Go workspace and must not reach the user's `go` commands, and a login shell sets the user's own `GOWORK` again from their startup files), and what describes the terminal or multiplexer the host was launched from, which is not this terminal: `COLUMNS` and `LINES` (its size), `TMUX`, `TMUX_PANE` and `STY` (its multiplexer), `VTE_VERSION` and `TERM_SESSION_ID` (its emulator). **Added:** `PWD` (the directory the shell starts in, as given and not resolved through a symlink), and the variables of 2.8.2. **`IUTF8`** is set on the pty (Alacritty, Ghostty and node-pty do it; creack/pty sets only `Setsid` and `Setctty`), so that in cooked mode the line discipline erases one multi-byte character and not one byte of it. **The login probe is surfaced:** `shellenv.Restore` records how its probe went (`ok`, `failed` with the reason, or `not-run`), and every terminal's answer states it in `environment.probe`. It does not change the terminal, whose shell computes the user's environment itself; it says whether the tools the host starts have the user's PATH, and it is no longer swallowed (`main.go` printed one line to stderr and went on). **2.8.5 Closing hangs up first.** `CloseSession`, and the end of a retired window's shells, send SIGHUP to the foreground process group and to the shell, wait `hangup_grace_ms` (1,500) for the shell to exit, then kill what is left: SIGKILL to the foreground group and to the shell. **2.8.6 Flow control: credit, for every terminal (no option). What it bounds, what it does not, and what every terminal UI MUST do.**

**REQUIREMENT, for the legacy `Terminal.tsx` and for the new terminal UI alike: a terminal UI MUST turn flow on and acknowledge every byte it parses (dropped bytes included); without acks a flood grows the host's memory without bound.** Turning flow on is its first call of `AckTerminal(sessionId string, n int) error`. `n` is the number of BYTES of decoded stdout payload the UI has taken in since its last call: written into its emulator, or dropped (a byte it drops and never acknowledges is credit the shell never gets back); characters are the wrong unit. It sends them in batches, from the emulator's write callback. From the first call on only its acknowledgements credit, and what the transport takes credits nothing. The host counts the bytes it delivered that nobody has credited; at `flow_high_bytes` (1 MiB, 1,048,576) it STOPS READING the pty, so the shell blocks in its own write (the kernel's pty buffer is the only buffer left), and it reads again when the count is down to `flow_low_bytes` (256 KiB, 262,144). A UI that stops acknowledging (a hidden tab, a page that is busy) pauses the shell at that mark and loses nothing. `AttachSession` forgets the debt (the client starts from the ring it is handed), and a close releases the pacing for good (B1, 2.8.9).

**Where the credit comes from when the client sends no acknowledgement (the default).** The host counts a stdout event as delivered when the TRANSPORT took it. For Wails' server mode that is when the worker that writes the client's socket serializes the event (`terminalOutput.MarshalJSON` in `backend/pkg/plugin/exec/terminal.go`; `delivery.go` recognizes that serialization): one event at a time, after the write of the one before, so it happens only as fast as the socket drains; a socket that stops reading stops the credit and the host stops reading the shell (rows 1 to 3). In a native build it is the window's serialization, which Wails makes in its dispatch worker just before it hands the event to the web view and waits for the main thread (what row 10 shows that credit does not see). A sink that returns when the transport has taken the bytes (a blocking write, a bounded queue) needs no more: the return of `Output` is the credit. A client that reads is never held up; the 10 MiB test runs with each source. **How this was found, and what it depends on:** the first version credited at the FIRST serialization; the review's real-host stall driver (`stall1.mjs`, a socket that completes the websocket handshake and stops reading, `yes` in the terminal) showed the host still going from 67 MiB to 3.5 GiB in 30 s, and a debug build printed why: a server build also serializes every event for a window it keeps (`WebviewWindow.DispatchWailsEvent` -> `Event.ToJSON`, `json.Marshal`, in the dispatch worker, which never waits for a socket), so the credit came before any socket was asked. A server build (`-tags server`) now counts only the serialization that writes a client's socket (`wsjson.Write`, which is `json.NewEncoder(w).Encode`), recognized by the caller's stack (`serializedForAClientSocket`: two microseconds, once or twice an event; the review did not find it to be the throughput limit); a native build counts the first. The recognition is pinned with the library Wails uses (`TestTheSerializationThatWritesAClientSocketIsTheOneThatIsRecognized`, a real `wsjson.Write` over a websocket) and by the server-tag test (`TestInAServerBuildOnlyTheSocketWritersSerializationIsDelivery`, run with `-tags server`). If a Wails version changes how server mode serializes, the answer is wrong in the safe direction (no credit) and the WATCHDOG below keeps terminals alive.

**The watchdog.** The transport's credit is an inference about a transport the host does not own, and an inference can fail in the way that matters: credit that never comes freezes every terminal at the high mark. So a pause on the TRANSPORT's credit (never one on a client's acknowledgements: that pause is the client's choice) has a watchdog: after `flow_stall_ms` (2,000) without credit it gives `flow_step_bytes` (256 KiB), and at most `flow_stall_ceiling_bytes` (8 MiB) in all until real credit comes again, with a warning in the log. **It only pauses the read and drops nothing**: with a transport that never credits, delivery stopped at 8.9 MB on macOS and 9.4 MB on Linux (the high mark plus the ceiling), the delivered stream was byte-identical (SHA-256) to the first N bytes of the source, and the shell stayed alive and blocked (the review). After the ceiling nothing resumes the read except an `AckTerminal` or an `AttachSession` [INFERENCE, read from `flow.go` by the review, not run: a client that connects later without either cannot unfreeze it; reachable by a call from no window (B-107) or a page that reconnects]. The only drop in this PR is the drain cap of B3, which is counted (`dropped_bytes`). What a client that really stalled costs the host in memory is rows 1 to 3 of the table (about +130 MiB over 60 s, then nothing more). With no client connected at all nothing serializes for a socket, so a flood stops at the high mark, then trickles to the ceiling and stops (row 2).

**2.8.5a Shutdown hangs up too, and the kill finds the foreground that is there (review B2, S-b).** A graceful host shutdown (SIGTERM, SIGINT, a quit) used to kill the shells alone (Wails cancels the application context first, and the shell's context was derived from it: Go's `CommandContext` kills with SIGKILL), so a background job outlived the host (67 of 67 in the review) although 2.8.5 says it ends with its terminal; a crash was cleaner than a quit. ## 7. Decisions for the lead

1. **`CreateTerminal(opts, launch)`, not one new options type.** A host `Options` type would have orphaned `exec.SessionOptions` in the generated bindings (I ran it: the generator drops a type no bound method names, and the runtime's `exec.ts`, its hooks and the `exec` namespace plugins compile against need it). Keeping the SDK options first and adding the host's `Launch` (size and cwd: every field optional) second keeps that type generated, keeps the legacy call one argument longer, and costs nothing.
2. A call from no window is refused. The UI agent's Node scripts (no page) can no longer start a terminal; a Playwright page can.
3. The default size is 80 x 24 (was 72 x 27 and hard-coded).
4. `seq` is optional: the UI may keep awaiting (correct without it) or number its calls and send them unawaited. The wait before a missing number is given up is 2 s: a longer wait stalls input behind a lost call, a shorter one refuses a late call.
5. The CLOSE payload of a local session changed from base64 text to an object. The legacy terminal ignores the payload (`Terminal.tsx` handles CLOSE without reading it).
6. `CreateSession("local", ...)` is refused: it started a shell with no owner.
7. Rule (a) for windows, and the native in-place reload gap (2.6): to close it, the host needs Wails' "runtime ready" for a native window, which I could not test.
8. Flow control is credit for every terminal and has no option: the transport credits what it took, and a terminal UI MUST turn flow on with its first `AckTerminal` and acknowledge every byte it parses, dropped bytes included (the requirement of 2.8.6); without acks a flood grows the host's memory without bound in the cases of the table there. It replaces the opt-in `launch.flow` of the first version.
9. Close, window retirement and host shutdown all hang up, then kill after 1.5 s (2.8.5, 2.8.5a). The host does not kill the process tree behind the shell's back, so background jobs follow the shell's own rule.
10. The shell starts from the environment the host was launched with, recorded first thing in `main`, never from its live process environment or the login environment it restored for its own tools (2.8.1, 2.8.1a). A Linux host is not restored.
