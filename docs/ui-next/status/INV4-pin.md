# Status: INV4-pin (the host cluster check pins plugin #281 and holds the demo's finding O2: a connection starts with an API group that cannot answer)

- Agent: PartialDiscovery
- Goal: the demo's finding O2 (`~/Notes/omniview/ui-migration/demo/2026-11-21/README.md`): with an aggregated API that cannot answer (a metrics-server that is down) the first Pods page of a fresh connection failed, "Connection admission requires complete discovered support.", and a press on Retry made it load. ## What the PR changes

- **The pin.** `KUBERNETES_PLUGIN_REF` is `8af576fff40a883ed8c6e799470a3e8c4032f656`, the head of the plugin's `feature/ui-next` on 2026-11-22 (`git ls-remote https://github.com/omniviewdev/omniview-plugin-kubernetes refs/heads/feature/ui-next` said so): #281, INV4, on top of #283, the restart-stream race fix (`c2a10e0b`); the previous pin ec5a06ea (#282) is its grandparent. `node scripts/ui-next-pods/pin.mjs <checkout at 8af576ff>`: "pin ok", the plugin's list of shared names is this host's, and its vendored host commit c707712d is in this history. The header of the workflow says what the pin is now, and that this bump changed the check by the one test below (the header's rule is that a bump changes nothing else; the test is the only thing that tells the pin from the one before it).
- **The test** (the check's mode `unavailable-group`, one test; `checkUnavailableGroup` in `parity.mjs`; the pure side is `unavailable.mjs`, with `unavailable-group.yaml` for the cluster). The job registers an APIService whose Service has no endpoints (the state a metrics-server that is down leaves, `Available=False (MissingEndpoints)`, the group a made-up `inv4-unavailable.example.com`), waits until the aggregator says so, and only then starts one more host, with a home of its own and nothing saved, so that the plugin connects to a cluster that already has the group. The check opens that host's first page the way a person does, from the list of plugins, and never presses Retry:
  1. the page lists the Pods `kubectl get pods -A` lists, with its footer's count (the existing parity comparison, `PAGE_MISMATCH`);
  2. the host refused no request of the page (`REQUEST_REFUSED`; the requests are recorded from the page's first call, with what was asked and what the host answered, as the seam check records them);
  3. the host's facts for the connection name the group (`FACT_MISMATCH`): `kubernetes.unavailable_api_groups` is current and is exactly `{"count":1,"groups":[{"groupVersion":"inv4-unavailable.example.com/v1beta1","reason":"stale"}]}`.

  Before any of it the cluster must hold the group (`GROUP_MISSING`: the APIService prints `False/MissingEndpoints`) and the fixture (`FIXTURE_MISSING`). When the page fails to agree, the requests the host refused are in its message.
- **The control** (mode `control-group-absent`, run on the main host, on the cluster as the main check left it, before the group is registered): the check must report `GROUP_MISSING`, so that a job that forgot to register the group, or a check that has gone blind to it, turns red. The steps run in this order, and `unavailable.test.mjs` holds the order: control, register and wait, start the host, check.
- **Facts through the host's API: yes, the check can read them.** `ServiceWrapper.GetConnectionMetadata(pluginID, connectionID)` through `/wails/runtime`, the call the runtime's `useConnectionMetadata` makes (`backend/pkg/plugin/resource/connection_metadata.go`); the answer is the host's envelope, `{ supported, transportAvailable, snapshot: { entries: { <fact>: { state, value, observedAt } } } }`, and the value is an object. Read live on the pinned plugin: `"kubernetes.unavailable_api_groups": { "state": "current", "value": { "count": 1, "groups": [ { "groupVersion": "inv4-unavailable.example.com/v1beta1", "reason": "stale" } ] } }`, beside the server version, platform, URL and provider. The connection's ID is the derived one, read from the host's list of connections as the lane test reads it.
- **One allowance, with its reason.** A 422 that says `CANCELLED` is the page's own cancelled query, not a refusal (INV4.md measured one on `Catalog` in about 1 of 3 first loads in Chromium with the plugin before #281 on a healthy cluster: an in-flight query cancelled by a readiness change), and the seam check's list of allowed failures is explicit for the same reason. Anything else, the admission the host refused among them, is a refusal. The test prints how many of them it let through (`the page's own cancelled queries the check let through`), so a run says whether the allowance was used: 0 in all the runs below.
- Files: `.github/workflows/ui-next-pods.yml` (the pin, the header, one no-cluster step, four steps, the diagnostics and the stop), `scripts/ui-next-pods/` (`unavailable-group.yaml`, `unavailable.mjs`, `unavailable.test.mjs` new; `parity.mjs`: `checkUnavailableGroup`, `readConnectionMetadata`, `recordRequests`, `openPluginPage` and `agreeWithKubectl` taken out of `openPods` and `checkParity`, which behave as before; `pods-cluster.check.mjs`: the two modes), this file and `INV4-pin/` (the tools).
