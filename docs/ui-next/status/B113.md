## 1. What was wrong

The host routes a call, an event and an end by the session id (`sessionIndex[id]`). A page chooses the id of the session it creates, so that it can listen first. `CreateTerminal` has always refused an id that is in the index (`terminal.go`, `ErrIDInUse`); `CreateSession` did not: it wrote the record of the id the plugin answered over the record that was there (`controller.go`, the write after `client.CreateSession`). The SDK refuses a duplicate only within one plugin (`manager.go:409`).

Measured on `b015ceb5` with a scratch test (not committed), window A's terminal `a-terminal` and window B calling `CreateSession` on a plugin with that id:

| Step | Result on main |
|---|---|
| B's `CreateSession(id = A's terminal)` | succeeds, `err = nil` |
| the record | now the plugin's (`local = false`) |
| A's `IsBusy` | `unknown`, reason `remote` (the host asks no shell) |
| A's `CloseSession` | goes to the plugin (1 close call) and does NOT end the shell: the manager still lists it, 0 CLOSE for the terminal |
| the plugin's session ends and sends its CLOSE | the frame is dispatched by id: the record (A's) is deleted and the windows get `core/exec/signal/CLOSE/a-terminal` while A's shell is still running |

The same with a session of another plugin: the record becomes the second plugin's, and the first plugin's session can no longer be written, attached or closed through the host. B needs an exec plugin and the id; the events name every id to every window (S1 of #677), so it has it.

## 2. The change (`controller.go`, 55 lines added, none removed)

1. **An id the page chose and the host holds is refused before any plugin is asked** (`hasSession`): `terminal.IDInUse`, the 409 `ALREADY_EXISTS` that `CreateTerminal` gives. It comes after the admission, the plugin and the connection checks, so a caller who may not use the reference learns nothing from it, and no process starts for a request that is refused.
2. **The id the plugin answers is the one that decides, where it is recorded** (two creates can be in flight; a plugin may choose its own id): if the index holds it, the session is refused (`IDInUse`) and CLOSED with the plugin that made it (`closeRefusedSession`: `client.CloseSession`, never the host's own `CloseSession`, which would find the other record and mark it `closing`). When the record names the SAME plugin the refusal does not close: the plugin holds one session under the id, the recorded one's, and closing by the id would end it (the SDK refuses a duplicate itself; a plugin that is not built on it may not).
3. **A plugin frame whose id the host recorded for another session is dropped** (`dispatchProviderOutput`, one more map read under the lock it already took). Without it the refusal in 2 is not safe: the closed session's CLOSE reaches the mux with the other session's id, deletes the record of a terminal (the last row of the table above) or marks the record of another plugin's session ended, which no window can use, and the windows are told that session closed. It also stops a plugin from writing output or an end into a session of another plugin, or into the local shell, by naming its id.

## 4. Not verified, and limits

- No real plugin: the SDK's own refusal of a duplicate within one plugin (`manager.go:409`) is read, not run; the plugins in the tests are fakes that keep what the SDK keeps (`aKeepingPlugin`).
- Not driven on the real host or in a native window. The change is in the controller: no binding, no event name and no UI changes.
- The refusal says "A terminal session with id ... exists" for a session of a plugin too (the words of `CreateTerminal`'s refusal); it is an existence answer of another kind than not-found (review N1 of #677). It matters little while the ids are in every window's event stream, and the capability design (`proposals/T-terminal-channel.md`) removes the stream.
- The frame guard compares the frame's plugin with the plugin the RECORD names. A frame for an id with no record is delivered as before (output that comes before the host records its session is how a fast command's output arrives), so a plugin can still name an id nobody has recorded yet.
- A refused session is closed best effort: if the plugin's close fails it is logged (`errorClass`) and the session lives on in the plugin, unrecorded, until the plugin ends it.
