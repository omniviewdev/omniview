## E10 acquisition mechanism: decision rule (written BEFORE any measurement)

Candidates.
- **C0, baseline:** `useResources({ collection: true })` only. The first row waits for the complete snapshot (`useResources.ts:300-307`).
- **B, a first explicit page beside the collection:** C0 plus `useResources({ collection: false, request: { ..., pageSize: 256 } })`, one `Enumerate` for the first 256 records, kept until the collection completes. Needs no change outside `ui-next/k8s/`.
- **A, partial snapshots from the collection hook:** the runtime would publish the records staged so far (`sourceView.ts` `staging`) before `snapshotEnd`. Needs a change in `packages/omniviewdev-runtime` (not mine; through the owner of the hooks). Reading `backend/pkg/plugin/resource/source_view.go` `syncLocked`, the host sends the first `snapshot` event only after its source session holds a complete snapshot, so a runtime-only change may not bring rows earlier. A is therefore measured as an UPPER BOUND only: the time its first `snapshot` event reaches the page, against its `snapshotEnd`, taken from WebSocket message timestamps with no runtime change.

Protocol. Sizes N = 25 (the fixture as is), 1,025 and 5,025 real Pod objects (Deployment `scale-probe` in namespace `scale`, unsatisfiable `nodeSelector`, plan A.7). The real Go host (`-tags production,server`, `OMNIVIEW_UI=next`), the Kubernetes plugin at the pin, a real kind cluster, headless WebKit at 1440 x 900 over HTTP from the host's own origin. The clock `t0` is the first commit in which the connection phase is `connected` (the connection start is outside the clock; the chain after it, catalog, target, acquisition, is the mechanism's domain). `tFirstRow` is the first commit that renders at least one row, `tComplete` the first commit that renders the complete set. Each cell is the median of 5 runs, on two conditions: COLD (the Go host and the plugin restarted before each run, so no source session is held) and WARM (page reload only). The decision rests on COLD. Machine load is recorded with every batch; differences under about 15% are noise.

Decision.
- **R1 benefit.** At N = 5,025: B's `tFirstRow` <= 1,000 ms and <= half of C0's `tFirstRow`; at N = 1,025 B is not later than C0.
- **R2 no small-cluster regression.** At N = 25: B's `tFirstRow` <= C0's + 50 ms.
- **R3 completion cost.** At N = 5,025: B's `tComplete` <= 1.15 x C0's, and the long-task time between `t0` and complete <= 1.25 x C0's.
- **R4 hand-off.** The `HostRecord.key` of a record in the first page equals the key the collection gives the same object, the first page is a subset of the final set, and no row is dropped at the hand-off. If the keys differ, B is rejected (a re-keyed hand-off remounts every row).
- **R5 ownership.** B stays inside `ui-next/k8s/` and hooks only. A is chosen only if R1 fails for B and A's upper bound meets R1 (first `snapshot` event <= 1,000 ms and <= half of C0's `tFirstRow` at N = 5,025); the runtime change is then requested from the lead, with `usePods` shipping without a bounded first set until it lands.
- If R1 holds and R3 fails, B2 (the collection starts after the first page paints) is measured and judged by R3. If neither B nor A's bound meets R1, no bounded first set is possible without a host change; that is reported to the lead with the numbers and `usePods` ships on C0.

Not measured, decided by design (tested, not benchmarked): while the set is provisional (`complete` false) the order of rows already shown never changes (new rows are appended, a removal closes the gap, a changed row stays in place); the user's own sort change re-sorts what is loaded; the complete set is sorted once and live updates then follow the active sort.

## What partial delivery from the collection would need (not done here; reported, as the lead asked)

HGO-3 and the measurement agree: no row leaves the host before the session's snapshot is complete, so no change confined to the runtime can paint rows earlier. Partial delivery needs both layers.

Host (Go), `backend/pkg/plugin/resource/`:
1. `source_view.go` `syncLocked` returns at once while `!v.session.hasSnapshot` (the state being neither `failed` nor `finished`) and builds the whole chunk list (`snapshotEnds`, `v.sequence = len(snapshotEnds) + 1`) from `v.session.members` at one moment. It would have to emit `snapshot` events for a session that is still `snapshotting`, chunk by chunk as members arrive, and send `snapshotEnd` only at the boundary; the sequence numbers, `snapshotOffset` and the view generation must tolerate a snapshot that is still growing.
2. `source_session.go` (where `hasSnapshot` is set at the plugin's snapshot boundary) holds the plugin's frames (at most 16 items each, HGO-1: about 313 frames at 5,000 Pods) as staged members that are not authoritative. A view would have to read them, with a rule for the rows already sent when the session resets or fails mid-snapshot (the client already drops its staging on `reset` and on a new generation).
3. The chunk walk is over a Go map, so row order is undefined (HGO-3). A useful first set needs a deterministic order: the plugin's own, which for Kubernetes is the API server's key order, namespace then name.
4. The bounds still hold: staged members count against the 256 MiB retained and 256 MiB transient pools (HGO-9), and a view queue is at most 256 events or 32 MiB (HGO-2).

Runtime (TypeScript), `packages/omniviewdev-runtime/src/`:
5. `resource/v2/sourceView.ts` keeps `staging` in a closure until `snapshotEnd`, and `SourceViewSnapshot.records` stays empty with `complete: false`. It would expose the staged records (a copy per delivery through the 100 ms coalescer of RTM-01, or a chunk list) without breaking RTM-02 ("a map handed out is never modified").
6. `hooks/resource/useResources.ts` publishes a page only when `snapshot.complete`. An opt-in (`partial: true`) would publish a page flagged incomplete while keeping `sharePage` (RTM-06), the no-work-for-an-equal-status rule (RTM-07) and `gcTime: 0` (RTM-09). It must stay off by default: the old shell shares this code.

Upper bound: with both layers changed the first rows could leave the host when the plugin's first frames reach it. The time from the open to that first frame was NOT measured (the host log line `source stream received first frame` marks it). The first explicit page already puts 256 rows on screen at 264 to 304 ms at 5,025 Pods with no change to either layer, so partial delivery would buy live updates during the load and one acquisition path instead of two, at the price of two layers of change and the rule 14 risk above.

## Spec disagreements and decisions for the lead (none chosen silently)

- **E13, Ready and Restarts.** The plan says regular containers only; kubectl (API server v1.35) also counts a native sidecar (a restartable init container) in Ready and its restarts, and counts init-container restarts while a Pod initialises. On real Pods `states/sidecar`: kubectl 2/2, here 1/1; `states/init-fail`: kubectl 3 restarts, here 0. The plan is followed; `golden.test.ts` asserts both differences (`DOCUMENTED`). Following kubectl is a change in `fields.ts` of about 15 lines. Status needs no choice: it is the port of `printPod`, sidecar logic included.
- **E4, restarts of a Pod with no container status.** `—` as the plan says; kubectl prints 0 for a Pending Pod. 5,001 of the 5,025 rows in the check above.
- **E14, Age format.** The mock's compact age (one unit, rounded down) cannot equal kubectl's, which prints seconds up to 2 minutes, minutes up to 3 hours, hours up to 48 and two units (`6m12s`, `3d5h`). The check is that kubectl's age lies inside the span our unit stands for: no mismatch. The exit test "Age equals kubectl" holds in that sense only.
- **E15, words kubectl prints that the mock's role table lacks.** `SchedulingGated` (seen on a real Pod) and `ContainerStatusUnknown` have no role and draw as plain text, as the mock's `Cell.status` does. Proposal for the errata: `SchedulingGated` is progress (the clock of queued work).
- **E16, `view.count`.** The plan says it drives the footer; it goes stale on a live add (above). `usePods` counts the records.
- **The page's QueryClient** (RTM-14, MNR-D8). Done in this PR: the old shell sets `refetchOnWindowFocus: false`, and the new tree's bare `new QueryClient()` did not. `ui-next/queryClient.ts` now builds the shell's one client (that default only; the hooks keep their own `retry: false` and `gcTime: 0`), `ui-next/main.tsx` mounts it once, and the skeleton no longer builds its own.
- **Wire cost, for planning.** 256 Pods are about 2 MB and 5,025 Pods about 39.6 MB over the event socket (7.9 KB a Pod in `Value` form); the first page takes about 240 to 290 ms of that.
