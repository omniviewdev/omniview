## The decision rule for the tooltip primitive (R5), written before any measurement

Candidates. **O** (owned): one set of listeners on `document`, one native `popover="manual"` element in the top layer, placement computed by the host (the mechanism of the mock, `core.js:3169-3608`). **B** (Base UI): `@base-ui/react` `Tooltip` with one shared handle and one `Tooltip.Trigger` per trigger, which is how the old table's `TooltipScope` shares one popup today (`optimisations.md` T-08).

Measured on one stress page of N plain triggers (N = 0, 100, 1,000), in WebKit and in Chromium, the same triggers and the same measuring code for every candidate, timings as the median of at least 9 runs:

| | Budget |
|---|---|
| L1 listeners | the number of `addEventListener` calls the page makes for N = 1,000 is the number for N = 0 plus a constant, and equals the number for N = 100 (O(1) in triggers) |
| M1 mount | 1,000 triggers cost at most 8 ms more than 1,000 plain elements to mount, at most 2 ms more to render again unchanged; at most 0 extra elements per trigger |
| P1 open latency | from the event that opens it (keyboard focus, or the end of the delay) to the frame that shows it placed: at most 2 frames (33 ms) at p95; hover and open cause 0 React commits in the trigger tree (plan B6) |
| P2 placement | never clipped by an ancestor with `overflow`, `contain` or a transform; inside the viewport with 8 px margin at the four corners; never over its trigger |
| V (veto) | a candidate is out if any of these fails: `role="tooltip"` and the trigger described by it while open (unless its name already is the text); the tip is hoverable and stays while the trigger is focused or hovered; Escape hides it and a dialog behind it still closes on that same press (design PB-13); no `title`; reduced motion honoured; a keyboard user gets the same tip on `:focus-visible` |

Rule: **Base UI is taken only if it meets L1, M1, P1, P2 and V in both engines and adds no element per trigger; a tie goes to the owned code.** A missed budget is not tuned for more than a day: the result is recorded here either way.

## Decisions

- **Tooltip primitive (R5): the owned host. Base UI was NOT measured.** The delegated controller (ten listeners on the document and the window, one `popover="manual"` element in the top layer, the mock's placement function) meets L1, M1, P1, P2 and the veto items in both engines (numbers below), so by the rule above Base UI is not needed: it would have to meet the same budget, add no element per trigger and close an accessibility gap, and the owned code has none named. The comparison page for Base UI's trigger-per-element handle was not built; that is a gap in the evidence, not a result.
- **Where it lives.** `packages/kit/src/components/TooltipHost/` (the plan's convention for a part), not `packages/kit/src/TooltipHost/` as the assignment wrote. Public: `TooltipHost` (no props, mount once beside `ThemeProvider`; a second host in one document throws) and `tip(text, { delay: 0 })`, which returns the data attribute `data-ov-tip` (and `data-ov-tip-delay="0"`). A kit part passes it through as any `data-*`. The kit's closed-props lint refuses a spread of `tip()` in an examples file, so the examples write the attribute out.
- **Behaviour** (the mock, `core.js:3169-3608`): 500 ms hover delay (a trigger may skip it); at once on `:focus-visible`; stays while the trigger is focused or the trigger or the tip is hovered (the stylesheet bridges the 8 px gap); closes on a press or click of the trigger (not of an `aria-disabled` one), a scroll of anything holding it, resize, window blur, trigger removed or its text changed, the trigger's own popup opening; `aria-describedby` while open unless the trigger's `aria-label` equals the text; placement below, above, right, left, 8 px gap, 8 px margin, height limited when no side has room; no transition or animation; no `title` ever.
- **Escape**: the mock's (see "Disagreements"): hides the tip and is never prevented or stopped; the same hover or focus does not reopen it.
- **The cut signal, agreed with Slice1aAtomsB** (the plan names none): an element marked `data-ov-clip` (its own box clips: overflow not visible) names its text in `data-ov-full` (else its own text); the host measures `scrollWidth > clientWidth + 1` when the pointer or focus arrives, so no row has an observer, and tips the text only while cut. The nearest `[data-ov-tip], [data-ov-clip]` decides: a name that fits does not fall through to a tip around it. An explicit `data-ov-tip` on the same element always shows. The host keeps a private copy of the rule and exports no `isCut`.
- **Shadow token.** `--ov-shadow-tooltip: 0 2px 8px #0006` (the mock's `.tooltip`) joins the manifest; it was the first elevation a part draws.
- **Fonts.** The kit delivers the mock's three faces under the aliases its tokens name: Inter 3.019 Regular (400) and SemiBold (600) and JetBrains Mono 2.304 Regular (the plan lists only Inter; the Pods rows draw mono). Each is a WOFF2 subset of the characters in `src/styles/fonts.css`'s `unicode-range` (Basic Latin, Latin-1, Latin Extended-A, general punctuation, arrows, operators and the key symbols the mock draws): 32,320 + 34,532 + 40,756 = 107,608 B against 790,652 B of source (318,000 B as whole WOFF2 files). Every layout feature, hinting and the name table stay; `scripts/verify-subset-fonts.py` shapes 63 string and feature combinations (kerning, `tnum`, `calt` off) in each source and each subset with HarfBuzz and finds no difference in any advance or offset. Licences: both OFL 1.1, no reserved font name, copied verbatim into `packages/kit/NOTICE` with the source hashes. The design chapter 09 says not to start with a Latin-only subset; this is Latin plus the symbols of the chrome, other scripts fall to the system font, and adding a script is one entry in `scripts/subset-fonts.ts`. `font-display: swap` (the design's choice).
- **Delivery.** Vite builds a library with every asset inlined, which would put 141 KB of base64 in `styles.css` (chapter 02 forbids it): `scripts/kitFonts.ts` takes the font URLs out of the build, ships `dist/fonts/*.woff2` beside `styles.css`, and `scripts/check-dist.ts` fails the build on a data URI, a missing file or a byte that differs from `fonts/manifest.json`. `ui-next/index.html` preloads the two Inter faces; Vite gives the link and the `@font-face` rule one hashed URL, so each file loads once (`crossorigin` is required). In `vite dev` the preload link resolves to a path the dev server does not have: it misses and the font loads from the CSS (a console warning, not tested).
- **Linux probes.** Headless Chromium on Linux hints and rounds each advance to a pixel (a 26-character sample is 189 px against 187.27 in WebKit and on macOS); `--font-render-hinting=none` (probe-lib `launch`) makes Linux and macOS agree to 1/64 px, so one reference holds on both. Measured in `mcr.microsoft.com/playwright:v1.64.1-noble` (arm64).
