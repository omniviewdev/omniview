### The gear is 1,735 bytes, over the 800-byte cap of one glyph

The mock's `LuSettings` is Int UI's gear drawn as an outline that was cut out of a stroke (four closed subpaths, 2,616 bytes in absolute coordinates). `undo` was a cut-out stroke redrawn as the stroke it came from (G-step note in the `glyphs.ts` header); a gear cannot be redrawn that way without inventing a centre line, which would no longer be the mock's artwork. So the path is kept and made smaller instead: coordinates round to three decimals, and every segment after a subpath's first moveto is written relative (`l`, `c`, `z`), tracking the rounded absolute position so no rounding drifts: 2,616 to 1,677 bytes of path data, 1,735 as an entry. The one-glyph cap of the budget test is 800 and now says `settings` may be 1,800; nothing else may pass 800. The alternative, Lucide's `settings` (a stroked cog, about 600 bytes, not the mock's gear), was not taken because ST1 names the mock's gear for the top row.

## The registry is not tree-shakeable per glyph: measured, and the proposal

**What was measured** (the `OMNIVIEW_UI=next` host bundle, `vite build`, minified; the registry is the object literal `{activity:{box:24,...}, ... waypoints:{...}}` cut out of the entry chunk; before is this tree with the old `glyphs.ts`):

| | entry chunk raw | gzip | brotli | registry raw | gzip | brotli | share of the entry (gzip) |
|---|---|---|---|---|---|---|---|
| before (77 glyphs) | 1,272,322 | 402,063 | 328,866 | 18,148 | 5,254 | 4,630 | 1.31 % |
| after (88 glyphs) | 1,276,339 | 403,412 | 329,982 | 22,165 | 6,611 | 5,781 | 1.64 % |
| G2 added | +4,017 | +1,349 | +1,116 | +4,017 | +1,357 | +1,151 | |

The registry is in the entry chunk once (the kit's `dist/index.js` and the host's entry hold one copy each; no lazy chunk holds one: `grep` of `M22 12h-2.48a2` over every chunk). Plugin bundles share the kit as a singleton at run time and carry none.

**Why a per-glyph import or lazy map does not keep the API.** `Icon` takes a `name` that is a run-time value, and `isIconName` exists to take one from the wire: a plugin sends a string, the host checks it against the registry and draws the glyph. Whatever the registry is written as (an object, a `switch`, one export per glyph with a map over them), a bundle that can draw "the glyph named by this string" must hold all of them. Shaking one glyph out needs the call site to name it statically (`<Icon glyph={Rocket} />` with `import { Rocket } from '@omniviewdev/kit/glyphs'`), which is a different contract: no string names, and `isIconName` and the plugin contract's `icon: string` fields (rail, tile, palette rows, tool, tab) would need a registry anyway. A lazy map (`import()` for each glyph, or for a group) keeps the names but makes `Icon` asynchronous: the first frame draws an empty box of the right size and the glyph arrives a frame later. Every probe that measures a glyph in the first paint (the geometry probe of this registry, the strip and rail probes) and every test that reads `data-ov-glyph` synchronously would need a wait, to save at most the glyphs the host's own source never names: **30 glyphs, 7,650 bytes of JSON (a rough count of the names that appear as string literals in shipped `ui-next` and kit source: 58 of 88 do), about 2.3 KB gzip (inference from the registry's 0.30 gzip ratio), 0.57 % of the entry's 403 KB**. That is not a small change and not a worthwhile gain, so it was not made.

**Proposal, for the lead to decide** (none is needed now):
1. Keep the registry as it is. The test's budget, with its history in the title, is the guard; each step says its bytes. Revisit when the registry passes about 40 KB raw (about 3 % of the entry's gzip).
2. If the entry chunk becomes a problem, take it from the big items first (the terminal engine alone is 361 KB raw in its own chunk, the entry is 1.27 MB); the registry is the smallest of the levers.
3. If a lean consumer ever needs it (a second window kind that draws six glyphs), add a second entry point that exports the glyph objects and a `Glyph` part that takes one, beside `Icon`, rather than changing `Icon`: the two contracts then differ on purpose.
