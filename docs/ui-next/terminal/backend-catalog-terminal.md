# Terminal and exec: the backend catalog entries that concern you

The lead keeps a catalog of everything UI work found to belong in the plugin SDK, a plugin's backend or the host's Go side (`docs/ui-next/backend-catalog.md`; rule 22 of `docs/ui-next/AGENTS.md` says how an entry is made). In this repository that file ends at B-90; B-91 and later live only in the lead's private notes. This page holds every entry that concerns the terminal or the exec lane: where each stands today and which child of the epic owns what is left (section 1), the rows of the in-repo catalog (section 2), and the entries of the lead's private catalog, copied word for word (section 3).

Classes, as in the catalog: BLOCKER = the new UI cannot behave properly without it; TANGENTIAL = a real gain or fix that can land alone; WIRE = it changes the plugin protocol. "Interim" = what the UI does meanwhile.

## 4. Not an entry: the extra CR that the terminal of macOS writes (2026-11-24)

**What it is.** The tty turns each LF a program writes into CR LF. On macOS, when the tty's output queue is full between the CR and the LF of that translation, it keeps the CR, finishes the character later and writes the CR again, so the bytes the host reads from the pty master have `CR CR LF` where the program wrote one line end. The first CR is the last byte of a read (the queue was full) and the next read begins with CR LF. [INFERENCE: that the kernel retries the whole character is how BSD's `ttyoutput` is written and fits every observation below; the kernel source of this macOS was not read.]

**What was measured** (macOS 27.0.1, Darwin 27.0.0 arm64, host load 4.7 to 17 from other work, so counts are exact and rates only compare):

- **It is the kernel's.** The flood test failed on both trees it was run on (12 of 100 runs on main before the channel PR, 13 of 100 with it, alternating runs, one at a time). A tee of every read of the master, taken before the host clones, counts or delivers a byte (`Manager.tee`, a seam of the tests), had the `CR CR LF` in 13 of 13 failing runs (22 of them): taking each back to `CR LF` gave exactly the text awk printed in all 13; every one of the 22 was the last byte of a read of 1,024 bytes with the next read beginning `CR LF`; none was within 2 bytes of an offset where a reloaded page was handed its replay (they are anywhere in the stream, from byte 1,426 to 16.8 million).
- **It needs no code of the host.** A small program that opens a pty (`creack/pty`), runs `awk 'BEGIN { for (i = 1; i <= 2000000; i++) print i }'` on it and does nothing but read the master saw it. With a reader that reads 64 KiB at a time as fast as it can, 1 of 20 runs had a `CR CR LF` (2 in all); with a reader that pauses 10 ms after every 256 KiB, 6 of 20 (88 in all); with 256-byte reads 2 of 20 (8 in all); with a 1 ms pause after every MiB, 0 of 20. Taking each `CR CR LF` back to `CR LF` gave the printed text exactly in all 80 runs. awk writes only `LF`: every CR is the kernel's.
- **Not measured:** other macOS versions; Linux (the flood tests have passed there in CI and in containers, and nobody looked for it); a program other than awk.

**Who sees it.** A user, rarely, on macOS (the only system it was seen on), when a program floods the terminal faster than the host reads it (a hidden or stalled page, a loaded machine). A terminal emulator does not show it: the first CR moves the cursor to column 0 and the second, directly before the LF, finds it there, so the screen is the same. A program that records the byte stream (a test, a transcript, a hash, a byte count) sees one byte more. It is harmless to the terminal.

**What the host does.** Nothing: it delivers exactly what it read, the offsets count the byte, and a replay or a re-attach hands it back again, byte for byte. It cannot tell the kernel's CR from a program's own `CR CR LF` without changing that contract.

**What the tests do.** The two tests that hold a flood to the text the program printed (`TestAReloadUnderAFloodReattachesByteExactByOffset` and `TestTenMebibytesOfOutputArriveCompleteAndInOrderWhoeverGivesTheCredit`) compare the page and the host's events with the tee, byte for byte, and the tee with the printed text less a CR that ends a read and is followed by `CR LF` (`backend/pkg/terminal/pty_cr_test.go`). A byte repeated or dropped at the join of a replay and the live output still fails them; the faults that show it are in `docs/ui-next/status/PTYCR.md`.
