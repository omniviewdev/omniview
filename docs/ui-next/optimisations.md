**Verdicts.**

- **CARRY AS ENGINE**: the code is UI-independent and worth keeping as it is. It moves (copied with its provenance noted, or stays where it is) behind a new API; the API is proposed in one to three lines.
- **RE-EXPRESS**: the technique must exist in the new tree, but the code is bound to the old markup, library or CSS, so it is written again. The row states the rule the new code must satisfy and the number or count that shows it does.
- **OBSOLETE**: the new tree does not need it; the row says why.

**Evidence.** Numbers are quoted from the source named next to them (a pull request description or comment, a benchmark README, a doc), never produced here: I ran no benchmark for this inventory. "Unmeasured" means no source reports a number. `[INFERENCE]` marks my own reasoning. Almost all recorded numbers come from a fixture backend inside the page, Chromium and an M5 Max; the only WKWebView numbers are the two the pull requests say were taken in the native app (host #487, Kubernetes #257). Read each PR's own "not verified" list before treating a number as a budget.

**Guards.** A guard is something that fails when the optimisation is undone. `G-existing` names one that runs today; `G-new` is a proposal with the exact assertion. A guard that lives in the frozen `lib` repository, or in a plugin's own UI tests, stops protecting the new tree at the flip, so it is marked "port": the test is to be rewritten against the new code, not trusted.

## 1. Tables

### 1.1 Where the cost of a table is controlled today

The Pods table is the plugin's own table, not the host's generic one. Both sit on the same library table and the same runtime hooks. A change in the new tree can undo an optimisation at any of five layers; the register in 1.2 is ordered by layer.

| Layer | Code | What it owns |
|---|---|---|
| 1. Delivery and acquisition | runtime `useResources`, source views, `sharePage` (`RT/hooks/resource/useResources.ts`, `RT/resource/v2/sourceView.ts`) | how rows reach the page, how often, and which records keep their object identity (§2 has the full register; 1.2 lists what the table depends on) |
| 2. Row model | plugin `decodeResourceTableRows`, `decodeRecordBody` (`KT/ResourceTable/rows.ts`, `k8s:ui/src/utils/recordBody.ts`); host `projectResourceRows` (`HT/rows.ts`) | one decoded body per `HostRecord` object; the reverse lookup that actions and metric demand use |
| 3. Table state | TanStack Table through `useTable` / `useDataTable`, the feature set, the adaptive sorted row model (`DT/constants.ts`, `DT/hooks/useDataTable.ts`, `DT/utils/createAdaptiveSortedRowModel.ts`) | sort, filter, selection, visibility, pinning, sizing |
| 4. Window and rows | `DataTable.VirtualBody` (`DT/DataTableVirtualBody.tsx`), `useVirtualizerSnapshot` (`lib:packages/base-ui/src/system/useVirtualizerSnapshot.ts`), `DT/DataTable.module.css` | which rows exist as DOM, how they are positioned, which re-render |
| 5. Cells and shared owners | `KC/cells/*`, `KC/TableMetrics.tsx`, `KT/TableActionsScope.tsx`, shared menu and tooltip handles | per-cell timers, popups, listeners, metric demand |

### 1.4 What the plan's decision rule does not cover

Plan 3.3 sets B1 to B7. Measured against what the old table's optimisations actually protect, five things are missing. Each is a proposed guard; none exists yet.

1. **G-T1: a sparse live-update workload.** Every retained win of the previous sprint showed up under updates (the adaptive sort, memoisation, range reuse), and plain scrolling hides them: the old team's no-update frame p95 did not improve (116.6 to 150.1 ms at 4x CPU) while the sparse-update run improved (1,199.9 to 250 ms, both "still unacceptable"; `bench/app/README.md:863-864`). B2 scrolls a static list. Add a B8 beside it: the same scripted scroll with the seeded sparse-update workload already in the repo (`bench/render/fixtures/updates.ts:133`, `--updates sparse`: 5 events a second touching 2 Pods, every tenth touch a delete and recreate), on 5,000 Pods, at 1x and 4x CPU throttle, comparing rAF p95, driver lateness p95 and comparator calls. Run it on both layout variants of T-03.
2. **G-T2: work counts, not times.** Times drift between passes on this machine (a startup median moved up to 16%, one scroll metric 46%: `docs/ui-next/baseline/2026-11-16.md:56-62`); counts do not. Add exact assertions to the kit's tests: comparator calls (T-15), `valueToJSON` calls (T-21), timers (T-26, T-27, T-28), listeners (T-07), popup roots (T-08), renders per patch (T-06). They are cheap, run in CI on every PR, and would have caught each regression class in the register.
3. **G-T3: WKWebView.** Several decisions here were taken in Chromium. Two native-only symptoms are on record: "native black rows" during fast scroll (not reproduced by the fixture, `bench/app/README.md:544`; lib #126's limit) and timer calls that are "slow in WKWebView" (host #487 and lib #126, the reason for T-27 and T-28). Plan 1a.11 is the only place they can show up; add "fast scroll shows no blank rows" and "timer calls during an 8 s scroll" to its checklist.
4. **G-T4: metric states.** The `bench/app` cells `--metrics hidden,unavailable,healthy` (`bench/app/README.md:400`) exist for the old table only. The new page needs the same three states in its real-page test (hidden: 0 observations; unavailable: static gaps, 0 pulsing; healthy), because the largest recorded cost among the retained choices (healthy target slots +21.1%) sits there.
5. **G-T5: memory.** Recorded once: retained JS heap after three scroll cycles and a full GC 74.81 to 73.58 MiB (host #470 comment), and "Not verified: memory held by four lingering views on a very large cluster" (host #487). No guard exists for retained DOM or views after open, scroll and close cycles. Add a leak check to 1a.3's bench: after ten open, scroll, close cycles the heap and the number of open source views return to the start (the host #470 comment reports "Closing the tab left zero source views and zero active metric observations" as a manual check).

One mismatch for the lead: **B2's budget is stricter than anything recorded for the old table.** The old table's best unthrottled no-update result is rAF p95 33.4 ms and it "still miss[es] the 20 ms frame goal" (`bench/app/README.md:942`); with sparse updates the candidate recorded 66.7 ms (`bench/app/README.md:945`). B2 asks for 16.7 ms. That is a fine target for a rewrite, but a miss against B2 is not by itself a regression against today's product, and trigger T1 should say which of the two it measures.
