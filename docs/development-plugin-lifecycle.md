# Managed development plugin lifecycle

Workspace plugins use the running host's managed lifecycle. The host owns plugin source watching, the plugin RPC process, controller initialization, and operation results. With the explicit outer supervisor configured, that persistent supervisor directly owns frontend install/Vite children and their groups, while the host consumes authenticated real process handles. A `.devinfo` file, a live numeric PID, or a positive port is not an attachment and cannot report a plugin connected. The independent standalone runner is retired; workspace clients submit operations through the authenticated, generation-targeted host control service.

## Startup and readiness

Source capabilities come from `plugin.yaml`, with its ID checked against the requested plugin ID. A backend-only plugin allocates no Vite port. A UI-only plugin starts no Go watcher or RPC process and reports backend stages as `n/a`; its `grpcConnected` value remains false.

The resolved workspace manifest is authoritative for development source selection before autostart. Persisted DEV bindings that were removed from `manifest.plugins` or now point at a different selected repository remain visible as stopped inventory with their original metadata/source/enabled setting and user data; they neither execute a cached binary nor start a watcher. Matching enabled selections start through the canonical install/build/load transaction, not cached-binary loading before managed readiness exists. Explicit development link/load/start uses the same selection guard; change the workspace selection and relink rather than implicitly adopting another source. Non-development installed archive policy is unchanged.

`DevServerState` exposes the managed `generation`, source `devPath`, `buildStatus`, `viteStatus`, `rpcStatus`, `controllerStatus`, aggregate `ready`, and actual ready-only `viteURL`/`hmrURL`.

| Stage | Required evidence |
| --- | --- |
| Build | Actual successful Go build, metadata/binary installation, and required trusted SDK artifact recording |
| Vite | Owned child advertises the exact strict loopback assignment and its `/@vite/client` HTTP endpoint returns nonempty JavaScript |
| RPC | Actual lifecycle `GetInfo`, `HealthCheck`, and `GetCapabilities` replies, matching plugin ID and current negotiated SDK protocol, with serving health |
| Controllers | Host manager/controller initialization and start return successfully |
| Ready | Every capability-required stage is ready; non-applicable stages do not masquerade as connections |

Compilation never sets `grpcConnected`. Entering a replacement build invalidates the prior RPC/controller readiness and rotates a private runtime-observation token, independently of the stable managed watcher generation. Only the replacement backend's loader observations may restore readiness; old backend callbacks are rejected, and periodic health checks cannot republish old successful readiness. A successful initial build may be ready while RPC/controllers remain pending until the installer calls `LoadPlugin`. A load or controller error fails the operation even when the build artifact is valid. A failed build leaves the watcher available for correction/rebuild. An exited Vite child immediately revokes Vite readiness; backend health checks and crash handling revoke RPC/controller readiness.

`WaitReady(ctx, id, generation)` returns only the requested generation's actual ready state, a stage error, a generation-change error, or cancellation. It does not manufacture a ready result from an advertised endpoint.

## Source changes, stop, and restart

The same-ID existing-instance path only accepts the same canonical source directory. Rebinding uses the install transaction: stop the old managed watcher/Vite child, unload the old backend/controllers, prepare the new source installation, build, and load. A request for source B cannot silently reuse source A.

`Manager.StopDevPlugin(id)` stops managed processes and retains the installed development binding as `Stopped`, with its metadata, source, and enabled setting intact and without stale backend clients. List/get remain available and the next start/reload creates a fresh backend. Frontend stop/restart use this canonical operation, rather than merely stopping the Vite watcher.

Queued rebuild callbacks use `ReloadManagedPlugin(ctx, id, source, generation)`. Cancellation and source/generation are checked after acquiring the plugin lifecycle lock, so an old watcher cannot reload a newly rebound ID.

## Tools and child environment

Explicit configured Go/pnpm/node executables are validated at execution. For workspace UI plugins, the launcher supplies `OMNIVIEW_PLUGIN_PNPM_COMMANDS`: a map keyed by plugin ID containing `{program, args, source}`. After ConfigureWorkspace, the host calls `ConfigurePNPMCommands` before managed starts. Each entry is an absolute native Node program plus an owned pnpm.cjs argument prefix, bound to that plugin's canonical source; install/dev task arguments are appended without a shell. Different plugins may therefore use different exact packageManager pins. Configuration is copied so caller mutation cannot change a running selection. A nonempty explicit `developer.pnpmpath` remains authoritative and receives no injected prefix. Without that override, missing or rebound workspace sources require reconfiguration rather than silently adopting another source's pin or a global pnpm. Outside workspace-managed command selection, tools default to `PATH`; GUI-entered paths are not mandatory. Missing or invalid required tools are operation errors.

Every managed child receives the resolved state root and workspace/instance/generation/plugin identity. Go commands explicitly use `GOWORK=off` and drop inherited `GOROOT`; an unrelated parent `go.work` cannot change source selection. The actual allocated Vite port is passed through strict CLI flags and `OMNIVIEW_VITE_PORT`, which the Vite plugin uses for HMR. The supervisor's selected-repository filesystem allowlist is propagated in the child environment.

## Retained frontend process supervisor

The launcher supplies both `OMNIVIEW_PROCESS_BRIDGE_ENDPOINT` and `OMNIVIEW_PROCESS_BRIDGE_TOKEN_FILE`. After `ConfigureWorkspace` and actual host identity capture, startup calls `ConfigureProcessSupervisor(devsession.ProcessBridgeConfig)` with the resolved manifest, workspace/supervisor generation, and captured current host. The client validates the selected host repository source and the exact private `workspace/.local/supervisor-<generation>.secret` namespace before opening the token. Partial, invalid, or foreign configuration fails closed before managed starts. Bridge authority references are stripped from Go, Node, and SDK plugin children.

The host requests only typed `dev` or `install` actions for the selected plugin repository root and managed plugin generation. The supervisor derives the actual frontend cwd and pinned native Node/pnpm prefix from its selected graph. Only explicit provider `developer.pnpmpath`/`developer.nodepath` executables are sent as overrides; mapped prefixes and arbitrary arguments never cross this API. Dev arguments are exactly `run dev --port N --strictPort --host 127.0.0.1`, without a `--` separator. Workspace install arguments are `install --frozen-lockfile --strict-peer-dependencies --ignore-scripts`; tracked source generation is owned explicitly by the graph, not implicit dependency lifecycle scripts. Nonworkspace legacy install behavior is unchanged.

Remote Vite stores an actual `RemoteProcess`, not a fabricated `exec.Cmd` or host-owned PGID. Identity uses workspace/supervisor generation and role `plugin-vite`; the separate managed plugin generation targets the operation. The shared lease owner retains its manifest source, independently checked against the captured host kernel identity. Actual bounded output feeds the normal advertisement parser, then the normal HTTP probe establishes readiness. Missing/overflowed output and observation errors fail readiness. Wait transport errors do not mean exit, and Stop only succeeds after the actual retained owner confirms exit/reaping/output drain. Uncertain accepted starts or failed stops retain their instance/lease and error rather than falling back to local execution or adopting a PID.

This persistent Cmd ownership lets the outer supervisor dispose of its frontend groups after a desktop host crash, including Darwin, without detached PID recovery. When no outer supervisor was explicitly configured, the real local retained runner remains available; it does not promise outer-supervisor crash cleanup. In supervisor mode host recovery never signals retained remote records, and neither cleanup nor save erases a live unresolved record merely because its generation matches.

Workspace frontend producers use `internal/devoutputs` controlled writer capabilities. Install opens ownership before executing pnpm and finishes its exact snapshot after actual command completion, including failed installs. Vite opens its explicit external cache writer before process start and receives the authoritative cache environment; its writer remains live until the actual retained process/descendant cleanup, output drain, and Cmd reaping have completed. Known no-process startup failures also finish the capability. Cancelled watch contexts do not skip final ownership recording. Failed or unconfirmed cleanup remains an error/open ownership record, never a stale hash presented as completed. The host owns these capabilities only for local execution; remote execution has one writer owner in the persistent supervisor, so host crashes cannot lose or double-finish it. Unknown preexisting output roots are not adopted.



## Trusted SDK build evidence

Workspace backend launch fails closed without independent host-owned artifact evidence. The trusted launcher supplies the reviewed fixed-SDK baseline revision; source YAML cannot supply or override it. The builder resolves the effective SDK using `go list -m -json`, including the actual replacement directory, and delegates source verification to `internal/devsource`.

The source verifier checks the reviewed baseline's ancestry and a deterministic current source digest, including ordinary dirty tracked and nonignored untracked source files. The exact identity must remain unchanged before and after the actual build, and the resulting executable must include the SDK module. Ordinary settings/log/proto API edits therefore do not require committing before rebuilding.

By default, the containment-critical `pkg/state/root.go`, `pkg/state/custom.go`, `pkg/profilecontract/profile.go`, `pkg/utils/store.go`, and `pkg/sdk/plugin.go` must match the reviewed baseline. The reviewed SDK commit must contain the shared profile contract; older baselines missing it are rejected, not silently exempted. Deliberate containment-core work requires the explicit workspace launcher option `--allow-isolation-source-changes`; its child marker `OMNIVIEW_ALLOW_ISOLATION_SOURCE_CHANGES=1` is only honored in a resolved workspace context. This is an explicit same-user safety acknowledgement, not a sandbox for arbitrary Go code.

After successful verification/build the builder calls `instance.RecordBuiltArtifactSource(resolvedWorkspace, id, binary, reviewedRevision, sourceDigest)`. Installed YAML gets newly generated provenance for that artifact, never the source file's self-attestation. The loader independently verifies the private host artifact record and executes a private digest-checked snapshot. Neither imported binaries nor arbitrary `state_isolation` YAML bypass this gate. Artifact storage is keyed by workspace UUID and is independent of a custom persistent-state directory's parent.

## Leases and owned cleanup

Workspace Vite assignments use the shared private `devsession` registry with workspace/role/plugin keys and explicit generations. The validated manifest's `ports.policy` applies to plugins as well as host services: `strict` rejects a collision without fallback; `sticky` retains a successful assignment and deterministically selects another available managed port when necessary. The canonical per-plugin override key is `plugin-vite:<pluginID>`. Overrides are exact and strict even under sticky policy; the lease service key still uses role `plugin-vite` with a separate plugin ID. ConfigureWorkspace snapshots the validated policy and override map. Vite always binds the selected assignment strictly. A bind/readiness race is an observable bounded failure, not an implicit Vite auto-increment. The bound lease is confirmed only after actual endpoint readiness. HTTP and HMR use that exact assignment.

Both `plugin_pids.json` and `devserver_pids.json` contain private atomic process-identity records: kernel start identity, executable, workspace, generation, role, and source. Legacy numeric records, foreign ownership, executable mismatch, and unsupported recovery are retained and reported, never converted into authority to kill by PID or process group. A new launch cannot overwrite an unresolved same-key recovery record.

Normal managed `exec.Cmd`/go-plugin children are stopped through their live owner. Vite has one reaper: Unix exit observation does not reap (Darwin kqueue, Linux WNOWAIT), allowing descendant disposal while the owned leader identity is still pinned; only then does Cmd.Wait run. Context cancellation signals that same owned tree instead of killing/reaping pnpm alone. No cached group is signalled after the reaping gate closes. Windows uses a process handle for exit observation and refuses post-exit numeric tree signalling; if tree cleanup was not completed while its owned leader was live, the error and ownership evidence remain rather than claiming success. Detached cleanup uses `devsession.TerminateOwnedProcess` only: Linux/Windows use process-stable handles; Darwin deliberately cannot terminate detached records safely and returns an unsupported-identity error. There is no Darwin numeric-kill fallback. Signal delivery alone is not cleanup completion: both trackers retain and report the record unless subsequent identity-safe observation confirms the process is gone, and unresolved backend records block the next launch before exec.

Darwin's POSIX group signal may return `EPERM` after every member has become a zombie: the [kernel's group filter excludes zombies and returns EPERM when no signalable member remains](https://github.com/apple/darwin-xnu/blob/master/bsd/kern/kern_sig.c#L1793-L1871). While its own leader is still unreaped and its signal/reaper gate is held, the local owner checks typed `kern.proc.pgrp` records before treating that result as already disposed. Any live member or inspection failure retains the error. This is actual group-exit evidence, not a detached PID fallback or unconditional permission-error suppression.


## One dependency watcher owner

The canonical plugin watcher watches plugin source/root changes and, by default, the effective local Go module replacements in full, including SDK settings/log/proto outside `pkg/`. It does not infer dependencies from `go.work` under `GOWORK=off`.

The workspace graph may own dependency invalidation instead. Before starting plugins, `ConfigureDependencyWatching(false)` disables initial duplicate dependency watches. Existing generations transfer ownership with `SetDependencyWatching(id, generation, enabled)`. `WatchedGoDirectories(id)` exposes resolved watches; `RebuildPluginGeneration(ctx, id, generation)` performs the actual serialized build/install/reload and returns its errors. The graph must invoke that canonical rebuild rather than start a second plugin process supervisor.
